# ERP-WMS-TMS-B2B 可扩展系统架构设计

> 开发阶段架构设计 v1.0  
> 日期：2026-06-14  
> 参考基准：`docs/子系统/01-系统架构设计.md`、`docs/architecture/01-系统架构设计.md`、V1.0 PRD 与原型  
> 目标：支撑 V1.0 ERP核心经营版快速落地，同时为后续 WMS、TMS、B2B、多入驻商、移动端、开放接口预留演进空间。

## 一、架构定位

### 1.1 当前开发阶段定位

当前进入 **V1.0 ERP核心经营版开发阶段**，重点先落地：

```text
系统底座 → 基础资料 → 库存底层 → 采购闭环 → 销售闭环 → 财务闭环
```

V1.0 不建议一开始就拆成大量微服务，否则会增加团队协作、部署、事务、联调成本。推荐采用：

> **模块化单体优先，边界按微服务设计，后续按业务域平滑拆分。**

即代码结构、数据库表、API、事件、权限边界先按领域划分，但部署形态初期可以是一个后端应用 + 一个前端应用。

### 1.2 后续演进目标

系统后续需要逐步支撑：

- ERP后台 PC
- WMS 仓库/PDA
- TMS 司机/配送
- B2B 后台
- 客户商城小程序
- 入驻商后台
- B2B业务员 APP
- 管理通 APP
- 开放接口 / 外部 ERP / 财务软件 / 税控 / 物流 / 支付

因此 V1.0 架构必须预留：

1. 多端统一认证能力。
2. 菜单、按钮、字段、数据权限能力。
3. 多组织、多仓、多货主、多入驻商扩展能力。
4. 事件驱动和异步任务能力。
5. 导入导出、打印、消息、文件、审计等平台能力。
6. 业务域后续拆服务能力。

## 三、演进式部署架构

### 3.1 V1.0 推荐部署形态：模块化单体

```text
Browser
  │
Nginx
  ├── frontend-admin
  └── erp-server
        ├── system module
        ├── base module
        ├── inventory module
        ├── purchase module
        ├── sales module
        ├── finance module
        ├── report module
        └── platform module
              ├── import/export
              ├── print
              ├── notify
              ├── job
              └── integration
        │
        ├── MySQL/PostgreSQL
        ├── Redis
        └── File Storage
```

优点：

- 快速开发交付。
- 本地调试简单。
- 事务一致性更容易保证。
- 适合 V1.0 团队规模和业务验证。

### 3.2 V1.x 扩展形态：模块化单体 + 异步事件

新增：

- MQ / 事件表。
- 异步导出中心。
- 定时任务服务。
- 库存同步、价格生效、报表汇总等后台任务。

```text
erp-server
  ├── sync transaction：核心审核写库
  └── domain events：异步通知/报表/导出/同步
```

### 3.3 V2.0+ 微服务形态

当 WMS、TMS、B2B、多入驻商、开放接口独立发展后，再拆分为：

| 服务 | 职责 |
|---|---|
| gateway-service | 网关、鉴权、路由、限流 |
| auth-service | 认证、Token、多端会话 |
| system-service | 用户、权限、菜单、参数、日志 |
| erp-base-service | 商品、客户、供应商、仓库、价格 |
| erp-inventory-service | 库存余额、流水、锁定、成本 |
| erp-purchase-service | 采购订单、入库、收货、费用、应付来源 |
| erp-sales-service | 销售订单、出库、收货、客户价格、应收来源 |
| erp-finance-service | 应收、应付、收付款、核销、资金 |
| report-service | 报表、看板、导出宽表 |
| wms-core-service | 收货、上架、拣货、复核、盘点 |
| tms-dispatch-service | 派单、路线、司机配送 |
| b2b-order-service | B2B订单、购物车、支付、售后 |
| integration-service | 外部系统对接、OpenAPI、幂等、重试 |

## 四、业务域设计

### 4.1 核心业务域

| 业务域 | V1.0 范围 | 后续扩展 |
|---|---|---|
| system | 用户、权限、菜单、参数、编号、日志 | 审批流、消息配置、多租户 |
| base | 商品、客户、供应商、仓库、价格、资金、费用 | 多货主、入驻商主数据、B2B商品扩展 |
| inventory | 库存余额、流水、锁定、批次、成本 | WMS库位、波次、库存同步、库存预占 |
| purchase | 采购订单、入库、收货、费用 | 采购预测、返利、供应商协同 |
| sales | 快速开单、销售订单、出库、收货、客户价格 | B2B订单、业务员APP、促销、售后 |
| finance | 应收应付、收付款、核销、资金流水 | 发票、凭证、结账、入驻商结算 |
| report | 经营概览、销售/采购/库存/财务报表 | 数据仓库、BI、经营预测 |
| integration | 导入导出、开放接口、外部系统 | ERP/B2B/支付/物流/税控/财务软件 |

### 4.2 边界原则

1. **基础资料域** 负责主数据，不直接产生库存、应收、应付。
2. **库存域** 是库存余额、流水、锁定、成本的唯一责任域。
3. **采购域** 负责采购业务流程，采购入库审核调用库存域，采购收货审核生成应付来源。
4. **销售域** 负责销售业务流程，销售订单审核锁库存，销售出库审核扣库存，销售收货审核生成应收来源。
5. **财务域** 负责应收应付余额、收付款、核销、资金流水。
6. **报表域** 只读聚合，不反向修改业务数据。
7. **集成域** 负责外部接口鉴权、幂等、重试、日志，不承载核心业务主责。

## 五、核心链路架构

### 5.1 采购链路

```text
采购订单审核
  → 形成采购在途
采购入库审核
  → 增加库存
  → 生成库存流水
  → 移动加权成本计算
  → 回写采购订单入库状态
  → 生成采购收货单
采购收货单审核
  → 生成应付账款
付款/核销
  → 更新应付与资金流水
```

### 5.2 销售链路

```text
销售订单/快速开单
  → 客户价格匹配
  → 信用校验
  → 库存校验
销售订单审核
  → 锁定库存
销售出库审核
  → 扣减实物库存
  → 释放锁定库存
  → 生成库存流水
  → 记录出库成本
  → 生成销售收货单
销售收货单审核
  → 生成应收账款
收款/核销
  → 更新应收与资金流水
```

### 5.3 客户价格链路

```text
新建客户价格调整单
  → 选择客户
  → 选择生效方式/有效范围
  → 添加商品明细
  → 保存草稿/待审核
审核客户价格调整单
  → 生成客户价格明细
  → 最新调价覆盖旧价
  → 旧价自动停用
销售开单
  → 匹配当前生效客户专属价
```

### 5.4 库存与成本链路

```text
入库类审核 → 增加库存 → 计算移动加权成本
出库类审核 → 扣减库存 → 按当前成本写出库成本
成本调整审核 → 不改数量，只改成本金额/单价
```

## 七、事件与异步架构

### 7.1 V1.0 事件落地方式

V1.0 如果不立即引入 MQ，可先使用 **本地事件表 + 定时任务**：

```text
业务事务提交
  → 写业务表
  → 写 event_outbox
定时任务扫描 event_outbox
  → 投递/执行异步任务
  → 成功标记已处理
```

后续引入 RocketMQ/Kafka 时，`event_outbox` 可作为可靠消息源。

### 7.2 核心事件

| 事件 | 发布域 | 消费域 |
|---|---|---|
| PurchaseOrderApproved | purchase | inventory/report/notify |
| PurchaseInboundAudited | purchase | inventory/cost/report |
| PurchaseReceiptAudited | purchase | finance/report |
| SalesOrderApproved | sales | inventory/report/notify |
| SalesOutboundAudited | sales | inventory/report |
| SalesReceiptAudited | sales | finance/report |
| CustomerPriceAdjustAudited | base | sales/b2b/report |
| PaymentAudited | finance | fund/report |
| StockChanged | inventory | report/b2b |

### 7.3 幂等要求

所有事件必须携带：

- eventId
- eventType
- bizId
- bizNo
- occurredAt
- version

消费者按 `eventId` 或 `bizId + eventType + version` 幂等处理。

## 八、权限与安全架构

### 8.1 权限模型

```text
用户 → 角色/权限组 → 菜单权限 + 按钮权限 + 字段权限 + 数据权限
```

### 8.2 数据权限维度

- 货主
- 仓库
- 客户
- 供应商
- 业务员
- 片区/线路
- 入驻商

### 8.3 字段权限维度

重点控制：

- 成本价
- 成本金额
- 毛利
- 毛利率
- 采购价
- 供应商余额
- 客户欠款
- 资金余额

### 8.4 安全策略

| 层面 | 策略 |
|---|---|
| 认证 | JWT/Session，后续支持多端 Token |
| 传输 | HTTPS |
| 密码 | 强 Hash + Salt |

| 审计 | 登录、权限、价格、库存、资金操作全记录 |
| 接口 | 参数校验、权限校验、幂等、防重复提交 |

## 十、后端工程架构

### 10.1 模块化单体目录建议

```text
erp-server
├── erp-common
├── erp-system
├── erp-base
├── erp-inventory
├── erp-purchase
├── erp-sales
├── erp-finance
├── erp-report
├── erp-integration
└── erp-web
```

### 10.2 模块内分层

```text
module
├── controller
├── application      # 应用服务，编排事务和权限
├── domain           # 领域模型、领域服务、状态流
├── repository       # 数据访问接口
├── infrastructure   # 外部依赖、MQ、文件、缓存
└── dto              # 请求、响应、查询对象
```

### 10.3 拆服务条件

满足以下任一条件时可考虑拆分服务：

1. 模块团队独立。
2. 模块流量明显高于其他模块。
3. 模块需要独立扩容。
4. 模块有独立部署窗口。
5. 模块对外部系统集成强依赖。
6. 模块事务边界清晰，跨域通过事件最终一致即可。

## 十二、V1.0 架构落地清单

### 12.1 必须落地

- 后端模块边界：system/base/inventory/purchase/sales/finance/report。
- 统一 API 响应、错误码、分页格式。
- 统一认证和权限模型。
- 统一单据状态流。
- 统一操作日志。
- 数据库表按模块前缀命名。
- 核心审核动作事务化。
- 客户价格、库存、应收应付、资金等关键业务有流水/来源。

### 12.2 预留但可后置

- MQ。
- 微服务网关。
- 搜索引擎。
- 对象存储。
- 报表数据仓库。
- 多租户 schema 隔离。
- WMS/TMS/B2B 独立服务。

### 12.3 暂不建议 V1.0 强行落地

- 全量微服务拆分。
- 分布式事务框架。
- 多数据库拆库。
- 微前端多应用拆分。
- 大规模 K8s 集群部署。

## 十三、架构决策记录

| 编号 | 决策 | 原因 |
|---|---|---|
| ADR-001 | V1.0 采用模块化单体优先 | 降低开发、联调、事务复杂度，保证核心业务快速闭环 |
| ADR-002 | 业务域按微服务边界设计 | 为后续 WMS/TMS/B2B/多入驻商拆分预留空间 |
| ADR-003 | 审核才产生业务影响 | 保证草稿/编辑不会污染库存、应收应付和资金 |
| ADR-004 | 库存、成本、资金、应收应付必须有流水 | 保证可追溯、可对账、可审计 |
| ADR-005 | 客户价格调整单审核生效 | 保证价格变更可审批、可追溯、可覆盖历史价 |
| ADR-006 | 事件表先行，MQ后置 | V1.0 降低基础设施复杂度，同时保留可靠事件演进路线 |
