## 一、背景与问题

司机在「现场退货」页（`DriverReturnCreatePage`）实际使用时暴露四个问题：

| # | 问题 | 根因 | 影响 |
|---|---|---|---|
| 1 | 客户名称靠手输，还要手填「客户编号」 | 页面是两个自由文本框，无客户选择器 | 名称随手写导致与客户档案对不上，编号司机根本记不住 |
| 2 | 收货仓库靠手输 | 无仓库下拉 | 仓库名写错后退货单无法匹配实物仓，返仓入账失败 |
| 3 | 商品关键字搜索**直接报错** | `goods-search` 用 Java 文本块拼 SQL，文本块裁掉行尾空格与开头换行，`inv_stock_balance s ` + `ON ...` + `WHERE` 被粘成 `...sON ...WHERE`，H2 语法错误，接口 500 | 现场退货录不了商品，功能全堵 |
| 4 | 退货商品不支持条码 | 只有关键字输入框 | PDA 扫枪无用武之地，只能逐字搜 |

---

## 二、目标与范围

1. **客户名称改为下拉选择控件**：点击默认展示距司机当前位置最近的 10 个客户；可输入关键字按名称/地址/电话模糊查询；下拉行显示**客户名称 + 地址**；**删除「客户编号」字段**（编号内部保留用于建单，不再展示）。
2. **收货仓库改为下拉**：只列正常的**实物仓**名称（虚拟仓、停用仓不出现）。
3. **退货商品支持扫码**：条码精确命中自动加入清单；关键字模糊搜索正常可用，下拉行显示**商品名称/规格/单位**。

**不在范围**：相机图像识别扫码（本阶段不引入新依赖，PDA 硬件扫码枪以键盘楔入方式工作，详见 §4.4）；客户/仓库主档维护（在 ERP 后台进行）。

## 三、接口设计

### 3.1 修复 `POST /tms/app/return/goods-search`

- 入参：`keyword`（名称/编码/条码/拼音码）。
- 修复：SQL 改为普通字符串拼接（空格显式写出），杜绝文本块空白裁剪导致的粘连。
- 调整：
  - 去掉 `inv_stock_balance` JOIN。退货发生在客户门口，「本店库存」无业务意义，且按批次 JOIN 会把同一商品扇出成多行；
  - 过滤 `status='NORMAL'` 且 `can_return=TRUE`（停用/不可退商品不出现）；
  - 模糊匹配增加 `simple_code`（拼音码）；
  - `ORDER BY CASE WHEN barcode=? THEN 0 WHEN goods_code=? THEN 1 ELSE 2 END`：**条码/编码精确命中排最前**，供扫码后自动选中。
- 返回：`[{goodsCode, goodsName, spec, unitName, barcode, price}]`。

### 3.2 新增 `POST /tms/app/return/customer-search`

- 入参：`keyword?`、`longitude?`、`latitude?`（司机当前坐标，APP 打开选择器时静默定位，失败不阻塞）。
- 规则：
  - **有关键字**：按客户名称/编码/收货地址/电话模糊匹配，最多 30 条；
  - **无关键字**：取客户档案（上限 500）在 Java 侧按 Haversine 球面距离排序，返回**最近 10 个**；档案无坐标的客户排在有坐标客户之后、按名称兜底（`base_customer` 经纬度大量为空，不能让下拉空白）。
- 地址取值：优先客户默认收货地址（`base_customer_address.is_default=1` 的 `detail_address`），回落 `base_customer.shipping_address` 主地址冗余。
- 坐标取值：同样优先地址子表的经纬度，回落 `base_customer.longitude/latitude`。
- 返回：`[{customerCode, customerName, address, distanceKm?}]`，`distanceKm` 保留 1 位小数，仅无关键字且坐标可得时存在。

### 3.3 新增 `POST /tms/app/return/warehouse-list`

- 无入参。返回状态正常的实物仓：
  ```sql
  WHERE COALESCE(status,'NORMAL')='NORMAL'
    AND COALESCE(warehouse_type,'实物仓') <> '虚拟仓'
  ```
  历史数据 `warehouse_type` 为 NULL 或「正常仓」的仓库按实物仓处理。
- 返回：`[{warehouseCode, warehouseName, warehouseType}]`；建单仍提交 `warehouseName`（与库存/退货单的仓库口径一致）。

## 四、APP 设计

### 4.1 客户选择

- 客户信息卡删除「客户编码」输入框；「客户名称」改为整行可点的下拉样式控件（`_PickerTile`），点击弹出底部选择器：
  - 打开即静默定位（`Geolocator`，medium 精度、8s 超时，权限拒绝/无定位均降级），无关键字时展示**最近 10 个客户**，每行：客户名称 + 距离徽标（`x.xkm`）+ 地址（单行省略）；底部提示「默认按当前位置由近到远展示，无坐标客户排在后面」。
  - 顶部搜索框输入关键字（350ms 防抖）调模糊查询。
  - 选中后回填客户名称；`customerCode` 仅存状态用于建单，界面不再展示。

### 4.2 仓库选择

- 「收货仓库」同为下拉控件，弹层列出实物仓（仓库图标 + 名称），选中回填仓库名称。

### 4.3 商品搜索与扫码

- 搜索框占位文案「扫码 / 输入名称·编码·条码」，输入 350ms 防抖后自动出下拉；下拉行按需求显示**商品名称 + 规格 · 单位**（不再显示编码与价格）。
- 右侧新增【扫码】按钮，弹出条码录入框：
  - **PDA 硬件扫码枪**以键盘楔入方式把条码打进焦点框并发送回车，`onSubmitted` 即一次扫码；
  - 手机无扫码枪时可手动输入条码后回车/点「查询」；
  - 搜索框本身同样支持回车直扫（焦点在搜索框时扫枪直接生效）。
- 扫码结果处理：条码/编码**精确命中 → 直接加入退货清单**并提示「已添加：商品名」（已在清单则数量 +1）；未精确命中但有模糊结果 → 回填关键字列出相似商品让司机点选；完全无结果 → 提示「未找到该条码对应的商品」。

### 4.4 为什么不引相机扫码

项目规范本阶段不引入新外部依赖。PDA 安卓手持终端的硬件扫头普遍以键盘楔入模式工作（扫码 = 往焦点框输入条码 + 回车），条码录入框 + 回车直查即可复用全部现有能力；普通手机可手动输入条码。相机图像扫码留待后续统一引入扫码组件时覆盖。

## 五、数据变更

无。复用 `base_customer(longitude/latitude/shipping_address)`、`base_customer_address`、`base_warehouse(warehouse_type/status)`、`base_goods(barcode/simple_code/can_return)`。

## 六、验收要点

1. 现场退货页不再出现「客户编码」字段；客户名称为下拉控件，点击弹出选择器。
2. 选择器无关键字时返回最近 10 个客户：有坐标的按距离升序、行内显示距离与地址；无坐标客户排后面；关键字搜索按名称/地址/电话命中。
3. 默认地址取 `base_customer_address` 子表（is_default=1）优先于 `shipping_address`。
4. 收货仓库下拉只出现实物仓：虚拟仓、停用仓不出现；历史「正常仓」/NULL 类型仓库正常出现。
5. 商品关键字搜索不再报错（原文本块 SQL 粘连 500）；停用商品、`can_return=FALSE` 商品不出现。
6. 条码精确命中自动加入清单；重复扫码数量累加；未命中给明确提示。
7. 定位权限拒绝/无 GPS 时客户选择器仍能打开（按名称兜底列表），不阻塞退货流程。
8. `flutter analyze` 无 issue；后端编译通过。
