## 一、背景与问题

PRD-25 已把司机配送签收结算全链路跑通，但**所有业务开关都是硬编码**。当前存在四类问题：

| 问题 | 现状 | 影响 |
|---|---|---|
| 行为不可配 | 签收拍照张数、结算是否必须拍照、是否允许现场退货等，全部写死在 APP 与后端代码里 | 不同客户运营口径不同（有的要求签名、有的嫌麻烦），只能改代码重新打包 |
| 参数无入口 | 后端 `sys_param_runtime` 表已有 16 条参数，但只能靠 Flyway 脚本或直连数据库改值，**没有任何可用的管理界面** | 运营无法自助调整，每次调参都要研发介入 |
| 读取方式原始 | 参数读取无 Service 层、无缓存，各处 Controller 裸写 `SELECT ... FROM sys_param_runtime WHERE param_key IN (...)` + `try/catch` 兜默认值 | 同一参数在多处重复查库；新增参数要在多个 Controller 复制样板代码 |
| 编号靠手工 | `param_id` 手工排号，V61 与 V60 都用了 `P0105` 已出过一次冲突 | 迁移脚本合并时容易撞号 |

本需求要解决的是：**把 11 项司机派送业务开关沉淀为可配置参数，配一个真正可用的参数设置页，并把参数读取收敛成一个带缓存的统一服务。**

## 二、需求方原文与口径确认

### 2.1 原文参数清单

需求原文 `docs/TMS系统参数设置.md` 列了 10 个编号，但**编号有重复**（出现两个「2、」），实际是 **11 项**参数。逐项抄录并确认口径：

| # | 参数名（原文） | 参数值 | 默认 | 原文行为说明 |
|---:|---|---|---|---|
| 1 | 是否开启TMS司机派送流程 | 是/否 | 是 | 是=启用司机系统进行签收；否=系统后台签收，不走司机派送流程 |
| 2 | 司机合并结算送货与退货单据冲抵资金账户 | 末级正常启用的资金账户 | — | 销退合并结算时冲抵部分写对应资金账户，一正一负，备注为【业务单号+合并结算冲抵】。结算后更新退货单已退金额、发货单已收金额。发货 > 退货，剩余按选择的结算方式处理（挂账则生成剩余金额应收流水）；退货 > 发货，剩余退货金额默认挂账生成应付流水 |
| 3 | 司机派送退货单与送货是否可合并结算 | 是/否 | 否 | 是=APP 司机签收后可选择送货单与退货单一起结算；否=不可一起勾选结算，退货回收单据在签收确认后自动完成，签收确认时提示【确认签收后即完成退货回收，请确认回收数量是否正确】，「是」完成流程，「否」返回签收页面<br>📌 **本次实施取默认 `Y`（保留 PRD-25 现状），不采用原文默认「否」，见 §2.2** |
| 4 | 司机派送单据签收是否需要客户电子签名 | 是/否 | 否 | 是=签收页显示签名相关信息和功能；否=不显示电子签名相关功能 |
| 5 | 司机送货签收需拍照片数 | 整数 | 2 | 用户可自定义修改。为 0 表示可不上传。最多支持 5 张 |
| 6 | 司机退货回收需拍照片数（包括司机现场退货） | 整数 | 2 | 同上，0~5 |
| 7 | 司机派送结算是否强制需要上传照片 | 是/否 | 否 | 是=需要上传照片 |
| 8 | 司机在上一个派送任务未交款前是否可接单 | 是/否 | 否 | 是=上一个任务未交款可接新单；否=必须上一个任务交款完成后才可接任务，避免配送未完成又领任务 |
| 9 | 司机是否可进行现场退货 | 是/否 | 是 | 是=司机端显示【现场退货】入口，可现场开退货单；否=不显示入口，不能开退货单 |
| 10 | 司机提交交账是否需要电子签名 | 是/否 | 否 | 否=不展示电子签名且可不签名；是=显示电子签名功能且须签名 |
| 11 | 司机发车后是否可追加任务 | 是/否 | 是 | 否=发车后的任务只能作为新一车次任务，不可追加到当前已发车任务；是=后台可添加任务到配送中任务，由司机端接单确认进入配送中任务列表 |

### 2.2 与已实现功能的冲突及处理口径

PRD-25 已实现了其中部分行为，但**默认值与需求原文不一致**，这是本需求必须显式说明的部分。

> **本节结论已由需求方确认（决策口径）**：
> 1. **默认值一律以需求原文为准**（原文优先）；
> 2. **唯一例外是参数 #3「退货与送货可合并结算」**，保留 PRD-25 现状默认 `Y`（允许合并），不采用原文默认「否」；
> 3. **参数 #2 冲抵账户采用「两者并存、职责切分」方案**（见 §2.3，已拍板）。

| 参数 | PRD-25 现状 | 原文要求默认值 | 处理口径 |
|---|---|---|---|
| #7 结算强制上传照片 | 3-C 阶段实现为**强制必填**（硬编码校验生效） | **否**（不强制） | ✅ **已确认：按原文，默认改为「否」**。即升级后默认放开结算拍照，需要强制的客户自行开启。这是一次**行为变更**，须在升级说明中提示运营方 |
| #11 发车后可追加任务 | V69 已通过 `tms_dispatch.parent_dispatch_id` 实现追加能力，且**无开关** | 是（默认允许） | 保留能力，加开关。默认「是」与现状一致，**无行为变更** |
| #5 签收拍照张数 | 硬编码（PRD-25 签收页固定张数校验） | 2 | 默认 2 与现状一致，改为读参数 |
| #2 合并结算冲抵账户 | PRD-25 已实现合并结算与一正一负流水，但**冲抵账户来自司机-账户关联表 `tms_driver_fund_account`** | 由参数指定一个全局账户 | ✅ **已确认：两者并存、职责切分**（司机真实收款走 `tms_driver_fund_account`，销退冲抵走全局参数 `TMS_OFFSET_FUND_ACCOUNT`），见 §2.3 |
| #3 退货与送货可合并结算 | PRD-25 已实现**允许合并结算** | 否（默认不允许） | ✅ **已确认：保留现状默认 `Y`（允许合并），不采用原文默认「否」**。理由：PRD-25 已实现并验证通过，默认关闭会使既有能力失效；原文「否」分支（退货签收即自动完成 + 确认提示语）属新增行为分支，归入**阶段 D / PRD-27**。参数本期照常落库，运营方可自行改为「否」，但「否」分支行为在阶段 D 上线前**仅表现为结算页禁止同时勾选**，不含自动完成 |
| #1 是否开启司机派送流程 | 无此开关，司机流程始终启用 | 是 | 默认「是」与现状一致。「否」分支（后台签收）**本期只做开关落库与 APP 侧拦截，后台签收入口不在本期范围** |

### 2.3 已确认设计点：冲抵账户方案

**参数 #2「合并结算冲抵资金账户」与 PRD-25 的司机-账户关联表存在职责重叠。**

- PRD-25 的设计决策是「司机收款账户 → 加一张司机-账户关联表 `tms_driver_fund_account`」，即**每个司机可用的收款账户是按人配置的**。
- 本需求原文要求「司机合并结算送货与退货单据冲抵资金账户」是**一个全局参数**。

两者并不矛盾，因为用途不同：

| 用途 | 数据来源 | 说明 |
|---|---|---|
| 司机实收现金/转账落哪个账户 | `tms_driver_fund_account`（按司机配） | 司机手上的现金账户、个人收款码等，因人而异 |
| 销退合并结算的**冲抵**部分落哪个账户 | 本参数 `TMS_OFFSET_FUND_ACCOUNT`（全局唯一） | 冲抵是账面对冲，不涉及真实资金收付，用一个全局虚拟/过渡账户更合理 |

✅ **已确认口径**：两者并存，职责如上表切分。冲抵专用账户**须在基础数据中单独建一个末级账户**（建议命名「销退冲抵过渡户」），避免与司机真实现金账户混在一起影响资金余额核对。

落地要求：

| 项 | 要求 |
|---|---|
| 账户建立 | 上线前由实施在 `base_fund_account` 建「销退冲抵过渡户」末级账户，`status='NORMAL'` |
| 参数配置 | `TMS_OFFSET_FUND_ACCOUNT` 指向该账户；**不允许指向任何司机的收款账户** |
| 校验 | 保存参数时校验为末级 + `NORMAL`；建议额外校验该账户未出现在 `tms_driver_fund_account` 中，命中则给出警示 |
| 流水 | 冲抵流水（一正一负、备注【业务单号+合并结算冲抵】）全部落该账户，净额为 0，便于对账时整户勾平 |
| 兼容 | 参数为空时，合并结算接口**明确报错**「未配置合并结算冲抵资金账户」，不静默回落到司机账户 |

## 三、参数字典（开发依据）

### 3.1 命名与编号规范

- `param_key` 统一 `TMS_` 前缀 + 大写下划线语义命名。
- `param_group` 统一取 **`TMS配送`**（与 V59/V62 已有的 TMS 参数保持同组，避免分组碎片化）。
- **`param_id` 从 `P0117` 起排**：现有已占用到 `P0116`（P0001~P0002 通用、P0101~P0104 到达打卡、P0105 销退应收时点、P0107~P0108 调度员、P0109~P0110 异常上报、P0111~P0116 推送与通知）。
- ⚠️ **V61 与 V60 曾同用 `P0105` 撞号**。本次迁移脚本的 `ON DUPLICATE KEY UPDATE` **以 `param_key` 为幂等键**（`param_key` 上有 UNIQUE 约束），`param_id` 仅作展示用主键，即使撞号也不会导致数据错乱。

### 3.2 参数明细表

| param_id | param_key | param_name | 类型 | 默认值 | 值域 | 消费方 |
|---|---|---|---|---|---|---|
| P0117 | `TMS_DRIVER_FLOW_ENABLED` | 是否开启TMS司机派送流程 | bool | `Y` | Y/N | 后端调度、APP 登录后能力控制 |
| P0118 | `TMS_OFFSET_FUND_ACCOUNT` | 司机合并结算冲抵资金账户 | account | 空 | `base_fund_account` 末级且 `status='NORMAL'` | `TmsStoreSettleController` 合并结算 |
| P0119 | `TMS_RETURN_MERGE_SETTLE` | 司机派送退货单与送货是否可合并结算 | bool | `Y` ⚠️ | Y/N | APP 结算页勾选逻辑（「否」分支的签收自动完成归阶段 D） |
| P0120 | `TMS_SIGN_ESIGN_REQUIRED` | 司机派送单据签收是否需要客户电子签名 | bool | `N` | Y/N | APP 签收页 |

| P0124 | `TMS_ACCEPT_BEFORE_SETTLE` | 上一个派送任务未交款前是否可接单 | bool | `N` | Y/N | 后端接单接口拦截 |

⚠️ **P0119 默认值说明**：需求原文默认为「否」，本次实施**取 `Y`**，这是需求方确认的例外（见 §2.2 决策口径）。迁移脚本的 `default_value` 与 `param_value` 均写 `Y`，保证首次落库后合并结算行为与 PRD-25 完全一致，**不产生行为变更**。

### 3.3 值域约束与钳制规则

沿用项目既有惯例（`TmsNotificationController.pollSeconds()` 把轮询秒数钳制在 `[30,600]`、`loadArriveConfig()` 用 `if (warn < normal) warn = normal` 做业务合法性钳制），本需求的钳制规则：

| 参数 | 钳制 |
|---|---|
| `TMS_SIGN_PHOTO_COUNT` / `TMS_RETURN_PHOTO_COUNT` | 解析失败或越界 → 钳制到 `[0,5]`，解析异常回落默认值 2 |
| bool 类参数 | 只认 `Y`；其余一切值（含空、null、`true`、`1`）均视为 `N`。**唯一例外**：默认值为 `Y` 的四项（`TMS_DRIVER_FLOW_ENABLED`、`TMS_RETURN_MERGE_SETTLE`、`TMS_ONSITE_RETURN_ENABLED`、`TMS_APPEND_AFTER_DEPART`）在**查库失败**时回落 `Y`，保证降级后不影响存量业务 |
| `TMS_OFFSET_FUND_ACCOUNT` | 保存时校验必须是 `base_fund_account` 中末级、`status='NORMAL'` 的账户；为空时合并结算功能不可用，需在结算接口给出明确报错而非静默失败 |

## 四、页面设计

### 4.1 交互结构（参照客户提供的界面）

参数设置页采用**左分组导航 + 右表单 + 顶部统一保存**三段式布局：

```
┌──────────┬────────────────────────────────────────────┐
│ 公共参数  │  [ 保 存 ]                                  │
│ 订单参数  │  ────────────────────────────────────────  │
│ 财务参数  │  参数标签：  [控件]                          │
│ TMS配送  │              灰色说明文字                     │
│ APP打印  │  参数标签：  ○是 ●否                         │
│          │              灰色说明文字                     │
└──────────┴────────────────────────────────────────────┘
```

关键交互规则：

| 元素 | 规则 |
|---|---|
| 左侧分组导航 | 竖向排列，选中态浅蓝底（`#eaf2ff`）+ 蓝字（`#1677ff`）+ 加粗。点击切换右侧表单，**不发起请求**（参数全量一次拉取） |
| 顶部保存按钮 | 独立置顶，**保存当前分组的全部改动**（不是保存单项）。保存后 toast 提示 |
| 参数项三段式 | 标签（右对齐、冒号结尾）+ 控件 + 控件下方灰色说明文字（`#667085`） |
| 控件类型 | ① 下拉框（资金账户选择、枚举取值）② 是/否 radio 对 ③ 数字输入（照片张数，带 0~5 范围提示） |
| 禁用态 | 不可修改的参数 radio 显示为灰色不可点（参照原界面「是否启动生产日期管理：禁用，统一WMS管理批次」），但**仍展示当前值与禁用原因** |
| 脏数据提示 | 有未保存改动时离开分组或页面，需二次确认 |

### 4.2 分组归属

本需求 11 项参数全部归入左侧 **「TMS配送」** 分组。其余分组（公共参数/订单参数/财务参数/APP打印参数）在本期只做导航占位与已有参数展示，不新增参数。

分组与 `param_group` 字段的映射：

| 左侧导航 | `param_group` 值 |
|---|---|
| 公共参数 | `通用` |
| 订单参数 | `订单` |
| 财务参数 | `财务` |
| TMS配送 | `TMS配送` |
| APP打印参数 | `APP打印` |

⚠️ 现有 16 条参数的 `param_group` 实际值需在开发时核对，缺失分组的参数统一落到「公共参数」兜底，**不能因为分组值对不上导致参数在页面上消失**。

## 五、开发方案

### 5.1 数据层（Flyway V75）

新建 `backend/src/main/resources/db/migration/V75__tms_param_setting.sql`，照 V59 样板写 upsert：

```sql
INSERT INTO sys_param_runtime (param_id, param_key, param_name, param_value, default_value, param_group, remark)
VALUES ('P0117', 'TMS_DRIVER_FLOW_ENABLED', '是否开启TMS司机派送流程', 'Y', 'Y', 'TMS配送',
        '是=启用司机APP签收；否=后台签收，不走司机派送流程')
ON DUPLICATE KEY UPDATE param_name = VALUES(param_name), default_value = VALUES(default_value), remark = VALUES(remark);
-- 其余 10 条同构
```

**要点**：

1. `ON DUPLICATE KEY UPDATE` 里**不更新 `param_value`**——重复执行迁移不能把运营已调的值冲回默认值，这是 V59 样板的核心用意。
2. 幂等键是 `param_key`（UNIQUE 约束），不是 `param_id`。
3. `default_value` 与首次的 `param_value` 写同一个值，保证 `COALESCE(param_value, default_value)` 两条路径一致。

### 5.2 后端：参数读取服务化

现状是**每个 Controller 裸查 + try/catch 兜默认值**，样板见 `TmsDeliveryAppController.loadArriveConfig()`。本需求新增一个统一读取入口，但**不推翻现有写法**（避免大范围回归）：

新建 `backend/src/main/java/com/erp/system/SysParamService.java`：

```java
@Service
public class SysParamService {
    // key -> value 的进程内缓存，参数更新时整体失效
    private volatile Map<String, String> cache = null;

    public String get(String key, String fallback);
    public boolean getBool(String key, boolean fallback);   // 只认 'Y'
    public int getInt(String key, int fallback, int min, int max);  // 带钳制
    public Map<String, String> getAll(Collection<String> keys);
    public void evict();   // 由 /system/param/update 调用
}
```

设计要点：

| 点 | 说明 |
|---|---|
| 缓存策略 | 进程内 `volatile Map` 全量缓存 + **写后整体失效**（参数量级只有几十条，全量重载成本极低，不做单 key 失效以避免一致性漏洞） |
| 降级 | 查库异常时**不抛出**，返回调用方传入的 `fallback`，与现有 `try/catch (Exception ignore)` 行为一致。参数服务永不成为业务链路的故障点 |
| 钳制内置 | `getInt` 把 min/max 钳制内置，避免各调用点重复写 `if (x < 0) x = 0` |
| 不改存量 | 现有 `loadArriveConfig()` 等裸查逻辑保持不动，本期只让**新增的 11 项参数**走 Service。存量收敛另开技术债需求 |

### 5.3 后端：参数管理接口

`com.erp.system.SystemController` 现有两个接口，需要改造：

| 接口 | 现状 | 本期改动 |
|---|---|---|
| `POST /system/param/page` | 全量 `queryForList` 后**内存分页**，筛选条件未下推 SQL | 新增 `paramGroup` 筛选并**下推到 SQL**；参数设置页不分页，走新接口 |
| `POST /system/param/update` | `UPDATE sys_param_runtime SET param_value=? WHERE param_key=?`，单条 | 保留。**新增更新后调用 `SysParamService.evict()`** —— 否则改了参数缓存不失效，是最容易漏的一步 |

新增两个接口：

| 接口 | 用途 | 说明 |
|---|---|---|
| `GET /system/param/setting` | 参数设置页一次性拉全量参数 | 返回按 `param_group` 分组的结构，不分页 |
| `POST /system/param/batch-update` | 分组内批量保存 | 入参 `[{paramKey, paramValue}]`，**单事务**逐条 `UPDATE`；全部成功后 `evict()` 一次。校验失败（如账户不合法、照片数越界）整批回滚 |

⚠️ 注意 `/system/param/update` 只能改 `param_value`，**不支持新增/删除参数**——这是有意的设计，参数集合由 Flyway 管理，界面只能改值。本期维持该约束。

### 5.4 前端：新增设置页的 5 处登记

项目里新增一个设置页必须在 **5 处**登记，缺一处页面就打不开（会弹「该功能正在开发中」）：

| # | 文件 | 内容 |
|---|---|---|
| 1 | 后端 `SystemController` | `/param/setting` + `/param/batch-update` |
| 2 | `frontend/src/router/index.js` | 扁平 children 注册，`meta.title='参数设置'` + **`meta.module='paramSetting'`** |
| 3 | `frontend/src/fallback-menus.js` | 在「系统管理」分组下加 `{ code: 'paramSetting', name: '参数设置' }` |
| 4 | `frontend/src/module-config.js` | 参数设置页是**自定义布局，不能复用 `GenericBusinessList.vue`** → 需新建独立组件，config 只登记标题与模块码 |
| 5 | `frontend/src/module-api.js` | `{ setting, batchUpdate }` 两个方法 |

⚠️ **`codeToPath` 隐式契约**（`AppShell.vue`）：`code.replace(/([a-z0-9]|(?=[A-Z]))([A-Z])/g,'$1-$2').toLowerCase()`，即 `paramSetting` → `param-setting`。**路由 path 必须精确写成 `param-setting`**，否则菜单点击无法命中路由。

前端新建组件 `frontend/src/views/system/ParamSetting.vue`（独立组件，因为分组导航 + 统一保存的布局与通用列表页差异过大）。

### 5.5 消费方改造清单

参数落库只是第一步，真正的工作量在**让 11 个参数在各自的业务落点生效**：

| 参数 | 落点 | 改造内容 | 工作量 |
|---|---|---|---|
| `TMS_DRIVER_FLOW_ENABLED` | APP 登录响应 / 后端调度 | 关闭时 APP 提示「司机派送流程已关闭」并禁用配送 tab | 中 |
| `TMS_OFFSET_FUND_ACCOUNT` | `TmsStoreSettleController` | 合并结算冲抵流水的账户由该参数指定（**不再取 `tms_driver_fund_account`**，职责切分见 §2.3）；为空时报错 | 中 |
| `TMS_RETURN_MERGE_SETTLE` | APP 结算页 | **默认 `Y`，本期只做「读参数」**：为 `N` 时结算页禁止同时勾选送货单与退货单。「否」分支的**签收即自动完成 + 确认提示语**归阶段 D | 小（本期）／大（阶段 D 分支） |
| `TMS_SIGN_ESIGN_REQUIRED` | APP 签收页 | 开启时显示电子签名控件并校验必签 | **大**（电子签名控件为新增能力） |
| `TMS_SIGN_PHOTO_COUNT` | APP 签收页 + 后端签收校验 | 张数改为读参数，0 时跳过校验 | 小 |
| `TMS_RETURN_PHOTO_COUNT` | APP 退货回收/现场退货 | 同上 | 小 |
| `TMS_SETTLE_PHOTO_REQUIRED` | APP 门店结算页 + 后端 | **把 PRD-25 的硬编码必填改为参数控制，默认放开** | 小 |
| `TMS_ACCEPT_BEFORE_SETTLE` | 后端接单接口 | 关闭时校验司机是否有未交款的历史任务，有则拦截接单 | 中 |
| `TMS_ONSITE_RETURN_ENABLED` | APP 门店详情页 | 控制【现场退货】入口显隐 | 小 |
| `TMS_HANDOVER_ESIGN_REQUIRED` | APP 交账页 | 开启时显示电子签名并校验必签 | 中（复用签收签名控件） |
| `TMS_APPEND_AFTER_DEPART` | 后端追加任务接口 | 关闭时禁止向已发车调度单追加（V69 `parent_dispatch_id` 路径） | 小 |

**APP 侧参数下发机制**：APP 不直连参数表。在司机登录响应（`POST /api/tms/app/login`）与任务列表拉取接口中**附带参数快照**，APP 本地缓存，避免每个页面单独请求参数。参数变更后司机下次登录或刷新任务列表时生效。

### 5.6 实施阶段建议

| 阶段 | 内容 | 可独立交付 |
|---|---|---|
| A | V75 迁移 + `SysParamService` + 管理接口 + 参数设置页（前端） | ✅ 参数可配可存，界面完整 |
| B | 小工作量消费方（照片张数 ×2、结算拍照、现场退货入口、发车追加、**合并结算开关读参数**） | ✅ |
| C | 中工作量消费方（冲抵账户切换到全局参数、未交款接单拦截、司机流程总开关） | ✅ |
| D | 大工作量消费方（电子签名控件 ×2、**`TMS_RETURN_MERGE_SETTLE=N` 时的退货签收自动完成分支与确认提示语**） | 建议单独开需求，因涉及新增签名能力与签收流程分支 |

**阶段 D 建议拆为 PRD-27**，范围包含：

1. 电子签名能力（签名画板、图片生成、存储通道），服务 `TMS_SIGN_ESIGN_REQUIRED` 与 `TMS_HANDOVER_ESIGN_REQUIRED`；
2. **`TMS_RETURN_MERGE_SETTLE=N` 的「否」分支**：退货回收单签收确认后自动完成，确认时弹【确认签收后即完成退货回收，请确认回收数量是否正确】，「是」完成流程、「否」返回签收页。

这两项与「参数设置」这件事本身是两回事。本需求的验收范围收在 **A+B+C**。由于 `TMS_RETURN_MERGE_SETTLE` 默认保留 `Y`，阶段 D 未上线期间**不影响任何默认行为**。

| 1 | 执行 V75 迁移 | `sys_param_runtime` 新增 11 条，`param_group='TMS配送'` |

## 七、风险与注意事项

| 风险 | 说明 | 应对 |
|---|---|---|
| **行为变更未告知** | 本需求**唯一的行为变更**是参数 #7：结算拍照由 PRD-25 的「强制必填」变为默认「不强制」 | 升级说明必须单列此项，让运营方决定是否手工把 `TMS_SETTLE_PHOTO_REQUIRED` 开回 `Y`。参数 #3 已确认保留默认 `Y`，**不构成行为变更** |
| **冲抵账户误配为司机账户** | 若 `TMS_OFFSET_FUND_ACCOUNT` 被配成某司机的真实现金账户，冲抵流水会污染该账户余额，导致司机交账对不上 | §2.3 要求单独建「销退冲抵过渡户」；保存参数时校验该账户未出现在 `tms_driver_fund_account` 中，命中给警示 |
| **缓存未失效** | `param/update` 忘记调 `evict()`，改了参数不生效，且现象是「偶尔生效」（重启后才对），极难排查 | 验收标准 #7 专项覆盖；代码评审重点检查 |
| **分组值对不上导致参数消失** | 现有 16 条参数的 `param_group` 实际值未逐条核对 | 开发时先查一遍 `SELECT DISTINCT param_group FROM sys_param_runtime`，未匹配的落「公共参数」兜底 |
| **`codeToPath` 契约** | 路由 path 拼错只会静默弹「该功能正在开发中」，不报错 | 登记后立即点菜单验证 |
| **假接口误导** | `/system/precision`、`/dictionary`、`/workflow`、`/print-template` 都是假数据（`simpleSystemPage` 返回硬编码单行，`saveSimpleConfig` 只写日志不落库） | **不要照抄这些接口的实现**，参数设置必须真落库 |
| Flyway 号串行 | `V75` 是全局串行资源，合并前须查重号 | 按 `V<n>__` 前缀分组计数检查 |
