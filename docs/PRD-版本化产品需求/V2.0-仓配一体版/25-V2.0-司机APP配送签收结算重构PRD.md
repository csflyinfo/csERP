# V2.0 司机APP配送签收结算重构 PRD

- 编号：PRD-25
- 版本：V2.0 仓配一体版
- 分支：`feat/tms-driver-app-redesign`
- Flyway：V69~V74
- 状态：开发中（后端全链路自测通过，真机验证与「返回二次确认」待补）

## 一、背景与问题

V2.0 首版司机 APP 把「装车 / 发车 / 签收 / 收款」四件事按**调度单整单**一刀切，
和司机的真实作业节奏对不上。逐条列出实际卡点：

| 问题 | 首版行为 | 后果 |
|---|---|---|
| 装车必须整车一起确认 | `tms_dispatch.status` 一个字段管全车 | 司机装一家确认一家的习惯无法表达；有一家缺货，全车都发不了 |
| 发车必须整车一起发 | 同上 | 部分门店缺货时，已装好的货被扣在库里等 |
| 一张调度单在途后无法加单 | `create` 全程没有按 `driver_id` 的占用性查询 | 同一司机被并行塞进多张 ASSIGNED 单，APP 首页冒出多张互不相关的待接单卡片 |
| 按单收款对不上账 | 签收页每单填收款金额 + 单一 `payMethod` | 同门店有发货单也有退货单，客户只按净额付钱；混合收款（现金+微信+挂账）表达不了 |
| 一次上门产生多张零散收款单 | 每单一张 | 财务对账痛苦 |
| 签收即回传 | 每单签收单独调后端 | 弱网下签一半断网，已传的改不回来，未传的要重录 |
| 交账审核不联动财务 | 收款单停在 PENDING 无人处理 | 钱已回公司，应收还挂着，账实不符 |

## 二、需求范围（需求方原文）

> 1、装车确认页面，「核对」改为【装车】按钮；司机可按单个配送点点击装车，
> 也可勾选/全选配送点用【装车】按钮快速完成装车。
> 2、确认发车时，如果当前列表存在未确认装车的配送点，仍要发车后，只更新确认装车了的
> 配送点的发车状态；未装车完成的配送点再次确认装车后可继续确认发车；确认了发车的
> 配送点不在列表展示。
> 3、配送点详情页中间的按钮占空间太多，优化布局，让司机能快速看到配送单据；
> 司机先对各单据确认签收，签收完成后进行结算；可以全选结算，也可勾选单个单分别结算；
> 在签收页不再进行结算操作；单个签收不回传后台更新数据，需在结算后统一更新后台单据数据；
> 返回上一页提示「当前配送点未完成结算，请确认是否返回」；返回上页再进来要保存前面的
> 签收数据再进行结算；结算页可选择【挂账】+ 资金账户配置的司机收款账户（多个则显示多个），
> 支持混合收款；结算后挂账之外的部分都为已收款，生成对应收款单，并自动完成应收结算和
> 收款单核销；多单合并结算时应收金额要冲减退货单金额；结算金额小于 0 或单选退货单时
> 默认选择【挂账】；结算时要进行拍照；结算后配送单和退货单冲减的部分默认已收和已退。

### 2.1 四条口径确认（与需求方确认结果）

这四条是本需求的关键设计决策，实现全程以此为准：

| 议题 | 结论 | 影响 |
|---|---|---|
| 司机收款账户怎么关联 | **新建一张司机-账户关联表** | 建 `tms_driver_fund_account`。不给 `base_fund_account` 加 `driver_id`——公司微信账户会被多个司机共用，一个司机也可持有多个账户，是纯多对多 |
| 结算生成的收款单初始状态 | **待审核，且后台不能删除**；司机交账单经财务确认后自动审核并走财务结算流程 | 收款单落 `PENDING`；`/receipt/delete` 拦截 `business_source='DRIVER_SETTLE'`；财务联动的触发点是**交账单审核**，不是结算本身 |
| 结算拍照怎么传 | **复用现有签收照片上传通道** | `bizType=SETTLEMENT`，不新建上传端点 |
| 交账应交回金额以什么为准 | **以门店结算表为准**（方案 A） | 应交回 = 门店结算 `received_amount` 的现金部分 + 旧签收路径现金；退货已在结算时冲减净额，交账不再重复减退货；收款流水页改读结算账户明细 |

## 三、装车与发车下沉到配送点粒度

首版把装车/发车做成**单据级**状态，本次下沉到**明细级**（配送点）。

### 3.1 状态字段与口径

| 字段 | 位置 | 含义 |
|---|---|---|
| `load_status` | `tms_dispatch_detail` | PENDING / LOADED，该配送点是否已确认装车 |
| `load_time` | `tms_dispatch_detail` | 确认装车时间 |
| `depart_time` | `tms_dispatch_detail` | 该配送点发车时间，NULL = 尚未随车出发 |

三条口径后端多处依赖，**不要改**：

1. `depart_time IS NOT NULL` 即「在车上、正在配送」，配送中列表以此为准，
   不再依赖 `tms_dispatch.status`——同一张调度单会同时存在「已发车的点」和「还没装车的点」。
2. `tms_dispatch.status` 仍保留：只有名下全部明细都发车后才置 `DEPARTED`，
   否则停在 `LOADED`，让司机能继续对剩余配送点装车/发车。
3. 已发车的配送点从装车列表移除，避免重复操作。

### 3.2 部分发车的行为

发车时若存在未装车的配送点，**不阻断**，只把已装车的点置上 `depart_time`。
未装车的点留在列表里，司机之后补装车再发一次即可。这正是需求 2 的原文诉求。

## 四、追加调度单（司机在途二次派活）

司机已出车，临时又来单，业务要能表达「这批是追加给这趟车的」。

### 4.1 为什么不把明细直接塞进在途单

在途单 `status` 已是 `DEPARTED`/`DELIVERING`，而**首版**装车/发车是单据级状态，
往里加明细等于要求把装车/发车下沉到明细级，`/loading/start`、`/depart`、
`/delivering/stores`、`/home/overview` 全部要重写，状态机还要引入「部分已发车」中间态。

因此选择：追加时**新建一张独立调度单**，用 `parent_dispatch_id` 指回被追加的在途单。
新单独立走 接单 → 装车 → 发车；发车后它的配送点在「配送中」列表里按门店与原单归并，
司机视角仍是同一趟车。

> 注：本需求同时做了第三节的明细级下沉，但追加单仍保持独立单据形态——
> 独立单据在「这批货是哪次派的、谁派的、什么时候派的」上有独立留痕，
> 合并进老单会丢掉这层信息。

### 4.2 为什么不建 append 关系表

追加是「一张单最多一个父」的一对多树形关系，主表一个外键列最省事，
也能被 create/查询直接带出。独立关系表只在「一张单追加到多张单」时才有意义，业务上不存在。

## 五、签收与结算分离（本需求的核心改动）

### 5.1 新流程

```text
配送点详情页
  ├─ 逐单签收（正常/部分/拒收）→ 只写本地草稿 sign_drafts，不回传后台
  ├─ 返回上页再进来 → 从本地草稿恢复，签收数据不丢
  └─ 结算（可全选、可勾选单个）
       ├─ 多单合并：应收净额 = Σ发货签收金额 − Σ退货金额
       ├─ 挂账 + N 个司机收款账户混合收款
       ├─ 现场拍照（必填）
       └─ 一次性落库：签收记录转正 + 门店结算单 + 收款单(PENDING) + 单据状态
```

**签收只存本地**是为了弱网可用：签一半断网不会出现「一半已传一半没传」的撕裂状态。
结算是**唯一的后台落库时点**，一次事务里把签收记录、结算单、收款单全部写完。

### 5.2 数据模型

| 表 | 作用 |
|---|---|
| `tms_driver_fund_account` | 司机可收款的资金账户（多对多） |
| `tms_store_settlement` | 门店结算单主表，MJ + yyyyMMdd + 4 位流水 |
| `tms_store_settlement_detail` | 参与结算的单据行，发货为正、退货为负，便于直接 SUM |
| `tms_store_settlement_account` | 各资金账户实收金额（混合收款，与 `fin_receipt_detail` 同构） |
| `tms_store_settlement_photo` | 结算现场照片 |

挂账金额单独存主表 `credit_amount`；账户放明细行而非主表，才能表达混合收款。

### 5.3 默认挂账的两种场景

`settle_amount < 0`（退货大于发货）或**单选退货单**时，前端默认且只允许挂账
（`creditOnly=true`）。原因是这两种场景钱是公司往外付或不涉及收款，
走收款单没有意义，应由财务在后台处理退款。

### 5.4 退货金额的取值来源

`tms_dispatch_detail.amount` 对 `RETURN` 行恒为 0（V55 起的已知缺陷），
因此结算时改为 JOIN `sales_return_apply.return_amount` 现取真值。
历史数据由 V72 回填（RECEIPT 取 `sales_receipt.deliver_amount`，
RETURN 取 `return_amount` 并**正数存放**，负向语义由 `bill_type` 表达）。

## 六、交账审核联动财务入账

这是本需求财务侧的闭环。**触发点是财务审核交账单**（钱确实回到公司），不是司机结算。

### 6.1 联动链路

```text
POST /tms/settlement/{id}/audit
  ├─ ① 交账单 → APPROVED
  ├─ ② 补认领门店结算单（见 6.2）
  └─ ③ approveStoreSettlements(settlementId)
        └─ 逐张门店结算 → auditReceiptForSettle(receiptId, arNos)
              ├─ 1. 按结算明细 ar_no 定向核销应收
              ├─ 2. 余额走 FIFO 兜底（按 due_date 排序）
              ├─ 3. 按收款明细逐账户记资金流水 + 更新余额
              ├─ 4. 记往来流水（CUSTOMER, IN）
              └─ 5. 收款单 → APPROVED，回写 verified_amount
```

单张结算失败不阻断整批：`try/catch` 收进 `failures` 并写 `APPROVE_FAIL` 日志；
未匹配余额写 `RECONCILE_REMAIN` 日志。重复审核由「已审核不可重复操作」拦截，保证幂等。

### 6.2 为什么审核时要再补认领一次门店结算

`settlement_id` 原先只在交账**提交**时按 `dispatch_id` 关联一次。但司机的实际操作顺序是
「先提交交账，再回配送点补做剩下门店的结算」——交账页和配送点页是两条独立入口。
那批后产生的结算单 `settlement_id` 永远是 NULL，审核时反查为空，收款单永远停在 PENDING。

因此审核时按「同司机 + 结算日期 = 交账日期 + 尚未被任何交账单认领 + 已结算」
再兜一次认领，口径与提交时一致，不会把别的交账单的结算抢过来。

### 6.3 定向核销为什么不能只靠 FIFO

`doReconcileAr` 有 `if (unreceived.signum() <= 0) continue;`，退货产生的**负向应收**
会被 FIFO 直接跳过。而门店结算明细里 `ar_no` 是有值的（来自 `loadBills` 的
`LEFT JOIN fin_ar ar ON ar.source_bill = dd.source_bill_no`），
因此先按 `ar_no` 定向核销，再让余额走 FIFO 兜底。

### 7.1 V71 不预置任何司机账户绑定

账户归属涉及资金安全，必须由财务在后台显式配置。未配置时 APP 结算页只显示【挂账】，
不会误把钱记到别人账上。

## 八、开发过程中修正的既有缺陷

这些都是本需求联调时暴露的**历史缺陷**，不属于新需求，但不修则链路不通：

| 缺陷 | 根因 | 处理 |
|---|---|---|
| 交账页应收总金额恒为 ¥0.00 | `insertDetail`/`assign` 的 INSERT 列清单漏了 `amount` | 两个 Controller 补列 + V72 回填 |
| 收款流水页看不出收在哪个账户 | 前端漏传 `fundAccountName` 时落了空串 | Controller 改为从 `base_fund_account` 回查，兜底「其他」+ V73 回填 |
| 同一客户往来余额分叉 | `counterparty_type` 写中文「客户」，财务模块用标准值域 | Controller 改写 `CUSTOMER` + V74 回填 |
| 收款核销一分钱都核不上 | `fin_ar.customer` 存的是**客户名称**，收款单 `counterparty_code` 存**编码**，两者对不上 | 编码查不到时统一回落名称匹配（原先只有 COUNTERPARTY 才回落） |
| 核销明细无法反查发货单 | `doReconcileAr` 调的是不写 `ar_no`/`source_bill` 的 V1 版 `writeReconcileRecord` | 改调 `writeReconcileRecordV2` 并补传 `sourceBill` |

> `fin_ar.customer` 存名称这件事之所以一直没暴露，是因为后台手工制单的老单据
> 恰好把名称填在了 code 位上，掩盖了列语义错位；司机交账收款单老实填了编码，
> 问题才浮出水面。该列是历史遗留的「弱引用」，本次不做列语义纠正（影响面过大），
> 只在查询侧做名称回落。

## 九、验收用例

### 9.1 装车与发车

| 用例 | 步骤 | 预期 |
|---|---|---|
| 单点装车 | 装车页点单个配送点【装车】 | 该点 `load_status=LOADED`，其余不变 |
| 批量装车 | 勾选多个/全选后点【装车】 | 所选点全部 LOADED |
| 部分发车 | 3 个点只装 2 个，确认发车 | 已装 2 个 `depart_time` 非空并从列表消失；未装 1 个仍在列表 |
| 补装后再发车 | 对剩余 1 个装车后再发车 | 该点发车成功；此时调度单 `status` 才置 DEPARTED |

### 9.2 签收与结算

| 用例 | 步骤 | 预期 |
|---|---|---|
| 签收不回传 | 逐单签收后不结算，查后端 | 后台单据状态无变化 |
| 草稿恢复 | 签收后返回上页再进入 | 签收数据完整恢复 |
| 退货冲减 | 发货 365.60 + 退货 70 合并结算 | 应收净额 295.60 |
| 默认挂账 | 单选退货单，或净额 < 0 | 默认选中【挂账】且不可选账户 |
| 混合收款 | 现金 200 + 微信 50 + 挂账余额 | 收款单含两条账户明细，`credit_amount` 为余额 |
| 拍照必填 | 不拍照直接结算 | 前端拦截，提示需拍照 |
| 收款单禁删 | 后台删除 DRIVER_SETTLE 收款单 | 返回「司机现场收款单不允许删除」 |

### 9.3 交账审核联动（已通过自测）

以测试数据 JZ202608200001（2 张门店结算，合计 500）为例：

| 校验项 | 预期 | 实测 |
|---|---|---|
| 审核返回 | `approvedCount=2, approvedAmount=500, failures=[]` | 一致 |
| 核销记录 | 7 条，全部带 `ar_no` + `source_bill`，合计 252.12 | 一致 |
| 定向核销 | AR202608200001/70、AR202608200002/70 全中 | 一致 |
| FIFO 兜底 | 按到期日 72.32 → 3.20 → 1.60 → 35.00 | 一致 |
| 资金流水 | 微信 50 / 现金 200 各两笔，`balance_after` 连续 | 一致 |
| 往来流水 | CUSTOMER K0001 IN 250 各两笔 | 一致 |
| 门店结算 | `fin_status` 均 APPROVED | 一致 |
| 幂等 | 重复审核返回 400 | 一致 |
| 操作日志 | 含 AUDIT / LINK / APPROVE / RECONCILE_REMAIN | 一致 |
