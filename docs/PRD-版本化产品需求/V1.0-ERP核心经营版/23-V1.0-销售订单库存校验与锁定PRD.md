## 一、背景与问题

索引文档 `00-PRD文档索引与版本路线图.md` 的 3.1 触发点表早已写明「销售订单审核 → 锁定库存」，
3.2 库存口径也写明「可用库存 = 实物库存 − 锁定库存 − 冻结库存」。但落地代码与该口径不符：

| 问题 | 改造前的实际行为 |
|---|---|
| 明细看不到库存 | 新建销售订单时明细列没有「可用库存」，录单人只能凭记忆判断有没有货 |
| 保存不校验 | 数量填多少都能存盘，超卖要等到出库单审核才报「库存不足」，此时订单早已流转下游 |
| 审核不锁库存 | `auditSales` 只改状态，`inv_stock_balance.locked_qty` 完全不动。接口返回的 `effect: "已锁定库存"` 是**假的** |
| 两单抢同一批货 | 因为不锁定，A 单和 B 单可以各自通过校验、都占同一批库存，谁先出库谁得手 |
| 反审核过死 | 只要 `sales_outbound` 有任意一条记录就拒绝反审核，哪怕那张出库单还没审核、什么都没动 |

## 二、需求范围

### 需求 1｜销售订单库存校验

1. 新建/编辑销售订单，明细列新增「可用库存」列，选择商品时按**单据所选仓库**带出。
2. 保存时数量 > 可用库存则提示库存不足，不允许保存。
3. 审核时重新校验库存（存单到审核之间库存可能已被别的单吃掉）。

### 需求 2｜销售订单反审核放宽

生成的销售出库单**若仍未审核**，允许反审核，并连带删除这些出库单。
只要有一张出库单已审核（实物库存已扣、发货单已生成），仍然拒绝反审核。

### 三条口径确认（与需求方确认结果）

| 议题 | 结论 |
|---|---|
| 判断方向 | **数量 > 可用库存才拦截**。需求原文「订单数量小于可用库存…提示库存不足」为笔误 |
| 是否真锁库存 | **一并实现锁定/释放**。只加校验不加锁定挡不住两单抢货，等于假需求 |
| 赠品行是否计入 | **全部计入**。销售属性为 正常/赠品/样品/兑换/陈列 的行一律算进需求量 |

## 三、库存口径与计量单位

### 3.1 口径

严格沿用 3.2 全局口径，不新造概念：

```text
可用库存 = 实物库存(physical_qty) − 锁定库存(locked_qty) − 冻结库存(frozen_qty)
```

匹配维度为 **商品编号 + 仓库**，不细分批次 —— 与 `InventoryCostService.salesOutbound` 的
既有校验维度保持一致，避免"订单能过、出库过不了"。

### 3.2 计量单位（重要）

校验与锁定比较的是明细的**业务单位数量 `qty`**，不是 `base_qty`。

理由：`SalesOutboundController.audit` 扣减的是 `sales_outbound_detail.qty`，
`PurchaseController.auditInbound` 增加的是 `detail.getReceivedQty()`，两者都是业务单位。
即库存事实上是按"单据单位"记账的。若此处改用 `base_qty`，会造出
"订单保存和审核都过、出库审核报库存不足"的新裂缝。

> 多单位换算失真（按箱进货、按瓶销售）是**系统既有的全局问题**，不在本需求范围内。
> 本需求只保证新增校验与既有扣减口径一致，不引入新的不一致。

### 3.3 同商品多行合并

同一商品可能因销售属性不同录成多行（如 10 箱正常 + 2 箱赠品）。
需求量按 `goods_code` **汇总后**再与可用库存比较，逐行单独比较会漏判。

## 四、状态与库存联动

| 动作 | 库存动作 | 说明 |
|---|---|---|
| 保存订单（PENDING） | 只校验，**不锁定** | 草稿不该占用库存 |
| 审核订单（→ APPROVED） | 重新校验 + `locked_qty += qty` | 通过后写 `stock_check='通过'` |
| 反审核（→ PENDING） | 释放全部锁定 | 未审核出库单一并删除 |
| 关闭（→ CLOSED） | 释放**剩余**锁定 | 剩余 = 订单量 − 已审核出库量 |
| 出库单审核 | **先释放锁定，再扣实物** | 顺序不能反，见 4.1 |
| 快速开单 | 建单即审核，同步锁定 | 复用 `createSales` 的校验 |

### 4.1 出库审核为什么必须先释放再扣减

订单审核后 `locked_qty` 上升、`available_qty` 下降。而 `InventoryCostService.salesOutbound`
内部校验的是 `available_qty >= 出库量`。若不先释放，出库单会被**自己订单的锁定**挡下，
报出莫名其妙的"库存不足"。故 `SalesOutboundController.audit` 在调 `salesOutbound` 之前
先按 `goods_code + warehouse` 调 `releaseLock`。无来源订单（`source_order` 为空）的
直接出库单不做释放——它从来没锁过。

### 4.2 历史数据兼容

改造前审核通过的 APPROVED 订单没有任何锁定记录。因此 `releaseLock` 内部做了
**向下夹取**：`release = min(要释放量, 当前locked_qty)`，历史单反审核/关闭时安全释放 0，
不会把 `locked_qty` 压成负数。

> **未对历史 APPROVED 未出库订单回灌锁定**。回灌会让可用库存在某次发版后突然下跌，
> 可能直接卡住正在进行的业务。历史单按"未锁定"对待，走完各自生命周期后自然消化。

## 五、数据库改动

`inv_stock_balance` 自 V1 起就有 `locked_qty / frozen_qty / available_qty`，**无需 DDL**。

V67 只做数据修复：`available_qty` 此前仅由 `purchaseInbound` / `salesOutbound` 维护，
期初导入、盘点、调拨、其他出入库等路径写了表却没同步该字段，存在 NULL 与不同步行。
新校验直接读这个字段，脏数据会导致误判，故全表重算一次：

```sql
UPDATE inv_stock_balance
SET locked_qty    = COALESCE(locked_qty, 0),
    frozen_qty    = COALESCE(frozen_qty, 0),
    physical_qty  = COALESCE(physical_qty, 0),
    available_qty = COALESCE(physical_qty, 0)
                    - COALESCE(locked_qty, 0)
                    - COALESCE(frozen_qty, 0);
```

## 六、接口

### 6.1 新增：批量查可用库存

```
POST /inventory/available-stock
请求：{ "warehouse": "东区仓", "goodsCodes": ["S0001", "S0002"] }
响应：{ "code":"0", "data":[
         { "goodsCode":"S0001", "physicalQty":4, "lockedQty":3, "frozenQty":0, "availableQty":1 }
       ] }
```

- 仓库或商品列表为空 → 返回空数组。
- **查不到库存行的商品不出现在结果里**，调用方按 0 处理（区别于"未取到"）。

### 6.2 行为变更

| 接口 | 变更 |
|---|---|
| `POST /sales/order/create` | 任何 INSERT 之前校验，不足返回 `400` + 具体商品与数量 |
| `POST /sales/order/update` | 改主表/删明细之前校验 |
| `POST /sales/order/audit` | 重新校验 + 逐商品锁定 + 写 `stock_check='通过'` + 操作日志 |
| `POST /sales/order/reverse-audit` | 见需求 2；返回新增 `deletedOutbounds` 数组 |
| `POST /sales/order/close` | 原状态 APPROVED 时释放剩余锁定 |
| `POST /sales/order/page` | SELECT 补 `credit_check, stock_check`，前端「库存检查」列不再空白 |
| `POST /sales/quick-order/create-and-audit` | 同步校验+锁定；并修掉 `createSales` 返回失败时的 NPE |
| `POST /sales/outbound/audit` | 扣实物前先释放锁定 |

### 6.3 反审核的拒绝与放行

```text
出库单全部为 PENDING          → 放行，删除这些出库单（明细 → 主表），释放锁定
存在 status <> 'PENDING'       → 拒绝，提示具体单号与状态
PENDING 出库单被发货单引用      → 拒绝（防御性检查，理论上不会发生）
```

删除 PENDING 出库单是安全的：`sales_outbound.status` 只会被写成 `PENDING`（创建）
或 `APPROVED`（审核），PENDING 单 `stock_updated = FALSE`、未生成发货单、无任何下游。

## 七、前端

### 7.1 明细「可用库存」列

- 位置：「小单位数量」之后、「单价」之前；**仅销售订单**显示（采购是加库存，无此概念）。
- 取数时机：选择商品、批量添加、弹窗添加、编辑回显、**切换仓库**（切仓后全部重取）。
- 未取到显示 `-`，与"确实为 0"区分开。
- 超卖时该格标红加粗并带 tooltip，但**不阻断输入**，保存时才拦——录单过程中允许先填数量再调整。
- 取库存接口失败不阻断录单（`availableStock` 保持 `null` 即跳过前端校验），后端仍会拦。

### 7.2 商品添加弹窗口径统一

`GoodsAddDialog` 原先调 `/base/goods/stock-summary`，那是**全仓合计、不分仓库**的数字，
与明细列按仓库取的数会对不上。改为销售场景 + 已选仓库时走 `/inventory/available-stock`，
采购或未选仓库时才退回全仓合计。

### 7.3 提示文案

反审核确认框不再是通用文案，明确告知会删除未审核出库单、释放锁定，以及已审核出库单会被拒绝。

## 九、已知边界

1. **仓库未选时跳过校验。** 历史接口允许不传 `warehouseId`，硬拦会打断既有流程（含快速开单）。
   此时 `effect` 会明确返回「未指定仓库，未锁定库存」，不谎报已锁定。
2. **不校验批次可用量。** 与 `salesOutbound` 一致，只按商品+仓库。按批次出库的可用量校验
   仍是调用方责任（既有问题，不在本需求范围）。
3. **并发。** 校验与锁定在同一事务内，靠 H2 行锁串行化。极高并发下的抢占以锁定动作为准，
   校验只是前置提示。
4. **多单位换算失真** 见 3.2，全局既有问题。
