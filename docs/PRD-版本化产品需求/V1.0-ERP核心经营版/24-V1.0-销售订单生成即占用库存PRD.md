# V1.0 销售订单生成即占用库存 PRD

- 编号：PRD-24
- 版本：V1.0 ERP核心经营版
- 分支：`feat/sales-order-lock-on-create`
- Flyway：无（不新增表结构，不做数据修复，见第五节）
- 状态：已完成
- 修订关系：**修订 PRD-23** 的占用时点与释放时点，PRD-23 中"审核才锁定/反审核即释放"的口径以本文为准

---

## 一、背景与问题

PRD-23 落地后，占用时点定在**审核**。实际业务里订单一生成货就该算被这张单占了：

| 问题 | PRD-23 的行为 | 后果 |
|---|---|---|
| 待审核订单不占货 | 保存只校验、不锁定 | A 单存好等审核，B 单把同一批货订走并先审核，A 单审核时才报库存不足，白录一遍 |
| 反审核就释放 | 反审核 → 释放全部锁定 | 只是改个客户名或数量，订单退回待审核的一瞬间货被别人抢走，改完存不回去 |
| 出库单不占批次 | 只在 balance 层按商品+仓库锁 | 两张出库单可以选同一批次的同一批货，谁先审核谁得手，另一张审核时才失败 |
| 按钮给了做不到的操作 | 已生成出库单仍显示【生成出库单】，已出库仍显示【反审核】 | 点了才被后端拒绝 |

## 二、需求范围（需求方原文）

> 1、销售订单生成后即占用销售库存、审核后继续占用销售库存直至销售订单出库后释放并扣减销售库存。
> 生成的销售出库单占用的是批次库存。
> 2、如果订单已生成销售出库单，不要显示【生成出库单】按钮。如果已出库不显示【反审核】按钮。

### 两条口径确认（与需求方确认结果）

| 议题 | 结论 | 影响 |
|---|---|---|
| 【生成出库单】隐藏条件 | **存在任何出库单即隐藏**（含未审核的） | 一张订单只能生成一张出库单，**分次出库能力被关闭**；后端同步拦截，不只靠前端隐藏 |
| 历史订单是否回灌占用 | **不回填**（沿用 PRD-23 决定） | 存量 PENDING/APPROVED 未出库订单按"未占用"对待，走完生命周期自然消化；因此本需求无需 Flyway |

## 三、两层占用模型

这是本需求的核心概念。两层各管一段，**互不重复计数**：

| 层 | 字段 | 占用方 | 维度 | 起 | 止 |
|---|---|---|---|---|---|
| balance 层 | `inv_stock_balance.locked_qty` | 销售订单 | 商品 + 仓库 | 订单创建 | 出库单审核 / 订单关闭 / 订单删除 |
| batch 层 | `inv_batch_stock.locked_qty` | 销售出库单 | 商品 + 仓库 + 批次 | 出库单创建 | 出库单审核 / 出库单被删（订单反审核） |

口径仍沿用索引文档 3.2，不新造概念：

```text
可用库存     = 实物库存(physical_qty) − 锁定库存(locked_qty) − 冻结库存(frozen_qty)
批次可用量   = 批次库存(qty) − 批次锁定(locked_qty)
```

### 3.1 batch 层为什么刻意不联动 balance 层

出库单锁批次时**不去加** `inv_stock_balance.locked_qty`。因为这批货在 balance 层
已经被来源订单占着了，再联动就是同一批货被占两次，可用库存会凭空少一半。

> 例：订单占 5 → balance locked 5、可用 5（实物 10）。据此生成出库单选批次 A 出 5。
> 若联动，balance locked 变 10、可用变 0 —— 但实物一件没动，仓库里明明还有 5 件可卖。

对照：仓管手工调的 `/inventory/batch/lock` 端点**是联动的**，那是一次独立的锁定动作，
没有任何订单在 balance 层替它占位，两层都得记。

### 3.2 出库单审核的释放顺序

```text
① 释放批次锁定 releaseBatchLock(商品, 仓库, 批次, 数量)
② 释放订单锁定 releaseLock(商品, 仓库, 数量)        ← 有来源订单才做
③ 扣减实物     salesOutbound(...)                   ← 内部校验 可用 ≥ 出库量
```

顺序不能反：③ 校验的是 `available_qty`，若不先释放 ①②，出库单会被**自己这条链上的占用**
挡下，报出莫名其妙的"库存不足"。无来源订单的直接出库单跳过 ②——它从没在 balance 层锁过。

## 四、状态与库存联动（对照 PRD-23 的变化）

| 动作 | PRD-23 | 本次（PRD-24） |
|---|---|---|
| 保存订单（PENDING） | 只校验，不锁定 | **校验 + 按仓库占用**，写 `stock_check='通过'` |
| 编辑订单 | 只校验 | 校验通过后**先释放旧占用、再按新数量占用**（换仓库则旧仓释放、新仓占用） |
| 审核订单（→ APPROVED） | 校验 + 锁定 | **不重复占用**，只校验实物库存是否仍够本单（见 4.1） |
| 反审核（→ PENDING） | 释放全部锁定 | **订单占用保持不变**；删除未审核出库单并释放其批次占用 |
| 关闭（→ CLOSED） | APPROVED 才释放剩余 | PENDING 与 APPROVED **都**释放剩余占用，并清空 `stock_check` |
| 删除订单 | 不释放（本就没锁） | **释放未出库部分的占用** |
| 生成出库单 | 不锁批次 | **按明细所选批次占用批次库存**；已有出库单则拒绝生成 |
| 编辑出库单 | 不动批次 | 先释放本单原批次占用，再按新明细重锁 |
| 出库单审核 | 释放锁定 + 扣实物 | **释放批次占用 + 释放订单占用 + 扣实物**（顺序见 3.2） |
| 快速开单 | 建单 + 审核各锁一次（重复） | 建单时锁一次，审核不再锁 |

### 4.1 审核为什么改成校验实物、不再校验可用

订单自己的占用已经算在 `locked_qty` 里，`available_qty` 已被自己压低。
若审核仍按"可用 ≥ 本单数量"校验，一张刚创建、货完全够的订单会被**自己的占用挡住**，
永远审不过去。

改为校验 **实物库存 ≥ 本单数量**。这不是敷衍的替代品，它拦的是真实风险：
创建之后发生盘亏、其他出库、调拨出库，把实物抽走到连本单都装不满，此时必须拦。

失败提示：`商品【S0003 农夫山泉矿泉水】实物库存不足：本单需 5，主仓 实物 3，无法审核`

### 4.2 编辑订单为什么不会"释放后锁不回去"

编辑的校验公式是：

```text
新数量 ≤ 可用库存 + min(旧数量, 该商品当前锁定量)
```

`min(...)` 是关键——历史订单可能根本没占用（不回填），加回去的量不能超过实际锁定量。
校验通过即意味着"全额释放 + 全额重锁"必然成功，不存在释放完锁不回去、把库存悬空的中间态。

校验全部前置在任何写操作之前：`ApiResponse.fail(...)` **不会回滚** `@Transactional` 方法，
所以任何校验都不能放在写之后。（批次锁定不足抛的是 `IllegalArgumentException`，会整单回滚。）

### 4.3 历史数据兼容

`releaseLock` / `releaseBatchLock` 都做**向下夹取**：`实际释放 = min(要释放量, 当前锁定量)`。
历史无锁定的单反审核/关闭/删除时安全释放 0，不会把 `locked_qty` 压成负数。

## 五、数据库改动

**无。**

- `inv_stock_balance.locked_qty` 自 V1 起就有；
- `inv_batch_stock.locked_qty` 自 V18 起就有；
- 不回灌历史订单占用（第二节口径确认），因此没有数据修复脚本。

> 顺带避开了与并行开发中的 TMS `V68` 撞号。

## 六、接口

### 6.1 变更：批量查可用库存

```
POST /inventory/available-stock
请求：{ "warehouse": "主仓", "goodsCodes": ["S0003"], "orderId": "SO321EFF2EE6" }   ← orderId 可选
响应：{ "code":"0", "data":[
         { "goodsCode":"S0003", "physicalQty":10, "lockedQty":3, "frozenQty":0,
           "availableQty":7, "ownLockedQty":3 }
       ] }
```

`orderId` 传订单号或订单 ID 均可，返回 `ownLockedQty` = **该订单自己占用的量**（已按实际锁定量夹取）。

为什么需要它：订单生成即占用，编辑自己这张单时本单占用已经从 `availableQty` 里扣掉了。
不把它加回来，一张刚存的单打开就报"库存不足"。前端展示与校验都用
`availableQty + ownLockedQty`，与后端编辑校验口径（4.2）完全一致。
不传 `orderId` 时 `ownLockedQty` 为 0，行为与改造前一致。

### 6.2 行为变更

| 接口 | 变更 |
|---|---|
| `POST /sales/order/create` | 校验通过后**逐商品占用库存**；`effect` 返回「已保存并占用库存」，未指定仓库时返回「已保存（未指定仓库，未占用库存）」 |
| `POST /sales/order/update` | 按 4.2 校验 → 释放旧占用 → 按新数量占用；同步更新 `stock_check` |
| `POST /sales/order/audit` | 不再锁定，改校验实物库存；`effect`「已审核，库存自创建时起持续占用」 |
| `POST /sales/order/reverse-audit` | **不再释放订单占用**；删除未审核出库单时释放其批次占用；不再清空 `stock_check` |
| `POST /sales/order/close` | PENDING 与 APPROVED 都释放剩余占用 |
| `POST /sales/order/delete` | 新增：释放未出库部分的占用 |
| `POST /sales/order/page` | SELECT 补 `outbound_count`、`outbound_audited_count` 两个子查询，供前端收敛行内按钮 |
| `POST /sales/quick-order/create-and-audit` | 删掉重复的锁定块（`createSales` 已占用） |
| `POST /sales/outbound/create` | 来源订单已有出库单 → 拒绝；每条明细按所选批次占用批次库存 |
| `POST /sales/outbound/update` | 先释放本单原批次占用，再按新明细重锁 |
| `POST /sales/outbound/audit` | 释放批次占用 → 释放订单占用 → 扣实物 |
| `GET /sales/outbound/available-batches` | 返回补 `lockedQty`、`availableQty`（= `qty − locked_qty`） |

```text
建单/编辑超量   400 商品【S0003 农夫山泉矿泉水】库存不足：本单需 11，主仓 可用 10（含本单已占用 10）
审核实物不足    400 商品【S0003 农夫山泉矿泉水】实物库存不足：本单需 5，主仓 实物 3，无法审核
重复生成出库单  400 该销售订单已生成出库单 XSCK202608190004，不能重复生成；如需重做请先反审核订单（会删除未审核的出库单）
批次可用量不足  400 批次可用量不足，无法锁定：S0001 / 批次 20260810，需 4，可用 2.0000
已出库反审核    400 出库单 XSCK202608190004(APPROVED) 已审核，无法反审核；请先处理出库单
```

## 七、前端

### 7.1 行内按钮收敛（需求 2）

销售订单列表 APPROVED 行：

| 按钮 | 显示条件 |
|---|---|
| 生成出库单 | `outboundCount === 0` |
| 反审核 | `outboundAuditedCount === 0` |

两个字段由 `/sales/order/page` 返回。后端也拦（6.2），前端隐藏只是少让用户白点一次。

### 7.2 明细「可用库存」列

- 编辑模式且**仓库未变**时传 `orderId`，格内显示 `availableQty + ownLockedQty`；
  换了仓库不加回（新仓库上本单一件都没占，后端同样不加回）。
- tooltip 写明「可分配 N（含本单已占用 M）」，免得用户以为数字算错了。
- 超卖仍是标红不阻断输入，保存时才拦。

### 7.3 销售出库抽屉

- 来源订单下拉过滤条件加 `outboundCount === 0`，已有出库单的订单不再出现，避免选了才被拒。
- 批次下拉显示「可用 X / 实物 Y」，默认优先选**还有可用量**的批次。
- 编辑模式把本行原先占用的量加回自己那一批（同样按实际锁定量夹取），否则打开自己这张单就报批次不足。
- 保存前按「商品 + 批次」汇总校验 ≤ 批次可用量；批次列表没取到就交给后端拦，不误伤。

## 九、已知边界

1. **分次出库能力关闭。** 一张订单只能生成一张出库单（需求方明确选择）。
   需要分批发货的场景请拆单，或后续另立需求恢复。
2. **仓库未选时跳过占用。** 沿用 PRD-23 边界，`effect` 明确返回「未指定仓库，未占用库存」，不谎报。
3. **无来源订单的出库单只占批次层。** balance 层没有订单替它占位，也不给它补占——
   相比改造前（完全不占）已是严格改进，不特殊处理。
4. **未指定批次的出库明细不落批次锁。** `batchNo` 为空直接跳过，行为与改造前一致。
5. **历史订单不占用。** 不回填（第二节），存量单按未占用对待。
6. **并发。** 校验与占用在同一事务内，靠 H2 行锁串行化；校验只是前置提示，最终以占用动作为准。
7. **多单位换算失真** 见 PRD-23 第 3.2 节，全局既有问题，本需求不引入新的不一致。
