## 1. 背景、目标与边界

### 1.1 背景

当前系统 V1.0 已打通进销存财最小闭环：采购订单→采购入库（审核即增库存、移动加权平均成本、生成应付）、销售订单（生成即占用库存）→销售出库（审核即扣库存）→TMS 配送签收→生成应收、调拨/盘点/其他出入库/报损。但库存维度只到"商品+仓库+批次"，**没有库位、没有 PDA 现场作业、没有波次拣货、没有质检/上架/复核环节，也没有条码标签能力**。仓库作业仍依赖纸质单和人工记忆，存在错拣漏拣、找不到货、库存账实差异大、作业绩效无法量化等问题。

V1.5 在不破坏 V1.0 财务库存口径的前提下，引入库位级实物管理和 PDA 标准化作业。

### 1.2 目标

1. **账实一致**：库位级实物库存与 ERP 批次库存实时对齐，收货/上架/拣货/复核/盘点全程扫码留痕。
2. **作业标准化**：把"收货→上架→拣货→复核→装车"变成 PDA 引导的标准动作，降低对错觉和经验的依赖，适配年龄偏大、信息化水平不高的仓库作业人员。
3. **多场景拣货**：支持按单拣、汇总拣、边拣边分、分区接力、越库等多种模式，按订单特征自动推荐，适配整箱/拆零、大客/小店等不同业务。
4. **灵活可配**：质检、上架推荐、复核、补货、批次分配等流程控制点全部做成**参数可开关、规则可配置**，不写死，适配管理水平不同的仓库。
5. **可量化**：作业进度实时可视，差错、工时、人均件数可统计，为计件绩效提供数据。

### 1.3 本期不做（边界）

- **质检模块本期不做独立功能**（用户明确）。预留数据结构与流程开关，后期以插件方式加入；PDA/后台不出现质检菜单，参数默认关。
- 序列号(SN)管理：预留字段，本期不实现。
- 电子标签拣货(DPS)、语音拣货、AGV/自动化设备对接、货到人：列为后期选配。
- 复杂仓储计费（仓租、操作费对账）、多入驻商：属 V3.0。
- 完整离线：PDA 做弱离线（作业录入可暂存，关键审核动作在线），不做全离线。
- 不重写成本核算，不改移动加权平均口径。

### 1.4 关键设计决策（已确认）

| # | 决策 | 说明 |
|---|---|---|
| D1 | **账实分离**：ERP 管金额库存账，WMS 管库位实物账 | 成本仍按"商品+仓库"移动加权平均，不按库位/批次；WMS 不碰金额，库位库存金额取所属批次成本 |
| D2 | PDA 采用 **Flutter**，与 TMS 司机 APP 同栈，仅支持安卓 | 可复用离线队列、dio 鉴权、拍照、统一响应协议；稳定优先 |
| D3 | PDA 仅**中文**，不做双语/蒙文 | — |
| D4 | 质检本期不做，**流程与参数预留**、默认关闭 | 后期加入不重构 |
| D5 | 所有流程控制点**参数化**，在"系统参数设置-WMS"分组统一维护 | 复用现有 `sys_param_runtime` 表 |
| D6 | 未启用库位管理的仓库**走原流程**，启用了才走 WMS 作业 | 平滑升级、可灰度、可回退 |

## 2. 总体架构

### 2.1 系统定位

```
        ┌─────────────── ERP 后台（PC）───────────────┐
        │ 采购/销售/库存/财务/报表 + WMS 后台管理       │
        └───────────┬──────────────────┬──────────────┘
                    │ 单据/审核          │ 策略/任务/监控
            ┌───────▼───────┐   ┌───────▼────────┐
            │  WMS 服务层    │   │  TMS 调度服务   │
            │ 库位/波次/作业 │◄──►│ 配送/司机/装车  │
            └───────┬───────┘   └───────┬────────┘
                    │ 作业指令/扫码       │ 配送任务
        ┌───────────▼──────────┐  ┌─────▼──────────┐
        │  WMS PDA（安卓/Flutter）│  │ TMS 司机 APP    │
        │  收货/上架/拣货/复核    │  │ 装车/签收/拒收  │
        │  盘点/移库/补货/查询    │  └────────────────┘
        └───────────┬──────────┘
          ┌─────────┼──────────┐
        蓝牙打印机 扫码枪/PDA键 蓝牙秤（可选）
```

### 2.2 账实分离模型（核心）

| 层 | 粒度 | 表 | 写入者 | 是否含成本 |
|---|---|---|---|---|
| 财务库存账（ERP） | 商品+仓库+批次 | `inv_stock_balance` / `inv_batch_stock` / `inv_stock_ledger` | `InventoryCostService`（单据审核时） | 是，移动加权平均 |
| 实物库位账（WMS） | 商品+仓库+批次+**库位** | `wms_bin_stock` / `wms_bin_stock_log` | WMS 作业实时写 | 否，取批次成本展示 |

**铁律**：
1. 同一仓库内 `SUM(wms_bin_stock.qty) GROUP BY goods_code,batch_no = inv_batch_stock.qty`。
2. WMS 不直接写 `inv_*` 库存表；库存增减一律在作业"完成节点"调用现有 `InventoryCostService` 完成。
3. 成本/应付/应收/锁定语义全部留在 ERP 层，WMS 只负责"货在哪、拣了多少、对不对"。

### 2.3 WMS 与 ERP 单据的衔接（行业惯例：作业驱动单据）

> 采纳 WMS 行业惯用方式：**入库以"收货实收"形成入库单，出库以"拣货实拣"形成出库单**，单据数量跟
> 随实际作业，而不是先把单据数量定死再让作业去凑。这样可天然容纳部分收货、少拣、缺货等现场差异。

| 业务 | 现状 | WMS 改造 |
|---|---|---|
| 采购入库 | 手工建入库单→审核（增库存） | **以已审核采购订单为收货源**：PDA 按采购订单收货（可一次/多次，可配）→收货完成按**实收**自动生成采购入库单→上架完成→系统自动审核（增库存、生成采购收货单/应付） |
| 销售出库 | 手工建出库单→审核（扣库存） | **以已审核销售订单为拣货源**（订单已锁商品+仓库库存）：波次分配批次（锁批次）→PDA 拣货→**一订单一出库单，拣货完成即生成并审核出库单、审核即扣库存**（若启用出库复核，则复核通过后才生成并审核）；装车只做实物发运确认，不再触发扣库存 |
| 调拨 | 申请→出库审核→入库审核 | 以已审核调拨申请为源：PDA 拣货发货→在途→对方 PDA 收货上架→生成调拨出入库 |
| 盘点 | 建单→录实盘→审核 | PDA 逐库位扫码盘点→提交→主管后台审核→盘盈盘亏调账 |
| 退货/拒收 | 已有自动生成单据 | 司机带回→PDA 收货到退货位→（判定）上架 |

**关键口径**：
- 采购订单必须**已审核**才能被 WMS 收货；未审核订单不在待收货列表。
- 一张采购订单可多次收货（参数控制，见 §10），每次收货生成一张采购入库单；订单入库状态随实收进度推进（未入库→部分入库→入库完成）。
- 销售订单必须**已审核**才能进波次拣货；**一张销售订单只生成一张销售出库单、只出库一次，不支持多次/部分出库结转下一波次**。
- 出库单不再由人工预先按订单数量建立，而是拣货完成的自然结果；**出库单审核（即扣库存、释放占用、生成发货单 `sales_receipt`）的时点是：无复核模式下拣货完成即审核；启用出库复核模式下复核通过即审核——不在装车环节**。
- 拣货/复核若发生缺货等无法拣齐的情况，不生成"部分出库单"，转**异常处理**（加急补货后重拣 / 异常挂起 / 与客户确认后整单结案，主管权限，差异留痕，见 §6.9）。
- WMS 与 TMS **统一以销售订单号（`source_order_no`）为关联单号**贯穿订单、出库单、发货单、配送单；任一环节的状态变化都回写订单、出库单、发货单状态（见 §5.9）。

## 3. 基础资料模块

### 3.1 仓库改造

在现有 `base_warehouse` 增列：

| 字段 | 说明 |
|---|---|
| location_managed | 是否启用库位管理（0否1是）。**总开关**：关则该仓走 V1.0 原流程，WMS 作业对其不可见 |
| wms_enabled | 是否启用 WMS 作业（入库收货/出库波次），与 location_managed 联动 |
| receiving_door / shipping_door | 收货月台/发货月台（可选，用于预约与越库） |
| contact_phone | 仓库联系电话 |

未启用库位管理的仓库，所有现有流程不变。

### 3.2 库区 wms_zone

库区是库位的逻辑分组，用于策略、权限、路径分区。

**字段（以 V78 + V84 迁移为准）**：

| 字段 | 说明 |
|---|---|
| zone_id / zone_code / zone_name | 主键 / 编码 / 名称。`(warehouse, zone_code)` 唯一 |
| warehouse | 所属仓库 |
| zone_type | 库区类型，见下表「库区类型与流程对应」 |
| pick_method | **V84 拣货方式**（仅 PICK/STORAGE 类库区有意义）：`CASE_PICK` 整件单拣 / `CASE_MERGE` 整件合拣 / `BULK_PICK` 拆零单拣 / `BULK_MERGE` 拆零合拣；空=未配置，走 `WMS_PICK_MODE` 兜底 |
| sort_mode | **V84 合拣分拣方式**（`pick_method` 为 `*_MERGE` 时必填）：`PICK_THEN_SORT` 先拣后分 / `SORT_WHILE_PICK` 边拣边分；单拣时为 NULL |
| storage_property | **V84 存储属性（温区）**，对应 `base_goods.storage_property`：常温/冷藏/冷冻/恒温/避光。入库上架推荐按此匹配库区，收货标签上标明，同一温区可建多个库区 |
| pick_seq | 拣货路径顺序（数字越小越先到，PDA 按此排序指引跨区路径） |
| frozen | 冻结标志 Y/N（盘点/异常时冻结整个库区，该区库位不可上下架/拣货） |
| remark | 备注 |
| created_at | 创建时间 |

> PRD 早期版本提及的 `temperature_zone`（常温/冷藏/冷冻）、`manager_name` 字段本期未建表；温区能力已由 V84 的 `storage_property` 字段承载，负责人字段后续以 `ADD COLUMN` 方式扩展。

#### 3.2.1 库区类型与流程对应

`zone_type` 对应入库/出库物理链路上的不同区段。V78 落地的枚举共 6 种，全部大写：

| 库区类型 | 代码 | 流程位置 | 对应作业 | 典型库位类型 |
|---|---|---|---|---|
| 储区 | `STORAGE` | 入库终点 / 拣货源 | 采购收货**上架**落在此处（整箱/整托储备）；补货任务从此处往拣货位补；盘点主要对象 | SHELF / FLOOR |
| 收货区 | `RECEIVE` | 入库最前段 | 采购到货先在月台/收货区暂存、点数、质检，再由上架任务搬到 STORAGE；采购入库单签收后实物的第一停留位 | STAGE |
| 拣货区 | `PICK` | 出库中段 | 拣货员从此处拣货。V83 拣货位商品绑定 `wms_bin_goods_binding` 主要挂在该区库位下，支撑「一品一位」、PDA 扫码定位、补货阈值（min/max/replenish_to_qty） | PICK |
| 分拣区 | `SORT` | 拣货后、集货前 | 「汇总拣货+先拣后分」（SUMMARY）或「边拣边分」（PICK_SORT）模式下，把整批拣出的货按订单/门店分播到笼车格口 | STAGE / COLLECT |
| 集货区 | `COLLECT` | 出库末段（装车前） | 按订单/门店集齐、等待复核和装车发运。波次下放时按参数 `WMS_COLLECTION_MODE`（一单/一门店/智能）占用此区下的集货位，装车发车后释放 | COLLECT |
| 发货区 | `SHIP` | 出库最末段（月台） | 复核通过、已生成销售出库单的货物在装车月台暂存，对接到 TMS 派车/装车交接 | STAGE |

**典型物理流向**：

```
到货 → [RECEIVE 收货区]  ──上架──▶  [STORAGE 储区]
                                        │
                                        │ 补货（按 V83 绑定阈值 min/max/replenish_to_qty）
                                        ▼
出库订单波次下放 → [PICK 拣货区] 拣货 ──▶ [SORT 分拣区] 按单分播
                                                  │
                                                  ▼
                                      [COLLECT 集货区] 集齐 / 复核
                                                  │
                                                  ▼
                                      [SHIP 发货区] 月台装车 ──▶ TMS
```

**越库（CROSS_DOCK）模式**跳过 STORAGE，路径简化为：

```
到货 → [RECEIVE 收货区] ──▶ [COLLECT 集货区] / [SHIP 发货区] ──▶ 发车
```

**退货流向**：销售退货入库（§4.4）进入 RECEIVE 区做收货质检后上架至 STORAGE；采购退货是出库单据，从 STORAGE 拣出后走 SHIP 区退厂。

#### 3.2.2 实现状态：当前是「语义标签」，非硬路由

V1.5 阶段，后端真正用于驱动作业路由的是**库位类型 `wms_bin.bin_type`**（SHELF/FLOOR/COLLECT/STAGE/PICK），库区类型目前承担：

1. **运营分区的语义标签**——在库区管理页、PDA 库位选择、报表分组中作为筛选与展示维度；
2. **路径排序**——配合 `pick_seq` 决定多库区拣货的先后顺序；
3. **冻结粒度**——盘点/异常时整区冻结；
4. **V83 拣货位绑定的挂载提示**——绑定 UI 推荐在 PICK 区下操作，但不强制（允许在 STORAGE/SORT 等区库位上建绑定，用于备货位 RESERVE、整托位 BULK）。

代码中当前按库位类型驱动流程的位置（作为后续按 zone_type 做硬路由的改造基线）：

- `WmsInternalService` 内部调拨/补货选源库位时：`bin_type IN ('PICK','SHELF')`，不看 zone_type；
- `WmsOutboundService` 波次下放占集货位时：`bin_type = 'COLLECT'`；
- V83 `WmsBindingService` 仅校验库位存在且属于目标仓库/库区，不校验 zone_type 必须是 PICK。

后续迭代计划（不在 V1.5 范围，登记于此便于追溯）：

- 上架策略（§4.3）按 `zone_type=RECEIVE → STORAGE` 限定源/目的库区；
- 波次下放按 `zone_type=COLLECT` 而非 `bin_type=COLLECT` 选集货位，以支持「一个集货区下混合 SHELF+COLLECT 库位」；
- 分播指令按 `zone_type=SORT` 限定分播作业库区；
- 月台装车按 `zone_type=SHIP` 限定出库暂存区。

届时若需要把「语义标签」升级为「硬路由」，应在服务层增加 `assertZoneType(binCode, expectedType)` 校验，并在参数中加开关（默认放行旧数据，切换后强制）。

## 4. 入库作业模块

### 4.1 入库类型

| 类型 | 来源单 | 是否有预报 | 入库去向 | 成本处理 |
|---|---|---|---|---|
| 采购入库 | 采购订单 | 有（可预约到货） | 暂收→上架 | 移动加权平均（现有逻辑） |
| 销售退货入库 | 销售退货单/司机带回 | 可有 | 退货位→（判定后）上架或损溢 | 取退货成本 |
| 拒收入库 | 司机拒收（现有 inv_reject_inbound） | 有 | 退货位 | **取原出库单成本**（现有逻辑） |
| 调拨入库 | 调拨出库单 | 有（在途） | 暂收→上架 | 调拨成本 |
| 其他入库 | 其他入库单（期初/赠品/样品等） | 无 | 收货即入默认库位 | 现有其他入库逻辑 |

### 4.2 标准采购入库流程（按已审核订单收货，收货后形成入库单）

> **源单规则**：只能对**已审核**的采购订单收货（未审核订单不出现在待收货列表）。这符合 WMS 行业惯例——
> 仓库只对"确认要进的货"负责，采购订单的审核是商务/采购环节的事。
>
> 质检预留：参数 `WMS_QC_ENABLED` 本期恒为 0。若开启，流程在收货与上架之间插入"质检判定（合格/让步/不合格）"，数据结构预留。
> **复检**：参数 `WMS_RECHECK_ENABLED` 控制收货后是否需要第二人复核数量（与质检不同，复检只点数量，不判质量），见 4.2.1。

```
采购订单审核（采购在途）
   │
   ▼
①【到货预约】（可选，参数 WMS_ASN_APPOINT_ENABLED）
   供应商按采购单预报到货数量/时间/车牌；月台调度，仓库提前准备
   │
   ▼
②【PDA 收货】 角色：收货员
   扫采购单号/送货单号，或从"待收货"任务进入（只列已审核订单）
   ├─ 显示供应商、订单商品、应收数量、订单剩余未收数
   ├─ 逐商品：扫商品条码 → 输实收数（大/小单位切换，默认应收数）
   │          → 录/生成批次号（沿用规则：手输 > 生产日期 yyyyMMdd > 空）
   │          → 录生产日期，自动算到期日（保质期天数）
   │          → 重量自动核算：= 商品档案单件重量(base_weight) × 实收数量（按单位换算）；
   │            称重商品可选连蓝牙秤采集实测重量做比对（参数 WMS_SCALE_WEIGHT_ENABLED）
   ├─ 支持部分收货（实收可<应收）
   ├─ 一次收货只收一张订单；一张订单能否多次收货由参数 WMS_PO_MULTI_RECEIVE 控制：
   │     · 开：允许分多次收，每次收完生成一张入库单，订单 未入库→部分入库→入库完成
   │     · 关：必须一次收齐（不足需选原因，按差异处理），生成一张入库单
   ├─ 支持同一商品多个批次/生产日期（自动拆多行）
   ├─ 支持整托收货（扫托盘码，整托数量一次确认）
   ├─ 盲收模式（参数 WMS_BLINDED_RECEIVE：不显示应收数，防止照单抄数）
   ├─ 超收控制（参数 WMS_OVER_RECEIVE_TOLERANCE：允许超收百分比/绝对值）
   ├─ 打印收货标签贴货/贴托
   └─ 确认收货 → 按【本次实收】自动生成采购入库单（pur_inbound，状态 PENDING）
                 货物落到"暂收位"，生成【上架任务】
   │
   ▼
②.5【PDA 收货复检】（可选，参数 WMS_RECHECK_ENABLED）
   复检员（非本人）扫描收货单/托盘 → 逐件复点 → 与收货数核对
   ├─ 一致：通过，进入上架
   └─ 差异：登记实点数量与原因，经主管确认后修正入库单实收数
   目的：贵重/易差商品双人点数，降低收货差错。是否复检、复检比例由参数控制
   │
   ▼
③【PDA 上架】 角色：上架员
   扫收货标签/托盘码 → 系统推荐库位 → 扫库位码校验 → 输上架数 → 确认
   ├─ 一次收货可分多次上架、可上多个库位
   ├─ 推荐库位按"上架策略"（见 4.3）
   ├─ 允许有经验的仓管改放：扫其他库位，记录改放原因（参数 WMS_PUTAWAY_FREE_BIN）
   ├─ 上架实时写 wms_bin_stock + 流水
   └─ 全部上架完成 → 触发采购入库单审核（增库存、加权成本、生成采购收货单/应付）
   │
   ▼
④【异常】 收货多发/错发/破损 → PDA 异常上报拍照 → 主管后台处理
   无订单送货 → 无单收货（建临时入库单，事后补关联采购订单，参数 WMS_RECEIVE_WITHOUT_ORDER）
```

#### 4.2.1 复检规则（参数化）

| 参数 | 说明 | 默认 |
|---|---|---|
| WMS_RECHECK_ENABLED | 是否启用收货复检 | 0（关） |
| WMS_RECHECK_MODE | 复检方式：全部复检 / 按金额阈值 / 按比例抽复检 | 全部 |
| WMS_RECHECK_AMOUNT_THRESHOLD | 金额阈值（超过必复检） | 5000 |
| WMS_RECHECK_RATIO | 抽复检比例(%) | 20 |
| WMS_RECHECK_SELF_NG | 是否允许收货员复检自己的单 | 0（必须他人，防串通/自错难发现） |

> 说明：质检（QC，判合格/让步/不合格）本期不做；复检只解决"点数准不准"，是仓储内部准确性控制，与供应商质量责任分开。

**上下游关联**：
- 上游：已审核采购订单（`purchase_order`）提供应收、供应商、仓库；系统计算订单剩余未收数。
- 收货确认：按本次实收生成 `pur_inbound`（主表+明细），并生成 WMS 入库任务 `wms_inbound_task`（状态：待上架）。
- 同层：上架产生 `wms_bin_stock` + 库位流水。
- 下游：上架完成回调采购入库单审核 → `InventoryCostService.purchaseInbound` → 回写 `purchase_order.inbound_status`、`base_goods.latest_purchase_price` → 自动生成 `purchase_receipt` → 收货单审核生成 `fin_ap` 应付。
- **重量**：入库重量按**商品档案单件重量 `base_weight` × 实收数量**自动核算（大/小单位按 `unit_config` 换算），用于绩效与计费参考，不影响财务数量/金额；可选蓝牙秤实测重量作比对并记录差异。

### 4.3 上架策略（可配置，参数 WMS_PUTAWAY_STRATEGY）

按"仓库 + 商品分类"组合配置，系统按顺序计算推荐库位，取第一个满足者：

1. **同品就近/同库位优先**：同商品已有库存的未满库位优先（减少散点）。
2. **ABC 分区**：A 类热销→拣货位（靠前/靠月台）；C 类→深处存储位。
3. **批次/效期分库位**：同批次集中，便于 FEFO。
4. **储存属性（温区）匹配**（V84 已落地）：取 `base_goods.storage_property`，优先推荐 `wms_zone.storage_property` 相同的库区下的空 SHELF 库位；找不到匹配温区才回退到任意未冻结空库位，并在标签/任务上标红提示「未匹配温区」。冷藏/冷冻品不匹配温区不允许自动推荐到常温区，需主管改放。
5. **容量/承重校验**：库位剩余容量、承重不足则不推荐。
6. **同品邻位**：原库位满则推荐相邻空库位（按 pick_seq 邻近）。
7. **越库（Cross-docking）**：若该商品有未配货的紧急出库需求且时间窗匹配，直接推荐到集货位/复核位，跳过存储（参数 WMS_CROSS_DOCK_ENABLED）。

**推荐返回数据**（V84）：`recommend_bin`（库位）+ `recommend_zone_code/name`（库区）+ `recommend_storage_prop`（温区），同时写入 `wms_putaway_task` 与 `wms_inbound_task_detail`。收货标签直接打印这三项，PDA 上架页展示「推荐库区：B 区（常温） → 推荐库位：B-01-01」，上架员一眼能看到该往哪个温区送。

仓管改放时，系统记录"推荐库位 vs 实际库位、原因"，用于后续优化策略与异常分析；改放到不同温区时弹窗二次确认。

### 4.4 退货入库流程

```
司机带回退货/拒收
   │
   ▼
PDA 退货收货：扫销售退货单/配送单 → 逐商品扫码录数量 → 入"退货位"
   ├─ 拒收：自动带原出库单成本（现有 inv_reject_inbound 逻辑）
   ├─ 销售退货：按销售退货单
   ▼
（质检预留，本期默认关）
   ▼
后台/PDA 判定处置：可二次销售 → 上架到正常库位；破损/临期 → 损溢位（走报损/降价）
   ▼
写库位库存 → 触发对应入库单审核 → 冲回/调整成本与应收
```

### 4.5 其他入库

- 无来源单的其他入库（期初、赠品、样品、盘外）：PDA 选入库类型 → 扫码录数 → 指定/推荐库位 → 直接入库（取当前成本，不改加权价，复用 `inboundAtCurrentCost`）。

## 5. 出库作业模块（多场景拣货，重点）

### 5.1 波次（Wave）

波次是出库拣货任务的组织单元，把**多张已审核销售订单**的出库需求聚在一起统一拣货。

> **源单规则**：波次只能选**已审核、未出库、未结案**的销售订单（销售订单生成即锁商品+仓库库存），并按订单**应发数量整单拣齐**。
> **一单一出库**：一张销售订单只进一个波次、只生成一张出库单、只出一次库，不拆成多次出库结转下一波次。出库单不在拣货前人工建立，而是在**拣货完成（或复核完成）后按实拣数量自动生成并审核**；拣不足按异常处理（§6.9），不出部分出库单。

**波次生成**：
- 后台手工勾选已审核销售订单组波次；
- 定时自动组波次（参数：组波时点，如每天 08:00/13:00，可多个时点），系统自动捞取"已审核未出库"的订单按策略聚合；
- 按策略自动聚合后，仓主管可在后台调整（加单、删单、拆波次、合波次）。

**聚合维度（参数 WMS_WAVE_GROUP_BY，可多选组合）**：
- 配送线路/片区（取销售订单/客户的 route_line / territory，现有字段）
- 承运商/司机
- 客户类型/客户优先级
- 订单类型（正常/加急/现结）
- 时效（当天达/次日达，发货截止时间）
- 商品重合度（重合度高→汇总拣；低→按单拣）
- 是否整箱为主

**拣货模式自动推荐（参数 WMS_PICK_MODE_RULE）**：

| 条件 | 推荐模式 |
|---|---|
| 单订单商品行数多、大客户、整单金额大 | 按单拣（摘果） |
| 多订单同商品重合度高、单订单件数小 | 汇总拣（播种） |
| 订单多、每单 1-3 个品项、便利店配送 | 边拣边分（摘播混合） |
| 仓库分整箱区/拆零区 | 分区接力（先整后零） |
| 到货即有对应订单 | 越库直发 |

最终拣货模式允许主管在波次上手手工覆盖。

**V84 起：拣货方式下沉到库区**（`wms_zone.pick_method` + `sort_mode`）。一个波次跨多个库区时，系统按各库区配置分别生成拣货任务并落 `wms_pick_task.pick_method/sort_mode`，PDA 按任务的拣货方式差异化作业：

- `CASE_PICK` 整件单拣：整件区商品按订单逐单拣（对应"按单拣"）；
- `CASE_MERGE` 整件合拣：整件区商品合并汇总拣，按 `sort_mode` 决定先拣后分（PICK_THEN_SORT）或边拣边分（SORT_WHILE_PICK）；
- `BULK_PICK` 拆零单拣：拆零区商品按订单逐单拣；
- `BULK_MERGE` 拆零合拣：拆零区商品合并拣 + 分播。

库区未配置 `pick_method` 时回退到参数 `WMS_PICK_MODE`（仓库级兜底，已在 V84 备注为兜底语义），波次下放弹窗的手工选择仍作为本波次的回退值。典型配置：A 区（整箱储区）= CASE_PICK，B 区（拆零储区）= BULK_MERGE + PICK_THEN_SORT。一张订单同时跨 A、B 两区时，A 区出整件单拣任务、B 区出拆零合拣任务，集货位按订单集齐。

**波次状态机**：
```
待生成(草稿) → 已下放(PDA可领/自动派) → 拣货中 → 拣货完成 → 复核中 → 复核完成 → 已发运(装车)
                                                                    └─→ 差异挂起(待处理)
```
波次取消/释放：未拣货可整波次取消（释放批次锁）；已部分拣货只允许主管权限终止，已拣货物归位。

### 5.2 五种拣货模式作业设计

#### 模式① 按单拣货（摘果式）
- 一张订单（或波次内一单一任务）由一名拣货员从头到尾拣完。
- PDA 按库位路径顺序逐行引导：到库位→扫库位码→扫商品码→输数量→确认→下一行。
- 拣完放周转箱，送复核区。
- **优点**：直观、责任清晰、新手友好；**适用**：订单品项多、大客。

#### 模式② 汇总拣货（播种式）
- 波次内同商品合并成"汇总拣货单"，拣货员一次性把总量从库位拣出到分拣区。
- 再到分拣区按客户/订单"播种"：PDA 显示每个客户应分数量，扫码/亮灯提示逐格投放。
- **适用**：商品重合度高、单订单件数少的 B2B 快消配送，显著减少行走。

#### 模式③ 边拣边分（摘播混合）
- 拣货员推多格拣货车，每格对应一个客户/订单（PDA 显示格口号）。
- 到库位一次拣出该商品在本波次的全部需求量，行走中直接投入对应格口，拣完即分完，无需二次分拣。
- **适用**：订单数多、每单品项少；PDA 每到一个库位显示"本库位商品 × 各客户数量"。

#### 模式④ 分区接力拣货（先整后零）
- 仓库按物理分区（整箱存储区 / 拆零拣货区 / 冷藏区等）划分作业段。
- 一张波次按库位所在区拆成多个"子任务"，分别派给各区拣货员，各自只在本区走动。
- 各分区拣完的货送到集货位按客户汇合，复核员合流。
- **适用**：大仓、整箱+拆零并存，减少单人行走距离；可与按单/汇总组合使用。

#### 模式⑤ 越库直发（Cross-docking）
- 收货时若该商品有匹配的紧急出库需求，上架步骤直接推荐到集货位/发货月台，不进存储位。
- 到波次拣货时该商品标记"越库直发"，复核装车直接发走。
- **适用**：高周转、到货即配；参数开关控制。

### 5.3 批次分配（出库自动算批次）

- 波次下放时由系统分配批次并锁定（复用现有批次锁 `inv_batch_stock.locked_qty` 与波次明细），PDA 只做确认与异常处理。
- 分配策略（参数 `WMS_BATCH_ALLOC_STRATEGY`）：
  - **FEFO**（默认，先到期先出，按 expiry_date ASC）—— 食品快消刚需
  - **FIFO**（先进先出，按 production_date ASC）
  - 指定批次（客户/订单锁定批次优先）
- 拣货现场若指定批次库位库存不足，PDA 提示可用其他批次库位，允许"改拣批次"并记录原因（参数 WMS_PICK_BATCH_CHANGE_ALLOWED）。

### 5.4 拣货路径与防错

- PDA 拣货明细按 `wms_bin.pick_seq` 升序排列，跨库区按区组内排序，形成不回头路径（S 形可配）。
- **三扫三对**：扫库位码（对货位）→ 扫商品码（对商品/批次）→ 输数（对数量）。
- 错误反馈（视觉+声音+震动）：
  - 错库位：红屏 + "这不是要找的货位，应去 A-01-02" + 急促音 + 强震动。
  - 错商品/批次：红屏 + "商品/批次不对，应拣 XX 批次 XX" + 音震。
  - 正确：绿闪 + "嘀" + 轻震。
- 数量默认填"应拣数"，扫码枪连扫自动累加；支持大/小单位。
- 可【跳过】当前行（暂时找不到/缺货），最后统一处理；可【缺货标记】触发补货。

### 5.5 补货（支撑拣货位）

| 类型 | 触发 | 流程 |
|---|---|---|
| 被动补货 | 拣货时拣货位库存不足，PDA 一键触发 | 从存储位补到拣货位，拣货员可等待或先拣其他 |
| 主动补货 | 定时任务扫描拣货位 < 安全库存(`safety_stock_pick`) | 自动生成补货任务，PDA 领取执行 |
| 手动补货 | 主管后台/PDA 手工建 | 指定源库位→目标拣货位 |

补货量算法（参数 WMS_REPLENISH_QTY_RULE）：补到拣货位容量上限 / 补到 N 天销量 / 固定量。
补货执行：扫源库位→商品→目标库位→数量确认，只移库位库存，不影响财务库存。

### 5.6 拣货完成 → 生成并审核销售出库单（审核即扣库存）

> **核心时点**：销售出库单在**拣货完成时**自动生成并审核、**审核即扣库存**；若参数开启出库复核（`WMS_CHECK_MODE` ≠ 免复核），则在**复核通过时**才生成并审核。装车/发运只做实物与责任交接，**不再触发扣库存**。

```
PDA 拣货完成（按订单确认实拣数量、批次、库位）
   │
   ├─ 无出库复核（WMS_CHECK_MODE=免复核）
   │     ▼
   │   按【实拣】为每张销售订单生成一张销售出库单 sales_outbound 并【自动审核】
   │     ├─ 出库数量 = 实拣数量，带出实拣批次/生产日期/成本
   │     └─ 审核：扣减库存、释放占用、生成发货单 sales_receipt（见下方口径）
   │
   └─ 有出库复核（强制逐件 / 抽核）
         ▼
       进入复核（§5.7）→ 复核通过 → 生成并审核出库单、扣库存、生成发货单
```

**拣货数量规则（一单一出库，不支持多次出库）**：
- 正常：实拣 = 订单应发 → 正常生成出库单。
- 拣不足（缺货/破损/找不到）：**不自动生成"部分出库单"**，订单行转异常（§6.9）：能加急补货的补完后重拣该行；确实无法配齐的，经主管权限**与客户确认后整单结案或整单调整**，差异留痕——不允许把剩余数量留到下一波次再出一次。
- 实拣 > 应发（错拣/多拣）：复核拦截，退回库位/更正。

> 出库单由系统按实拣自动生成，PC 端不允许手工建 WMS 仓的出库单（未启用库位的仓库保留原手工流程）。
> **扣库存口径不变**：仍由 `InventoryCostService.salesOutbound` 在出库单审核时执行（释放批次锁与商品+仓库层占用、扣减 `inv_batch_stock`、写库存流水），与 V1.0 完全一致，只是触发点从"人工审核/装车"前移到"拣货或复核完成"。

### 5.7 复核（复检可配置）

- 出库单（实拣结果）随箱送到复核位，复核员扫波次号/箱码。
- PDA 逐件扫商品码，系统比对**出库单(实拣) vs 复核实点**：一致绿、差异红。
- 差异处理（必须选原因，可拍照）：
  - 少发：缺货 / 破损 / 拣错 → 按参数决定"少发也能出（WMS_CHECK_SHORT_ALLOWED）"或"挂起待补/退回重拣"，差异回写出库单数量。
  - 多发/错发：退回库位/更正出库单。
- **是否复核可配置**（参数 WMS_CHECK_MODE）：
  - 强制逐件复核（默认，最严）
  - 按比例抽复核（参数 WMS_CHECK_RATIO，抽中才逐件扫，其余免复核）
  - 免复核（信任拣货，仅对低值/可信拣货员，参数 WMS_CHECK_SKIP_ALLOWED）——此模式下拣货完成即生成并审核出库单（见 §5.6）
- 高价值商品（金额阈值 WMS_CHECK_HIGH_VALUE_THRESHOLD）强制复核，不可免。
- 复核通过：**立即生成并审核出库单，审核即扣库存、释放占用、生成发货单 `sales_receipt`**（不是等到装车）。复核差异（少发/多发/错发）必须先处理并回写出库单数量，再通过；少发是否允许按差异出库由 `WMS_CHECK_SHORT_ALLOWED` 控制，否则转异常挂起（§6.9）。

> 说明：收货端也有"复检"（WMS_RECHECK_ENABLED，双人点数）；出库端叫"复核"。两者独立配置，互不影响。
> 注意：因扣库存提前到拣货/复核完成，装车环节（§5.9）只做实物清点与责任交接，不再做账务扣减；若装车时发现实物与出库单不符，走差异异常与库存调整（报损/补单），不反审核已扣账的出库单。

### 5.8 打包与箱码

- 复核通过后装箱，打印/贴**出库箱码**（客户、地址、本箱商品、件数、波次/订单号条码）。
- 一个客户可多箱；箱与商品绑定，配送签收可按箱核对（与 TMS 对接预留）。

### 5.9 装车确认与司机交接（衔接 TMS，以销售订单号贯穿）

> **关联键**：WMS 与 TMS 统一以**销售订单号 `source_order_no`** 作为贯穿销售订单、销售出库单、发货单 `sales_receipt`、TMS 配送单 `tms_dispatch`/明细的关联键。任一环节的操作（出库、装车、改派、签收、拒收、改派返仓）都必须**回写订单、出库单、发货单三者的状态**，保证全链路状态一致、可追溯。

#### 5.9.1 调度派单时机（两种，均可）

| 派单时机 | 说明 | 对 TMS 的影响 |
|---|---|---|
| **① 波次预分配时指派（拣货前）** | 组波次/波次下放时就指派司机/车辆/线路（按线路聚合时自然带出） | **预分配后即生成 TMS 调度单 `tms_dispatch`（待接单/待装车）**，司机 APP 立即可见任务与客户/件数预告，但**在订单出库完成前不能装车** |
| **② 出库完成后指派** | 拣货/复核完成、出库单审核、发货单生成后，调度在 TMS 调度池再指派司机 | 生成调度单后司机即可装车 |

- 两种时机由作业习惯选择（参数 `WMS_DISPATCH_TIMING`：波次分配时 / 出库后 / 两者皆可）；核心约束是：**司机只能对"出库已完成（出库单已审核、发货单已生成）"的订单/发货单执行装车**。
- 订单出库完成后，回写销售订单 `outbound_status`、发货单 `dispatch_status`，并更新 TMS **装车任务单状态为"待装车"**，司机 APP 装车列表才可拣。

#### 5.9.2 仓管装车确认（只确认实物，不扣库存）
```
出库完成（出库单已审核扣库存、发货单已生成）→ 集货位按线路/客户集货
   │
   ▼
仓管 PDA / 司机 APP 装车：扫发货单/箱码逐车确认，或按波次/调度单批量装车
   ├─ 前置校验：订单必须"出库完成"，否则拦截提示"该单尚未出库，不能装车"
   ├─ 装车校验：扫错单/错箱报警；确认本车装了哪些客户哪些箱
   └─ 装车完成：释放集货位、波次置"已发运"、回写发货单/装车任务单"已装车"、TMS 配送单待发车
```
- **装车不再触发扣库存**（扣库存在出库单审核时已完成，见 §5.6/§5.7）。装车只做实物清点与仓库→司机的责任交接。
- 装车时若发现实物与已出库单不符（少件/破损/错装），走差异异常（§6.9）与库存调整（报损/补单），**不反审核已扣账的出库单**。
- 司机发车后，TMS 配送/导航/签收/拒收/应收链路按现有 V2.0 逻辑不变。

#### 5.9.3 未发车改派：后台改司机 / A 转 B 扫码接收（状态变换，不生新单）

适用：单据已生成调度单、但**司机尚未发车**（待接单/待装车/已装车未发车），需要换司机。

- **后台调度直接改司机**：调度在 TMS 调度池把配送单的司机/车辆从 A 改为 B（复用 `tms/dispatch/assign` 语义），配送单与发货单 `driver`/`driver_id` 更新，任务从 A 列表移到 B 列表。
- **A 司机主动转给 B 司机（扫码交接）**：
  ```
  A 在司机 APP 选"转交单据" → 选要转出的配送单/客户（可批量，按客户聚合）
     → 生成转交二维码（含销售订单号/发货单号）
     → B 用自己的司机 APP/PDA 扫码确认"接收"
     → 配送单、发货单司机由 A 改为 B，任务进入 B 的任务列表、从 A 消失
  ```
  - 改派**对源配送单/发货单直接做状态与司机字段更新，不生成新的业务单据**，全程留痕（交出人、接收人、时间、原因、件数）。
  - **送货单转移时，该客户名下的退货取货单（RETURN 明细）自动跟随转移到 B**（同客户的送/退单绑定，避免送的人和退的人脱节）。
  - 已发车/配送中/已签收/已交账的单据不能走此改派；配送中需改派的走 5.9.4。

#### 5.9.4 配送中改派返仓：回仓 PDA 签收、记集货位、调度重派（不入库、不动库存）

适用：司机已发车、在**配送过程中**因客户不在/地址错/联系不上/客户要求改期等，无法送达需返仓改期（复用现有 TMS 改派返仓能力 `tms_reschedule_return`，单号前缀 GPRC）。

```
司机在司机 APP 配送中发起"改派返仓"（选原因/日期/拍照）
   → TMS 建改派返仓留痕记录 tms_reschedule_return(PENDING)，配送明细置 RESCHEDULED
   → 货物随车带回仓库
   │
   ▼
仓管 PDA【改派单签收】：扫改派单号/发货单号/箱码
   ├─ 显示原销售订单号、客户、商品、应回件数、退回原因
   ├─ 逐单/逐箱扫码核对，登记实收件数与差异（拍照+原因）
   ├─ 扫/选放入的【集货位】并确认签收
   └─ 提交：改派返仓记录 PENDING→CHECKED，发货单 sales_receipt.dispatch_status=RESCHEDULED(待改派)，
           并在发货单/改派记录上回写【集货位】（仅货物位置标记，便于找货）
   │
   ▼
★ 全程不生成入库单、不写 wms_bin_stock、不增不减库存
  （货本就是已出库状态，只是回到仓库集货位等待再配送）
   │
   ▼
调度在 TMS 后台对"已签收/待改派"的源发货单重新指派司机（redispatch）
   → 新司机到集货位取货装车 → 正常发车/签收链路
```

**关键规则**：
- 改派返仓是**对源配送单/发货单的状态变换**（`RESCHEDULED → 待派送`），复用 `tms_reschedule_return` 仅作留痕记录，**不生成新的业务单据、不反审核出库单、不动库存**。
- 集货位是**货物位置标记字段**（记录货放在哪个集货位），不参与库位库存账，不进 `wms_bin_stock`。
- 签收差异（少件/破损）登记异常并留痕，按报损/追查处理，但不因此把退回货当作入库。
- 仓库 PDA 签收是调度可重新指派的前置条件（签收后才可 redispatch）。

**上下游关联（状态回写）**：
- 出库审核：拣货完成/复核通过 → 生成并审核 `sales_outbound` → `InventoryCostService.salesOutbound` 扣库存、释放占用、生成 `sales_receipt`，回写销售订单 `outbound_status`。
- 装车：以销售订单号关联发货单与 TMS 配送单，装车后回写三者状态（订单/出库单/发货单）。
- 未发车改派：直接改源配送单/发货单司机字段，同客户退单跟随转移，状态回写。
- 配送中改派返仓：源发货单 `dispatch_status` 在 `RESCHEDULED → 重新指派 → 再配送` 间变换，WMS 签收记集货位，全程不动账。
- 签收/拒收/应收：沿用现有 V2.0 TMS 链路。

## 6. 库内作业模块

### 6.1 盘点（多方式，行业通行）

#### 6.1.1 盘点方式（按范围/触发）

| 方式 | 适用 | 范围 | 是否停业/冻结 |
|---|---|---|---|
| **动盘（动态盘点）** | 作业间隙随时盘，高频、A 类、账实疑点 | 现场扫某库位/某商品/某批次即盘，盘完即走 | 不停业；默认不冻库位（参数 `WMS_DYN_COUNT_FREEZE_BIN` 可设短时冻结） |
| **全盘（全面盘点）** | 月末/季末/年末大盘 | 全仓所有库位、所有商品、所有批次 | 可冻结全仓作业（参数 `WMS_COUNT_FREEZE_WHOLE`），多人分区同时盘，分初盘→复盘→审核 |
| **指定盘（定向盘点）** | 按管理需要圈定范围 | 后台选条件生成任务：按库区/库位、按商品/分类/品牌、按批次/效期、按 ABC、按供应商、按库存阈值（零库存/负库存校验） | 只冻结被盘范围（参数 `WMS_COUNT_FREEZE_BIN`） |
| **抽盘** | 日常抽查 | 按库区/商品/ABC 随机或按比例抽样 | 同指定盘 |
| **循环盘** | 常态化盘点 | 按 ABC 设不同频率（A 类每月、B 类每季、C 类每半年），系统自动到期生成盘点任务 | 同指定盘 |

> 动盘走 PDA 快速入口（扫库位即盘、随作业走，轻量留痕）；全盘/指定盘/抽盘/循环盘走"建盘点计划→领盘→初盘→复盘→审核→调账"的正式流程。

#### 6.1.2 盘点模式（按是否显示账存）

- **明盘**：PDA 显示系统库存，仓管核对录差异（效率高，防作弊弱）。
- **暗盘（盲盘）**：不显示系统数，仓管实打实录入（防照抄，食品/高值推荐）。
- **复盘**：差异超过阈值（`WMS_COUNT_RECOUNT_THRESHOLD`）或有争议的库位，换人再盘。

#### 6.1.3 正式盘点流程

```
后台建盘点计划（方式=全盘/指定盘/抽盘/循环盘，范围/明暗盘/责任人）或 PDA 发起动盘
   → 冻结相关库位（按参数：全盘可冻全仓，其余冻被盘库位；动盘默认不冻）
   → PDA 逐库位扫码：扫库位 → 逐商品扫码录实盘数（整托可扫托码带出账内数再确认）
   → 实时显示差异（明盘）或不显示（暗盘）
   → 全部盘完提交 → 系统自动算差异，超阈值生成复盘任务 → 复盘
   → 主管后台审核差异
   → 审核通过：盘盈入库/盘亏出库，调 inv_batch_stock 与库位库存，写流水（复用现有盘点审核逻辑，补库位明细）
   → 解冻库位
```

**数据**：复用现有 `inv_count_sheet` / `inv_count_detail`，新增 `wms_stocktake_bin`（库位级实盘、复盘记录、盘点方式字段）。

### 6.2 移库 / 库位整理

- PDA：扫源库位→扫商品/容器→输数量→扫目标库位→确认。
- 整托移位：扫托盘码→扫目标库位，一次完成。
- 仅变动 `wms_bin_stock`（库位维度），财务库存数量/金额不变，写库位流水。
- 触发：整理库位、合并同品、把滞销品挪到深处、给热销品腾拣货位。

### 6.3 补货

见 §5.5。

### 6.4 组合/拆分

- 后台建组合申请（如礼盒：A 水×10 + B 面×5 → C 礼包×1，BOM 在商品资料维护）。
- PDA 按申请：散件从库位出库 → 组合品入库到指定库位。
- 成本按 BOM 汇总（与现有组合口径一致）；库位库存对应增减。
- 拆分为逆向。

### 6.5 报损

- PDA：扫库位→商品/批次→输数量→选报损原因→拍照→进损溢位临时隔离。
- 主管后台审核后正式报损出库，成本取当前批次成本（复用 `InventoryCostService` 与现有报损逻辑），写库位/财务流水。

### 6.6 效期管理

- 收货录入生产日期，按 `shelf_life_days` 算到期日；临期（`warning_days`）与过期在 PDA/后台预警。
- FEFO 出库自动优先早到期批次。
- 过期批次自动冻结（`frozen_qty`），不可拣，需处置（报损/退货/降价）。
- PDA 提供"生产日期修改"（现有原型已有）：扫库位+商品→选新日期→主管权限确认并留痕。

### 6.7 库存查询（PDA + PC）

- PDA 扫库位码：显示该库位所有商品/批次/数量。
- PDA 扫商品码：显示该商品在各库位、各批次分布（找货）。
- PC：库位库存查询、库位占用率热力图、批次分布、临期库存。

### 6.8 冻结/解冻

- 质检（预留）、盘点、异常、过期可冻结库位/批次/库位上某批商品。
- 冻结量不可拣（`frozen_qty`），解冻需主管权限并留痕。

### 6.9 异常处理（全作业环节）

> 现场异常是常态。WMS 异常分两类：**业务异常**（数量/质量/单据/客户等业务问题）和**作业/系统异常**（设备、网络、错扫、库存冲突、账实差异等）。所有异常统一进 PC 端"异常中心"（§8.6），PDA 可一键上报；每种异常都有明确的发现入口、现场处置、状态变化、库存/占用影响、责任人与处理闭环，全程留痕。
>
> **通用原则**：① 现场能即时纠正的（扫错码、输错数）当场重扫/改数，不立异常单；② 当场无法解决的才"挂起"并冻结相关库存/库位，进异常中心分派；③ 任何异常处理**不得绕过库存与单据状态**，已审核单据不直接删除/反审核，只走调整/退货/报损等正规链路；④ 所有数量修正必须选原因、可拍照、写操作日志。

#### 6.9.1 通用异常机制

- **统一异常单 `wms_exception`**：来源环节、来源单号、销售订单号、异常类型、严重等级（普通/加急/严重）、描述、图片、当前状态、上报人、责任人、超时截止时间、处理过程留痕。
- **异常状态机**：
  ```
  异常发现（PDA/PC 上报 或 系统自动判定）
     → 待处理（进异常中心；需要时挂起并冻结相关库存/库位/批次）
     → 处理中（分派责任人：补货/归位/改约/报损/与客户/供应商确认/重扫重盘）
     ├─ 已解决（恢复作业：继续拣货/重拣/解冻/重盘）
     └─ 已结案（取消订单/整单结案/报损/盘盈亏调账等终态）
  ```
- **超时升级**：挂起超 `WMS_EXCEPTION_SUSPEND_TIMEOUT` 未处理自动提醒并升级主管；严重异常（账实不平、已出库差异）即时告警。
- **加急异常**：影响急单发车的异常自动置"加急"，在异常中心与 PDA 置顶。
- **权限**：普通作业员可上报、可处理分派给自己的；冻结/解冻、作废已审核单、整单结案、盘盈亏审核、报损审核需主管或对应审批权限。

#### 6.9.2 入库/上架环节异常

| 异常 | 发现/触发 | 现场处置 | 库存/单据影响 | 后续闭环 |
|---|---|---|---|---|
| 无订单送货（送错货/无采购单） | PDA 扫单查无已审核采购订单 | 暂收区隔离，禁止上架；可选"无单收货"建临时入库单（参数 `WMS_RECEIVE_WITHOUT_ORDER`） | 货物入暂收位，不生成正式入库单、不增库存 | 采购补单后关联；无法关联的退回供应商 |
| 超收（实收>应收） | 收货数量校验 | 按超收容差 `WMS_OVER_RECEIVE_TOLERANCE` 内放行；超容差需主管确认收或退 | 按确认实收生成入库单 | 超收留痕；供应商多发的结算按合同 |
| 少收/欠交（实收<应收） | 收货数量校验 | 选原因（短装/分批/破损），按实收收；多次收货开关决定是否等下批 | 按实收入库；采购订单进部分入库/入库完成 | 采购跟催欠交；关闭未交数量需主管 |
| 错发/串货（商品/规格不符） | 扫商品码与订单不符 | 红屏拦截，该品隔离暂收位，不上架 | 不入该订单应收 | 拍照上报，退换货处理 |
| 破损/质量异常 | 收货肉眼发现 | 隔离到损溢/退货位，拍照选原因，登记破损数 | 破损数不进正品库存；走报损/退换 | 与供应商定责，索赔或退货 |
| 批次/生产日期缺失或异常 | 录批次时 | 手输或按生产日期生成；过期/临期拦截（参数） | 异常批次冻结，不上正常架 | 临期入特区位，过期走退货/报损 |
| 多批次混收 | 同一商品多批次 | PDA 自动拆多行分别录批次/数量 | 按批次分别入账、分别上架 | — |
| 盲收/复检差异 | 复检复点不一致 | 登记实点与差异原因，主管确认后修正实收 | 以确认数生成入库单 | 收货差错计入收货员绩效 |
| 上架找不到推荐库位/库位满 | 上架推荐校验 | 系统改推邻近库位；仓管可改放并选原因（`WMS_PUTAWAY_FREE_BIN`） | 按实际上架库位记账 | 改放记录用于策略优化 |
| 上架扫码错库位/错商品 | 扫库位/商品码校验 | 红屏+音震拦截，指引正确库位/商品 | 不写错误库存 | 即时重扫，不立单 |
| 上架数量与收货数不符 | 上架确认时 | 不能部分"找不到"就结束；逐行核对，差异挂起 | 以实际上架为准，未上架部分留暂收位 | 差异追查（漏上架/丢失） |

#### 6.9.3 出库/拣货/补货/复核/打包环节异常

| 异常 | 发现/触发 | 现场处置 | 库存/单据影响 | 后续闭环 |
|---|---|---|---|---|
| **取消订单** | 客户撤单 | 未下放：作废需求释放锁；已下放未拣：先取消下放再作废；已拣/已复核/已出库：货物归位或走退货，不删已审核出库单 | 释放商品+仓库占用与批次锁；已出库按退货链路 | 主管审批；`WMS_CANCEL_RELEASE_LOCK` |
| **取消下放（撤波次）** | 错单/客户改约/紧急调整 | 未拣可整波撤回草稿、删拣货任务、释放批次锁；已部分拣需主管终止、已拣货归位 | 释放 `locked_qty`，订单回待组波池 | 重新组波 |
| **订单加急** | 客户催单 | 波次/拣货/补货/复核/装车全链置顶插队，显著标识；可插当前波或组急单波、触发越库 | 不改库存量，只改优先级；加急优先锁批次 | `WMS_EXPEDITE_ENABLED` |
| 拣货缺货（账面有、库位无） | 到库位无货/数量不足 | PDA【缺货标记】：能补则触发**加急补货**；补不到则该行**异常挂起**，不硬出 | 挂起部分冻结；锁定不释放待裁决 | 加急补货后重拣；确无货走整单调整/结案 |
| **加急补货** | 拣货位不足但单急 | 一键从存储位/整托紧急补到拣货位，补货任务置顶 | 仅库位间转移，不动财务库存 | 补完续拣 |
| 拣货位库存不足（存储位也无） | 补货时无货 | 库存差异上报，挂起订单行 | 触发账实差异核查 | 盘点核查、与销售确认改期/替换/取消 |
| 错库位/错商品/错批次 | 三扫三对校验 | 红屏音震拦截，指引正确货位/商品/批次；允许改拣批次（参数）并选原因 | 不记错误拣货 | 改批次留痕 |
| 拣货数量多/少 | 输数/复核发现 | 少：补拣或挂起；多：退回库位 | 以实拣为准生成出库单；不足按异常不部分出库 | 见 §5.6 一单一出库口径 |
| 复核少发/多发/错发 | 复核实点 vs 出库单 | 选原因拍照；少发按 `WMS_CHECK_SHORT_ALLOWED` 决定可出或挂起补拣；多发/错发退回更正，回写出库单 | 复核通过才审核扣库存，差异在扣账前纠正 | 差错计入拣货/复核绩效 |
| 复核高值/数量异常 | 超阈值/高值商品 | 强制逐件复核，不可免 | — | `WMS_CHECK_HIGH_VALUE_THRESHOLD` |
| 打包错箱/漏装 | 装箱扫码校验 | 扫箱码/商品码核对，漏装报警 | 箱与商品绑定，错装拦截 | — |
| 箱码/标签打印失败 | 打印机异常 | 重打；设备故障转人工临时标识，事后补打 | 不影响库存 | 设备报修 |

#### 6.9.4 装车/交接/改派环节异常

| 异常 | 发现/触发 | 现场处置 | 库存/单据影响 | 后续闭环 |
|---|---|---|---|---|
| 未出库订单尝试装车 | 装车前置校验 | 拦截提示"该单尚未出库，不能装车" | 不允许装车 | 先完成拣货/复核出库 |
| 装车少件/多件/错装 | 扫箱码/发货单核对 | 少件回集货位/库位找，多件退回，错装换箱；当场处理 | 出库已扣账，实物差异转异常**不反审核出库单** | 少件走报损/补发，多件退回入库（其他入库/调整） |
| 司机拒装/件数争议 | 司机交接时 | 仓管与司机当场清点复核，签字确认实收 | 以双方确认件数交接；差异登记 | 责任界定 |
| 未发车改派 A→B 交接差异 | B 扫码接收时发现缺箱/破损 | 当场登记拍照，差异部分不接收 | 只改源单司机字段；差异转异常 | A 负责追查/报损 |
| 配送中改派返仓差异 | 仓管 PDA 签收时 | 逐箱核对，登记实收件数与差异、选集货位 | **不入库、不动库存**，仅状态变换+位置标记 | 差异追查/报损；签收后调度可重派 |
| 客户拒收/退货 | 司机配送时（TMS） | 走现有拒收/退货链路，货物带回入退货位 | 拒收按原成本入拒收库（现有逻辑） | 判定后上架或报损 |
| 集货位货物丢失/错放 | 装车找不到货 | PDA 查集货位+箱码定位；找不到挂起 | 库存已扣，实物缺失走报损 | 责任追查 |

#### 6.9.5 库内作业异常（盘点/移库/报损/效期/组合）

| 异常 | 发现/触发 | 现场处置 | 库存/单据影响 | 后续闭环 |
|---|---|---|---|---|
| 盘点账实差异 | 实盘 vs 账面 | 明盘即时显示；暗盘提交后算；超阈值自动生成复盘任务，换人重盘 | 复盘后仍有差异，主管审核做盘盈入库/盘亏出库 | 调 `inv_batch_stock` 与库位账，写流水 |
| 复盘仍不一致 | 复盘环节 | 主管现场抽盘裁定 | 以裁定数调账 | 差异原因记录、责任界定 |
| 盘点中发生作业冲突 | 冻结库位仍被作业 | 冻结库位禁止上下架/拣货（参数）；动盘默认不冻，以盘点时刻快照为准 | — | `WMS_COUNT_FREEZE_BIN`/`WMS_DYN_COUNT_FREEZE_BIN` |
| 移库源/目标库位错误 | 扫码校验 | 红屏拦截重扫 | 不写错误流水 | — |
| 移库数量超可用 | 输数校验 | 拦截，按可用量移或查库存 | 不超扣 | 库存核查 |
| 报损审核不通过 | 主管审核 | 退回或改判（让步/退回供应商） | 不做出库；货物解冻结 | 重新处置 |
| 临期/过期批次 | 效期预警/FEFO | 临期预警、特区位；过期自动冻结不可拣 | 过期 `frozen_qty` | 报损/退货/降价促销 |
| 组合/拆分 BOM 不符 | 组合作业 | 散件库存不足拦截，BOM 变更需后台 | 按 BOM 增减库位库存 | — |
| 库存冻结异常 | 质检/盘点/异常冻结 | 解冻需主管审批留痕 | 冻结量不可拣 | 定期审查长期冻结 |

#### 6.9.6 系统/设备/数据异常

| 异常 | 发现/触发 | 处置 | 说明 |
|---|---|---|---|
| 扫码无响应/识别失败 | 硬件扫描键/摄像头 | 切换摄像头扫码/蓝牙枪/手工输入单号；设备报修 | PDA 提供多扫码通道降级 |
| 蓝牙打印机/秤断连 | 外设连接 | 重连；失败则手工记录、事后补打/补录 | 不阻断主作业 |
| 断网/后端不可用 | connectivity 监听 | 进入离线暂存（§11.5），作业存本地，顶部红条提示；联网自动同步 | 关键审核/扣库存动作需在线 |
| 离线提交冲突（乐观锁版本不一致） | 同步时 | 不静默覆盖，生成异常由主管实测裁决后调整 | 库位库存带 version |
| 重复提交/幂等冲突 | 网络重试 | 按 `client_action_id` 幂等，重复返回首次结果 | 防重复扣库存 |
| 账实对账不平 | 每日对账（SUM(wms_bin_stock) vs inv_batch_stock） | 差异告警，生成差异核查异常单，定位到商品/批次/库位 | 事件全部发布后理论恒等 |
| 事件过账失败/积压 | outbox 重试/死信 | 退避重试；超 24h 进死信，事件异常中心可见，手工重试/作废 | ERP 恢复后自动补齐 |
| PDA 崩溃/闪退 | 全局异常捕获 | 崩溃日志上传；已暂存数据不丢，重进断点继续 | 稳定优先原则 |
| 时间/数据不同步 | 离线缓存过旧 | 首页标注"离线数据 HH:mm"；库存类校验在线为准，离线降级为提示 | — |

> 异常中心（§8.6）提供：待处理/处理中/已解决/已结案分栏、按环节/严重度/责任人/时间筛选、超时与加急高亮、批量分派、处理过程留痕、导出，并与绩效差错率、账实对账、事件死信联动。

## 7. PDA 设计（面向中老年/低学历作业人员）

### 7.1 技术方案

- **Flutter + Android**，与 TMS 司机 APP 同栈；复用：Riverpod、dio 拦截器、统一 `{code,message,data}`、sqflite 离线队列、拍照服务、离线横幅。
- **稳定优先**：
  - 关键操作幂等（带客户端请求号，防重复提交）；
  - 全局异常捕获，崩溃有日志可上传；
  - 弱网/断网作业可暂存、联网自动同步，顶部彩条状态明示；
  - 关键审核/扣库存动作强制在线；
  - 充分在低端 PDA、安卓 8+ 真机回归，不追求花哨动画。
- **扫码（WMS 核心，TMS 无现成实现，需新建）**：
  - 主力：PDA 硬件扫描键（斑马/霍尼韦尔/东集等），通过安卓广播 Intent 接收扫描结果，快、省电、戴手套可用；
  - 辅助：摄像头扫码（`mobile_scanner`，给手机/平板用）；
  - 兼容：蓝牙扫码枪（键盘模式 + 回车）。
- 硬件外设：蓝牙标签打印机（收货标签/箱码）、可选蓝牙电子秤（称重商品自动带重量）。

### 7.2 易用性设计原则（强约束）

> 大、少、响、防错、不用想。

1. **一屏一任务**：作业中整屏只显示"现在去哪、拿什么、拿多少"，其余收起。
2. **首页是"我的活"不是菜单**：按角色显示待收货/待上架/待拣货/待复核的数字与大按钮，点进去直接干活。
3. **超大字号与按钮**：关键数字≥28sp，主按钮高度≥64dp、满宽，戴手套可点；高对比配色。
4. **扫码优先，少输入**：数量默认应拣数，核对即确认，仅差异才输入；数字用大数字键盘。
5. **看+听+震动三反馈**：正确绿闪+嘀+轻震；错误红屏+急促音+强震动+大字说明"该去哪/该拿什么"。可选语音播报（蓝牙耳机）。
6. **错误用人话**：不出现技术报错；断网提示"网络断了，数据已存着，到有网处点同步"。
7. **防误点**：提交按钮点后变"提交中…"并禁用；关键差异/报损二次确认+选原因/拍照。
8. **可暂存可返回**：任意步骤可暂存离开，回来断点继续；扫错可返回上一行修正。
9. **不强迫记单号**：任务显示供应商/商品/件数；可扫单号/条码直接进入，不在列表里翻。
10. **新员工引导**：首次进入有"跟着做"高亮引导。
11. **登录简单**：工号+密码，支持扫工牌码/记住工号。

### 9.6 仓库作业人员绩效（重点）

**数据来源**：所有 PDA 作业都记录"谁、什么时间、做了哪张任务、数量多少、重量、金额、指令行数、起止时间、是否差异"。作业任务表统一含 `assignee_id / assign_time / start_time / finish_time / qty / weight / amount / line_count / error_count`。

**个人绩效指标**：

| 指标 | 计算口径 |
|---|---|
| **指令行数** | 本次作业处理的作业指令/明细行数（收货行、上架行、拣货行、复核行、盘点行）。"一行"=一个库位×一个商品×一个批次动作，是计件最常用口径 |
| 收货件数 | 按收货任务明细的实收数量汇总（大单位统一折基本单位，同时保留原单位件数） |
| **入库重量** | 收货实收重量汇总 = Σ 商品档案单件重量 `base_weight` × 实收数量（按单位换算）。称重商品可选连蓝牙秤采集实测重量做比对、记录差异。用于计重计件、装卸量统计 |
| 上架件数/行数 | 上架确认数量/行数 |
| 拣货件数/行数 | 拣货确认数量/行数（区分按单/汇总/边拣边分/分区接力模式） |
| **拣货金额** | 拣货确认数量 × 销售单价（含税/不含税可切），按订单价格取数。衡量拣货员经手货值，用于高价值货区考核与异常关注，不作为工资直接依据 |
| 复核件数/行数 | 复核扫描数量/行数；同时记录复核纠出的差错行数（算上一环节差错，不算复核员差错） |
| 装车箱数/件数 | 装车确认的箱数、件数 |
| 盘点库位数/件数/行数 | 盘点完成库位数、商品行数、件数 |
| 移库/补货代行数/件数 | 库内作业量 |
| 作业时长 | finish_time − start_time（有效作业工时，支持多段暂停/中断） |
| **人均效率** | 件/小时、行/小时、（入库）吨/小时，按作业类型分别统计 |
| **差错率** | 差异（少发/错发/拣错被复核纠出/收货复检差异/盘点差异）行数 ÷ 总作业行数 |
| 缺货上报次数 | 拣货缺货标记次数（触发补货） |
| 改放/改批次次数 | 上架改放、拣货改批次（合规但记录，用于策略优化与培训） |
| 异常上报与处理 | 上报数、闭环时效 |
| 改派交接 | 交出/接收单据次数、件数、差异（5.9.3） |

**计件口径可配置**：不同作业类型可按"件数 / 指令行数 / 重量 / 箱数"之一作为主计件单位（参数 `WMS_PERF_UNIT_*`），报表同时展示多维度，避免一刀切。

**绩效报表形态**：
- **个人绩效日报/月报**：按人、作业类型统计指令行数、件数、重量、拣货金额、工时、效率（件/行/吨每小时）、差错率，可钻取到每张任务/每行明细。
- **班组/库区绩效对比**：按班组、库区、班次横向对比作业量、效率与差错。
- **入库作业报表**：收货件数、**入库重量**、行数、复检差异、上架及时率。
- **拣货作业报表**：拣货件数、行数、**拣货金额**、各拣货模式占比、缺货率、人均效率。
- **拣货员排行榜**（可选，主管可见）：可按件数/行数/效率/差错率/拣货金额切换排名，配合计件激励。
- **绩效参数配置**：不同作业类型设"标准件/小时（或标准行/小时、标准吨/小时）"基准（参数维护），报表显示达成率；可按客户需要导出计件工资底稿。
- 权限：作业员只能看自己；主管看本组/全仓；**拣货金额、成本等敏感字段按字段权限控制**，普通作业员不可见他人金额。

**注意**：
- 绩效只做客观数据输出与查看，**本期不做自动算薪/工资模块**；提供导出（Excel）供外部计件核算。
- 拣货金额用于"经手货值/高值货区管理"，不建议直接作为计件工资唯一依据（会导致挑贵的拣、轻的不愿拣）；计件以行/件/重量为主、金额为辅。

### 9.7 报表通用能力
- 所有报表支持多条件筛选、分页、列设置、导出 Excel（复用现有导出中心 `/report/export` 与 `sys_export_task_runtime`）。
- 图表复用现有 `ReportChartPage` 能力（趋势图、分布图、排行榜）。
- 报表权限按角色/数据范围控制。

## 11. 技术架构与高可用方案

> 目标：仓库作业是"生产线"，ERP 是"管理台"。必须保证：①ERP 后台多人操作、大量查询不拖慢仓库 PDA；②即使 ERP 应用/网络异常，仓库收货、上架、拣货、复核、装车仍能继续，恢复后自动同步、账实最终一致。
>
> 现状底座：单体 Spring Boot（包按业务域划分）、生产 MySQL 8 + Redis、HikariCP；开发用 H2 文件；项目要求"轻量底座、不盲目引入重依赖"。据此，方案分**两层**：逻辑隔离 + 离线自治（现在就做，低成本拿大头收益），并保留**物理拆服务**的接缝（规模到了再拆，不改业务代码）。

### 11.0 推荐结论（最终效果导向）

**推荐采用"模块化单体 + 资源隔离 + PDA 离线自治"起步（11.2–11.5），把 WMS 独立进程/微服务作为规模到位后的演进选项（11.6），而不是一开始就拆。**

你要的最终效果是"仓库作业不被 ERP 拖垮、ERP 挂了仓库照样能收货拣货"。达成这个效果**靠的不是"拆成几个服务"这个动作本身，而是三件事**：

1. **资源隔离**——WMS 有自己的连接池/线程池，ERP 的慢 SQL 抢不到 WMS 的资源（解决"被拖慢"）；
2. **解耦过账**——现场作业只写 WMS 库位账并立即返回，财务过账走事件异步，ERP 挂了不阻塞仓库（解决"挂了不能作业"）；
3. **PDA 离线自治**——断网/后端不可用时作业暂存本地，恢复自动同步（解决"网络/服务中断"）。

这三件事在单体内就能做到 80–90% 的效果，且运维简单、数据一致容易保证。**微服务只是把第 1、2 点的隔离从"进程内"升级为"进程间/机器间"**，当单台机器扛不住、或需要 WMS 与 ERP 独立发布/独立伸缩、或仓库 7×24 运行而 ERP 常需停机维护时，这个升级才有价值。当前是单仓、团队小、底座轻，没有这些刚性需求，硬拆只会提前背上分布式复杂度。

### 11.0.1 为什么不盲目拆微服务（理由与风险）

| # | 不急于拆的理由 | 盲目拆会引入的风险/成本 |
|---|---|---|
| 1 | **数据一致性变难**：现状收货/上架要同时改库位库存和财务库存，单体内一个本地事务即可；拆成服务后变成跨服务/跨库，必须引入分布式事务或事件+对账，移动加权平均成本的串行正确性更难保证 | 重复过账、成本错乱、账实对不上，需额外对账/补偿/死信机制 |
| 2 | **运维复杂度陡增**：要服务注册发现、配置中心、网关、链路追踪、多个部署单元与监控；当前团队与 docker-compose 单机部署不匹配 | 部署排障难度上升，反而降低可用性（"分布式"本身是故障来源） |
| 3 | **网络即故障点**：进程内调用变网络调用，多了延迟、超时、重试、雪崩、服务间版本兼容问题 | PDA 一个收货动作可能跨多次 RPC，弱网仓库更不稳定 |
| 4 | **数据共享与联调成本**：商品/订单/库存数据跨服务，要么冗余缓存、要么远程查，接口契约一旦变动两边协同 | 开发联调周期拉长，小团队产能被稀释 |
| 5 | **当前规模不需要**：单仓 PDA 并发有限，单进程加连接池隔离足以支撑；瓶颈更可能在 DB 和现场网络，不在服务数 | 为想象中的规模付出真实成本，过度设计 |
| 6 | **项目纪律要求轻量**：CLAUDE.md 明确"保持轻量底座、禁止乱引入外部依赖" | 引入 MQ/注册中心等重中间件违反约定 |

**关键判断**：隔离故障不一定要拆服务。单体内的"舱壁隔离 + 异步事件 + PDA 离线"已经能满足"仓库继续作业"；只有当监控数据证明单体成为瓶颈、或组织上确实需要 WMS 与 ERP 独立发布/独立伸缩时，再按 11.6 演进（因为代码边界已划清，拆分是机械工作，不需要推翻重做）。

> 一个务实的中间选项：当"ERP 重启/发布不能影响仓库 7×24 作业"成为硬要求时，用 **11.6 的演进 1（同产物双进程 / WMS 独立 profile 启动）**——WMS 和 ERP 跑两个进程但共用一个库，既能独立重启，又不引入分布式事务，性价比最高。

### 11.1 必须区分的三类故障

| 故障场景 | 现象 | 对策 |
|---|---|---|
| A. ERP 被拖慢（PC 多人用、大查询/导出） | PDA 接口响应慢、超时 | **资源隔离/舱壁**：WMS 独立连接池+线程池，查询限流与超时，重导出异步化 |
| B. ERP 应用进程挂了 / 后端服务重启 | PDA 连不上后端 | **PDA 离线自治** + 作业写本地；WMS 关键链路不与 ERP 财务写库做同步强绑定；可选"WMS 独立进程"部署 |
| C. 数据库（MySQL）宕机 | 后端整体不可用 | 只能靠 PDA 本地暂存（作业不丢），DB 恢复后同步；WMS 服务侧无法绕开 DB。需配合 DB 备份/可用性保障 |

> 关键认知：C 类（DB 宕）任何服务端都无法作业，唯一兜底是 PDA 本地暂存；A、B 类靠隔离与解耦解决。下面分别设计。

### 11.2 模块化隔离（现在做，为物理拆服务留缝）

**代码结构**：在现有单体内新增独立模块包 `com.erp.wms`，与 purchase/sales/inventory 平级，强约束边界：

- `com.erp.wms.domain`：WMS 自己的聚合（库位库存、波次、作业任务），只访问 `wms_*` 表。
- `com.erp.wms.api`：PC 接口 `/wms/**`、PDA 接口 `/wms/app/**`。
- `com.erp.wms.integration`：**唯一**与 ERP 域（inventory/purchase/sales/finance）交互的地方，通过事件/接口适配，不允许 WMS 业务代码直接写 `inv_* / pur_* / sales_*` 表、不允许直接调用 ERP 的 Controller。
- ERP 域也不直接写 `wms_*` 表。

这样未来物理拆服务时，把 `com.erp.wms` + `wms_*` 表整体搬走即可，业务逻辑零改动。

**数据库归属**：
- WMS 独占 `wms_*` 表；ERP 独占 `inv_* / pur_* / sales_* / fin_*` 表。
- 同一 MySQL 实例（现阶段不引入分布式事务），但跨域写一律走"领域事件 + 本地消息表"，不做跨库强事务（见 11.4）。
- 读侧需要 ERP 数据（如商品档案、采购订单、销售订单）时，WMS 通过接口/只读视图获取，并在本地缓存必要快照。

### 11.3 资源隔离（解决场景 A：ERP 慢不拖垮仓库）

即便在同一进程、同一 MySQL，也要把 WMS 作业链路的资源与 ERP 大查询隔开：

1. **独立数据库连接池（舱壁）**
   - 配置两个 HikariCP 数据源指向同一个库：`erpDataSource`（默认，给 PC/报表/财务用）和 `wmsDataSource`（给 `/wms/app/**` PDA 作业用），各自独立 `maximum-pool-size`。
   - 效果：PC 端一个慢报表占满 ERP 池，也不会耗尽 WMS 池，PDA 仍能拿到连接作业。
   - WMS 池容量小而专（建议按 PDA 并发数评估，如 10–20），配 `connection-timeout` 短（如 3s），快速失败而非长时间排队。

2. **独立 Web 线程池 / 信号量舱壁**
   - `/wms/app/**` 接口用独立的异步线程池或信号量限流，排队长度有限，满了快速返回"系统繁忙请重试"而不是堆积 Tomcat 线程拖死整个进程。
   - PDA 端对 503/超时自动重试（幂等）。

3. **SQL 级保护**
   - 所有查询强制分页、禁止全表扫；为 WMS 高频查询（库位库存按 goods+warehouse+batch+bin、波次明细按 wave、任务按 assignee+status、流水按时间）建联合索引。
   - WMS 作业 SQL 设 `statement_timeout`（或 Hikari 连接初始化时设查询超时），防止偶发慢 SQL 占连接。
   - 库位流水 `wms_bin_stock_log` 按月/按时间分区或定期归档（数据量大时），报表查归档表不碰在线表。

4. **重操作异步化**
   - PC 报表/大导出全部走已有异步导出中心（`sys_export_task_runtime`），不在请求线程里算。
   - 成本计算、批量过账等重活不阻塞 PDA 响应（见 11.4 事件解耦）。

5. **可选：读写分离（后期）**
   - 量大时给 MySQL 挂只读副本，PC 报表/查询走从库，PDA 作业走主库；WMS 作业写主库、库存查询可走从库（接受秒级延迟并在 PDA 标注）。

6. **监控告警**
   - 对 WMS 连接池使用率、线程池排队、PDA 接口 P95 时延、同步队列积压单独埋点告警；WMS 指标与 ERP 分开看，一眼看出是不是仓库链路出问题。

### 11.4 领域事件 + 本地消息表（解决场景 B：ERP 挂了仓库照样转）

这是最关键的设计：**把"仓库物理作业"与"ERP 财务过账"从同步事务解耦为最终一致。**

现状是"上架/出库审核 → 同一事务里调 `InventoryCostService` 写财务库存、生成收付"。如果这一步强绑定，ERP 财务逻辑一挂，仓库就点不了"完成"。改造为：

```
PDA 作业完成（上架 / 拣货完成或复核通过=出库审核）
   │
   ▼
① WMS 本地事务（只用 wmsDataSource，只写 wms_* 表）：
   - 更新 wms_bin_stock 库位实物库存
   - 写 wms_bin_stock_log 流水
   - 作业任务置"已完成"
   - 同时往 outbox 本地消息表 wms_domain_event 插一条待发布事件
     （事件类型、业务单号、负载 JSON、状态=待发布、重试次数、next_retry_time）
   → PDA 立刻收到"成功"，仓库继续下一单。②不阻塞现场。
   │
   ▼
② 事件发布（独立线程/定时任务，与 PDA 请求无关）：
   - 读取 wms_domain_event 待发布记录，调用对应 ERP 应用服务：
     · 上架完成 → InventoryCostService.purchaseInbound（增财务库存、加权成本、生成收货单/应付）
     · 出库审核（拣货完成/复核通过）→ InventoryCostService.salesOutbound（扣财务库存、释放占用、生成发货单）
     · 盘点/报损/移库 → 对应库存服务
   - 成功 → 事件标记"已发布"
   - 失败（ERP 服务异常/SQL 报错）→ 不影响①，按退避策略重试（1m/5m/15m/1h…），记录失败原因
   │
   ▼
③ ERP 恢复后事件自动补齐，财务账最终一致。
```

**为什么用本地消息表而不是 MQ**：项目要求轻量，DB 表 + 定时发布即可达到"生产消费可靠、至少一次"效果；将来上 Redis Stream / Kafka 只需替换发布器，业务不变。事件发布与 WMS 本地事务在**同一个库**写入，天然原子，不需要分布式事务。

**配套机制**：
- **幂等消费**：每个事件有全局唯一 event_id；ERP 侧处理做幂等（同一 event_id 重复投递不重复过账）。
- **死信与人工干预**：超过最大重试次数（如 24h）进死信，后台"事件异常中心"可见，主管可查看原因、手工重试或作废（作废需留痕并触发库位库存反向处理预案）。
- **在途差异可见**：提供"作业已完成、财务未过账"监控看板，明确哪些单物理已入库/出库但账还没记，让老板/财务心里有数，不会误以为账实对不上。
- **对账兜底**：每日定时跑账实对账（`SUM(wms_bin_stock)` vs `inv_batch_stock`），差异告警；事件全部发布后理论一致，差异即故障信号。
- **顺序性**：同一商品/仓库/批次的库存相关事件，按事件产生顺序串行消费（按 key 哈希到串行队列或加悲观锁/乐观锁版本号），避免并发过账导致成本错乱。
- **成本一致性**：移动加权平均的重算必须在 ERP 侧按事件顺序串行处理；WMS 不算成本，只报"发生了什么、数量多少"。

> 注意：销售订单"生成即占用库存"、波次"锁批次"等锁定逻辑，在 WMS 分配波次时仍需在线与 ERP 库存校验/锁定（因为可售量是 ERP 口径）。这一步属于"计划"，不是"现场作业"，ERP 不可用时可以暂停新波次下放，但**已下放的波次拣货不受影响**——这是可接受的：仓库继续发已经排好的车，新单等恢复再排。

### 11.5 PDA 离线自治（解决场景 B/C：断网/后端不可用仍能作业）

复用并增强 TMS 司机 APP 已验证的离线架构（sqflite 本地库 + pending_actions 队列 + connectivity 监听 + SyncService 网络恢复自动同步 + 顶部离线横幅）。WMS 作业对可用性要求更高，需额外做到：

1. **任务与基线数据预下载缓存**
   - PDA 登录/联网时，拉取本人的待作业任务（收货/上架/波次拣货/复核/补货/盘点）及所需明细、相关**库位库存快照**、商品/库位/批次字典，写入本地 SQLite。
   - 这样断网时拣货员仍能看到"去哪个库位、拿什么、拿多少"，收货员能看到采购订单应收。
   - 首页"待作业数"在离线时仍可显示缓存值（标注"离线数据，HH:mm 同步"）。

2. **离线可执行的作业**
   - 收货（含多批次、数量、生产日期）、上架确认、拣货确认/缺货标记/跳过、复核扫描、装车确认、盘点录入、移库、库存查询（查缓存），全部可离线录入本地暂存。
   - 扫码校验在本地用缓存数据做（库位码/商品码/批次匹配），错了照样红屏震动；但库存不足类校验在离线时降级为"提示+允许继续并标记待服务端复核"。

3. **本地暂存与同步协议**
   - 每条暂存作业带：全局唯一 `client_action_id`（UUID，防重）、客户端时间戳、操作人、设备号、业务单号、负载。
   - 网络恢复后 SyncService 按优先级同步（出库审核=拣货完成/复核通过、上架完成 = 高，因为要触发过账；拣货录入 = 中；照片/定位 = 低），逐条提交 `/wms/app/sync`。
   - 服务端按 `client_action_id` 幂等处理，逐条返回成功/失败/冲突；PDA 失败项进入"待处理"由作业员/主管处理，不丢数据。
   - 顶部横幅明示：离线（红）/待同步 N 条（橙）/同步中（蓝）/同步失败需处理（红，可点进重试）。

4. **冲突与账实保护**
   - 库位库存用**乐观锁版本号（version）**：PDA 提交时带上它读取快照时的版本；服务端版本已变（别人也动了同库位同批次）→ 返回冲突，不静默覆盖，生成异常让主管裁决（实测差异后调整）。
   - 离线期间同一库位的多次作业在本地串行排队，联网按顺序提交。
   - 最终以服务端对账为准；PDA 不自行算成本、不自行改可用量，只报作业事实。

5. **必须在线的动作**（明确边界，不强行离线）
   - 财务过账/审核、波次创建与批次分配锁定、影响成本的动作、跨仓调拨的出库审核——这些保持在线；离线时按钮置灰并提示"需联网"，但**不影响已经在手上的现场作业**。

6. **本地数据安全**
   - 本地敏感数据（供应商价格、成本）不缓存或加密缓存；作业数据保留 N 天（参数）；退出登录清理；设备绑定/工号登录。

### 11.6 部署形态演进

| 阶段 | 形态 | 适用 | 说明 |
|---|---|---|---|
| 现阶段（推荐） | **单进程 + 资源隔离 + PDA 离线** | 中小规模、单仓 | 同一 Spring Boot 内独立 WMS 包/连接池/线程池/outbox；改动小、运维简单，已能解决 A 类、大幅缓解 B 类 |
| 演进 1 | **同产物双进程**（ERP profile / WMS profile） | WMS 负载变大或要独立重启 | 同一套 jar，用不同 Spring profile 启动两个进程：ERP 进程只加载非 WMS 组件，WMS 进程只加载 `com.erp.wms` + 必要适配；可分别重启（重启 ERP 不影响仓库）。因代码已按 11.2 划清边界，此步主要是配置与组件扫描 |
| 演进 2 | **WMS 独立服务 + 独立库** | 多仓、高并发、独立伸缩 | WMS 拆成独立服务/独立 schema，与 ERP 通过事件/接口集成；PDA 直连 WMS 服务。因 11.2 的边界，业务代码基本不动 |

> 不建议现在就上微服务/独立库：会引入分布式事务、数据同步、运维复杂度，与"轻量底座"不符，且当前规模不需要。先用模块化单体验证业务，把接缝留好，拆分是水到渠成的事。

### 11.7 高可用运维配套

- **进程守护**：docker-compose `restart: always`（已有）；WMS 独立进程形态时配健康检查，崩溃自动重启。
- **数据库备份**：MySQL 定时备份（与现有 H2/MySQL 备份策略一致）；WMS 上线前确认备份与恢复演练。
- **灰度开关**：按仓库 `location_managed`/`wms_enabled` 逐个仓启用，出问题可对某仓关闭 WMS 退回原流程（D6 决策）。
- **可观测**：操作日志（`sys_operation_log_runtime`）+ WMS 作业全链路留痕 + 事件发布/重试/死信日志 + PDA 崩溃日志上传。
- **性能基线**：上线前压测 PDA 关键接口（收货提交、拣货确认、装车），明确单进程支撑的 PDA 并发数，据此决定是否进入演进 1。

## 13. 接口规划（约定）

- PC 后台：`/api/wms/**`（基础资料、策略、波次、任务、监控、报表）。
- PDA：`/api/wms/app/**`（对称 TMS 的 `/api/tms/app/**`）：
  - 登录 `/wms/app/login`、参数 `/wms/app/params`、首页概览 `/wms/app/home/overview`
  - 入库 `/wms/app/inbound/*`（任务列表、收货提交、标签打印、上架推荐、上架确认）
  - 出库 `/wms/app/wave/*`、`/wms/app/pick/*`、`/wms/app/replenish/*`（含 urgent 加急补货）、`/wms/app/check/*`、`/wms/app/loading/*`
  - 库内 `/wms/app/stocktake/*`（动盘/全盘/指定盘）、`/wms/app/move/*`、`/wms/app/damage/*`、`/wms/app/stock/query`
  - 异常 `/wms/app/exception/*`（上报、挂起、加急、取消下放、处理）、图片上传 `/wms/app/upload/image`
  - 离线同步 `/wms/app/sync/pull`（拉取任务/基线快照）、`/wms/app/sync/push`（提交离线作业，按 client_action_id 幂等）、`/wms/app/sync/status`
- 全部 POST、`Authorization: Bearer <token>`、统一 `ApiResponse{code,message,data}`、写操作入 `sys_operation_log_runtime`。
- 交接/改派（以销售订单号关联）：
  - 装车：`/wms/app/loading/confirm`（仅出库完成可装，回写订单/出库单/发货单/TMS 装车任务状态）；
  - 未发车改派：后台 `/tms/dispatch/assign`（改司机，复用 TMS）、A→B 扫码转交 `/wms/app/dispatch/transfer`（生成转交码、B 扫码确认，同客户退单自动跟随转移，只改源单司机字段、不生新单）；
  - 配送中改派返仓签收：`/wms/app/reschedule/pending`、`/wms/app/reschedule/receive`（扫 GPRC/发货单/箱码、核对、记集货位、差异登记），签收后回调 TMS `/tms/reschedule-return/{id}/check`；重新指派走 TMS `/tms/reschedule-return/{id}/redispatch`。
- 对接 TMS：WMS 出库审核/装车完成通过事件或接口同步 TMS，更新装车任务单与配送单状态；WMS↔TMS 以销售订单号 `source_order_no` 为关联键。

## 14. 分阶段实施与排期（建议）

| 阶段 | 周期建议 | 交付范围 | 验收核心 |
|---|---|---|---|
| **P0 底座** | 2-3 周 | 库位/库区/容器模型与管理、库位库存表、条码生成打印、PDA 框架（登录/扫码/离线/反馈/参数拉取）、库存查询、WMS 角色权限 | 库位可建可打印可扫，PDA 能扫码查货 |
| **P1 入库闭环** | 3-4 周 | 到货预约、PDA 收货（部分收/多批次/盲收/超收/无单收）、上架策略与 PDA 上架、退货/拒收/其他入库、对接采购入库审核、入库报表 | 采购到上架账实一致，应付链路不破坏 |
| **P2 出库闭环** | 4-5 周 | 波次（手工+自动）、按单拣+汇总拣两种模式、FEFO/FIFO 批次分配、路径指引与防错、复核（复核通过即生成并审核出库单扣库存）、打包箱码、补货（被动+主动+加急）、装车对接 TMS（以销售订单号关联、未发车改派 A→B）、出库报表 | 一单一出库、拣货/复核完成即扣库存准确，错拣漏拣下降 |
| **P3 库内作业** | 3-4 周 | 盘点（动盘/全盘/指定盘/抽盘/循环盘、明暗盘、复盘）、移库、组合拆分、报损、效期预警、冻结、异常中心（取消订单/取消下放/订单加急/异常挂起）、配送中改派返仓 PDA 签收、库内报表 | 盘点/移库/报损账实一致，异常闭环 |
| **P4 策略与绩效** | 2-3 周 | 边拣边分、分区接力、越库、波次/上架策略增强、作业进度看板、人员绩效报表与导出 | 多拣货模式可配、绩效数据可查可导 |
| **P5 增强（后期）** | 按需 | 质检模块、序列号、语音拣货、DPS、AGV 对接 | 按客户成熟度选配 |

> P0–P2 为首个可交付里程碑（约 9–12 周），实现"入库+出库+库位"主闭环；P3 起迭代。每阶段保证"启用库位管理的仓库走新流程，未启用的走原流程"，可灰度、可回退。每个阶段含：页面原型→接口契约→数据库迁移→开发→测试（正常/异常/权限/状态流转/库存财务联动/操作日志）。

## 15. 风险与对策

| 风险 | 对策 |
|---|---|
| PDA 扫码在低端设备/弱网不稳定 | 硬件扫描键为主、摄像头为辅；弱离线队列；真机充分回归；关键动作幂等 |
| 中老年作业员不会用/抵触 | 极简一屏一任务、大字号大按钮、语音/震动反馈、新员工引导、上线前培训与试点仓 |
| 库位库存与 ERP 库存对不上 | 同事务维护；账实对账报表每日核对；任何调整留痕；灰度先在一个仓跑顺再推广 |
| 流程过重拖慢现场 | 所有控制点参数可关；小仓库可关推荐/复核/预约，走最简流程 |
| 批次/成本被 WMS 破坏 | WMS 不碰金额，库存增减只走 InventoryCostService；上线前用 smoke test 回归采购/销售/成本链路（注意 smoke 会删单据，先备份 H2） |
| 与 TMS 装车/改派边界不清 | 明确：出库单在拣货/复核完成即审核扣库存；仓管装车只做实物确认、不扣账；WMS/TMS 以销售订单号关联，未发车改派直接改源单司机（同客户退单跟随），配送中改派返仓回仓 PDA 签收记集货位、不入库不动账，调度再重派；接口契约阶段对齐 |
| 绩效数据引发争议 | 只做客观数据输出，标准件/小时基准可配；差异数据可钻取申诉；不自动算薪 |
| ERP 高负载拖慢仓库 / ERP 宕机导致无法作业 | 第 11 章：WMS 独立连接池+线程池舱壁、重导出异步、领域事件+本地消息表解耦财务过账、PDA 离线自治、事件失败重试与对账、按仓库灰度开关；初期单进程隔离，必要时演进为 WMS 独立进程/服务 |
| 离线并发导致库位库存冲突 | 库位库存乐观锁版本号；离线提交冲突不静默覆盖，生成异常由主管裁决；最终以服务端对账为准 |
| 事件积压/重复消费导致成本错乱 | 事件按商品+仓库+批次串行消费；消费端幂等；移动加权平均只在 ERP 侧按序重算；每日账实对账 |

## 16. 待评审问题清单

1. 波次"自动组波时点"与"聚合维度"默认值是否符合贵司实际配送节奏？线路/片区数据是否已在客户资料完整维护？
2. 首版（P0–P2）只做"按单拣 + 汇总拣"是否足够？边拣边分/分区接力是否要提前到 P2？
3. 补货的"拣货位/存储位"双层布局在贵司仓库是否普遍？是否有仓库是平面堆放无货架（需适配无库位/区库位模式）？
4. 出库复核模式（强制逐件/抽核/免复核）默认取哪种？免复核即"拣货完成即审核扣库存"，需确认现场是否接受此节奏。
5. 调度派单默认采用"波次预分配时指派"还是"出库完成后指派"（参数 `WMS_DISPATCH_TIMING`）？预分配时司机即可见任务但需出库后才能装车。
6. 集货位是否需要作为正式库位（占用/容量/释放管理），还是仅作发货单上的位置标记字段即可？
7. 全盘是否需要冻结全仓作业（`WMS_COUNT_FREEZE_WHOLE`）？动盘是否允许边作业边盘？
8. 计件绩效的口径：按"件数"还是"行数"还是"件数+重量/体积"？是否需要按商品设不同计件权重？
9. 打印硬件：现场用什么品牌型号 PDA 和蓝牙打印机？是否需要我们适配指定 SDK？是否需要蓝牙秤（默认按档案核算重量）？
10. 多仓库是否一次性全部上线，还是先选一个样板仓试点？
11. 商品条码完整度如何？是否存在大量无条码商品（需提前补打/贴码）？
12. 盘点频率：ABC 循环盘天数默认值（A30/B90/C180）是否合适？全盘通常安排在什么时间？
13. 越库（Cross-docking）本期是否有真实场景，还是列为后期？
14. **技术架构**：当前单进程 + 资源隔离 + PDA 离线自治的方案是否认可？还是一开始就希望 WMS 独立进程/独立部署（会增加运维与数据同步成本）？
15. **ERP 宕机容忍度**：现场对"作业已完成、财务账延后过账"的最长可接受时间是多少（分钟级/小时级/半天）？这决定事件重试与告警策略。
16. **离线时长**：仓库 Wi-Fi 死角/断网一般持续多久？PDA 本地缓存需支持多大离线作业量（多少单/多少行）？
17. **服务器资源**：WMS 独立连接池/线程池、独立进程都要占内存，当前生产服务器配置（CPU/内存）是否足够？是否需要单独的 WMS 服务器？
18. **数据库**：现生产已用 MySQL 8（docker-compose），WMS 直接复用该实例是否可行？还是要求物理独立库？
