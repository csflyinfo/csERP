## 1. 文档目的与前提

### 1.1 文档目的

本方案定义在三独立法人主体架构下，B2B 商城平台的完整系统设计。重点覆盖：**业务流程分解、基础资料如何跨系统管理、费用如何计算与分摊、结算如何闭环、自营 ERP 如何对接、仓配 WMS 如何对接，以及入驻商自配不入下游系统如何处理**。

### 1.2 三主体定义

| 主体 | 法人 | 拥有系统 | 核心业务 |
|------|------|---------|----------|
| **平台主体** | 商城运营公司 | **B2B 商城** + 结算中心 + 来源申报 | 商品展示、交易撮合、统一收款、多方法结算、税务来源申报 |
| **自营主体** | 经销商 | **ERP**（进销存+财务） | 自营品采购、进销存管理、成本核算、自营收入记账 |
| **仓配主体** | 仓储物流公司 | **WMS** + PDA | 多货主入库、仓储管理、订单履约（拣货/复核/出库）、配送管理 |

### 1.3 核心设计原则

| # | 原则 | 说明 |
|---|------|------|
| **P1** | **同一法人内的数据才共享** | 三主体的系统拥有独立数据库。数据跨主体流转必须通过明确的 API 契约 |
| **P2** | **平台统一收款** | 所有买家支付统一进入平台主体的微信/支付宝商户号 |
| **P3** | **谁收款谁结算** | 平台对买家收款 → 平台对各入驻商/自营主体/仓配主体统一结算 |
| **P4** | **谁管仓谁履约** | 仓配主体负责所有统仓商品的出入库和订单履约，不管是自营品的还是入驻商的 |
| **P5** | **谁卖货谁记账** | 自营主体在 ERP 中记自营品的进销存和收入；入驻商在自己的系统记账；ERP 不存入驻商数据 |
| **P6** | **来源溯源在 B2B 闭环** | 下单时 B2B 标记每行交易的实际货主（来源主体），结算和税务申报均以此为准 |

### 1.4 一个核心场景帮助理解全文

> 买家小王在 B2B 商城下单：
> - 2 箱可乐（自营品，货主是自营主体，仓配方是仓配主体）
> - 3 箱矿泉水（入驻商老张的货，放在仓配主体的仓库，FBP 代发）
> - 5 箱方便面（入驻商老李的货，老李自己发货，SOP 自配）
>
> 小王用微信支付了 500 元，钱进入了平台主体的商户号。
>
> — 这 500 元到底怎么分？订单怎么拆？库存怎么扣？发票谁开？
> — 可乐的部分，自营 ERP 怎么记账？矿泉水的仓储费谁出？方便面老李怎么知道该发货了？
>
> 本方案回答的就是上面这一系列问题。

## 2. 三主体的法律关系与职责边界

### 2.1 法律关系图

```
                    ┌─────────────────────────┐
                    │       平台主体            │
                    │  （商城运营公司）          │
                    │                          │
                    │  拥有：B2B商城 + 结算中心  │
                    │  职责：展示/下单/收款/结算  │
                    └──────┬────────┬──────────┘
                           │        │
              服务协议      │        │      服务协议
              +结算单       │        │      +结算单
                           ▼        ▼
         ┌──────────────────┐  ┌──────────────────┐
         │    自营主体        │  │    仓配主体        │
         │  （经销商）        │  │  （仓储物流公司）    │
         │                   │  │                   │
         │  拥有：ERP         │  │  拥有：WMS + PDA   │
         │  职责：进销存/财务  │  │  职责：仓储/履约    │
         └──────────────────┘  └──────┬────────────┘
                                      │
                         仓储服务协议   │
                                      ▼
                              ┌──────────────────┐
                              │    FBP 入驻商     │
                              │  （老张的货在此）   │
                              └──────────────────┘

     ┌──────────────────┐
     │    SOP 入驻商     │    ← 不入仓配主体仓库
     │  （老李自己发货）   │       不入自营 ERP
     └──────────────────┘       仅与 B2B 交互
```

### 2.2 三主体之间的合同关系

| 合同 | 甲方 | 乙方 | 核心条款 |
|------|------|------|----------|
| **平台入驻协议** | 自营主体 | 平台主体 | 自营品上架 B2B、平台代收货款、平台收取佣金/服务费、按周期结算 |
| **平台入驻协议** | FBP 入驻商 | 平台主体 | FBP 品上架 B2B、平台代收货款、仓配费从货款中扣除后结算 |
| **平台入驻协议** | SOP 入驻商 | 平台主体 | SOP 品上架 B2B、平台代收货款、平台抽佣后结算、入驻商自行发货 |
| **仓储服务协议** | 仓配主体 | FBP 入驻商（或平台代签） | 入库标准、仓储费率、出库操作费、配送费、损耗责任 |
| **仓储服务协议** | 仓配主体 | 自营主体（或平台代签） | 自营品入库/出库、仓储费率、配送费 |
| **平台-仓配服务协议** | 平台主体 | 仓配主体 | 费用数据同步、履约状态回传、结算口径、对账 |

### 3.2 数据流向速览

| 数据 | 出发 | 到达 | 时机 |
|------|------|------|------|
| 自营品订单 | B2B → 自营 ERP | 自营 ERP | 买家支付完成后 |
| 自营品出库指令 | 自营 ERP → WMS | 仓配 WMS | ERP 审核订单后 |
| FBP 订单 | B2B → WMS | 仓配 WMS | 买家支付完成后 |
| 出库结果 + 费用 | WMS → B2B | B2B 结算中心 | 出库扫描完成 |
| SOP 订单通知 | B2B → 入驻商 | SOP 入驻商 | 买家支付完成后 |
| SOP 物流回传 | SOP 入驻商 → B2B | B2B | 入驻商发货后 |
| 商品 + 库存 | 自营 ERP → B2B | B2B | 定时同步（如每 5 分钟） |
| FBP 库存 | WMS → B2B | B2B | 入库/出库后实时 |
| 结算单 | B2B → 各主体 | 自营/FBP/SOP/仓配 | 按周期生成 |
| 来源申报数据 | B2B → 税务系统 | 税务系统 | 按日/月 |

## 4. 基础资料管理

基础资料是三系统协同的"共同语言"。由于三主体独立，基础资料的管理必须明确一个权威来源。

### 4.1 基础资料归属矩阵

| 资料类型 | 权威来源 | 说明 | 同步给谁 |
|----------|----------|------|----------|
| **店铺/商户** | **B2B** | 所有入驻商（含自营主体作为特殊商户）的信息：营业执照、纳税人资质、银行账户 | WMS（仅 owner_id+名称） |
| **商品 SPU/SKU** | **B2B**（展示层）/ **自营 ERP**（自营品主数据）/ **入驻商**（FBP/SOP品） | 分两层：① B2B 存展示信息（标题/图/描述）；② 各货主在自己的系统中存完整商品档案 | WMS（SKU+条码+规格，不入价格） |
| **仓库** | **B2B** | 统仓（仓配主体管理）的仓库列表；自配入驻商仓库无需在此管理 | WMS（库位级数据） |
| **合同/费率** | **B2B** | ① 平台佣金费率（按入驻商）；② 仓配服务费率（按入驻商+商品类目）；③ 结算周期 | 结算时使用 |
| **税收分类编码** | **自营 ERP**（自营品）/ **B2B**（FBP/SOP品由入驻商在商户中心填写） | 开票时必需 | 税务申报时使用 |
| **往来单位** | **自营 ERP** | 自营品的供应商、客户在 ERP 内管理；B2B 结算主体映射 | 不对外同步 |
| **银行账户** | **B2B** | 各主体的结算收款账户 | 结算打款使用 |

### 4.2 关键基础资料的详细设计

#### 4.2.1 商品主数据 —— 分三层管理

```
第一层：B2B 商品目录（展示层）
  ┌─────────────────────────────────────────────────┐
  │ 商品ID: P001                                     │
  │ SPU名称: 可乐 330ml                               │
  │ 商户: 自营主体（merchant_id = SELF）               │
  │ 售价: ¥3.50（平台统一定价或商户自主定价）            │
  │ 图片、描述、类目                                  │
  │ 履约方式: fulfillment_type = SELF                 │
  │ 来源主体: source_entity = 自营主体                  │
  │ 来源主体纳税人识别号: source_entity_tax_id = XXX    │
  └─────────────────────────────────────────────────┘
           │ B2B侧只存展示信息
           │ 源头数据在各自系统
           ▼
第二层：货主自有系统（源头层）
  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐
  │ 自营ERP      │ │ 入驻商A系统  │ │ 入驻商B系统  │
  │ SKU: P001   │ │ SKU: P002   │ │ SKU: P003   │
  │ 成本价: ¥2.0│ │ 成本价: ¥1.5 │ │ 成本价: ¥2.5 │
  │ 税收编码: XX │ │ 税收编码: XX │ │ 税收编码: XX │
  │ 税率: 13%   │ │ 税率: 13%   │ │ 税率: 9%    │
  └─────────────┘ └─────────────┘ └─────────────┘

第三层：WMS 实物层
  ┌─────────────────────────────────────────────────┐
  │ SKU: P001, owner_id: SELF                        │
  │ SKU: P002, owner_id: M001 (入驻商A)               │
  │ 条码、规格、重量、体积                             │
  │ 不含任何价格/税率信息                             │
  └─────────────────────────────────────────────────┘
```

**规则**：
- 自营品：B2B 的商品数据由自营 ERP 通过 `商品同步接口` 推送。ERP 是主数据源头
- FBP/SOP 品：入驻商在 B2B 商户中心手动录入或 Excel 导入。B2B 是这些品的展示层主数据
- WMS 只接收 SKU + 基础物理属性（重量/体积/条码），不接收价格

#### 4.2.2 入驻商管理 —— 商户入驻流程

```
入驻商注册
  │
  ├── 步骤1: 主体信息登记
  │    ├── 营业执照上传 → OCR 自动校验（电商法第27条要求）
  │    ├── 纳税人资质（一般纳税人/小规模）
  │    ├── 纳税人识别号（税号）
  │    └── 对公银行账户信息
  │
  ├── 步骤2: 选择合作模式
  │    ├── □ FBP（统仓统配）→ 需签约仓储服务协议
  │    ├── □ SOP（自行配送）→ 仅需平台入驻协议
  │    └── □ 两者都要（部分品 FBP，部分品 SOP）
  │
  ├── 步骤3: 签约
  │    ├── 平台入驻协议（必签）→ 结算周期/佣金率/开票义务
  │    └── 仓储服务协议（FBP必签）→ 仓储费率/配送费率/操作费/损耗
  │
  ├── 步骤4: 费率配置（B2B后台录入）
  │    ├── 平台佣金率: 3%（范例）
  │    ├── 仓储费: ¥0.5/件/天
  │    ├── 配送费: ¥5/件
  │    ├── 操作费: ¥2/件（拣货+复核+打包）
  │    └── 结算周期: 月结 / 半月结 / 周结
  │
  └── 步骤5: 上架商品
       ├── FBP品 → B2B商户中心录入 → 入驻商送货到仓配仓库 → WMS入库
       └── SOP品 → B2B商户中心录入 → 自行管理库存
```

#### 4.2.3 合同费率配置表结构（B2B 侧）

```
合同费率主表 b2b_contract_rate
├── contract_id        合同ID
├── merchant_id        入驻商ID
├── contract_type      合同类型: PLATFORM / WAREHOUSE
├── rate_type          费率类型: COMMISSION(佣金) / STORAGE(仓储) / DELIVERY(配送) / OPERATION(操作)
├── rate_value         费率值
├── rate_unit          单位: PERCENT(%) / FIXED_PER_UNIT(元/件) / FIXED_PER_KG(元/kg) / FIXED_PER_DAY(元/天)
├── category_id        适用商品类目（空=全部）
├── effective_date     生效日期
└── expiry_date        失效日期
```

## 5. 商品与库存管理

### 5.1 库存视图总览

三主体架构下，库存数据分散在三个系统中，各有职责：

```
┌──────────────────────────────────────────────────────┐
│                   可售库存（买家看到）                    │
│                   权威来源：B2B                          │
│                                                       │
│  自营品可售 = 从自营ERP同步                              │
│  FBP品可售 = 从WMS同步(按owner_id)                      │
│  SOP品可售 = 入驻商自行维护                              │
└──────────────┬──────────────┬──────────────┘
               │              │
               ▼              ▼
┌────────────────────┐  ┌────────────────────┐
│   自营ERP 库存       │  │   WMS 实物库存       │
│   权威来源：ERP      │  │   权威来源：WMS      │
│                    │  │                    │
│  自有库存数量+成本   │  │  库位×SKU×批次      │
│  可用量=实物-占用    │  │  ×owner_id×数量    │
│                    │  │                    │
│  成本：移动加权平均   │  │  成本：不存         │
└────────────────────┘  └────────────────────┘
```

### 5.2 自营品的库存同步链路

```
自营 ERP
  │ 库存变动事件（采购入库/销售出库/盘点调整）
  ▼
  计算可用量 = WMS实物库存 - 订单占用
  │
  ▼
  推送至 B2B 库存同步接口
  │ POST /api/v1/inventory/sync
  │ { sku: "P001", available: 120, source: "SELF" }
  ▼
B2B 更新可售库存缓存
  │
  ▼
  买家端商品详情页显示 "库存：120件"
```

### 5.3 FBP 品的入库流程

```
入驻商送货到仓配主体仓库
  │
  ▼
WMS 收货
  ├── 创建 ASN（预到货通知单）
  ├── 质检（按合同标准）
  ├── 扫码入库
  │     ├── owner_id = M001（入驻商A）
  │     ├── sku = P002
  │     ├── 批次号 = B20260721
  │     ├── 数量 = 500
  │     └── 库位 = A-01-03
  │
  ├── WMS 库存更新: owner_id=M001, sku=P002, 可用量+500
  │
  └── 推送到 B2B
       │ POST /api/v1/inventory/sync
       │ { sku: "P002", available: 500, owner_id: "M001" }
       ▼
       B2B 更新 FBP 品可售库存
```

## 6. 三种履约模式的完整业务流程

### 6.1 自营模式（SELF）—— 完整 8 阶段流程

```
阶段1: 下单与支付
  ┌──────────────────────────────────────────────────────┐
  │ 买家在 B2B 下单(自营品) → B2B 库存校验（扣可售缓存）     │
  │ → 微信支付 → 钱入平台商户号                            │
  │ → B2B 生成订单：order_id=O001                         │
  │   每行标记 source_entity=自营主体                       │
  └──────────┬───────────────────────────────────────────┘
             ▼
阶段2: 订单推送到自营ERP
  ┌──────────────────────────────────────────────────────┐
  │ B2B → POST /api/v1/order/sync → 自营ERP              │
  │   推送完整订单数据（含 source_entity 标记）             │
  │ → 自营ERP 创建销售订单                                 │
  │ → 自营ERP 锁定库存（自有库存可用量扣减）                 │
  │ → 回传 B2B: order_status=received                   │
  └──────────┬───────────────────────────────────────────┘
             ▼
阶段3: ERP 审核 → WMS 出库指令
  ┌──────────────────────────────────────────────────────┐
  │ 自营ERP 审核订单（信用/库存/价格校验）                   │
  │ → 生成发货单 → POST /api/v1/delivery/create → WMS     │
  │   发货单上有: delivery_id, order_id, sku列表, 数量      │
  └──────────┬───────────────────────────────────────────┘
             ▼
阶段4: WMS 履约
  ┌──────────────────────────────────────────────────────┐
  │ WMS 接收发货单 → 生成波次 → 分配库位                   │
  │ → PDA 拣货 → 复核台扫描 → 打包 → 称重 → 出库扫描      │
  │ → 扣减 WMS 实物库存                                   │
  └──────────┬───────────────────────────────────────────┘
             ▼
阶段5: WMS 回传履约结果
  ┌──────────────────────────────────────────────────────┐
  │ WMS → 自营ERP（履约完成通知）                          │
  │   出库时间、物流单号、实发数量、包裹重量                │
  │ → 自营ERP 确认出库：减少实物库存、触发成本核算           │
  └──────────┬───────────────────────────────────────────┘
             ▼
阶段6: 自营ERP 成本核算
  ┌──────────────────────────────────────────────────────┐
  │ 移动加权平均计算出库成本                               │
  │ → 生成会计分录：                                       │
  │    借：主营业务成本-自营    ¥2.0×2 = ¥4.0              │
  │    贷：库存商品             ¥2.0×2 = ¥4.0              │
  │    借：应收账款-平台主体     ¥3.5×2 = ¥7.0             │
  │    贷：主营业务收入-自营     ¥6.19（不含税）            │
  │    贷：应交税费-销项税       ¥0.81（13%）               │
  └──────────┬───────────────────────────────────────────┘
             ▼
阶段7: 自营ERP → B2B 回传状态
  ┌──────────────────────────────────────────────────────┐
  │ 自营ERP → POST /api/v1/order/status → B2B            │
  │   状态: shipped，物流单号: SF1234567890                │
  │ → B2B 更新买家端 "已发货"                             │
  └──────────┬───────────────────────────────────────────┘
             ▼
阶段8: B2B 结算给自营主体
  ┌──────────────────────────────────────────────────────┐
  │ 月末结算周期：                                        │
  │   B2B 汇总自营品销售金额 = ¥7.0                        │
  │   - 平台佣金（1%）= ¥0.07                             │
  │   - 仓配费（仓储+配送+操作）= 待仓配对账确认            │
  │   = 打款给自营主体对公账户                              │
  │                                                       │
  │   自营ERP 收到结算单后：                                │
  │    借：银行存款               ¥6.93（净额）             │
  │    借：销售费用-平台佣金       ¥0.07                    │
  │    借：销售费用-仓储服务费     ¥X.XX                    │
  │    贷：应收账款-平台主体        ¥7.0                    │
  └──────────────────────────────────────────────────────┘
```

### 6.2 FBP 代发模式 —— 完整 7 阶段流程

```
阶段1: 下单与支付（同自营）
  ┌──────────────────────────────────────────────────────┐
  │ 买家在 B2B 下单(FBP品) → 库存校验（查 WMS 的 owner_id=M001）│
  │ → 微信支付 → 钱入平台商户号                            │
  │ → B2B 生成订单                                        │
  │   每行标记 source_entity=入驻商M001                    │
  │   此订单不进自营ERP！                                  │
  └──────────┬───────────────────────────────────────────┘
             ▼
阶段2: B2B 直接推送 WMS
  ┌──────────────────────────────────────────────────────┐
  │ 关键区别：FBP订单不经过自营ERP，B2B直接推WMS！          │
  │                                                       │
  │ B2B → POST /api/v1/delivery/create → WMS（仓配主体）   │
  │   { delivery_id, order_id: O002,                      │
  │     items: [{ sku: P002, qty: 3, owner_id: M001 }],  │
  │     source_entity: M001,                              │
  │     source_entity_tax_id: "纳税人识别号" }             │
  │                                                       │
  │ → WMS 创建发货单（owner_id=M001 的库存）               │
  └──────────┬───────────────────────────────────────────┘
             ▼
阶段3: WMS 履约（同自营）
  ┌──────────────────────────────────────────────────────┐
  │ 波次 → 拣货(按owner_id分配) → 复核 → 打包 → 出库       │
  │ → WMS 扣减 owner_id=M001 的库存                       │
  │                                                       │
  │ WMS 费用测算（出库时自动计算）：                         │
  │   仓储费: 3件 × ¥0.5/天 × 存储天数                     │
  │   配送费: 1单 × ¥5                                    │
  │   操作费: 3件 × ¥2 = ¥6                              │
  └──────────┬───────────────────────────────────────────┘
             ▼
阶段4: WMS → B2B 回传履约结果 + 费用
  ┌──────────────────────────────────────────────────────┐
  │ WMS → POST /api/v1/delivery/complete → B2B           │
  │   { delivery_id, order_id: O002,                     │
  │     shipped_at, tracking_no,                         │
  │     fee: { storage: 1.5, delivery: 5, operation: 6 } │
  │     actual_items: [{ sku: P002, qty: 3 }] }          │
  │                                                       │
  │ → B2B 更新订单状态 + 记录费用数据                       │
  │ → B2B 更新买家端 "已发货"                             │
  └──────────┬───────────────────────────────────────────┘
             ▼
阶段5: 通知入驻商开票
  ┌──────────────────────────────────────────────────────┐
  │ B2B → 入驻商M001（商户中心站内信 + 可选API回调）       │
  │   通知: 订单O002已发货，买家收件信息，交易金额           │
  │   → 入驻商M001 开具发票给买家                          │
  │   → 入驻商在商户中心上传发票或标记"已开票"              │
  └──────────┬───────────────────────────────────────────┘
             ▼
阶段6: B2B 结算给入驻商
  ┌──────────────────────────────────────────────────────┐
  │ 月末结算周期:                                         │
  │   买家支付: ¥3.5 × 3 = ¥10.5（全部进入平台商户号）     │
  │   - 仓配费: ¥1.5 + ¥5 + ¥6 = ¥12.5（仓配主体收取）    │
  │   - 平台佣金: ¥10.5 × 3% = ¥0.32                     │
  │   = 入驻商M001净结算 = ¥10.5 - ¥12.5 - ¥0.32 = -¥2.32│
  │                                                       │
  │   若净结算为负 → 入驻商需补缴差额给平台                  │
  │   若净结算为正 → 平台打款给入驻商                       │
  └──────────┬───────────────────────────────────────────┘
             ▼
阶段7: B2B 与仓配主体结算
  ┌──────────────────────────────────────────────────────┐
  │ B2B 汇总本期所有FBP出库的仓配费                        │
  │ → 生成仓配服务费对账单 → 仓配主体确认                  │
  │ → B2B 打款给仓配主体（仓配服务费总额）                  │
  └──────────────────────────────────────────────────────┘
```

**FBP 关键设计要点**：

| 要点 | 说明 |
|------|------|
| 为何不进自营ERP | 入驻商的货不属于自营主体，其库存/订单/收入与自营无关。自营ERP存入驻商数据=法人数据混同 |
| 为何B2B直接推WMS | 仓配主体对自营品和FBP品的履约流程是一样的（拣货→复核→出库），WMS只认owner_id，不需要ERP做中间人 |
| 费用为何在WMS测算 | 出库时的件数/重量/存储天数是WMS实测的，不是B2B估算的。WMS测算后回传B2B，B2B据此结算 |
| 入驻商开票 | FBP品来源主体是入驻商→入驻商开票给买家。平台不介入FBP品的发票流 |

```
  └──────────┬───────────────────────────────────────────┘

阶段2: 通知入驻商
  ┌──────────────────────────────────────────────────────┐

阶段3: 入驻商回传物流
  ┌──────────────────────────────────────────────────────┐
  │ 入驻商M002 → B2B（商户中心 或 API）                    │
  │   物流单号: YT9876543210                              │
  │   快递公司: 圆通                                       │
  │                                                       │

阶段4: 入驻商开票
  ┌──────────────────────────────────────────────────────┐
  │ 入驻商M002 开具发票给买家（SOP品来源主体=入驻商）       │

阶段5: B2B 结算给入驻商
  ┌──────────────────────────────────────────────────────┐
```

**SOP 关键设计要点**：

| 要点 | 说明 |
|------|------|
| 不入任何下游系统 | SOP 订单仅在 B2B 内流转。自营 ERP 和仓配 WMS 都不感知 SOP 订单 |

| 结算在B2B | 买家付款已进平台商户号，平台扣除佣金后打款给入驻商 |

## 7. 订单路由与拆分规则

### 7.1 统一购物车拆分规则

买家一次下单可能包含多种履约方式的商品。B2B 必须在生成订单时就做好拆分。

```
购物车内容:
  SKU-A (自营品, fulfillment_type=SELF)
  SKU-B (FBP品, fulfillment_type=FBP, merchant_id=M001)
  SKU-C (FBP品, fulfillment_type=FBP, merchant_id=M002)
  SKU-D (SOP品, fulfillment_type=SOP, merchant_id=M003)
  SKU-E (SOP品, fulfillment_type=SOP, merchant_id=M004)

        按「谁来履约」拆分

┌──────────────┐ ┌──────────────┐ ┌──────────────┐
│ Order #1     │ │ Order #2     │ │ Order #3     │
│ 平台统仓履约  │ │ M003自行履约  │ │ M004自行履约  │
│              │ │              │ │              │
│ SKU-A (SELF) │ │ SKU-D (SOP)  │ │ SKU-E (SOP)  │
│ SKU-B (FBP)  │ │              │ │              │
│ SKU-C (FBP)  │ │              │ │              │
└──────┬───────┘ └──────┬───────┘ └──────┬───────┘
       │                │                │
       ▼                ▼                ▼
   进入ERP+WMS      仅B2B通知M003    仅B2B通知M004
```

### 7.2 拆分规则详解

| 规则 | 说明 | 举例 |
|------|------|------|
| **R1: 按履约方式拆分** | SELF/FBP（统仓履约）→ 合并为一单；SOP → 按入驻商各拆分一单 | 统仓的3个SKU合并为Order#1 |
| **R2: SOP按入驻商拆分** | 不同SOP入驻商独立履约、独立发货、独立开票 → 必须各自独立订单 | 两个SOP入驻商 → 两笔独立订单 |
| **R3: SELF和FBP可以合并** | 同一仓库、同一配送 → 合并为一个运单，买家一次收货 | 合并理由见下方 |
| **R4: 合并订单仍需行级标记** | 合并订单内，每行独立标记 source_entity | Order#1行1: SELF, 行2: M001, 行3: M002 |

### 7.3 为什么 SELF 和 FBP 可以合并？

```
理由1: 履约端一致
  自营品和FBP品都在仓配主体的同一个仓库 → 拣货路径可以合并

理由2: 配送端一致
  同一个收件地址 → 同一个司机 → 同一个运单号 → 买家一次收货

理由3: 来源溯源不丢失
  虽然合并为一个运单，但订单行级 source_entity 始终保留
  → WMS出库后 B2B 可以按行分拆结算
```

### 7.4 订单路由总表

| 订单类型 | B2B → | 接收系统 | 后续动作 |
|----------|-------|----------|----------|
| 纯自营 | B2B → 自营ERP → WMS | 自营ERP | ERP审核→下发WMS→成本核算→回传B2B |
| 纯FBP | B2B → WMS | 仓配WMS | WMS履约→回传B2B(含费用) |
| 自营+FBP混合 | B2B → 自营ERP → WMS | 自营ERP | ERP将整单下发WMS，但FBP行跳过成本核算 |
| 纯SOP | 仅B2B | B2B自身 | 通知入驻商→入驻商自行发货 |
| 统仓+SOP混合 | 拆为两单分别处理 | — | 统仓部分走统仓流程，SOP部分独立 |

## 8. 费用管理

### 8.1 费用全景

在三主体架构下，费用发生在三个方向：

```
                    ┌──────────┐
                    │  买家    │
                    └────┬─────┘
                         │ 支付商品价款
                         ▼
              ┌─────────────────────┐
              │   平台主体 (B2B)     │
              │  收款后统一分配      │
              └──┬──────┬──────┬───┘
                 │      │      │
      仓配服务费  │      │      │ 平台佣金
                 ▼      ▼      ▼
         ┌────────┐ ┌──────┐ ┌──────┐
         │仓配主体 │ │自营  │ │入驻商 │
         │(收费)  │ │主体  │ │(被扣费│
         └────────┘ │(被扣费│ │+收货款│
                    │+收货款│ │余款)  │
                    └──────┘ └──────┘
```

### 8.2 费用类型与计算规则

#### 8.2.1 仓配服务费（仓配主体收取）

| 费用类型 | 计算方式 | 数据来源 | 谁承担 | 计费时机 |
|----------|----------|----------|--------|----------|
| **仓储费** | 按件/按体积 × 存储天数 | WMS 出库时记录存储天数 | 货主（自营/FBP入驻商） | 出库时由 WMS 测算 |
| **配送费** | 按件/按重量/按距离 | WMS 出库称重 + 配送距离 | 货主（同上） | 出库时测算 |
| **操作费** | 拣货费 + 复核费 + 打包费，按件计算 | WMS 作业记录 | 货主（同上） | 出库时测算 |
| **增值服务费** | 贴标/组装/质检等，按合同约定 | WMS 作业记录 | 货主（同上） | 服务完成时 |
| **入库费** | 卸货/质检/上架，FBP入驻商入库时产生 | WMS 入库记录 | FBP入驻商 | 入库时测算 |

**费用计算公式（FBP入驻商单笔出库）**：

```
仓配费 = 仓储费 + 配送费 + 操作费 + 增值服务费

仓储费 = Σ(每件商品 × 仓储单价/天 × 实际存储天数)
配送费 = 按合同费率（按件/按重量/按距离取高者）
操作费 = 拣货费/件 × 件数 + 复核费/件 × 件数 + 打包费/包裹 × 包裹数
```

#### 8.2.2 平台佣金（平台主体收取）

| 费用类型 | 计算方式 | 谁承担 |
|----------|----------|--------|
| **自营品佣金** | 自营品销售金额 × 佣金率 | 自营主体 |
| **FBP品佣金** | FBP品销售金额 × 佣金率 | FBP入驻商 |
| **SOP品佣金** | SOP品销售金额 × 佣金率 | SOP入驻商 |

#### 8.2.3 费用承担总结

| 场景 | 仓储费 | 配送费 | 操作费 | 平台佣金 | 平台技术服务费 | 支付手续费 |
|------|--------|--------|--------|----------|---------------|-----------|
| 自营品 | 自营主体 | 自营主体 | 自营主体 | 自营主体 | — | 平台主体 |
| FBP品 | FBP入驻商 | FBP入驻商 | FBP入驻商 | FBP入驻商 | 可选 | 平台主体 |
| SOP品 | — | — | — | SOP入驻商 | 可选 | 平台主体 |

### 8.3 费用数据流

```
WMS 出库
  │
  ├──→ 回传 B2B: 出库结果 + 费用明细
  │    { fee: { storage: 1.5, delivery: 5, operation: 6 } }
  │
  ▼
B2B 结算中心
  │
  ├── 按 merchant_id 汇总本周期所有费用
  │    自营主体: 仓储费¥50 + 配送费¥200 + 操作费¥80 = ¥330
  │    M001:    仓储费¥15 + 配送费¥50 + 操作费¥20 = ¥85
  │
  ▼
B2B 对账中心
  │
  ├──→ 生成仓配服务费对账单 → 仓配主体确认
  ├──→ 生成自营主体结算单（货款 - 佣金 - 仓配费）
  ├──→ 生成 FBP 入驻商结算单（货款 - 佣金 - 仓配费）
  └──→ 生成 SOP 入驻商结算单（货款 - 佣金）
```

## 9. 结算管理

### 9.1 结算全景

B2B 的结算中心是三主体架构的资金枢纽。核心规则：**平台收款 → 平台结算 → 按合同周期打款**。

```
本周/月买家总支付（进入平台商户号）
            │
            ▼
   ┌─────────────────┐
   │  B2B 结算中心    │
   │  按结算周期汇总   │
   └────────┬────────┘
            │
   ┌────────┼────────┬────────────┐
   ▼        ▼        ▼            ▼
┌──────┐┌──────┐┌──────┐    ┌──────────┐
│自营   ││FBP   ││SOP   │    │仓配主体   │
│结算单 ││结算单 ││结算单 │    │服务费对账单│
└──┬───┘└──┬───┘└──┬───┘    └────┬─────┘
   │       │       │             │
   ▼       ▼       ▼             ▼
┌──────────────────────────────────────┐
│            结算打款                    │
│                                      │
│ 自营主体   ← 货款 - 佣金 - 仓配费      │
│ FBP入驻商  ← 货款 - 佣金 - 仓配费      │
│ SOP入驻商  ← 货款 - 佣金              │
│ 仓配主体   ← 全部仓配服务费            │
└──────────────────────────────────────┘
```

### 9.2 各模式结算公式

#### 9.2.1 自营主体结算

```
自营净结算 = Σ自营品销售金额
            - 平台佣金（销售金额 × 佣金率）
            - 仓配费（仓储费 + 配送费 + 操作费 + 增值服务费）
            - 支付手续费（如有）
            - 其他扣款（损耗/罚款）
```

> **说明**：自营主体不直接对买家收款。买家付的钱全部进入平台商户号。平台在扣除佣金和仓配费后，将余款打给自营主体。自营 ERP 中记录「应收账款-平台主体」，收到打款后核销。

#### 9.2.2 FBP 入驻商结算

```
FBP净结算 = Σ该入驻商FBP品销售金额
            - 平台佣金（销售金额 × 佣金率）
            - 仓配费（仓储费 + 配送费 + 操作费 + 增值服务费）
            - 入库费（本周期新入库产生的费用）
            - 损耗赔偿
            - 其他扣款

若 FBP净结算 < 0 → 入驻商需补缴差额
若 FBP净结算 > 0 → 平台打款给入驻商
```

#### 9.2.3 SOP 入驻商结算

```
SOP净结算 = Σ该入驻商SOP品销售金额
            - 平台佣金（销售金额 × 佣金率）
            - 支付手续费（如有）
```

> 最简单的一种。SOP 入驻商自己发货，平台不产生仓配费。

#### 9.2.4 仓配主体服务费结算

```
仓配服务费 = Σ (所有自营品 + 所有FBP品) 的
            仓储费 + 配送费 + 操作费 + 增值服务费 + 入库费
```

> 仓配主体不跟每个货主单独结算，而是跟平台主体统一对账结算。平台从各货主的货款中扣下仓配费，集中打给仓配主体。

### 9.3 结算周期与对账流程

#### 9.3.1 支持的结算周期

| 周期类型 | 生成对账单时间 | 入驻商确认期 | 打款日 |
|----------|-------------|------------|--------|
| 月结 | 次月 1 日 | 次月 1-10 日 | 次月 15 日 |
| 半月结 | 16 日 + 次月 1 日 | 生成后 5 工作日 | 17 日 / 次月 6 日 |
| 周结 | 每周一 | 生成后 3 工作日 | 周三 |

#### 9.3.2 对账确认流程

```
结算日到达
  │
  ▼
B2B 自动生成对账单
  ├── 汇总本期所有交易明细（订单号/商品/金额/费用/扣款）
  ├── 站内信通知 + 邮件通知
  │
  ▼
接收方确认
  ├── 自营主体：在商户中心查看+确认（或通过API自动拉取）
  ├── FBP入驻商：在商户中心查看+确认
  ├── SOP入驻商：在商户中心查看+确认
  └── 仓配主体：在商户中心查看+确认
  │
  ├── 确认期内提出争议 → B2B运营处理 → 重新生成
  └── 确认期内无异议 → 自动确认
  │
  ▼
确认完成后
  ├── 入驻商必须在确认后5工作日内完成买家开票
  ├── 发票未完成 → 结算款暂扣，滚存至下一期
  └── 发票已完成 → 进入打款
  │
  ▼
B2B 打款
  └── 打款至各主体的对公银行账户（与营业执照名称一致）
```

### 9.4 结算的硬约束

| 约束 | 说明 |
|------|------|
| **禁止个人账户** | 所有结算打款必须打入对公银行账户，账户名称必须与营业执照一致 |
| **发票先于打款** | FBP/SOP 入驻商必须先给买家开票，平台校验后才能打款 |
| **最低打款额** | 单次打款额不足 ¥100 时滚存至下一期 |
| **超期默认确认** | 对账单发出后满确认期未回应，视为默认确认，不可再异议 |
| **不可修改结算结果** | 结算金额由系统按合同费率自动计算，运营不可人工修改 |
| **负数需补缴** | FBP 净结算为负时，入驻商需在 5 工作日内补缴差额至平台对公账户 |

### 9.5 会计分录（各主体视角）

#### 9.5.1 平台主体

```
B2B 收款时:
  借: 银行存款（微信/支付宝）    ¥500
    贷: 其他应付款-待结算        ¥500

B2B 结算时（以FBP入驻商为例）:
  借: 其他应付款-待结算           ¥100
    贷: 应付账款-入驻商M001       ¥85
    贷: 应付账款-仓配主体         ¥12.5
    贷: 主营业务收入-平台佣金      ¥2.5

B2B 打款时:
  借: 应付账款-入驻商M001        ¥85
  借: 应付账款-仓配主体          ¥12.5
    贷: 银行存款                 ¥97.5
```

#### 9.5.2 自营主体

```
收到B2B推送的订单数据:
  借: 应收账款-平台主体           ¥7.0
    贷: 主营业务收入-自营         ¥6.19
    贷: 应交税费-销项税           ¥0.81

出库成本结转:
  借: 主营业务成本-自营           ¥4.0
    贷: 库存商品                  ¥4.0

收到B2B结算单:
  借: 销售费用-平台佣金           ¥0.07
  借: 销售费用-仓储服务费         ¥X.XX
    贷: 应收账款-平台主体          ¥记入费用

收到B2B打款:
  借: 银行存款                   ¥净额
    贷: 应收账款-平台主体          ¥净额
```

## 10. 自营 ERP 对接设计

### 10.1 自营 ERP 在三主体架构中的定位变化

| 旧定位（V5.0之前） | 新定位（三主体架构） |
|-------------------|---------------------|
| 全平台订单的处理中枢 | **仅自营品的进销存管理系统** |
| 接收所有订单（自营+FBP） | **仅接收自营品订单** |
| 统一结算 | 接收 B2B 推送的结算单，自动记账 |
| 管理代管库存 | 不管理代管库存（FBP品库存归WMS管） |

### 10.2 自营 ERP 需要新增的接口

#### 10.2.1 接收 B2B 推送的接口（ERP 暴露给 B2B）

| 接口 | 方法+路径 | 说明 | 何时调用 |
|------|----------|------|----------|
| 订单同步 | POST /api/v1/order/sync | B2B 推送自营品订单 | 支付完成 |
| 订单取消 | POST /api/v1/order/cancel | B2B 通知取消 | 买家取消/超时 |
| 结算单推送 | POST /api/v1/settlement/sync | B2B 推送结算单 | 结算确认后 |
| 仓配费通知 | POST /api/v1/warehouse-fee/sync | B2B 推送本期仓配费 | 仓配费对账确认后 |

#### 10.2.2 向 B2B 推送的接口（ERP 调用 B2B）

| 接口 | 方法+路径 | 说明 | 何时调用 |
|------|----------|------|----------|
| 订单状态回传 | POST /api/v1/order/status | 回传审核/出库/完成状态 | 状态变更时 |
| 商品同步 | POST /api/v1/product/sync | 同步自营品SPU/SKU | 商品新增/变更 |
| 库存同步 | POST /api/v1/inventory/sync | 同步自营品可售库存 | 定时 + 变动时 |
| 开票状态回传 | POST /api/v1/invoice/status | 回传自营品发票状态 | 开票完成后 |

### 10.3 自营 ERP 的处理逻辑

```
收到 B2B 推送的订单 (POST /api/v1/order/sync)
  │
  ├── 1. 校验订单
  │     ├── 所有行 fulfillment_type = SELF？（不应出现FBP/SOP行）
  │     ├── SKU 是否在自营商品库中？
  │     └── 价格与合同价是否一致？
  │
  ├── 2. 创建销售订单
  │     └── erp_sales_order 表，source = "B2B", ext_order_id = B2B订单号
  │
  ├── 3. 锁定库存（可用量扣减）
  │     └── 自有库存: available = available - 订单占用
  │
  ├── 4. 审核
  │     ├── 信用审核
  │     ├── 库存确认
  │     └── 审核通过 → 生成发货单
  │
  ├── 5. 下发 WMS
  │     └── POST /api/v1/delivery/create → 仓配WMS
  │
  ├── 6. 等待 WMS 出库回调
  │     └── WMS 回调: delivery_id=XX, status=shipped, tracking_no=XX
  │
  ├── 7. 成本核算
  │     └── 移动加权平均 → 计算 COGS → 生成会计凭证
  │
  ├── 8. 回传 B2B
  │     └── POST /api/v1/order/status → B2B (shipped + tracking_no)
  │
  └── 9. 等待 B2B 结算单
        └── B2B推送结算单 → ERP自动记账 → 核销应收账款
```

### 10.4 自营 ERP 与 B2B 的商品 / 库存同步

```
同步触发:
  ├── 商品新增/修改 → 实时推送 B2B
  ├── 库存变动 → 实时推送 + 每5分钟全量兜底
  └── 价格变更 → 实时推送

同步内容 (商品):

    sku: "P001",
    spu_name: "可乐 330ml",
    category: "饮料",
    price: 3.50,           // 建议零售价

    tax_rate: 13,          // 税率(%)
    unit: "箱",
    spec: "330ml × 24罐"
  }

同步内容 (库存):
  {
    sku: "P001",
    available: 120,
    warehouse_id: "WH001"
  }
```

## 11. 仓配 WMS 对接设计

### 11.1 WMS 在三主体架构中的定位

WMS 是仓配主体的核心作业系统。关键认知：**WMS 不区分自营和 FBP，它只认 owner_id（货主）**。

| WMS 知道的 | WMS 不知道的 |
|-----------|-------------|
| 货主是谁 (owner_id) | 这个货主是自营还是入驻商 |
| SKU + 数量 + 库位 + 批次 | 商品价格 |
| 入库/出库/盘点 | 成本 |
| 仓储作业费（按合同规则测算） | 平台佣金 |
| 包裹重量/体积 | 发票 |

### 11.2 WMS 需要暴露的接口

#### 11.2.1 被自营 ERP 调用的接口

| 接口 | 方法+路径 | 调用方 | 说明 |
|------|----------|--------|------|
| 创建发货单 | POST /api/v1/delivery/create | 自营ERP | 自营品出库指令 |
| 取消发货单 | POST /api/v1/delivery/cancel | 自营ERP | 审核不通过时取消 |
| 查询发货单状态 | GET /api/v1/delivery/{id} | 自营ERP | 查询履约进度 |

#### 11.2.2 被 B2B 直接调用的接口

| 接口 | 方法+路径 | 调用方 | 说明 |
|------|----------|--------|------|
| 创建发货单（FBP） | POST /api/v1/delivery/create-fbp | B2B | FBP品出库指令，不进自营ERP |
| 取消发货单（FBP） | POST /api/v1/delivery/cancel-fbp | B2B | 买家取消FBP订单 |
| 查询库存 | GET /api/v1/inventory/{sku}?owner_id=XX | B2B | 查询FBP品实物库存 |

#### 11.2.3 WMS 主动回调的接口

| 接口 | 方法+路径 | 回调到 | 说明 |
|------|----------|--------|------|
| 出库完成（自营） | POST /callback/delivery/complete | 自营ERP | 自营品出库完成通知 |
| 出库完成（FBP） | POST /callback/delivery/complete-fbp | B2B | FBP品出库完成 + 费用明细 |
| 入库完成 | POST /callback/receiving/complete | B2B | FBP品入库完成 → 库存同步 |
| 库存变动通知 | POST /callback/inventory/change | B2B | 实时库存变动 |

### 11.3 WMS 的多货主管理

```
WMS 内部核心表结构:

wm_inventory（库存表）
├── sku           商品编码
├── owner_id      货主ID（SELF / M001 / M002...）
├── location_id   库位
├── batch_no      批次号
├── qty           数量
├── available_qty 可用数量
├── locked_qty    锁定数量
└── updated_at    更新时间

wm_delivery_order（发货单）
├── delivery_id   发货单号
├── source_system 来源: ERP / B2B（区分谁下的指令）
├── ext_order_id  外部订单号（ERP订单号 或 B2B订单号）
├── owner_id      货主ID
├── status        状态: PENDING/PICKING/PACKED/SHIPPED
└── items[]       [{ sku, qty, owner_id }]
```

**关键规则**：同一发货单可以包含多个 owner_id 的商品（如自营+FBP混合订单），WMS 拣货时按 owner_id 分拣，复核台合并为同一包裹。

### 11.4 WMS 费用测算引擎

WMS 在出库时自动测算费用，附加在出库完成回调中：

```
出库扫描完成
  │
  ▼
WMS 费用测算引擎
  │
  ├── 查合同费率（从 B2B 同步过来的缓存）
  │     仓储费单价: ¥0.5/件/天
  │     配送费单价: ¥5/件
  │     操作费单价: ¥2/件
  │
  ├── 计算
  │     仓储费 = 3件 × ¥0.5/天 × 5天 = ¥7.5
  │     配送费 = 1单 × ¥5 = ¥5
  │     操作费 = 3件 × ¥2 = ¥6
  │     合计 = ¥18.5
  │
  └── 回传 B2B
       {
         delivery_id: "D001",
         status: "shipped",
         fee: {
           storage: 7.5,
           delivery: 5,
           operation: 6,
           total: 18.5
         }
       }
```

> **注意**：WMS 的费用测算结果是可以被争议的。入驻商/自营主体在对账时可以提出异议，核实后调整。WMS 测算是"初步结果"，B2B 结算时使用"确认后的结果"。

## 12. 自配 (SOP) 不入下游系统处理

SOP 模式的核心特征：**入驻商自己管货、自己发货，B2B 只需要做三件事：通知 → 收状态 → 结算**。

### 12.1 SOP 订单的生命周期（仅在 B2B 内）

```
买家下单(SOP品)
  │
  ▼
B2B 支付完成 → 订单状态 = 待发货
  │
  ├── 通知入驻商:
  │     ├── 站内信（默认，所有入驻商有）
  │     └── Webhook 推送（入驻商主动配置）
  │
  ▼
入驻商在自己的系统中处理发货
  │ （B2B完全不感知这个过程）
  │
  ▼
入驻商回传物流信息
  │ 方式1: 商户中心手动录入
  │ 方式2: API 调用 B2B /api/v1/logistics/update
  │ 方式3: Excel 批量导入
  │
  ▼
B2B 状态变更 → 已发货
  │
  ├── 通知买家（物流单号 + 快递公司）
  │
  ▼
买家签收 → 入驻商回传签收或买家确认
  │
  ▼
B2B 状态变更 → 已完成
  │
  ▼
结算周期到达 → 生成对账单 → 入驻商确认 → 打款
```

### 12.2 SOP 入驻商需要做的事情

| 事项 | 如何做 | B2B 提供的工具 |
|------|--------|---------------|
| 获取订单 | 商户中心查看 / API 拉取 / Webhook 接收 | 订单列表页 + `GET /api/v1/orders?status=pending` |
| 发货 | 在自己的仓库自行处理 | — |
| 回传物流 | 商户中心录入 / API 调用 | `POST /api/v1/logistics/update` |
| 给买家开票 | 自己的开票系统 | B2B 提供买家信息和交易金额 |
| 查看对账单 | 商户中心查看 | 结算中心 |
| 提现 | 对账确认后等待平台打款 | 打款记录页 |

### 12.3 B2B 为 SOP 入驻商提供的 API

| 接口 | 方法+路径 | 说明 |
|------|----------|------|
| 待发货订单列表 | GET /api/v1/merchant/orders | 拉取所有待发货订单 |
| 订单详情 | GET /api/v1/merchant/orders/{id} | 查看单个订单详情（含买家信息）|
| 回传物流 | POST /api/v1/merchant/logistics/update | 录入物流单号和快递公司 |
| 批量导入物流 | POST /api/v1/merchant/logistics/batch | Excel 批量上传物流单号 |
| 商品上架 | POST /api/v1/merchant/products | 新增/修改 SOP 商品 |
| 库存更新 | POST /api/v1/merchant/inventory/update | 更新 SOP 品可售库存 |
| 对账单查询 | GET /api/v1/merchant/settlements | 查看各期对账单 |
| 对账单确认 | POST /api/v1/merchant/settlements/{id}/confirm | 确认对账单 |
| Webhook 配置 | POST /api/v1/merchant/webhook/config | 配置订单通知回调 URL |

### 12.4 SOP 入驻商不接入 API 怎么办？

不少小入驻商没有技术能力对接 API。B2B 必须提供**零代码**的商户中心操作能力：

| 功能 | 纯手工操作路径 |
|------|--------------|
| 查看订单 | 登录商户中心 → 订单管理 → 待发货 → 逐个查看 |
| 发货录入 | 点击"发货" → 选择快递公司 → 输入单号 → 确认 |
| 批量发货 | 下载待发货订单 Excel → 填入物流单号 → 上传 |
| 查看对账 | 商户中心 → 结算中心 → 查看本期对账单 → 确认 |
| 商品管理 | 商户中心 → 商品管理 → 新增/编辑/下架 |

> **设计原则**：API 是给有技术能力的入驻商提效的，商户中心的纯手工操作是兜底的。

### 12.5 SOP 订单的超时与催单

| 规则 | 说明 |
|------|------|
| **发货超时** | 买家支付后 48 小时（可配置）未回传物流 → 站内信提醒入驻商 |
| **超时未处理** | 72 小时后仍无响应 → B2B 运营人工介入 → 可能取消订单退款 |
| **自动确认收货** | 发货后 15 天买家未操作 → 系统自动确认收货 |
| **发货时效考核** | 记录每次从下单到发货的时长 → 入驻商 KPI 考核 → 影响推荐排序 |

## 13. 税务来源申报设计

### 13.1 来源溯源的起点与终点

在三主体架构中，来源溯源的责任完全落在 B2B：

```
B2B 下单时标记 source_entity（每行）
  │ (自营品: source_entity = 自营主体税号)
  │ (FBP品:  source_entity = 入驻商税号)
  │ (SOP品:  source_entity = 入驻商税号)
  │
  ▼
汇总期（按日/月）B2B 生成来源申报表
  │
  ├── 按 wx_transaction_id 逐笔匹配
  │    ├── 能匹配 → 按 source_entity 申报
  │    └── 不能匹配 → 标记为"来源不明" → 记入平台主体
  │
  ▼
B2B 提交至税务系统
  │ (API对接或文件上传)
  ▼
税务系统返回匹配结果
  │
  ├── 匹配成功 → 按来源主体分别记税
  └── 匹配失败 → 全部记入平台主体 ← 平台承担本不应承担的税负
```

### 13.2 B2B 来源申报数据表

```
b2b_source_attribution_report（按日/月汇总）
├── report_id           申报表ID
├── report_date         申报日期
├── period_start        统计周期起
├── period_end          统计周期止
├── total_transaction   总交易笔数
├── matched_count       已匹配来源主体笔数
├── unmatched_count     未匹配来源主体笔数
├── total_amount        总金额
├── unmatched_amount    未匹配金额（全部记入平台主体）
├── status              状态: PENDING/SUBMITTED/CONFIRMED
└── submitted_at        提交时间

b2b_source_attribution_detail（每笔交易的来源详情）
├── detail_id
├── report_id
├── wx_transaction_id   微信/支付宝交易流水号
├── order_id            订单号
├── order_line_id       订单行号
├── source_entity       来源主体（纳税人识别号）
├── source_entity_name  来源主体名称
├── source_type         来源类型: SELF/FBP/SOP
├── amount              金额
├── match_status        匹配状态: MATCHED/UNMATCHED
└── tax_response        税务系统回执
```

### 13.3 来源丢失的损失量化

| 场景 | 单笔交易金额 | 来源标记 | 平台损失 |
|------|------------|---------|---------|
| 正常 | ¥100 | 正确标记为 M001 | ¥0（M001 自己承担税负）|
| 丢失 | ¥100 | 标记丢失→记入平台 | 销项税 ¥11.5 + 附税 ¥1.38 = **¥12.88** |

> 假设月丢失 200 笔 × ¥100 = 平台年损失约 ¥30,912。加之虚增收入可能影响小微企业税收优惠资格（年应纳税所得额 ≤300 万），**来源溯源是 B2B 的第一优先级数据质量要求**。

## 17. 关键设计决策

| # | 决策 | 理由 | 权衡 |
|---|------|------|------|
| 1 | **三主体独立数据库** | 不同法人数据不可混存，各自独立 | API 通信增加了延迟和不一致风险 |
| 2 | **FBP订单 B2B→WMS 绕开自营ERP** | 入驻商数据不应进入自营ERP；ERP不应做纯转发 | B2B需要增加WMS直推能力 |
| 3 | **SELF和FBP在WMS内合并为一单** | 同一仓+同一配送，买家一次收货 | WMS需要支持行级owner_id区分 |
| 4 | **SOP按入驻商拆分独立订单** | 不同履约方独立发货+独立开票 | 买家可能收到多个包裹 |
| 5 | **平台统一收款+统一结算** | 买家支付入口唯一，资金流清晰 | 平台是资金中转站，增加了资金二清合规要求 |
| 6 | **仓配费在WMS侧测算** | 出库数据（件数/重量/天数）在WMS最准确 | WMS需要新增费用测算模块 |
| 7 | **来源溯源在B2B闭环** | 平台是税务申报责任方，必须在收款端标记 | B2B承担了核心税务风险 |
| 8 | **自营ERP通过结算单闭环** | 自营ERP不直接收款，收入通过B2B结算确认 | 自营ERP的收入记账依赖B2B结算数据的准确性 |
| 9 | **SOP提供纯手工操作兜底** | 小入驻商无技术能力对接API | 运营成本高（人工录入物流单号等）|
| 10 | **B2B不存入驻商的成本和进价** | 入驻商的成本数据是自己的商业机密 | B2B无法做更深度的数据分析 |

## 18. 风险与缓解

| # | 风险 | 级别 | 缓解措施 |
|---|------|------|----------|
| 1 | **来源标记丢失 → 平台多承税负** | 🔴🔴 | 下单时强制校验，订单行 source_entity 不可为空；每日巡检未标记订单并告警 |
| 2 | **FBP净结算为负时入驻商不补缴** | 🔴 | 合同明确补缴条款+违约金；连续两期不补缴→下架商品+冻结商户 |
| 3 | **资金二清合规** | 🔴 | 接入持牌支付机构做资金托管；B2B只下发分账指令不动资金池 |
| 4 | **B2B结算引擎故障** | 🔴 | 结算批处理+幂等设计+人工兜底；灾难恢复演练 |
| 5 | **WMS费用测算误差** | 🟡 | 提供费用明细和复核通道；争议期内可调整；定期校准费率 |
| 6 | **SOP入驻商超时未发货** | 🟡 | 自动催单→运营介入→超时自动取消退款 |
| 7 | **API版本不兼容** | 🟡 | URL版本号（/v1/）+ 契约测试 + 灰度发布 |
| 8 | **数据保存期不满足法规** | 🟡 | 交易记录≥3年不可物理删除；来源申报≥10年 |
| 9 | **入驻商不开发票** | 🔴 | 合同强制开票义务；结算打款前校验发票状态；不开票→暂扣结算款 |
