## 1. 文档目的与核心设计原则

### 1.1 文档目的

定义 B2B 商城、ERP、WMS 三个系统的职责边界、数据归属、订单拆分策略、API 契约、结算模型和部署架构。

**核心约束**：税务系统从微信/支付宝抓取全量交易流水，平台必须向税务提交每笔交易的"来源主体"申报。系统设计中，每一处订单数据流转都必须保持"这个交易到底是谁的"的溯源能力——这是不可妥协的设计底线。

### 1.2 核心设计原则

| # | 原则 | 说明 |
|---|------|------|
| **P1** | **商城主体公司统一收款** | 所有买家支付统一进入商城主体公司的微信/支付宝商户号。资金入口唯一。 |
| **P2** | **平台须向税务提交交易来源主体** | 税务系统从微信/支付宝抓取全量交易流水后，不会自动归属。平台必须提交每笔交易的"来源主体"（自营 / 哪个入驻商），税务据此分别记税。**平台分不清的交易，全部记入平台主体**。 |
| **P3** | **发票流与交易来源主体一致** | 谁被税务认定为交易主体，谁给买家开票。自营→平台开票；入驻商→入驻商开票。 |
| **P4** | **三系统独立数据库** | B2B / ERP / WMS 各有独立数据库，通过 API 契约通信，不共享数据库。 |
| **P5** | **WMS 不感知价格和税务** | WMS 只管实物数量，价格、成本、税率、发票是 ERP 的事。 |

### 1.3 税务机制说明

```
                     微信支付 / 支付宝
                  （商城主体公司商户号）
                           │
                           │ 全量交易流水（T+1 或实时）
                           ▼
                   ┌─────────────────┐
                   │    税务系统       │
                   │  （金税/电子税务局）│
                   │                  │
                   │  收到全量流水后：   │
                   │  "这些交易是谁的？" │
                   └────────┬────────┘
                            │
              平台必须提交来源主体申报
                            │
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
   ┌─────────────┐  ┌─────────────┐  ┌─────────────┐
   │ 来源=平台自营 │  │ 来源=入驻商A  │  │ 来源=无法判断 │
   │ → 记入平台   │  │ → 记入入驻商A │  │ → 全部记入   │
   │   平台开票   │  │   入驻商A开票 │  │   平台！     │
   └─────────────┘  └─────────────┘  └─────────────┘
```

**关键认知**：税务系统不会替平台"自动归类"。平台的技术能力和数据质量直接决定税务归属——**系统每丢失一笔交易的来源信息，平台就多承担一笔不应承担的税负**。这不是税务合规的问题，是税务成本的问题。

## 2. 业务场景

### 2.1 角色定义

| 角色 | 说明 | 使用的系统 | 在税务归属中的位置 |
|------|------|-----------|-------------------|
| **商城主体公司**（平台运营方/经销商） | B2B 平台的法人主体，也是自营卖家，拥有实体仓库 | B2B（管理端）、ERP、WMS | ① 自营品 → 来源主体=平台；② 向税务提交全量来源申报 |
| **入驻商**（第三方卖家） | 在 B2B 商城开店，可通过商城代发或自配 | B2B（商户中心） | 代发/自配品 → 来源主体=入驻商；入驻商给买家开票 |
| **买家**（下游客户） | 在 B2B 商城浏览、下单、支付 | B2B（买家端） | 消费者/采购方，发票由税务归属方开具 |
| **仓储操作员** | 经销商仓库的拣货、复核、打包人员 | WMS、PDA | — |
| **配送司机** | 经销商配送车队 | TMS（本文不展开） | — |

### 2.2 三种履约模式

| 模式 | 货主 | 仓储方 | 配送方 | 订单经系统 | 交易来源主体 | 谁开票给买家 |
|------|------|--------|--------|-----------|-------------|-------------|
| ① 自营 | 商城主体公司 | 自营仓 | 自配 | B2B → ERP → WMS | **商城主体公司** | 商城主体公司 |
| ② 代发（FBP） | 入驻商 | 商城主体公司仓 | 商城配 | B2B → ERP → WMS | **入驻商** | 入驻商 |
| ③ 自配（SOP） | 入驻商 | 入驻商仓 | 入驻商配 | 仅 B2B | **入驻商** | 入驻商 |

> **三种模式的共同点**：买家付款全部进入商城主体公司商户号 → 税务系统拿到全量流水 → 平台必须向税务申报每笔交易的实际来源主体。不同之处仅在于来源主体是谁以及由谁开票。

## 3. 系统职责矩阵

### 3.1 B2B 商城

| 模块 | 职责 | 税务相关职责 |
|------|------|-------------|
| 商品展示 | 多商户商品目录、搜索、详情 | 商品详情页展示"由XX（入驻商名称）开具发票"或"由XX商城开具发票" |
| 交易下单 | 购物车、下单、拆单、统一收款 | 支付统一走商城主体公司商户号；下单时记录 `source_entity`（来源主体标记） |
| 支付对接 | 对接微信支付/支付宝 | 存储 `payment_transaction_id`，用于后续来源主体申报 |
| 商户中心 | 入驻商上架商品、管理订单、查看结算单 | 入驻商上传纳税人资质、开票信息，供税务归属申报使用 |
| 税务归属申报 | **新增模块** | 按交易周期（日/月）生成"交易来源主体申报表"，提交至税务系统 |
| 开放 API | 订单通知（自配）、物流回传 | 向入驻商提供对账接口 |

### 3.2 ERP

| 模块 | 职责 | 税务相关职责 |
|------|------|-------------|
| 订单处理 | 接收 B2B 下发的自营+FBP 订单 | 订单行必须携带 `source_entity`（来源主体），不可丢失 |
| 税务归属溯源 | **新增模块** | ① 对每笔订单确保 `source_entity` 不丢失；② 生成来源主体汇总数据提交给 B2B 税务归属申报模块；③ 标记"来源不明"订单并告警 |
| 库存中心 | 可用量计算、库存占用/释放、成本核算 | 自营品成本核算；代管品仅记数量 |
| 财务核算 | 应收应付、结算 | 按来源主体分科目核算 |
| 发票管理 | **新增模块** | 自营品→平台开票给买家；代发/自配品→入驻商开票给买家（平台提供开票数据） |

### 3.3 WMS

WMS 不感知税务。出库回调时携带 `owner_id`，ERP 据此做来源溯源。WMS 自身不区分自营/代发。

## 4. 数据归属矩阵

| 数据域 | 权威来源 | B2B 侧 | ERP 侧 | WMS 侧 | 税务系统侧 |
|--------|----------|--------|--------|--------|-----------|
| **支付流水** | 微信/支付宝 | 全量支付记录 | 同步对账 | 不存 | **抓取全量流水**（待平台申报来源） |
| **来源主体** | **B2B** | **生成并提交税务申报** | 处理订单时带入，不可丢失 | `owner_id`（辅助判断） | **接收平台申报** |
| **商品 SPU/SKU** | ERP（自营+代发）<br>B2B（自配品） | 展示信息+来源方标识 | 主数据+税收分类编码+税率 | 不存 | 读取税收分类编码 |
| **实物库存** | WMS | 不存 | 读快照计算可用量 | 库位×SKU×批次×货主 | 不存 |
| **可用库存** | ERP | 下单校验用缓存 | 可用量=WMS实物-占用 | 不存 | 不存 |
| **订单** | B2B | 全量+来源主体标记 | 处理副本+来源主体 | 不存 | 不存（从来源申报获取） |
| **销售发票** | 谁开票谁负责 | 买家查看 | 自营品→ERP生成；代发/自配→入驻商生成 | 不存 | 接收发票数据 |
| **商户资料** | B2B | 入驻信息+纳税人资质 | 结算+来源归属 | owner_id | 不存 |
| **结算数据** | ERP | 商户看结算单 | 按来源主体分科目 | 不存 | 不存 |
| **来源申报记录** | **B2B** | **提交记录+回执** | 不存 | 不存 | **接收+返回匹配结果** |

### 关键原则（税务视角）

1. **支付流水是税务的输入**，交易来源主体申报是平台的输出。输出质量决定平台的税务成本。
2. **B2B 是来源数据的起点和终点**——开始于订单创建时的 `source_entity` 标记，结束于向税务提交来源申报。
3. **ERP/WMS 在流转中不可丢失来源标记**——每经过一个系统，`source_entity` 必须原样传递，任何环节丢失都会导致该笔交易"来源不明"，最终记入平台。

## 5. 交易溯源与税务归属（顶层核心约束）

本章是整套架构的**第一约束**——所有后续设计（订单流转、数据表、API）都必须保证来源主体信息不丢失。

### 5.1 税务系统的工作机制

```
Step 1: 税务系统从微信/支付宝拉取全量流水
         → 按商户号维度，拿到该商户号下所有交易记录
         → 状态：待匹配。每笔交易都在问："这是谁的？"

Step 2: 平台（B2B）向税务提交"交易来源主体申报"
         → 格式：交易流水号 + 来源主体（纳税人识别号/主体名称）
         → 来源主体有三种可能值：
           a) 商城主体公司（自营品）
           b) 入驻商A / 入驻商B / ...（代发/自配品）
           c) 未匹配/无法判断

Step 3: 税务系统按申报结果分别记税
         → 来源=商城主体公司 → 记入商城主体公司的销售收入
         → 来源=入驻商A → 记入入驻商A的销售收入
         → 来源=无法判断 → 全部记入商城主体公司（兜底规则）

Step 4: 税务系统返回匹配回执
         → 已匹配 N 笔，未匹配 M 笔
         → 未匹配部分 = 平台的额外税务成本
```

### 5.2 平台如何确定每笔交易的来源主体

**核心逻辑**：来源主体的确定发生在 B2B 下单时，贯穿 ERP/WMS 全程，最终由 B2B 汇总提交给税务。

```
买家下单
  │
  ▼
B2B 购物车 → 拆分为订单
  │
  │  对每个订单，判断：
  │
  ├── 订单内全部为自营品 → source_entity = 商城主体公司
  │
  ├── 订单内全部为同一入驻商的代发品 → source_entity = 入驻商X
  │
  ├── 订单内全部为同一入驻商的自配品 → source_entity = 入驻商Y
  │
  ├── 订单内混合（自营+代发） → 订单级 source_entity = MIXED
  │   → 行级必须分别标记，最终申报时拆分提交
  │
  └── 无法判断 → source_entity = UNKNOWN（触发告警，人工介入）
```

### 5.3 三种模式下的来源主体与税务归属

| 模式 | 来源主体 | 谁给买家开票 | 税务归属 | 对平台的影响 |
|------|---------|-------------|---------|-------------|
| ① 自营 | **商城主体公司** | 商城主体公司 | 商城主体公司 | 平台正常记销项+进项，标准进销 |
| ② 代发（FBP） | **入驻商** | 入驻商 | 入驻商 | 平台不记此笔销售的销项税，仅收取仓配服务费 |
| ③ 自配（SOP） | **入驻商** | 入驻商 | 入驻商 | 平台不记此笔销售的销项税，仅收取平台佣金 |
| ⚠️ 来源不明 | **平台兜底** | 平台被迫开票 | **平台** | 平台额外承担不是自己的税负 |

### 5.4 来源不明 = 平台的直接经济损失

```
假设：一笔 1000 元的代发品订单，来源主体标记丢失
     原本应由入驻商开票、入驻商记税
     因来源不明 → 全部记入平台

平台额外成本：
  销项税额（13%）= 1000 ÷ 1.13 × 0.13 = 115.04 元
  附加税费（城建7%+教育3%+地方教育2%）= 115.04 × 12% = 13.80 元
  ─────────────────────────────────────────────
  合计 = 128.84 元/每笔丢失

如果每月有 100 笔来源不明交易：
  月损失 = 12,884 元
  年损失 = 154,608 元
```

**这就是为什么"来源溯源"不是锦上添花，而是直接影响利润的底线设计。**

## 6. 支付通道设计（税务归属前置）

### 6.1 支付流程

```
买家在 B2B 下单
       │
       ▼
┌──────────────────────────────────────┐
│  微信支付 / 支付宝（统一收银台）        │
│  ┌────────────────────────────────┐  │
│  │  商户号：商城主体公司              │  │
│  │  • 自营品买家付款                 │  │
│  │  • 代发品买家付款                 │  │
│  │  • 自配品买家付款                 │  │
│  │  → 全量进入同一商户号              │  │
│  └────────────────────────────────┘  │
└────────────────┬─────────────────────┘
                 │
       ┌─────────┴─────────┐
       ▼                   ▼
┌─────────────┐    ┌──────────────┐
│  税务系统    │    │  B2B 商城     │
│  全量抓取    │    │  记录流水号   │
│  等待申报    │    │  标记来源主体  │
└──────┬──────┘    └──────┬───────┘
       │                  │
       │                  │ 按日/月生成
       │                  │ "来源主体申报表"
       │                  │
       │◄──提交申报────────┘
       │   流水号 + 来源主体
       │
       ├── 匹配成功 → 按来源分别记税
       ├── 匹配失败 → 记入平台
       │
       └── 返回申报回执
            → B2B 记录匹配结果
            → ERP 据此确认收入科目
```

| 环节 | 系统 | 动作 | 关键数据 |
|------|------|------|----------|
| 1 | 微信/支付宝 | 买家支付成功 | `payment_transaction_id` |
| 2 | 税务系统 | 拉取全量流水，等待平台申报 | 状态=待匹配 |
| 3 | B2B | 存储流水号 + 订单级/行级 `source_entity` | `source_entity` = 税号或主体名称 |
| 4 | B2B | 按日/月汇总生成"来源主体申报表" | 流水号 ↔ 来源主体映射 |
| 5 | B2B → 税务 | 提交申报表 | JSON/API 对接 |
| 6 | 税务 → B2B | 返回申报回执 | 匹配成功/失败明细 |
| 7 | B2B → ERP | 同步申报结果 | ERP 据此确认各模式收入 |

## 7. 库存模型设计

### 7.1 WMS 侧的实物库存

```sql
-- WMS 库位级库存表
wms_stock (
    id              BIGINT PRIMARY KEY,
    owner_id        VARCHAR(32) NOT NULL,  -- 货主（自营=0，入驻商=merchant_id）
    sku_id          VARCHAR(32) NOT NULL,
    location_id     VARCHAR(32) NOT NULL,
    batch_no        VARCHAR(32),
    production_date DATE,
    quantity        DECIMAL(18,4) NOT NULL,
    locked_quantity DECIMAL(18,4) DEFAULT 0,
    tax_category    VARCHAR(16),           -- 税收分类编码（入库带入，出库透传）
    version         INT DEFAULT 0,
    UNIQUE (owner_id, sku_id, location_id, batch_no)
);
```

### 7.2 ERP 侧的库存可用量

```sql
erp_stock_balance (
    id                BIGINT PRIMARY KEY,
    sku_id            VARCHAR(32) NOT NULL,
    warehouse_id      VARCHAR(16) NOT NULL,
    owner_id          VARCHAR(32) NOT NULL,
    total_quantity    DECIMAL(18,4),
    locked_quantity   DECIMAL(18,4),
    available_quantity DECIMAL(18,4),
    cost_price        DECIMAL(18,2),        -- 仅 owner_id=0 时有效

    tax_rate          DECIMAL(5,4)
);
```

### 7.3 库存同步

```
WMS 出库确认
  → WMS 扣减库存，回传 owner_id + tax_category
  → ERP 接收
    → owner_id=0 → 自营品：重算成本 + COGS 记账
    → owner_id≠0 → 代发品：记录数量，触发入驻商结算
  → ERP 推送库存快照到 B2B
```

## 10. ERP 行级区分自营与代发

同一订单通过行级 `sourceEntityTaxId` 区分，订单级 `sourceEntityType=MIXED` 表示混合：

```json

    { "fulfillmentType": "SELF", "sourceEntityTaxId": "91110108XXXXXXXXXX",
```

出库确认后的全流程差异：

| 处理环节 | 自营（SELF） | 代发（FBP） | 自配（SOP） |

## 13. 平台结算分佣设计

本章定义平台与入驻商之间的结算规则、分佣模型、对账流程和打款机制。这是 B2B 平台商业模型的核心——平台收益来源决定了结算逻辑。

### 13.1 结算参与方与资金关系

```
买家付款（全部进入商城主体公司商户号）
         │
         ▼
  ┌──────────────┐
  │  商城主体公司   │ ← 资金归集方
  │  （平台）      │
  └───────┬──────┘
          │
          │ 根据履约模式，分三条路径：
          │
  ┌───────┼───────────────────────────────────────┐
  │       │                                       │
  ▼       ▼                                       ▼
┌──────┐ ┌──────────────────┐              ┌──────────────┐
│ 自营  │ │ 代发（FBP）       │              │ 自配（SOP）   │
│      │ │                  │              │              │
│ 平台  │ │ 入驻商应结 =       │              │ 入驻商应结 =   │
│ 全额  │ │ 买家实付          │              │ 买家实付      │
│ 自留  │ │ - 仓配服务费      │              │ - 平台佣金     │
│      │ │ - 其他扣费        │              │              │
│      │ │ = 净结算额        │              │ = 净结算额    │
└──────┘ └──────────────────┘              └──────────────┘
```

| 参与方 | 角色 | 资金方向 |
|--------|------|----------|
| **商城主体公司（平台）** | 收款方 + 分账发起方 | 收全款 → 付入驻商净结算额 |
| **入驻商** | 结算对象 | 收到净结算额（货款 - 各项费） |
| **买家** | 付款方 | 向平台付款 |
| **税务系统** | 监管方 | 接收来源申报 + 发票数据 |

### 13.2 分佣规则定义

#### 13.2.1 分佣配置项

平台需要为每类结算配置以下费项，支持按入驻商、按品类、按合同差异化设置：

| 费项 | 适用模式 | 计费基数 | 计费方式 | 示例 |
|------|----------|----------|----------|------|
| **平台佣金** | SOP | 订单金额（含税） | 按比例（1%~15%）或固定金额 | 销售额 × 5% 或 每单 5 元 |
| **仓储费** | FBP | 日均库存量 / 入库件数 | 按件·天 / 按体积·天 / 按入库单 | 0.1 元/件·天 |
| **配送费** | FBP | 包裹重量/体积/距离 | 按区段一口价 或 按实际结算 | 首重 3kg 内 8 元，续重 2 元/kg |
| **操作费** | FBP | 出库件数 | 按件计费 | 1 元/件（含拣货+复核+打包） |
| **增值服务费** | FBP | 服务项目 | 按服务项计费 | 贴标 0.5 元/件、质检 2 元/件 |
| **罚款/扣款** | FBP / SOP | 按违约次数 | 按次/按比例 | 发货超时罚 50 元/单 |

> **配置原则**：分佣规则写在入驻合同中，ERP 结算模块按合同约定的费率和计费方式自动计算，不允许人工修改计算结果（如需调整须重签合同并留痕）。

#### 13.2.2 三种模式的分佣公式

**① 自营模式 — 无分佣**

```
平台净收入 = 买家实付金额 - 库存商品成本 - 销项税额
平台毛利率 = (买家实付 - 成本) / 买家实付 × 100%
```

自营品的利润属于平台自身经营成果，不涉及与入驻商分账。ERP 直接按进销差价核算毛利。

**② 代发模式（FBP）— 仓配费扣除**

```
入驻商应结金额 = 买家实付金额（含税）
                - 仓储费（∑ 日库存量 × 仓储费率 × 在库天数）
                - 配送费（按包裹重量/体积/距离计费）
                - 操作费（出库件数 × 操作费率）
                - 增值服务费（贴标/质检等）
                - 退货损耗分摊
                - 其他合同约定的扣款

平台服务收入 = 仓储费 + 配送费 + 操作费 + 增值服务费
入驻商净收入 = 入驻商应结金额（入驻商自行核算，平台不记）
```

> **示例**：入驻商 M001 的 SKU-B 售出 3 件，买家实付 240 元（含税）。
> - 仓储费：3 件在库 15 天 × 0.1 元/件·天 = 4.50 元
> - 配送费：包裹 2kg，区段计费 = 8.00 元
> - 操作费：3 件 × 1 元/件 = 3.00 元
> - 入驻商净结算 = 240.00 - 4.50 - 8.00 - 3.00 = **224.50 元**
> - 平台服务收入 = 4.50 + 8.00 + 3.00 = **15.50 元**

**③ 自配模式（SOP）— 佣金扣除**

```
平台佣金 = 买家实付金额 × 佣金率（如 5%）
         或 = 固定佣金（如每单 5 元）

入驻商应结金额 = 买家实付金额 - 平台佣金
平台佣金收入 = 平台佣金（其他业务收入-平台佣金）
```

> **示例**：入驻商 M003 的 SKU-D 售出 2 件，买家实付 300 元，佣金率 5%。
> - 平台佣金 = 300 × 5% = 15.00 元
> - 入驻商净结算 = 300 - 15 = **285.00 元**
> - 平台佣金收入 = **15.00 元**

### 13.3 结算周期设计

平台提供三种结算周期，由入驻合同中约定，入驻商不可自行修改：

| 结算周期 | 对账日 | 开票截止日 | 打款日 | 适用场景 |
|----------|--------|----------|--------|----------|
| **日结** | 每日 T+1 生成前日结算单 | 对账确认后 3 工作日内 | 开票后 3 工作日 | 高频交易、资金周转快的入驻商 |
| **周结** | 每周一生成上周结算单（周一~周日） | 对账确认后 5 工作日内 | 开票后 5 工作日 | 中等交易频次 |
| **月结** | 次月 3 日生成上月结算单 | 对账确认后 10 工作日内 | 开票后 10 工作日 | 交易量少、对账成本高的入驻商 |

> **默认周期**：新入驻商默认月结，运营 3 个月后可申请调整为周结或日结。

**结算周期的关键时间节点（以月结为例）**：

```
上月交易     次月 1 日     次月 3 日     次月 13 日前      次月 23 日前
   │            │            │              │                │
   ├──交易发生──→│            │              │                │
   │            │            │              │                │
   │            ├──系统汇总──→│              │                │
   │            │  上月数据   │              │                │
   │            │            │              │                │
   │            │            ├──生成结算单──→│                │
   │            │            │              │                │
   │            │            │   入驻商确认   │                │
   │            │            │   （10日内）   │                │
   │            │            │              │                │
   │            │            │              ├──入驻商开票─────→│
   │            │            │              │  （发票给买家）  │
   │            │            │              │                │
   │            │            │              │                ├──平台打款
   │            │            │              │                │  给入驻商
```

#### 13.4.1 对账单生成

#### 13.4.2 对账操作

| 步骤 | 操作方 | 操作 | 时限 |
|------|--------|------|------|
| 1 | **ERP（自动）** | 结算日自动生成对账单，推送至 B2B 商户中心 | 结算日当天 |
| 2 | **入驻商** | 在商户中心查看对账单，逐笔核对交易明细和费项 | 对账日 + 10 工作日 |
| 3 | **入驻商** | 确认（无异议）或 提出异议（指定争议订单/费项） | 同上 |
| 4 | **平台运营** | 处理异议：核实数据、协商调整、重新生成对账单 | 接到异议后 3 工作日 |
| 5 | **入驻商** | 最终确认（确认后不可再提异议，视为认可全部数据） | 调整后 3 工作日 |
| 6 | **系统** | 锁定结算单，进入开票→打款流程 | 确认后即刻 |

#### 13.4.3 争议处理

| 争议类型 | 处理方式 |
|----------|----------|
| 订单金额不符 | 以 B2B 系统中买家实际支付金额为准，调取支付流水为证据 |
| 退货未计入 | 已完成的退货自动关联扣减，未完成的退货不计入当期 |
| 费项计算争议 | 以合同约定费率为准，调取出入库记录逐笔核对 |
| 配送费争议 | 以物流系统记录的包裹重量/体积为准 |
| 数据不一致 | 暂停该笔结算，升级至运营主管。ERP 调取全链路审计日志 |

> **原则**：对账期内未确认的，系统自动视为默认确认。超期未确认的入驻商，须在下一结算周期中补确认上一期，但不影响当期正常结算。

### 13.5 结算打款

#### 13.5.1 打款触发条件

入驻商净结算额打款须同时满足：

| 条件 | 检查方式 | 不满足时的处理 |
|------|----------|---------------|
| ① 对账单已确认 | 系统状态=CONFIRMED | 不触发打款 |
| ② 入驻商已向买家开具发票（所有已发货订单） | 系统记录发票号码+上传凭证 | 暂停打款，提醒入驻商 |
| ③ 结算金额 ≥ 最低打款额（如 100 元） | 系统校验 | 滚存至下一期合并打款 |
| ④ 入驻商无未处理的平台扣款/罚款 | 系统校验 | 先扣后打 |
| ⑤ 入驻商资质有效（营业执照未过期） | 系统校验 | 暂停打款，提醒入驻商更新 |

> **开票与打款的约束关系**：入驻商必须已完成所有本结算周期内发货订单的买家开票，平台才启动打款。未开票的订单对应的结算款暂扣在平台，待开票完成后在下一周期补打。

#### 13.5.2 打款流程

```
入驻商确认对账单 → 入驻商向买家开票 → 系统校验开票完成
                                         │
                               ┌─────────┴─────────┐
                               │ 全部开票           │ 部分未开票
                               ▼                   ▼
                         ERP 自动创建        暂扣未开票对应的结算款
                         付款申请单          已开票部分正常打款
                               │
                               ▼
                         财务审核
                         （批量审核）
                               │
                               ▼
                         财务通过网银/银企直连
                         打款至入驻商对公账户
                               │
                               ▼
                         打款完成 → 通知入驻商
                         记录银行流水号
                         生成付款凭证
```

#### 13.5.3 打款关键规则

| 规则 | 说明 |
|------|------|
| 打款账户 | 必须为入驻商**对公账户**（与营业执照名称一致），不允许打款至个人账户 |
| 打款金额 | 净结算额（已扣除所有费项 + 罚款 + 暂扣），精确到分 |
| 银行手续费 | 由收款方（入驻商）承担，在打款时扣除 |
| 打款凭证 | 银行回单自动归档至 ERP，入驻商可在 B2B 商户中心下载 |
| 打款失败 | 银行退票后自动重新发起，连续 3 次失败转人工处理 |

### 13.6 结算科目与会计分录

#### 13.6.1 代发模式（FBP）— 入驻商 M001 结算 224.50 元

## 16. ERP 税务稽查合规设计

本章从税务稽查视角出发，定义 ERP 系统必须满足的数据完整性、可追溯性和抗审查要求。核心原则：**ERP 的数据要经得起查——每一笔交易、每一分钱、每一张票，都能在系统里找到完整闭环**。

### 16.1 税务稽查的核心关注点

税务机关对电商平台及关联企业的稽查，通常围绕以下 6 个维度展开：

| 稽查维度 | 稽查内容 | ERP 必须提供的数据 |
|----------|----------|-------------------|
| **收入完整性** | 是否存在账外收入、少报收入 | 全量交易流水 + 收入明细账 + 按来源主体分类的收入汇总 |
| **成本真实性** | 采购成本是否真实、合理 | 入库单 + 采购发票 + 付款凭证 + 库存台账（移动加权平均计算过程） |
| **发票合规性** | 是否虚开、漏开、迟开 | 销项发票明细 + 进项发票明细 + 发票与交易的逐笔勾稽 |
| **资金流一致性** | 资金流向是否与发票流、货物流一致 | 银行流水 + 支付流水 + 收款与订单的逐笔匹配 |
| **库存真实性** | 账面库存是否与实际库存一致 | 库存余额表 + 收发存汇总表 + 盘点记录 |
| **关联交易** | 与入驻商之间的定价是否公允 | 仓配费定价依据 + 佣金率合理性说明 + 关联方清单 |

> **稽查红线**：如果 ERP 无法提供某笔交易的完整数据闭环（订单→支付→出库→开票→记账），该笔交易将被视为"存疑交易"，可能引发全额补税 + 罚款。

### 16.2 "三流一致"在ERP中的实现

税务机关要求**资金流、发票流、货物流三流一致**，ERP 必须在系统中建立三者之间的强制关联。

```
                    ┌─────────────────────────────┐
                    │        ERP 数据闭环          │
                    │                              │
    资金流          │  发票流          货物流       │
  ┌─────────┐      │ ┌─────────┐   ┌─────────┐     │
  │ 支付流水 │──────┼→│ 销售发票 │   │ 出库单  │     │
  │ 银行流水 │      │ │ 采购发票 │   │ 入库单  │     │
  │ 收款凭证 │      │ │ 进项认证 │   │ 库存台账│     │
  └────┬────┘      │ └────┬────┘   └────┬────┘     │
       │           │      │             │          │
       └───────────┼──────┼─────────────┘          │
                   │      │                        │
                   │  ┌───┴──────┐                 │
                   │  │  勾稽关系  │                 │
                   │  │ 不可断开  │                 │
                   │  └──────────┘                 │
                   └─────────────────────────────┘
```

ERP 需要实现的勾稽规则：

| 勾稽项 | 规则 | 校验方式 |
|--------|------|----------|
| **支付→订单** | 每笔银行/支付流水必须有对应的 B2B 订单 | 系统自动匹配，未匹配的流水标记为"待核实" |
| **订单→出库** | 已发货订单必须有对应的出库单 | 订单状态 = 已发货 时 `ship_order_id` 不可为空 |
| **出库→开票** | 已完成出库的自营品必须开具销项发票 | 每日扫描"已出库未开票"列表，超出时限告警 |
| **开票→收入确认** | 已开票金额必须计入当期收入 | 发票金额与收入科目的月结勾稽 |
| **入库→进项票** | 采购入库必须有对应的进项发票 | `purchase_receipt` 与 `invoice_in` 的强制关联 |
| **进项票→认证** | 收到的进项发票必须在规定期限内认证 | 发票接收日期 + 360 天超过未认证 → 告警 |

### 16.3 财务凭证链：从原始凭证到会计报表的可追溯

ERP 必须保证每一笔会计分录都能追溯到原始业务凭证。稽查时，检查员可能从任意一个环节切入，要求调取整个链路的数据。

#### 16.3.1 凭证五级追溯链

```
L5  会计报表
     ↑
L4  总账 / 明细账
     ↑
L3  记账凭证（会计分录）
     ↑
L2  业务单据（订单、入库单、出库单、费用单、对账单、结算单）
     ↑
L1  原始凭证（支付流水、发票、签收单、合同）
```

| 追溯级别 | 示例：一笔自营销售 | 数据来源 | 存储位置 |
|----------|-------------------|----------|----------|
| L1 原始凭证 | 微信支付流水 WX...01 + 销售发票 #12345678 | 微信/支付宝 / 开票系统 | B2B / ERP `tax_invoice_out` |
| L2 业务单据 | 销售订单 B...001 → 出库单 SHIP...001 | ERP `sales_order` / WMS | ERP / WMS |
| L3 记账凭证 | 借：银行存款 860 / 贷：主营业务收入 761.06 + 销项税 98.94 | ERP 财务模块 | ERP `gl_voucher` + `gl_voucher_line` |
| L4 明细账 | 主营业务收入-自营 7 月累计 | ERP 财务模块 | ERP `gl_account_ledger` |
| L5 会计报表 | 7 月利润表：营业收入 = 含自营 + 服务费 + 佣金 | ERP 报表模块 | ERP 报表 |

#### 16.3.2 ERP 必须维护的财务主数据

| 数据 | 要求 | 说明 |
|------|------|------|
| **科目表** | 与财政部《企业会计准则》一致，不可随意增删 | 收入科目须区分自营/服务费/佣金 |
| **税收分类编码** | 每个 SKU 绑定国家税务总局限定的税收分类编码 | 如 109051299（其他食品）、109041099（其他日用品） |
| **税率表** | 按税收分类编码维护销项税率（13%/9%/6%/0%）| SKU 入库时必须填写，不允许为空 |
| **供应商税率** | 每个供应商/入驻商维护进项税率 | 与入驻商的纳税人资质关联 |
| **辅助核算** | 收入按"来源主体"辅助核算，成本按"SKU+仓库"辅助核算 | 支持多维度查账 |

### 16.4 发票全生命周期管理

#### 16.4.1 发票状态流转（ERP侧）

```
                      ┌── 已作废
                      │
  待开具 → 已开具 → 已交付 → 已入账
                │                │
                └── 红冲（退货）  └── 已认证（进项票）
```

| 发票类型 | 生命周期节点 | ERP 必须记录的数据 |
|----------|-------------|-------------------|
| **销项发票**（自营品，平台→买家） | 待开 → 已开 → 已交付 → 已入账 | 发票号、开票日期、金额（含税/不含税/税额）、买方税号、关联订单号、关联出库单号 |
| **进项发票**（入驻商→买家，ERP备案） | 接收 → 登记 → 已入账 | 发票号、开票日期、金额、入驻商税号、关联订单号（用于来源申报佐证） |
| **进项发票**（供应商→平台，采购入库） | 接收 → 认证 → 已入账 | 发票号、认证日期、认证结果、关联入库单号 |

#### 16.4.2 发票与订单的逐笔勾稽

ERP 必须维护以下强制关联：

```sql
-- 发票-订单勾稽表
erp_invoice_order_mapping (
    id                  BIGINT PRIMARY KEY,
    invoice_id          BIGINT NOT NULL,
    invoice_type        VARCHAR(8) NOT NULL,   -- OUT(销项) / IN(进项)
    b2b_order_id        VARCHAR(32) NOT NULL,
    line_id             INT,                   -- 发票对应订单行（可空=整单）
    invoice_amount      DECIMAL(18,2) NOT NULL,
    matched_order_amount DECIMAL(18,2) NOT NULL,
    match_status        VARCHAR(16) DEFAULT 'MATCHED', -- MATCHED / PARTIAL / UNMATCHED
    INDEX idx_invoice (invoice_id),
    INDEX idx_order (b2b_order_id)
);
```

> **稽查场景**：检查员随机抽取一张发票号，要求 10 分钟内调出该发票对应的订单、支付流水、出库记录。ERP 必须能通过 `invoice_order_mapping` 表在 3 次查询以内完成全链路追溯。

### 16.5 库存台账的税务合规要求

税务机关对库存的稽查关注两点：① 账面库存与实物是否一致；② 成本结转是否合规。

| 要求 | ERP 实现 |
|------|----------|
| **收发存汇总表** | 按月生成，格式符合税务局模板：期初+本期入库-本期出库=期末，附出入库明细 |
| **成本计算过程可追溯** | 移动加权平均的每一次重新计算须保留快照：入库触发重算的时间、参与计算的批次、计算结果 |
| **不允许负库存** | 出库时校验 `available_quantity >= 出库数量`，负库存的出库单不可提交 |
| **盘点差异处理** | 盘盈/盘亏须生成独立的盘点调整单，经审批后记账，不直接修改库存余额 |
| **库存账与财务账勾稽** | 月末"库存商品"科目余额 必须 = WMS 实物库存 × 移动加权平均成本 |

```sql
-- 库存成本变动日志（每次移动加权平均重算时记录）
erp_cost_recalc_log (
    id              BIGINT PRIMARY KEY,
    sku_id          VARCHAR(32) NOT NULL,
    warehouse_id    VARCHAR(16) NOT NULL,
    trigger_type    VARCHAR(16) NOT NULL,       -- PURCHASE_RECEIPT / RETURN / CORRECTION
    trigger_doc_id  VARCHAR(32) NOT NULL,        -- 触发本次重算的单据号
    before_cost     DECIMAL(18,4) NOT NULL,      -- 重算前的单位成本
    after_cost      DECIMAL(18,4) NOT NULL,      -- 重算后的单位成本
    before_quantity DECIMAL(18,4) NOT NULL,      -- 重算前的库存数量
    trigger_quantity DECIMAL(18,4) NOT NULL,     -- 触发重算的入库数量
    after_quantity  DECIMAL(18,4) NOT NULL,      -- 重算后的库存数量
    created_at      DATETIME NOT NULL,
    INDEX idx_sku_wh (sku_id, warehouse_id)
);
```

> **稽查场景**：检查员质疑某 SKU 的 7 月出库成本偏高。ERP 必须能调出该 SKU 7 月份所有入库记录和每次成本重算日志，证明成本计算过程符合移动加权平均法。

### 16.6 资金流与税务的对应关系

平台统一收款后，ERP 必须在银行流水与业务交易之间建立逐笔对应关系：

| 资金流向 | ERP 银行日记账 | 关联业务单据 | 税务处理 |
|----------|---------------|-------------|----------|
| 买家付款（自营品） | 借：银行存款 | 销售订单 + 支付流水 | 平台记销项收入 |
| 买家付款（FBP代发品） | 借：银行存款 | 销售订单 + 支付流水 | 平台代收，入驻商记销项 |
| 买家付款（SOP自配品） | 借：银行存款 | 销售订单 + 支付流水 | 平台代收，入驻商记销项 |
| 平台打款给入驻商 | 贷：银行存款 | 结算单 + 打款凭证 | 入驻商确认收入 |
| 退款给买家 | 贷：银行存款 | 退货单 + 退款凭证 | 冲减原销项/原代收 |
| 费用支出 | 贷：银行存款 | 费用报销单 | 平台记费用/成本 |

**银行流水与业务单据的对账规则**：

```
ERP 每日自动执行：
  1. 拉取银行流水（网银/支付平台）
  2. 逐笔匹配 ERP 中的收款/付款记录
     → 流水金额 = 业务单据金额 → 自动匹配
     → 金额相近（±0.01）→ 标记为"待确认"（可能为手续费差异）
     → 无法匹配 → 标记为"未达账项"，生成银行余额调节表
  3. 未达账项超过 3 天 → 告警 + 人工排查
```

### 16.7 稽查追溯能力设计

#### 16.7.1 一笔交易的全链路追溯（5 分钟内完成）

税务稽查时，检查员可能从以下任意一个入口发起追溯，ERP 必须在 5 分钟内返回完整链路：

| 入口 | 追溯路径 | 期望响应时间 |
|------|----------|-------------|
| **订单号** | 订单 → 支付流水 → 出库单 → 发票 → 记账凭证 → 会计科目余额 | <30s |
| **发票号** | 发票 → 订单 → 支付流水 → 出库单 → 记账凭证 | <30s |
| **支付流水号** | 支付流水 → 订单 → 出库单 → 发票 → 记账凭证 | <30s |
| **SKU + 日期** | SKU → 当天所有销售订单 → 各自出库单 / 发票 / 支付流水 | <120s |
| **银行流水号** | 银行流水 → 业务单据(收款/付款) → 关联订单/结算单 | <30s |

#### 16.7.2 ERP 统一查询视图

建议在 ERP 中实现一个统一的"税务稽查追溯视图"，将五级数据关联在一起：

```sql
-- 税务稽查追溯视图（跨表联合查询，覆盖五级追溯链）
CREATE VIEW erp_tax_audit_trail AS
SELECT
    o.b2b_order_id,
    o.order_type,
    o.source_entity_name,
    p.payment_transaction_id,
    p.amount AS payment_amount,
    p.payment_time,
    s.ship_order_id,
    s.shipped_at,
    inv.invoice_no,
    inv.invoice_amount,
    inv.invoice_date,
    inv.invoice_type,
    v.voucher_no,
    v.voucher_date,
    vl.account_code,
    vl.account_name,
    vl.debit_amount,
    vl.credit_amount
FROM erp_order o
LEFT JOIN b2b_payment_record p ON o.b2b_order_id = p.b2b_order_id
LEFT JOIN erp_ship_order s ON o.b2b_order_id = s.b2b_order_id
LEFT JOIN erp_invoice_order_mapping iom ON o.b2b_order_id = iom.b2b_order_id
LEFT JOIN erp_tax_invoice inv ON iom.invoice_id = inv.id
LEFT JOIN erp_gl_voucher_line vl ON o.b2b_order_id = vl.ref_doc_id
LEFT JOIN erp_gl_voucher v ON vl.voucher_id = v.id;
```

### 16.8 审计日志设计

ERP 中所有影响财务数据的关键操作必须记录审计日志，满足税务机关对"不可篡改、不可抵赖"的要求。

#### 16.8.1 必须记录审计日志的操作

| 操作类型 | 示例 | 记录内容 |
|----------|------|----------|
| **数据创建** | 创建订单、创建发票、创建记账凭证 | 创建时间、操作人、数据内容 |
| **数据修改** | 修改订单金额、修改发票信息 | 修改前后值、修改时间、操作人、修改原因 |
| **数据删除** | 删除订单行（逻辑删除，不可物理删除） | 删除时间、删除前数据快照、操作人、审批记录 |
| **状态变更** | 订单审核通过、出库确认、发票开具 | 状态变更时间、操作人、变更前后状态 |
| **财务过账** | 凭证记账、成本结转、月结 | 操作时间、操作人、影响范围（科目/金额） |
| **配置变更** | 修改税率、修改结算费率 | 修改前后值、操作人、审批记录 |

#### 16.8.2 审计日志表结构

```sql
erp_audit_log (
    id              BIGINT PRIMARY KEY,
    entity_type     VARCHAR(32) NOT NULL,    -- ORDER / INVOICE / VOUCHER / SETTLEMENT / CONFIG
    entity_id       VARCHAR(64) NOT NULL,     -- 实体主键
    action          VARCHAR(16) NOT NULL,     -- CREATE / UPDATE / DELETE / STATUS_CHANGE / POST
    operator_id     VARCHAR(32) NOT NULL,     -- 操作人 ID
    operator_name   VARCHAR(64) NOT NULL,     -- 操作人姓名
    operator_ip     VARCHAR(45),             -- 操作人 IP
    old_value       TEXT,                    -- 修改前值（JSON）
    new_value       TEXT,                    -- 修改后值（JSON）
    change_summary  VARCHAR(500),            -- 变更摘要
    request_id      VARCHAR(64),             -- 请求追踪 ID（关联调用链）
    created_at      DATETIME NOT NULL,
    INDEX idx_entity (entity_type, entity_id),
    INDEX idx_operator (operator_id, created_at),
    INDEX idx_time (created_at)
);
```

> **设计原则**：审计日志对业务系统透明写入（AOP 拦截），不影响正常业务流程。日志表按月分区，超过 3 年的归档至冷存储。审计日志对 ERP 管理员不可删除，对系统管理员只读。

### 16.9 数据归档与保存期

| 数据类型 | 最低保存期 | 法律依据 | 归档策略 |
|----------|-----------|----------|----------|
| 交易记录（订单+支付） | **≥ 3 年** | 电子商务法第 31 条 | 3 年内在线（可即时查询），超过 3 年可归档但不可销毁 |
| 会计凭证（原始凭证+记账凭证） | **≥ 30 年** | 会计档案管理办法 | 永久保存电子版，纸质版 30 年 |
| 发票数据 | **≥ 5 年** | 发票管理办法 | 与交易记录同期保存 |
| 库存台账 | **≥ 10 年** | 企业会计准则 | 永久在线 |
| 合同 | **合同期满后 ≥ 5 年** | 合同法 / 民法典 | 电子版永久保存 |
| 审计日志 | **≥ 5 年** | 网络安全法 + 税务稽查惯例 | 3 年内在线，超过可归档 |
| 来源主体申报记录 | **≥ 10 年** | 税务稽查惯例 | 永久在线（因涉及税务归属的长期追征期） |

> **关键约束**：ERP 中的任何数据，标记为"已删除"时均为**逻辑删除**（`is_deleted=1`），不能物理删除。物理删除仅允许在超过法定保存期后执行，且须有审批记录。

### 16.10 税务稽查数据包（ERP 必须能一键导出）

以下清单是税务稽查时最可能被要求提供的数据，ERP 必须支持在 30 分钟内一键导出：

| 序号 | 数据项 | 导出格式 | 数据来源 |
|------|--------|----------|----------|
| 1 | 收入明细表（按来源主体分类） | Excel | `erp_revenue_detail` + `source_entity` |
| 2 | 销项发票明细 | Excel + XML | `erp_tax_invoice_out` |
| 3 | 进项发票明细（含认证状态） | Excel + XML | `erp_tax_invoice_in` |
| 4 | 库存收发存汇总表 | Excel | `erp_stock_balance` + `erp_stock_transaction` |
| 5 | 成本计算过程（移动加权平均日志） | Excel | `erp_cost_recalc_log` |
| 6 | 银行流水与业务单据对账表 | Excel | 银行流水 + `erp_receipt` + `erp_payment` |
| 7 | 入驻商结算明细（含费项） | Excel | `erp_settlement_order` + `erp_settlement_fee_detail` |
| 8 | 来源主体申报记录 | Excel | B2B `source_attribution_report` |
| 9 | 会计分录序时簿 | Excel | `erp_gl_voucher` + `erp_gl_voucher_line` |
| 10 | 操作审计日志 | CSV | `erp_audit_log` |
| 11 | 合同清单（与入驻商的结算费率/佣金率） | PDF + Excel | 合同管理系统 |
| 12 | 盘点报告（最近一次） | Excel + PDF | WMS 盘点模块 |

### 16.11 ERP 税务合规自检清单

ERP 上线前必须通过以下自检：

| # | 检查项 | 判断标准 | 不通过后果 |
|---|--------|----------|-----------|
| 1 | 全链路追溯 | 从任意订单号/发票号/支付流水号出发，5 分钟内核出完整数据闭环 | 稽查时无法自证 → 存疑交易补税 |
| 2 | 三流勾稽 | 每月末：发票金额 = 出库金额 = 收款金额（差异率 < 0.1%） | 三流不一致 → 虚开发票嫌疑 |
| 3 | 来源主体不丢失 | 每日扫描 `any_loss_flag=1` = 0 条 | 来源丢失 → 平台多承税负 |
| 4 | 发票-订单逐笔匹配 | `erp_invoice_order_mapping` 表中已发货订单 100% 匹配发票 | 未开发票 → 隐匿收入嫌疑 |
| 5 | 库存账实一致 | 月末库存科目余额 = WMS 实物 × 成本，差异 < 0.5‰ | 虚增/虚减成本 |
| 6 | 成本计算可追溯 | `erp_cost_recalc_log` 记录完整，每次重算原因可追溯 | 成本不实 → 多结转/少结转 |
| 7 | 不可物理删除 | 所有表 `is_deleted` 逻辑删除，无 DELETE 语句 | 数据完整性缺失 |
| 8 | 审计日志覆盖 | 所有关键操作（创建/修改/删除/过账）有日志 | 操作无法追溯 |
| 9 | 数据保存期 | 交易记录 ≥ 3 年，会计凭证 ≥ 30 年 | 违规销毁档案 |
| 10 | 稽查数据包导出 | 12 项数据包全部可在 30 分钟内导出 | 稽查时被动、延误 |

## 21. 关键设计决策

| # | 决策项 | 结论 | 理由 |
|---|--------|------|------|
| 1 | 统一收款方 | **商城主体公司商户号** | 资金入口唯一，支付体验统一 |
| 2 | **税务归属机制** | **平台向税务提交来源主体申报** | 税务不自动归集；平台分不清→全部记入平台 |
| 3 | 发票流 | **谁被税务认定为来源主体，谁开票** | 自营→平台开票；代发/自配→入驻商开票 |
| 4 | **来源溯源底线** | **B2B→ERP→WMS 全链路不可丢失来源标记** | 丢失一笔 = 平台多承担一笔税负（约 13%+） |
| 5 | 来源申报方 | **B2B 统一提交申报** | B2B 是订单创建方，掌握最完整的来源信息 |
| 6 | 三系统数据库 | **各自独立**，不共享 | 独立扩缩容，避免耦合 |
| 7 | ERP+WMS初期部署 | **同一应用**，`com.erp.wms` 包 | 降低初期成本，后期可拆分 |
| 8 | 库存可用量权威来源 | **ERP** | 统一口径 |
| 9 | WMS 是否知道税务 | **否**，仅透传 `owner_id` | 职责单一 |
| 10 | 订单拆单 | SOP 按入驻商拆；自营+FBP 合并 | 同仓+同配送 |
| 11 | ERP 区分自营/代发 | 订单行级 `sourceEntityTaxId` | 同一订单可能多来源 |
| 12 | WMS 多货主拣货 | 波次按 owner_id 拆，复核台合并 | 库存隔离，物流共包裹 |
| 13 | 来源申报频率 | **按日**（T+1） | 确保及时申报，减少"待匹配"积压 |
| 14 | 来源不明处理 | 立即告警 + 人工排查 + 24h内补齐 | 超过申报窗口期 → 平台承担 |
| 15 | 纳税义务发生时间 | 自营/FBP：WMS出库扫描；SOP：入驻商发货回传 | 增值税暂行条例 |
| 16 | **结算分佣模型** | **FBP：按合同费率逐笔扣除仓配费；SOP：按佣金率扣除；结算结果不可人工修改** | 保障入驻商公平，防止平台舞弊 |
| 17 | **对账确认机制** | **超期未确认默认确认，确认后不可再提异议** | 避免对账流程无期限拖延 |
| 18 | **打款前置条件** | **入驻商必须先完成买家开票，平台才启动打款** | 确保发票流完整，降低税务稽查风险 |
| 19 | **审计日志** | **所有影响财务数据的操作强制记录审计日志，对管理员只读** | 满足税务稽查"不可篡改、不可抵赖"要求 |
| 20 | **数据物理删除** | **禁止物理删除，统一逻辑删除（is_deleted=1）；超过法定期限后经审批物理删除** | 会计档案管理办法、电商法第31条 |
| 21 | **五级追溯链** | **原始凭证→业务单据→记账凭证→明细账→报表，任一环节可3次查询内追溯到源头** | 税务稽查核心要求 |

## 22. 风险与缓解

| # | 风险 | 严重程度 | 缓解措施 |
|---|------|----------|----------|
| **1** | **来源主体标记在 B2B→ERP→WMS 链路中丢失** | 🔴🔴 **极高** | ERP 来源传递日志记录每个环节；每日扫描 `any_loss_flag=1` 并告警；丢失即人工补录 |
| **2** | **来源申报与支付流水匹配失败 → 交易记入平台** | 🔴🔴 **极高** | 每日自动对账；匹配失败队列；申报前预校验；24h 内人工补齐 |
| **3** | **入驻商纳税人识别号不实 → 来源申报被拒** | 🔴 高 | 入驻时与国家企业信用信息公示系统交叉校验；定期复核 |
| **4** | 入驻商不出具发票 → 买家投诉 | 🔴 高 | 入驻协议强制开票义务；逾期暂扣结算款 |
| **5** | 入驻商营业执照/资质过期 | 🔴 高 | B2B 每天扫描即将过期执照；超期限制接单 |
| **6** | ERP 和 WMS 拆不开 | 🟡 中 | 从第一天起 WMS 包不直接访问 ERP 的 Mapper |
| **7** | 库存数据不一致 → 超卖 | 🟡 中 | 定时全量对账 + 差异告警 |
| **11** | **税务稽查时无法提供完整数据闭环** | 🔴🔴 **极高** | 每日自动检查五级追溯链完整性；稽查数据包每季度预演导出一次 |
| **12** | **三流不一致（发票≠出库≠收款）** | 🔴 高 | 月末自动勾稽，差异率 > 0.1% 告警；差异订单冻结暂不结算 |
| **13** | **入驻商结算纠纷（费项计算争议）** | 🟡 中 | 出库扫描记录时间戳+批次，结算单附逐笔费项明细，支持在线申诉 |
| **14** | 成本重算日志缺失 → 成本结转不合规 | 🔴 高 | 每次移动加权平均重算强制记录日志，日志不可删除 |
| **15** | 交易记录保存不足 3 年 | 🟡 中 | 归档策略，3 年内不可物理删除；每年全面检查一次 |
| **16** | 库存账实不一致 | 🟡 中 | 定时全量对账 + 差异告警；月末库存科目余额 = WMS 实物 × 成本 |
| **17** | 混合订单行级来源拆分错误 | 🟡 中 | 下单时 B2B 校验每行 `sourceEntityTaxId` 非空；ERP 二次校验 |
| **18** | 各系统金额精度不一致 | 🟢 低 | 全系统统一 `DECIMAL(18,2)` |
| **19** | API 版本不兼容 | 🟢 低 | `/v1/` 版本号，契约测试 |

## 23. 前端购物车拆单交互

买家购物车中包含多来源商品时，提交时自动拆分为多个 B2B 订单：

```
购物车：自营(SKU-A) + FBP(SKU-B,M001) + FBP(SKU-C,M002) + SOP(SKU-D,M003) + SOP(SKU-E,M004)
                                    │
                    按「来源主体+履约方」拆分
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
   B2B Order #1    B2B Order #2   B2B Order #3
   平台履约(合并)    M003自配       M004自配
   source=MIXED    source=M003    source=M004
   → ERP → WMS     → 仅B2B        → 仅B2B

Order #1 行级：
  SKU-A: source=平台（自营）
  SKU-B: source=M001（FBP）
  SKU-C: source=M002（FBP）
  → 同一包裹发货，但来源申报时分三行申报
```

前端提示："您的订单包含多个商家的商品，将拆分为 3 个订单分别处理。同一仓库的商品将合并配送。"
