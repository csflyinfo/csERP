# B2B-ERP-WMS 订单拆分与系统交互详细设计

## 1. 文档目的

回答架构设计中两个关键的操作性问题：

1. **B2B 同一客户订单如何拆分** — 购物车里混了自营品、代发品、自配品，结账时拆成几个订单？
2. **ERP 如何区分自营与代发** — 自营和代发共用同一套仓库和配送，ERP 如何在不混淆货权的前提下做好核算？
3. **三系统交互细节** — 从买家下单到出库结算，每个阶段三个系统如何协作、传递什么数据？

## 2. 订单拆分策略

### 2.1 问题场景

买家在同一购物车中添加了：

| 商品 | 履约类型 | 货主 | 仓储方 | 配送方 |
|------|----------|------|--------|--------|
| SKU-A × 5 | 自营 | 经销商 | 经销商仓库 | 经销商 |
| SKU-B × 3 | FBP | 入驻商 M001 | 经销商仓库 | 经销商 |
| SKU-C × 2 | FBP | 入驻商 M002 | 经销商仓库 | 经销商 |
| SKU-D × 1 | SOP | 入驻商 M003 | 入驻商 M003 | 入驻商 M003 |
| SKU-E × 4 | SOP | 入驻商 M004 | 入驻商 M004 | 入驻商 M004 |

**核心问题**：结账时生成几个 B2B 订单？

### 2.2 拆分规则

```
                         ┌─────────────────────────┐
                         │      B2B 购物车           │
                         │ 自营 + FBP + SOP 混装     │
                         └───────────┬─────────────┘
                                     │
                    ┌────────────────┼────────────────┐
                    │                │                │
             按「谁来履约」拆分       │                │
                    │                │                │
              ┌─────┴─────┐    ┌────┴────┐    ┌─────┴─────┐
              │ 经销商履约  │    │ M003履约 │    │ M004履约   │
              │ (SELF+FBP) │    │  (SOP)   │    │  (SOP)     │
              └─────┬─────┘    └────┬────┘    └─────┬─────┘
                    │               │               │
                    ▼               ▼               ▼
             B2B Order #1     B2B Order #2    B2B Order #3
           (PLATFORM_FULFILLED)    (SOP)           (SOP)
                    │               │               │
                    ▼               ▼               ▼
              ERP + WMS         入驻商自系统      入驻商自系统
```

**拆分规则（两级）**：

| 规则 | 说明 | 原因 |
|------|------|------|
| **规则 1**：SOP 与平台履约分离 | SOP 商品不跟自营/FBP 混在一个订单 | 不同的履约方，不同的物流，不同的售后 |
| **规则 2**：不同 SOP 入驻商各自独立 | M003 和 M004 各自一个 B2B 订单 | 独立发货、独立开票、独立结算 |
| **规则 3**：自营 + FBP **合并**为一个 B2B 订单 | SKU-A/B/C 进同一个订单 | 同一仓库、同一配送司机、同一运单号、买家体验好 |

### 2.3 为什么自营和 FBP 合并而不是分开

| 维度 | 合并（推荐） | 分开 |
|------|------------|------|
| 买家体验 | ✅ 一个订单，一次收货 | ❌ 两个订单，可能两次收货 |
| 配送成本 | ✅ 一次送货 | ❌ 可能两次送货 |
| 物流跟踪 | ✅ 一个运单号 | ❌ 两个运单号 |
| ERP 复杂度 | 🟡 需要行级货主区分 | 🟢 简单 |
| WMS 复杂度 | 🟡 需要多 owner 拣货合并 | 🟢 简单 |

**结论**：ERP/WMS 多付出的复杂度远小于改善买家体验和降低配送成本的收益，推荐合并。

## 3. ERP 如何区分自营与代发订单

### 3.1 核心设计：行级履约标记

原架构文档中 `fulfillmentType` 放在订单头（`"fulfillmentType": "SELF"`），但合并订单后同一个订单里既有自营又有 FBP，必须在**订单行**上加标记。

```json
// B2B → ERP 订单推送（修订版）
{
  "b2bOrderId": "B2026072100001",
  "orderType": "PLATFORM_FULFILLED",
  "buyerId": "B001",
  "totalAmount": 860.00,
  "lines": [
    {
      "lineId": 1,
      "skuId": "SKU_A",
      "quantity": 5,
      "salePrice": 100.00,
      "fulfillmentType": "SELF",       // ← 行级标记
      "merchantId": null               // ← 自营无商户
    },
    {
      "lineId": 2,
      "skuId": "SKU_B",
      "quantity": 3,
      "salePrice": 80.00,
      "fulfillmentType": "FBP",        // ← 行级标记
      "merchantId": "M001",            // ← 代发有商户
      "settlementPrice": 55.00         // ← 代发有结算价
    }
  ],
  "shippingAddress": {},
  "buyerRemark": "周一送货"
}
```

### 3.2 ERP 订单内部结构

ERP 接收到平台履约订单后，内部存储为：

```
erp_order（头）
├── order_id = "B2026072100001"
├── order_type = "PLATFORM_FULFILLED"
├── buyer_id = "B001"
├── total_amount = 860.00
│
└── erp_order_lines（行）
    ├── line 1: sku=SKU_A, qty=5, price=100.00, fulfillment_type=SELF, merchant_id=NULL
    ├── line 2: sku=SKU_B, qty=3, price=80.00,  fulfillment_type=FBP,  merchant_id=M001
    └── line 3: sku=SKU_C, qty=2, price=60.00,  fulfillment_type=FBP,  merchant_id=M002
```

**区分逻辑**：ERP 所有处理逻辑按 `fulfillmentType` 字段分支，核心差异如下：

### 3.3 自营 vs 代发：ERP 全流程差异对照

| 处理环节 | 自营（SELF） | 代发（FBP） |
|----------|------------|------------|
| **下单库存校验** | 校验经销商自有库存可用量 | 校验该入驻商在 WMS 的可用量 |
| **库存锁定** | 锁定经销商自有库存 | 锁定入驻商代管库存（owner_id = merchant_id） |
| **WMS 发货单** | owner_id = 0（经销商） | owner_id = merchant_id |
| **WMS 拣货** | 从自营库位拣货 | 从入驻商专属区/混合区拣货 |
| **出库成本核算** | ✅ 移动加权平均法计算 COGS | ❌ 不核算成本（货权归属入驻商） |
| **出库后记账** | 借记：主营业务成本<br>贷记：库存商品 | 借记：代发出库商品（数量辅助核算）<br>贷记：代管库存商品 |
| **收入确认** | 借记：应收账款/银行存款<br>贷记：主营业务收入 | **不确认销售收入** |
| **结算** | 无 | 生成应付入驻商货款 + 应收入驻商仓配费 |
| **发票** | 经销商 → 买家 | 入驻商 → 买家 |

## 5. WMS 内部多货主合并拣货设计

当 ERP 下发的发货单同时包含自营和 FBP 行时，WMS 的执行逻辑如下：

### 5.1 WMS 发货单内部结构

```json
{
  "shipOrderId": "SO001",
  "warehouseId": "WH01",
  "b2bOrderId": "B2026072100001",
  "consolidated": true,          // 标记为合并包
  "lines": [
    { "lineId": 1, "skuId": "SKU_A", "qty": 5, "ownerId": 0,         "batchNo": "B20260715" },
    { "lineId": 2, "skuId": "SKU_B", "qty": 3, "ownerId": "M001",    "batchNo": "B20260701" },
    { "lineId": 3, "skuId": "SKU_C", "qty": 2, "ownerId": "M002",    "batchNo": "B20260710" }
  ]
}
```

### 5.2 波次与拣货任务拆分

```
                    WMS 发货单 SO001
                           │
                    生成波次 Wave-001
                           │
              ┌────────────┼────────────┐
              ▼            ▼            ▼
        PickTask-1    PickTask-2    PickTask-3
        owner = 0     owner = M001  owner = M002
        SKU_A × 5     SKU_B × 3    SKU_C × 2
        库位 L01-A     库位 L05-B    库位 L08-C
              │            │            │
              └────────────┼────────────┘
                           ▼
                    复核台合并
                    3 个拣货容器 → 1 个包裹
                           │
                           ▼
                    包裹: 运单号 SF1234567890
                    内含: SKU_A×5 + SKU_B×3 + SKU_C×2
```

**关键设计点**：

| 环节 | 规则 |
|------|------|
| 拣货任务拆分 | 按 owner_id 拆分，每个 owner 一个拣货任务（同一 SKU 不同 owner 的货物理位置不同） |
| 拣货顺序 | WMS 波次引擎自动排最优路径（不区分 owner，按库位物理顺序排列） |
| 复核合并 | 所有拣货任务完成后统一到复核台，合为一个包裹 |
| 包裹内容记录 | 包裹内记录每个 SKU 的 owner_id → 出库后 ERP 据此做分货主结算 |

### 5.3 PDA 拣货界面示意

拣货员用 PDA 扫描 Wave-001，系统按最优路径排列：

```
┌─────────────────────────────────┐
│  波次: Wave-001                  │
│  发货单: SO001                   │
│                                 │
│  ☐ L01-A-03 → SKU_A × 5        │
│    货主: 自营                    │
│    批次: B20260715               │
│                                 │
│  ☐ L05-B-01 → SKU_B × 3        │
│    货主: XX商贸(M001)            │
│    批次: B20260701               │
│                                 │
│  ☐ L08-C-02 → SKU_C × 2        │

## 7. 关键设计决策（补充）

在架构文档 12 章 10 条决策基础上，补充以下 4 条：

| # | 决策项 | 结论 | 理由 |
|---|--------|------|------|
| 11 | B2B 购物车混装时如何拆单 | SOP 按入驻商拆；自营+FBP 合并为一个平台履约订单 | 同一仓库+同一配送 → 一次收货，改善买家体验 |
| 12 | ERP 订单区分自营/代发方式 | 订单头 `orderType` + 订单行 `fulfillmentType` 联合标记 | 同一订单可能同时含自营和代发行，行级标记是唯一准确的方式 |
| 13 | WMS 一个发货单含多货主时 | 波次系统按 owner_id 拆拣货任务，复核台合并为同一包裹 | 保持 WMS 库存隔离，但物流层面允许共包裹 |
| 14 | SOP 订单是否进入 ERP | 否。SOP 订单 B2B 独立闭环，与 ERP/WMS 零交互 | 经销商不碰货、不碰钱、不负责履约，进入 ERP 没有业务意义 |

## 8. 前端购物车拆单交互建议

买家在 B2B 前端购物车下单时：

```
┌─────────────────────────────────────────────────────────┐
│                     结算页                               │
│                                                         │
│  ┌─ 包裹 1：平台仓配 ──────────────────────────────┐    │
│  │  SKU-A (自营)           ¥100.00 × 5  = ¥500.00 │    │
│  │  SKU-B (XX商贸)          ¥80.00 × 3  = ¥240.00 │    │
│  │  SKU-C (YY食品)          ¥60.00 × 2  = ¥120.00 │    │
│  │  小计: ¥860.00  预计 1 个工作日送达             │    │
│  └─────────────────────────────────────────────────┘    │
│                                                         │
│  ┌─ 包裹 2：XX商贸 自行配送 ───────────────────────┐    │
│  │  SKU-D (XX商贸)         ¥200.00 × 1  = ¥200.00 │    │
│  │  小计: ¥200.00  预计 2-3 个工作日送达            │    │
│  └─────────────────────────────────────────────────┘    │
│                                                         │
│  ┌─ 包裹 3：YY食品 自行配送 ───────────────────────┐    │
│  │  SKU-E (YY食品)          ¥50.00 × 4  = ¥200.00 │    │
│  │  小计: ¥200.00  预计 2-3 个工作日送达            │    │
│  └─────────────────────────────────────────────────┘    │
│                                                         │
│  合计: ¥1,260.00  共 3 个包裹                           │

└─────────────────────────────────────────────────────────┘

**交互要点**：
- 购物车自动按"谁来配送"分组展示，买家一目了然
- 平台仓配的包裹明确标注"预计 1 个工作日"（自有仓配时效可控）
- SOP 包裹标注入驻商名称和预计时效（由入驻商在商户中心配置）
- 下单后生成 3 个 B2B 订单（内部），买家在订单列表看到 3 个订单，但支付合并一次完成
