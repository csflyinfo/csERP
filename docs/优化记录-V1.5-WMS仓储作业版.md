## V78 — 库区/库位/容器/库位库存底座（2026-08-22）

### 背景
V1.0 ERP 只有仓库（`base_warehouse`）和货位字段（`base_goods.location` 文本），没有库区/库位/容器/实物库存账，WMS 作业无处落地。V78 是 V1.5 的地基。

### 数据库
新建表：
- `wms_zone` 库区：zone_id/zone_code/zone_name/warehouse/zone_type/pick_seq/frozen/remark；`zone_type` 六类（STORAGE 储区/RECEIVE 收货/SHIP 发货/PICK 拣货/SORT 分拣/COLLECT 集货）。
- `wms_bin` 库位：bin_id/bin_code/bin_name/warehouse/zone_code/bin_type(SHELF/FLOOR/COLLECT/STAGE/PICK)/aisle/slot/layer/capacity_qty/used_qty/frozen/status。
- `wms_container` 容器（托盘/周转箱/笼车）。
- `wms_bin_stock` 实物位置账（goods/warehouse/batch/bin/container 维度，含 locked_qty）。
- `wms_bin_stock_log` 库位流水（IN/OUT/MOVE/ADJUST）。
- `sys_param_runtime` 插入 P0129–P0154 共 26 个 WMS 参数（波次/拣货/批次/复核/集货/异常等）。

种子数据：总仓下 A 区(整箱储区)、B 区(拆零储区)、COL 集货区、SORT 分拣区 + 5 个库位。

### 关键设计决策
- **账实分离**：`wms_bin_stock` 只记位置与数量，财务金额永远走 `InventoryCostService`，WMS 不写钱。
- **无外键**：与既有 WMS 风格一致，靠服务层校验。
- **H2 MODE=MySQL + CASE_INSENSITIVE_IDENTIFIERS**：SQL 别名禁止驼峰（会被大写），应用层用 `TmsUtil.queryCamel` 转换。

### 影响文件
- `backend/src/main/resources/db/migration/V78__wms_base_zone_bin.sql`
- 后端 `com.erp.wms.*` 首批类、前端 `WmsZone.vue`（后在 V83 拆分）

## V79 — 出库波次、拣货任务、集货位分配（2026-08-22）

### 背景
销售订单审核后需要按波次集中下放、拣货、集货、复核、装车，对接 TMS。

### 数据库
- `wms_wave` 波次、`wms_wave_detail` 波次明细（含 alloc_batch_no/alloc_bin_code/alloc_zone_code/collection_bin_code）。
- `wms_pick_task` 拣货任务（按库区拆分，含 source_orders 逗号列表）。
- `wms_outbound_check` 出库复核记录、`wms_handover` 装车交接、`wms_dispatch_link` WMS↔TMS 关联（以销售订单号贯穿）。

### 关键流程
- 下放：锁批次（`InventoryCostService.lockBatch`）→ 选拣货库位（`pickBin`）→ 物理预占（`lockBinStock`）→ 写波次明细 → 按库区生成拣货任务 → 一单一集货位分配。
- 拣货完成 → 自动生成并审核销售出库单 → 扣库存。
- 装车：只确认实物，不扣账；未发车改派改源单司机字段，不生新单。

### 影响文件
- `V79__wms_outbound_wave.sql`
- `WmsOutboundService.java`、`WmsController.java`、`WmsAppController.java`
- 前端 `WmsPreallocation.vue`、`WmsWave.vue`、`WmsPick.vue`、`WmsCheck.vue`

## V80 — 出库下放幂等 + 孤儿 PENDING 自愈（2026-08-23）

### 问题
生产环境发现下放偶发产生重复的销售出库单：网络重试/重复点击导致同一订单生成两张出库单。根因是下放接口没有幂等键；同时 `sales_outbound` 存在历史孤儿 PENDING 记录（source_order_no 重复），阻塞了"一订单一出库单"唯一索引建立。

### 修复
- V80 迁移在 `CREATE UNIQUE INDEX uk_sales_outbound_source_order` 之前**先 DELETE 孤儿 PENDING**（自愈），然后建唯一索引。
- `WmsOutboundService.release()` 增加重复下放保护：`SELECT COUNT(*) FROM wms_wave_detail WHERE source_order_no=?`，已在波次中的订单拒绝二次下放。
- 错误信息明确指出订单号，便于现场定位。

### 生产事故与恢复（2026-08-23 晚）
- 事故现象：用户在"新建分类/品牌"弹窗保存时收到"服务响应异常"。
- 根因：当天早前一次失败的 V80 迁移（CREATE UNIQUE INDEX 撞孤儿 PENDING）在 `flyway_schema_history` 留下 `success=FALSE` 记录，导致后端启动时 Flyway 中止在 V80，V81–V83 全部未跑，8080 端口根本没起来。前端 Vite 代理拿到 connection refused 被翻译成"服务响应异常"。
- **不是 V83 代码 bug**。
- 处理：备份 `erp-v1.mv.db` → H2 Shell `DELETE FROM flyway_schema_history WHERE success=FALSE`（V80 当时已回滚、索引未建成，删历史安全）→ 重启后端，V80（带自愈）→V81→V82→V83 在 0.373s 内顺序应用成功 → 验证分类/品牌保存返回 code=0。
- 历史数据完好（4 分类/2 品牌/3 商品/18 销售订单/16 发货单/4 库区/5 库位）。

### 教训
- Flyway 失败必须查 `flyway_schema_history.success`，不能只看日志；
- 新建唯一索引前先自愈重复数据，把自愈写进迁移本身（而不是靠人工）；
- 生产 DB 任何写操作前先 `cp erp-v1.mv.db erp-v1.mv.db.bak-...`。

## V81 — WMS 系统参数数字化枚举（2026-08-23）

### 背景
V78 的 WMS 参数用英文字符串枚举（ORDER/SUMMARY/PICK_SORT/...），前端下拉、后端比较、报表分组都要字符串匹配，且不同参数的取值长度不一。V81 把所有枚举型参数统一数字化（0/1/2/...），后端 `SysParamService.getInt` 强类型读取。

### 改动
- 迁移把 `WMS_PICK_MODE` 等参数的 `param_value/default_value` 从英文转为数字，并通过 `option_json` 提供 value/label 映射（前端下拉直接渲染）。
- 后端兼容：`WmsOutboundService.normalizeEnum()` 同时接受旧英文与新数字，返回数字。
- 不改 PRD 文案中对英文枚举的业务描述（ORDER/SUMMARY 等仍作为术语），但落库与接口传值都是数字。

### 注意
数字化后**旧波次数据里的 pick_mode 字段可能仍是英文**，读取时统一走 normalizeEnum。新数据全部是数字字符串。

## V82 — 内部调拨/其它入库 + 收货/复检/上架任务表（2026-08-23）

### 背景
V79 只覆盖了采购入库的主链路，实际仓内还有调拨入库、其它入库、退货入库等多来源；且 V78 阶段把入库任务建在 `wms_inbound_task` 上，字段在多次迭代中不够用。

### 数据库
- 新建/补齐 `wms_inbound_task`（头）、`wms_inbound_task_detail`（明细，含 recommend_bin/actual_bin/qualified_qty/unqualified_qty）、`wms_putaway_task` 上架任务（含 recommend_bin/actual_bin/assignee）、`wms_recheck_record` 复检记录。
- 新增内部调拨单 `wms_internal_transfer`（从储区到储区/仓到仓，不涉及采购销售）。

### 关键流程
- 采购到货 → PDA 收货（盲收/超收容差）→ 可选复检 → 生成上架任务（推荐库位）→ PDA 扫库位上架 → 写 `wms_bin_stock` → 全部上架完成回调采购入库单审核（`InventoryCostService.purchaseInbound`）。
- 内部调拨走 `wms_internal_transfer`，调出方扣减、调入方新增，不产生应收应付。

### 影响文件
- `V82__wms_internal_inbound.sql`
- `WmsInboundService.java`、`WmsInternalService.java`
- 前端 `WmsInbound.vue`、`WmsInternal.vue`

## V83 — 库区/库位治理 + 拣货位商品绑定 + 预分配按线路（2026-08-23）

### 背景
用户反馈四个问题：
1. 库区管理不能新建；
2. 库位需要新建；
3. 拣货位商品绑定（在哪绑、怎么解绑/转移）缺失，PDA 无法快速改绑；
4. 预分配模块没有"左线路右订单"的交互。

### 数据库
新建：
- `wms_bin_goods_binding` 拣货位/备货位/整托位与商品的固定绑定（binding_type=PICK/RESERVE/BULK，min_qty/max_qty/replenish_to_qty 驱动补货，active_flag Y/N）。
- `wms_binding_change_log` 绑定/解绑/改绑/转移审计日志（含 source=PC/PDA）。

**唯一约束设计**（重要）：
- 只有 `uk_bin_goods UNIQUE (warehouse, bin_code, goods_code)`，保证同库位+同商品只有一条历史记录（重复绑定走 UPDATE 重新激活）。
- **没有**加 `uk_goods_warehouse (warehouse, goods_code, binding_type)`，因为"一品一位"约束如果放 DB，转移/解绑后保留的历史行（active_flag=N）会与新行冲突。V83 把"同仓+同品+同类型只能有一条生效绑定"放在 `WmsBindingService` 服务层（bind/transfer 时先把其它 active 置 N）。
- 这是 V83 冒烟阶段踩出来的教训：第一版迁移加了这个 DB 唯一约束，转移接口直接被挡。删掉约束、保留服务层校验后通过。

### 后端
- `WmsBindingService`：list/bind/unbind/transfer/updateThresholds/lookup。transfer 自动解析目标库区（不必前端传 toZoneCode），写 TRANSFER 日志。
- `WmsController`：新增 `/wms/warehouse/list`（带 zone_count）、库区分页/save/toggle/delete、库位分页/save/toggle/delete、绑定 page/bind/unbind/transfer/thresholds/log-page、预分配 route-pool/order-pool/by-route。
- 库区/库位删除守卫：库区下有库位不允许删；库位在 wms_bin_stock 有库存不允许删，删库位时同步停用该库位上的绑定。
- `WmsOutboundService.routePool()` 按 `c.route_line` 分组（无线路用 `__NONE__` 哨兵），统计订单数/件数/金额，关联 base_route_line 司机车辆；`orderPoolByRoute()` 按线路筛未分配订单。
- `WmsAppController` 加 PDA 绑定端点（/lookup/bind/unbind/transfer），强制 source=PDA。

### 前端
- 新建/重写：`WmsZoneMgmt.vue`（左仓库右库区）、`WmsBinMgmt.vue`（左库区右库位）、`WmsPickBinding.vue`（含阈值/转移/解绑/变更日志抽屉）、`WmsBinStock.vue`、`WmsException.vue`、`WmsPreallocation.vue`（左线路卡片右订单）。
- 删除旧的 tabbed `WmsZone.vue`，路由与兜底菜单同步更新。

### 影响文件
- `V83__wms_zone_bin_binding.sql`、`WmsBindingService.java`、`WmsController.java`、`WmsAppController.java`、`WmsOutboundService.java`
- 前端 6 个 vue 文件 + router + fallback-menus

## V84 — 拣货方式下沉到库区 + 库区温区（2026-08-23）

### 背景
用户反馈两点：
1. 仓库级 `WMS_PICK_MODE` 只能配一个默认值，实际现场"整件区按单拣、拆零区合拣"是同一仓并存的常态，必须按库区配。
2. 入库推荐只按 `bin_type='SHELF'` 过滤，不看商品的温区（常温/冷藏/冷冻/恒温/避光，即 `base_goods.storage_property`），冷藏品会被推荐到常温区。

### 数据库
`wms_zone` 新增三列：
- `pick_method`：CASE_PICK 整件单拣 / CASE_MERGE 整件合拣 / BULK_PICK 拆零单拣 / BULK_MERGE 拆零合拣；空=未配置，走 WMS_PICK_MODE 兜底。
- `sort_mode`：合拣时的分拣方式 PICK_THEN_SORT 先拣后分 / SORT_WHILE_PICK 边拣边分；单拣为 NULL。
- `storage_property`：温区，值域对齐 `base_goods.storage_property`（常温/冷藏/冷冻/恒温/避光）。

冗余字段（为了标签直接打印、不 JOIN）：
- `wms_pick_task` 加 pick_method/sort_mode（下放时按库区冻结当时值，库区配置后改不影响历史任务）。
- `wms_inbound_task_detail`、`wms_putaway_task` 各加 recommend_zone_code/recommend_zone_name/recommend_storage_prop。

种子：A 区 → 常温 + CASE_PICK；B 区 → 常温 + BULK_MERGE + PICK_THEN_SORT。

**WMS_PICK_MODE 参数不删、不改值**，V84 只改 remark 为"库区未配置时的兜底"，避免破坏历史波次数据。

### 后端
- `WmsController.saveZone()` 增加枚举校验：非法 pickMethod/sortMode/storageProperty 静默清空（不 500）；非 *_MERGE 时强制 sort_mode=NULL。
- `WmsInboundService.recommendBin()` 重写为返回 `Recommendation(binCode, zoneCode, zoneName, storageProperty)` record，推荐顺序：
  1. 同品已有库存库位（一品一位就近补位）；
  2. 商品档案 `base_goods.location` 默认库位；
  3. **温区匹配的空 SHELF 库位**（`z.storage_property = goods.storage_property`）；
  4. 任意未冻结空 SHELF 库位兜底（不阻断收货，标签上会显示实际温区，便于人工识别未匹配）。
- `WmsOutboundService.createPickTask()` 插入任务时按 warehouse+zone_code 查库区 pick_method/sort_mode 落库，波次级 pickMode 作为兜底。

### 前端
- `WmsZoneMgmt.vue`：表单加三个字段。库区类型非 PICK/STORAGE 时自动清空并禁用拣货方式；选了 *_MERGE 才显示 sort_mode 下拉并默认 PICK_THEN_SORT；存储属性下拉直接给常温/冷藏/冷冻/恒温/避光。列表加"拣货方式""存储属性"两列，温区用彩色 tag。
- `WmsInbound.vue`：上架任务和入库详情加"推荐库区/温区"列，收货标签可直接打这两列。

### PRD 同步
- §3.2 字段表更新到 V78+V84 口径；
- §3.2.1 库区类型与流程对应（V83 已写）+ §3.2.2 实现状态说明；
- §4.3 上架策略新增温区匹配说明与返回字段；
- §5.1 波次新增"V84 起拣货方式下沉库区"小节，含跨区组合示例。

### 验证
- V84 迁移在生产库 0.129s 成功；
- A/B 区种子值正确；
- 新建测试库区（PICK + BULK_MERGE + SORT_WHILE_PICK + 冷藏）保存并读回一致；
- 非法枚举值被静默清空；
- 测试库区已清理，现网只剩原 4 个库区。

### 影响文件
- `V84__wms_zone_pick_method_storage.sql`
- `WmsController.java`、`WmsInboundService.java`、`WmsOutboundService.java`
- `WmsZoneMgmt.vue`、`WmsInbound.vue`

## PDA 1.0：WMS 仓库作业手持端 APP（2026-08-23）

> 本节不是 Flyway 迁移，是**新工程交付**。V78~V84 落的库表与 `/wms/app/*` PDA 端点一直没有真实的移动端调用方，PDA 1.0 把它们打通成可装到雷电模拟器/真机的 APK。

### 背景

V1.5 前期 PDA 只在 `prototype/wms-pda/index.html` 做了静态原型（12 个屏，全是写死数据），无法扫码、不连后端、不能在模拟器/真机上装。后端 `WmsAppController` 已在 V82~V84 陆续备齐 `/wms/app/*` 端点，缺一个真实的 Flutter 客户端。

### 工程结构

```
wms_pda_app/                       # 新建 Flutter 工程（com.erp.wms.wms_pda_app）
├── lib/
│   ├── config/app_config.dart     # API 地址：编译参数 > 运行时配置 > 内置默认 192.168.x.x
│   ├── theme/pda_theme.dart       # 暗色 PDA 主题，与原型视觉对齐
│   ├── services/
│   │   ├── api_service.dart       # dio 封装：Bearer、{code,message,data} 解包、中文错误
│   │   ├── auth_service.dart      # /auth/login，JWT + SharedPreferences 持久化
```

### 关键设计决策

1. **不复用 tms_driver_app，新建独立工程**。司机端是"智速达"（`com.erp.tms.tms_driver_app`），路由全是配送/收款/拒收/返场；仓库员作业（收货/上架/拣货/盘点）是完全不同的业务域。混在一起会让启动路由、首页九宫格、消息推送、权限都分叉。包名用 `com.erp.wms.wms_pda_app`，与司机端 `com.erp.tms.tms_driver_app` 物理隔离，可同机共存。
2. **不新增任何后端接口**。后端 V82~V84 已备齐 `/wms/app/*` 全套 PDA 端点（`WmsAppController`），PDA 1.0 只做调用方。原型中"组装拆改/生产日期修改/拒收入库"三个屏后端暂无 PDA 端点，首版用 `PlaceholderPage` 明确告知"请在 PC 端作业"，不做假按钮。
3. **默认后端地址钉宿主机局域网 IP**。雷电/MuMu 是 VirtualBox 系，网段 172.16.x.x，没有 Android Studio AVD 的 10.0.2.2 别名。`AppConfig.devHost` 在编译时用 `--dart-define=DEV_HOST=192.168.3.16` 钉死当前机器 IP；运行时还能在"登录页→服务器地址"或"首页右上角→服务器地址"里改，存 SharedPreferences，换 WiFi 不重新出包。
4. **JWT 与后台同一套**。PDA 登录走 `/api/auth/login`（BCrypt + JWT，与 PC 后台同一个 `sys_user_runtime`），不再像 TMS 司机端那样单独开 `/tms/app/login` 验证码通道。仓库员账号需要后台预先建用户并分配 WMS 相关角色；首版默认 admin 登录用于联调。
5. **拣货页按 `pick_method` 渲染提示条**，但不做四种完全不同的交互流程。CASE_PICK/CASE_MERGE/BULK_PICK/BULK_MERGE 的任务详情都用同一个逐件拣货列表，顶部一条 `PdaAlert` 说明"整件合拣（先拣后分）"之类，分播去向 `sortDestination` 直接显示在商品行副标题。完全差异化的分播格口 UI 留待 PDA 1.1。
6. **复核页直接扫波次号**，不依赖独立的"待复核列表"端点（后端没有）。拉 `pickTaskDetail` 后按 `sourceOrderNo` 分组，每张订单两个按钮：复核通过 / 差异登记。
7. **扫码全部走输入框 + 键盘提交**。PDA 扫码枪本质是 HID 键盘，不需要相机权限；不引入 `mobile_scanner`/`barcode_scan` 这类相机扫码库，APK 体积少 10MB+，也避免雷电模拟器摄像头兼容问题。
8. **所有写操作走 `runWithBusy`**：自动弹 loading、捕获异常、用 SnackBar 提示中文错误（`ApiService.friendlyError` 把 DioException 翻译成人话），不把 RawStackTrace 甩给仓库员。

## V85 + PDA 1.0.1：库位三件套 / 采购审核自动下发 / PDA 九宫格（2026-08-24）

### 背景

PDA 1.0 出包后试跑，发现三处影响一线作业的卡点：

1. **库位模块输入慢**：巷列层三行单独输，编码还要人手敲；库位只有"最多件数"一个容量维度，无法承载重货/抛货场景；PDA 拣货没有顺序，全靠库工自己绕。
2. **采购单审核后 PDA 看不到收货任务**：`OrderController.auditPurchase` 只更新 `purchase_order.status`，没有调 `WmsInboundService.createFromPurchase`，导致 `wms_inbound_task` 无记录、PDA "收货作业"永远空列表。这是 P1 级流程断裂。
3. **PDA 主界面一屏只能看到 2-3 个入口**：任务卡一行一个，11 个作业入口要滑半天，扫码枪场景下效率低。

### 数据库（V85，PRD-28）

```sql
ALTER TABLE wms_bin ADD COLUMN capacity_weight DECIMAL(18,3) DEFAULT 0;  -- kg
ALTER TABLE wms_bin ADD COLUMN capacity_volume DECIMAL(18,4) DEFAULT 0;  -- m³
ALTER TABLE wms_bin ADD COLUMN pick_seq INT DEFAULT 0;                   -- 拣货顺序，升序
CREATE INDEX idx_bin_pick_seq ON wms_bin(warehouse, zone_code, pick_seq);
CREATE INDEX idx_bin_type     ON wms_bin(warehouse, zone_code, bin_type);
-- 已有库位按 bin_code 字母序回填默认顺序
MERGE INTO wms_bin (bin_id, pick_seq) KEY(bin_id)
SELECT bin_id, ROW_NUMBER() OVER (PARTITION BY warehouse, zone_code ORDER BY bin_code)
FROM wms_bin WHERE COALESCE(pick_seq,0)=0;
```

踩坑记录：第一版用 `UPDATE wms_bin b SET pick_seq=s.rn FROM (...) s WHERE ...`（PostgreSQL 语法），H2 2.2.224 在 MODE=MySQL 下仍报语法错误，Flyway 记一条 success=FALSE。本机 Maven 无 `flyway-maven-plugin` 无法 `flyway:repair`，改为：H2 Shell 删失败记录 → 用 H2 原生 `MERGE INTO ... KEY(...) SELECT ...` 改写 → 重新打包启动。所有 DDL 是 `ADD COLUMN IF NOT EXISTS`/`CREATE INDEX IF NOT EXISTS` 幂等的，重跑安全。

### 后端

- **WmsController**：
  - `/wms/bin/page` SELECT 增加 `capacity_weight / capacity_volume / pick_seq`，ORDER BY 改为 `warehouse, zone_code, pick_seq, bin_code`（拣货顺序在前，PDA 按此引导路径）。
  - `/wms/bin/save` INSERT/UPDATE 全部接收三个新字段。
  - **新增 `/wms/bin/import`**：body `{warehouse, zoneCode, binType?, rows:[{binCode, binName?, aisle?, slot?, layer?, capacityQty?, capacityWeight?, capacityVolume?, pickSeq?, remark?}]}`，按 `(warehouse, bin_code)` upsert，返回 `{inserted, updated, failed:[{binCode,reason}]}`。`pickSeq` 缺省时按库区 `MAX(pick_seq)+1` 递增，让"按 Excel 行序粘贴即得到行序作为拣货顺序"成为默认用法。
- **OrderController.auditPurchase**：
  - 构造函数注入 `WmsInboundService`。审核 UPDATE 后立刻 `wmsInboundService.createFromPurchase(orderNo, "系统管理员")`。
  - **关键：去掉方法上的 `@Transactional`**。原方法只有一条 UPDATE，单语句天然原子；若保留外层事务，`createFromPurchase` 内部抛 `IllegalStateException("已有进行中的任务")` 时即便被 catch，Spring 也会把外层事务标 rollback-only，导致审核 UPDATE 回滚。文档里加了注释说明。
  - WMS 建任务异常不阻断审核主流程：`IllegalStateException`（重复）→ 提示"已有任务"；其他异常 → 返回 `wmsWarning` 字段提示前端"自动建任务失败，可手工补建"，审核状态仍然落库。
- **WmsInboundService 顺手修两个真实 BUG**（影响所有 PO → WMS 任务下发，不只是这次的审核）：
  - `SELECT ... supplier ...` 实际列名是 `supplier_name`（V13 DDL），原来一调就 `Column "SUPPLIER" not found [42122-224]`。
  - `SELECT ... batch_no, production_date FROM purchase_order_detail` 这两列在 V13 DDL 里根本不存在（采购订单明细只到数量/单价/金额，批次是入库时才确定的）。改为只 SELECT 真实存在的列，明细 INSERT 时 batch_no/production_date 传 NULL，符合"采购下单时不指定批次"的业务口径。

## V86：销售退货接入 PDA 收货 / 上架自动审核（2026-08-24）

### 背景与问题

PC 后台制作销售退货单 → 确认 → 推送仓库后，退货入库单 `sales_return_inbound` 已经生成（PENDING 状态），
但 **PDA 上的「收货」页完全看不到这些单据**。原因：PDA 收货页查的是 `wms_inbound_task`，
而销售退货路径只写了 ERP 单据，从未建 WMS 任务，与采购订单审核自动下发 RK 任务的链路不对称。

采购订单 V85 已修通「审核 → 自动建 wms_inbound_task → PDA 收货 → 上架 → 自动审核采购入库单」整条链；
本次把同样的模式套到销售退货上。

### 设计要点

1. **`source_order_no = 退货入库单号（THRK…）`，不是退货申请号（XTSQ…）**。
   申请单已生成 ERP 入库单，PDA 收完上架后需要回写并审核的是入库单本身；申请号放在 `wms_inbound_task.remark`
   里展示为「销售退货 XTSQ…」，便于现场一眼对应。
2. **明细回写通过 `remark` 传 ERP detail_id**：建任务时把 `sales_return_inbound_detail.detail_id`
   写进 `wms_inbound_task_detail.remark`，格式 `SRI_DID=<id>`。上架完成的回调里按这个 ID 反查回写
   `qty / batch_no / production_date / warehouse`，不依赖商品编码做匹配（同单同商品多行时编码不唯一）。
3. **Controller 层去掉 `@Transactional`**：与 V85 采购审核同理，`pushWarehouse` 要调用
   `generateInboundFromApply`（自己有事务）和 `wmsInboundService.createFromSalesReturn`（自己有事务），
   如果外层包事务，WMS 侧抛「已有进行中的任务」会把外层事务标 rollback-only 导致物流状态 UPDATE 一起回滚
   （见 [[spring-caught-exception-marks-tx-rollback-only]]）。物流状态 UPDATE 是单语句，天然原子，
   不需要外层事务。
4. **WMS 任务失败不阻断推送**：入库单已生成是主结果，下发 PDA 失败由异常中心排查或用补建接口重试。
5. **司机回收路径暂不建 WMS 任务**：`onDriverCollected` 已经在司机确认回收时按签收数量生成了入库单，
   且入账时点 = DRIVER_SIGN 时会直接自动审核写负向应收。这条线是"司机把货直接带回"，不经过仓库收货，
   仓库侧不重复建任务；如果入账时点是 WAREHOUSE_INBOUND，司机已回收的单也会进 PENDING，
   后续如需要再补一个 `pushToWarehouse` 动作（本期不做）。
6. **`postInbound` 新增 SALES_RETURN 分支**：所有上架任务完成后，把 PDA 实收数量/批次/仓库回写
   到 `sales_return_inbound_detail`，再调用 `salesReturnController.auditFromWms()` 走原有审核链
   （当前库存成本回库 + 回写退货单已入库数量/金额 + 流转状态推进到「已入库」）。
   审核失败时把 `wms_inbound_task` 标 EXCEPTION，**不回滚实物上架**（货已经在货架上）。
7. **幂等**：`createFromSalesReturn` 按 `(source_order_no, inbound_type='SALES_RETURN', status NOT IN CANCELLED/DONE)`
   去重；`auditFromWms` 发现入库单已 APPROVED 时直接返回不重复回库。

### 关键设计决策

- **批量上架不放外层 `@Transactional`**：每个 `confirmPutaway` 是独立事务，失败的任务跳过并返回原因，其他任务照常完成。这是为了绕开 Spring 那个臭名昭著的"内层 `@Transactional` 抛异常被外层 catch，外层仍被标 rollback-only"陷阱（见 [[spring-caught-exception-marks-tx-rollback-only]]）。
- **状态过滤放客户端**：PDA 一次拉全部状态（空串）再过滤 `PENDING/PUTTING`，因为同一屏既要显示"可领取"也要显示"我已领未上架"，分两次请求没有意义；后端只在显式传具体状态值时才做 SQL 过滤。
- **`base_goods.unit_name` vs `base_unit`**：踩了一次 H2 42122 才记牢——`base_goods` 用 `base_unit`，而单据明细才用 `unit_name`；以后 JOIN base_goods 取单位一律写 `g.base_unit AS unit_name`。
- **生产日期下沉到 `wms_bin_stock`**：之前库位库存只记 `batch_no`，但同批次可能跨生产日期（理论上批次规则是 `YYYYMMDD = 生产日期`，但允许手工改批次/空批次），所以单独加 `production_date / expiry_date` 两列；老数据默认 NULL，"查看库存"里空日期不展示。
- **不做"整容器一次上架"**：本期只做"多选任务 → 全上推荐位"。容器内多 SKU 的整托一次确认还需要"容器 → 上架任务集合"的反查与"容器所在库位 = 推荐库位"校验，放下一版。

### 上线后补丁（同日 13:08）：销售退货空批次无法审核

**现象**：真机验收 THRK202608240001（RK202608240005）的农夫山泉上架，点"确认上架"返回 400 `商品 农夫山泉纯净水 未指定批次号，无法审核`。

**根因**：该单是今早 V86b 收货页加批次/生产日期增强**之前**收的，`wms_inbound_task_detail.batch_no/production_date` 都为空；上架完成后 `postInbound → salesReturnController.auditFromWms` 回写明细再走 `doAuditInbound`，而 `doAuditInbound` 第 1165 行硬校验 `if (batchNo.isBlank()) throw ...`，不允许空批次。这跟项目全局规则「商品库存支持空批次和空生产日期；生产日期也未填 → 批次号留空」（`CLAUDE.md`）以及采购入库链 `PurchaseController.createAndAuditForWms` 的行为（有生产日期无批次自动生成 `YYYYMMDD`，都空则留空）都不一致。

**修复**（`SalesReturnController.doAuditInbound`）：
- 去掉"批次不能为空"的硬抛错；
- 加生产日期回填：有 `production_date` 且 `batch_no` 为空 → 自动生成 `YYYYMMDD`，并 `UPDATE sales_return_inbound_detail SET batch_no=?` 回写，保证审核后明细与库存一致；
- 都没有时批次留空（`InventoryCostService.upsertBatchStock` 已用 `COALESCE(batch_no,'')` 支持空批次聚合）；
- `purchaseInbound` 改为调用带 `productionDate` 的重载，把生产日期一并写入批次表。

**验证**：重打包重启后，对 PT65122EE04168 重发 confirm，返回 `code:0`，`wms_inbound_task.status=DONE / generatedInboundNo=THRK202608240001`，财务库存已按空批次回库 10 箱。

### 上线后补丁（同日 13:33）：生产日期非空时销售退货上架直接 500，退货入库单不审核

**现象**：上一补丁空批次通了，但凡是 PDA 收货时**录入了生产日期**的销售退货单，点"确认上架"后端直接 500，`wms_inbound_task` 停在 `PUTAWAY`，后台退货入库单也一直是 `PENDING`，没有触发自动审核。用 THRK202608200003（批次 `20260806`，生产日期 `2026-08-06`）端到端复现。

**根因**：V87 我在 `confirmPutaway` 第 784 行写了 `(java.time.LocalDate) p.get("productionDate")`。但 H2 2.x 的 JDBC 驱动对 `DATE` 列经 `JdbcTemplate.queryForList` 返回的是 `java.sql.Date`，**不是** `LocalDate`，只要生产日期非空就抛：

```
java.lang.ClassCastException: class java.sql.Date cannot be cast to class java.time.LocalDate
    at com.erp.wms.WmsInboundService.confirmPutaway(WmsInboundService.java:784)
```

异常让整个 `@Transactional confirmPutaway` 回滚——实物账没写、上架任务没置 DONE、`postInbound` 自然也没触发，所以后台退货入库单不会被自动审核。上一条测的 THRK202608240001 恰好两个日期都是 NULL，强转 null 不报错，才"碰巧通过"。

`OTHER` 类型过账分支第 905 行也有同样的 `instanceof LocalDate` 判定，命中不了 `java.sql.Date`，生产日期会被静默丢成 null，本次一并修掉。

**修复**：
- 在 `TmsUtil` 新增 `toLocalDate(Object)`，兼容 `LocalDate / java.sql.Date / java.sql.Timestamp / java.util.Date / String / null`；
- `confirmPutaway` 用 `TmsUtil.toLocalDate(p.get("productionDate"/"expiryDate"))` 替换强转；
- `postInbound` 的 OTHER 分支同样改用 `TmsUtil.toLocalDate(ln.get("productionDate"))`；
- 全工程再无 `(LocalDate)` / `(java.time.LocalDate)` 强转。

**验证**（THRK202608200003 端到端）：
- `PT3499150AA147 confirm actualBin=A-01-01` 返回 `code:0`；
- `wms_inbound_task ITF952FC8AA4D0` → `status=DONE / generatedInboundNo=THRK202608200003 / putawayQty=2`；
- `sales_return_inbound THRK202608200003` → `status=APPROVED / auditUser=admin / auditTime=2026-08-24 13:34:47 / stockUpdated=true / costAmount=52.00`（2 箱 × 26 成本）；
- 明细 `batchNo=20260806 / productionDate=2026-08-06 / costPrice=26`；
- `wms_bin_stock` A-01-01 上批次 `20260806` 正确写入 `production_date=2026-08-06, qty=2`，没有重复库存。

### 补丁 3：预分配页看不到已审核销售订单（2026-08-24）

**现象**：销售订单已审核，但 WMS 预分配/下放页订单池为空，无法选择订单下放。

**根因**：状态值口径不一致。
- `OrderController` 审核销售订单时设置 `outbound_status = '待出库'`（[OrderController.java:270](backend/src/main/java/com/erp/sales/OrderController.java#L270)、第 432 行）；
- `SalesOutboundController` 出库审核后根据累计出库量重算为 `'未出库'/'部分出库'/'已出库'`；
- `WmsOutboundService` 的订单池 SQL（`orderPool`、`routePool`、`orderPoolByRoute` 三处）只过滤 `COALESCE(o.outbound_status,'未出库') = '未出库'`，把 `'待出库'` 的订单全排除了。

刚审核完的订单 `outbound_status` 是 `'待出库'`，只有走过一次出库审核链才会变成 `'未出库'`——而预分配页本就是出库前的第一步，所以这些订单永远不会出现。

**修复**：三处过滤条件改为 `COALESCE(o.outbound_status,'未出库') IN ('未出库','待出库')`，两个值都视为"已审核待下放"。

**验证**：
- `POST /api/wms/order-pool` 返回 XSDD202608240001、XSDD202608190002（均 `outboundStatus=待出库`）；
- `POST /api/wms/route-pool` 返回"开福线路一"，2 单 / 31 件 / 5630 元。

## V88：集货区管理独立模块（2026-08-24）

**需求**：集货区/集货位原本混在通用【库区管理】【库位管理】里维护，业务语义不同（停用应级联、位可单独锁定/释放）。另开【集货区管理】模块，左右表格结构：左侧集货区（新建/编辑/停用/导入），右侧该集货区下集货位（新建、停用/启用、释放/锁定单个、导入）；集货区停用后其下所有集货位不可被使用。

### 设计决策

复用现有 `wms_zone(zone_type='COLLECT')` / `wms_bin(bin_type='COLLECT')`，**不新建表**（V78 已建种子 `ZN-COL/COL` + `COL-01/COL-02`，分配链路 `allocateCollectionBin` 已按这两张表查）。字段语义：

| 操作 | 字段 | 说明 |
|---|---|---|
| 集货区停用/启用 | `wms_zone.frozen` Y/N | 停用后分配时级联排除该区下所有集货位；不逐行改位状态，重新启用时各位原有停用/锁定态保留 |
| 集货位停用/启用 | `wms_bin.status` DISABLED/NORMAL | 停用后不参与自动分配，保留占用与历史 |
| 集货位锁定/释放 | `wms_bin.frozen` Y/N | 人工挂起，不参与自动分配；区别于 `used_qty` 实际占用数，锁定不改占用数 |

### 改动清单

1. **Flyway V88**（`V88__wms_collect_zone_module.sql`）：仅加 `CREATE INDEX IF NOT EXISTS idx_zone_type ON wms_zone(zone_type)`，无结构变更，无数据迁移。
2. **后端 WmsController** 新增端点（均强制 type=COLLECT，复用 `str/bd/intOr/PageResult/TmsUtil.log`）：
   - 集货区：`POST /wms/collection-zone/{page,save,toggle,delete,import}`
   - 集货位：`POST /wms/collection-bin/{page,save,toggle,delete,import}` + **`/lock`、`/release`**（翻转 `wms_bin.frozen`，此前该列无任何端点写它）
   - `/collection-bin/page` JOIN `wms_zone` 带出 `zone_frozen`，供前端展示"集货区已停用"态。
3. **修复分配 BUG**（`WmsOutboundService.allocateCollectionBin`）：候选集 SQL 原本只按 `bin_type='COLLECT'` 查，**未排除已停用/已锁定位、也未排除父区停用的位**。改为 JOIN `wms_zone z` 并加 `b.status='NORMAL' AND COALESCE(b.frozen,'N')='N' AND COALESCE(z.frozen,'N')='N'`。
4. **前端新建 `WmsCollectZoneMgmt.vue`**：左右主从（300px+1fr），左侧仓库下拉+集货区列表（编码/名称/状态/位数/编辑停用删除），右侧集货位表（编码/名称/容量/已占用/状态/编辑停用锁定释放删除），两个粘贴文本导入弹窗（照搬 WmsBinMgmt 的 `parseImport` 模式）。状态优先级：集货区停用 > 位停用 > 位锁定 > 正常。
5. **旧页面移除 COLLECT 入口**：`WmsZoneMgmt.vue` 从 `ZONE_TYPES` 删 COLLECT 并在 `loadZones` 过滤 `zoneType!=='COLLECT'`；`WmsBinMgmt.vue` 从 `BIN_TYPES` 删 COLLECT 并过滤库区树与库位列表。后端通用 `/zone/page`、`/bin/page` 不改（内部按 zone_code/bin_type 精确查的逻辑不受影响）。
6. **预分配集货区下拉动态化**：`WmsPreallocation.vue` 原硬编码 `<option value="COL">`，改为 `onMounted` 调 `/wms/collection-zone/page` 拉取 `frozen!='Y'` 的集货区填充，停用区不可选。
7. **路由/菜单**：`router/index.js` 加 `wms-collect-zone` → `WmsCollectZoneMgmt`；`fallback-menus.js` 仓储作业(WMS)分组在"库位管理"后加"集货区管理"。
