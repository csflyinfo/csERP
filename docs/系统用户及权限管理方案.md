## 一、背景与目标

### 1.1 现状盘点（2026-08-23）

经勘察当前 `main` 线代码，权限体系现状如下：

| 维度 | 现状 | 问题 |
|---|---|---|
| 用户/角色表 | 仅有 `sys_user_runtime`、`sys_role_runtime` 两张表 | 用户-角色靠 `role_name` 字符串对碰，无关联表；一个用户只能属于一个角色 |
| 菜单/权限表 | **无**。菜单树硬编码在 `SystemController.userMenuTree()` 与前端 `fallback-menus.js` | 菜单无法在线维护，新增模块必须改代码重新部署 |
| 功能/按钮权限 | 角色表三个字符串列 `menu_scope`/`field_scope`/`data_scope`，仅 SALE/PURCHASE 两个分支硬编码过滤 | 无功能点表，无按钮级编码，无方法级鉴权 |
| 数据权限 | `data_scope` 列存 'ALL'/'SELF' 等字符串，**后端查询不读取、不过滤** | 形同虚设，存在越权风险 |
| 字段权限 | `usePermission.loadFieldScope` 调 `/system/field-scope`，但 `GenericBusinessList.vue:37` **硬编码 `roleCode='ADMIN'`** | 成本/毛利等敏感字段实际未受控 |
| 方法级鉴权 | 无 `@PreAuthorize`、无 AOP、无自定义注解 | 除 `/system/**` 配了 `hasRole('ADMIN')` 外，其余接口"有 token 即放行" |
| 司机登录 | `POST /tms/app/login`，手机号 + 固定验证码 `888888`，从 `base_employee(is_deliveryman=TRUE)` 查人，签发 `roleCode=DRIVER` | 无密码、无验证码下发、无失败锁定 |
| 仓库 PDA | **无独立登录**，`WmsAppController` 直接复用后台 admin 的 JWT | PDA 设备无明确使用人，作业留痕全部写成"管理员" |
| 租户/系统方 | **完全没有** `tenant_id`、系统方表、菜单元数据表 | PRD-19 描述的"系统方管理后台"尚未启动 |
| 种子账号 | `admin/admin123`，BCrypt 存储；且 `AuthController.findUser` 有**代码级后门**：库中查不到 admin 时硬编码返回全权限账号 | 后门可绕过 DB 停用/锁定，生产必须移除 |
| 前端菜单 | `AppShell.vue` 直接渲染本地 `fallbackMenus`，未调用 `/system/menu/user-tree` | 所有登录用户看到全部菜单 |
| 个人中心 | 后台 Web 顶栏只有退出登录，无修改密码/切换仓库；司机 APP 有"我的"页但无改密 | 改密、切换身份无入口 |

### 1.2 设计目标

1. **三端统一账号体系**：后台 Web、WMS PDA、司机 APP 共用一套用户/角色/权限模型，但登录入口、令牌 claim、首页按 `app_type` 隔离。
2. **RBAC + 四维权限**：菜单权限（看不看得见入口）、功能权限（能不能点按钮/调接口）、字段权限（看不看得见成本/金额）、数据权限（看不看得见别人的单）。
3. **数据权限可落地、默认安全**：后端在 Service 层强制注入过滤条件，前端隐藏只是体验；缺省拒绝（未配置数据范围=只看自己），避免越权。
4. **权限在线可配置**：菜单、功能点、角色、用户数据范围全部走管理页面维护，新增模块只加 SQL 种子不改代码。
5. **作业端按角色裁剪首页**：WMS PDA 收货员/上架员/拣货员/复核员/仓管/主管看到不同的"我的任务"卡片；TMS 司机只看配送相关功能。
6. **平滑迁移**：不推倒重来，在现有 `sys_user_runtime`/`sys_role_runtime` 基础上扩表，保留 admin 账号与现有 JWT 链路；PRD-19 的"系统方/多租户"作为**远期预留字段**，本期单租户但表结构留好 `tenant_id`。
7. **全程留痕**：登录、权限变更、敏感数据导出、代管操作全部写审计日志。

| 6 | 10 §2 草案表名 `sys_user`/`sys_permission_group`/`sys_module_permission` 等 | 实际已上线表名为 `sys_user_runtime`/`sys_role_runtime`（带 `_runtime` 后缀），**沿用现名扩列**，不新建无 `_runtime` 表 | 避免数据迁移与历史脚本混乱；统一 `_runtime` 后缀表示"运行时可改" |
| 7 | 19 §6.3 MFA/IP 白名单/异地登录 | **本期只预留字段不启用**（`mfa_enabled`、`last_login_ip`），MFA 列为 P2 | 当前是内网/专网部署，优先把基础 RBAC 跑通 |
| 8 | WMS PRD §7.4 "权限复用现有 `sys_role_runtime`，在 SystemController 增加分支" | 改为**菜单表 + 角色-菜单关联**驱动，不再在 Java 代码里按 roleCode 写 `if/else` 分支 | 每加一个角色改一次代码不可控 |
| 9 | 08 §3.4 "每个模块至少包含 查看/新增/修改/删除/审核/反审核/关闭/导入/导出/打印/查看日志" | 这套功能点**标准化为 `VIEW/ADD/EDIT/DELETE/AUDIT/UNAUDIT/CLOSE/IMPORT/EXPORT/PRINT/LOG`** 11 个，作为每个业务菜单的默认子节点，权限编码规范见 §6 | 统一编码便于前后端约定与 `@RequirePerm` 注解 |
| 10 | 司机登录固定验证码 888888 | 保留开发期回落，但增加：① 生产环境走真实短信验证码（`sms_code` 表，5 分钟有效）；② 连续失败 5 次锁定手机号 15 分钟；③ 允许"工号+密码"登录作为备选 | 固定验证码是严重安全隐患 |

| 12 | 原方案菜单管理列 P2、仅改名称/排序/可见性，菜单仅两级 | **本期即做【模块菜单管理】**：仅 SYS_ADMIN 可用、授权树不可见不可授权；支持改名/换上级/调排序；菜单结构放宽到**三级**（目录/目录/页面）；管理员自定义值受标志位保护，不被代码同步覆盖 | 现场实施需要按客户习惯调菜单；二级装不下"总账"等分组；超管入口必须严防误授权 |

## 二、设计原则

1. **权限拦截在后端，前端只做体验优化**。菜单隐藏、按钮禁用不能替代后端鉴权——所有写操作接口必须校验功能权限，所有列表查询必须注入数据权限条件。
2. **最小权限原则**。新建角色默认零权限，逐项勾选；新建用户默认停用状态，分配角色后启用。
3. **默认拒绝**。数据权限未配置时按"仅自己"（`create_by = currentUserId`）处理，而不是"全部"。
4. **角色可叠加、权限取并集**。多角色的菜单/功能/字段权限取并集；数据范围取**最宽**（并集），但用户层的"收窄"配置优先于角色层。
5. **权限编码全局唯一、稳定不改名**。菜单/功能编码一旦上线只能停用不能修改，避免历史数据失效。
6. **三端同源但分端授权**。用户表不区分端，但登录时根据 `app_type` 只返回该端的菜单与功能；同一账号可同时拥有后台权限和 PDA 权限（如仓库主管既用 PC 也用 PDA）。
7. **不引入新中间件**。不加 Spring Security 复杂配置、不引入 Sa-Token/Shiro，复用现有 JWT + `JwtAuthFilter`，只加一个方法级 AOP 注解 `@RequirePerm`。
8. **审计不可篡改**。权限变更、登录失败、敏感字段查看（成本/毛利）、数据导出全部写 `sys_operation_log_runtime`，日志只追加不修改不删除。

## 三、总体权限模型

### 3.1 四维权限模型

```
┌─────────────────────────────────────────────────────────────┐
│                          用户 sys_user                        │
│                     （可绑定 0..1 个员工）                      │
└───────────────┬─────────────────────────────────┬───────────┘
                │ 多对多                           │ 1..1 收窄
                ▼                                 ▼
        sys_user_role_rel                 sys_user_data_scope
                │                                 │
                ▼                                 ▼
          角色 sys_role  ◄─────── 多对多 ───────►  数据范围（角色默认）
        sys_role_data_scope
                │
        ┌───────┴────────┬───────────┬──────────────┐
        ▼                ▼           ▼              ▼
   菜单权限         功能权限      字段权限       数据权限
sys_role_menu    sys_role_func  sys_role_field  sys_role_data_scope
        │                │           │              │
        ▼                ▼           ▼              ▼
   sys_menu_meta    sys_func_meta  sys_field_meta  （维度枚举）
   （目录/菜单/      （按钮/API/   （成本/金额/
    页面）           动作）        毛利等敏感列）
```

- **菜单权限**：控制目录/菜单/页面是否可见。父菜单不可见则子菜单全部不可见。
- **功能权限**：菜单下的按钮/动作（新增、审核、导出…）。功能权限依附于菜单，没有菜单权限时其下功能全部无效。
- **字段权限**：敏感字段是否可见/可导出。字段权限全局定义，按角色授权（如 `VIEW_COST`）。
- **数据权限**：按组织维度过滤行数据（仓库、客户、业务员、供应商、货主、商品分类、品牌）。

### 3.2 三端与 app_type

| app_type | 端 | 登录入口 | 首页特征 | JWT claim |
|---|---|---|---|---|
| `ERP` | 后台管理 Web | `/auth/login`（账号+密码） | 左侧菜单树 | `appType=ERP` |
| `WMS_PDA` | 仓库 PDA（Flutter，待开发；当前为静态原型） | `/wms/app/login`（工号+密码） | 按角色显示任务卡片 | `appType=WMS_PDA`, `warehouseId` |
| `DRIVER` | 司机配送 APP（Flutter，已上线） | `/tms/app/login`（手机号+验证码，或工号+密码） | 底部 4 Tab | `appType=DRIVER`, `driverId` |

三端共用 `sys_user_runtime` 与角色体系，但：
- `sys_menu_meta.app_type` 决定菜单属于哪端；
- 登录时只下发当前端的菜单树与功能点；
- 司机可没有后台账号——`base_employee.is_deliveryman=TRUE` 的人员，首次登录自动创建一个"仅 DRIVER 端"的用户（见 §5.4）。

### 3.3 角色分类

| 分类 | 说明 | 是否可删 | 举例 |
|---|---|---|---|
| 系统内置角色 | 系统初始化时种子，编码以 `SYS_` 开头 | 否（可停用） | `SYS_ADMIN`、`SYS_VIEWER` |
| 业务角色 | 管理员在页面创建 | 无用户引用时可删 | 销售主管、采购员 |
| 作业角色 | PDA/APP 端用，编码以 `WMS_`/`TMS_` 开头 | 否（可停用） | `WMS_PICKER`、`TMS_DISPATCHER` |

## 四、内置角色矩阵

### 4.1 后台 Web 角色

| 角色编码 | 角色名 | 数据范围 | 核心权限 |
|---|---|---|---|
| `SYS_ADMIN` | 系统管理员 | 全部 | 全部菜单+功能+字段；唯一可管理用户/角色/参数的角色；**不可停用、不可删除** |
| `SYS_VIEWER` | 只读观察员 | 全部 | 全部菜单的 `VIEW`+`EXPORT`+`PRINT`+`LOG`，无写权限 |
| `BIZ_OWNER` | 老板/管理层 | 全部 | 工作台、报表、所有查询；含成本/毛利字段；无单据增删改 |
| `PURCHASE_MANAGER` | 采购主管 | 全部供应商+仓库 | 采购模块全部功能，含审核/反审核/费用/发票；含采购价字段 |
| `PURCHASE_BUYER` | 采购员 | 指定供应商（按人收窄）+ 全部仓库 | 采购订单/入库/收货/退货的增改；无审核他人单 |
| `SALES_MANAGER` | 销售主管 | 全部客户+全部业务员 | 销售模块全部功能，含审核/反审核；含成本/毛利字段 |
| `SALES_CLERK` | 销售员 | 自己的客户（`salesman_id=自己`）+ 仅自己 | 销售快速开单、订单、出库；无成本/毛利字段；不可看他人单 |
| `WAREHOUSE_MANAGER` | 仓库主管 | 绑定仓库（全部库区） | 库存查询、库存调整/成本调整/报损/盘点审核、WMS 后台任务看板；无财务结算 |
| `WAREHOUSE_KEEPER` | 仓管员 | 绑定仓库 | 库存查询、其他出入库、调拨、盘点；无成本单价、无成本调整 |
| `FINANCE_MANAGER` | 财务主管 | 全部 | 应收/应付/收付款/核销/费用/资金流水/对账；含金额字段 |
| `FINANCE_CLERK` | 财务出纳 | 全部 | 收款单/付款单/核销录入；无成本/毛利；不可删除已审核单据 |

### 4.2 WMS PDA 角色（与 V1.5 PRD §7.4 对齐）

| 角色编码 | 角色名 | PDA 首页卡片 | 数据范围 |
|---|---|---|---|
| `WMS_RECEIVER` | 收货员 | 收货、退货收货、其他入库 | 绑定仓库；只看分配给自己的收货任务 |
| `WMS_PUTAWAY` | 上架员 | 上架、补货、移库 | 绑定仓库；只看自己的上架任务 |
| `WMS_PICKER` | 拣货员 | 波次拣货、缺货上报、库存查询 | 绑定仓库；只看分配给自己的拣货任务 |
| `WMS_CHECKER` | 复核员 | 复核、打包、装车确认 | 绑定仓库；看待复核任务 |
| `WMS_KEEPER` | 仓管员（多面手） | 全部作业卡片 | 绑定仓库；看本仓全部任务（不按人过滤） |
| `WMS_LEADER` | 仓库主管 | 任务分派、异常处理、盘点审核、进度监控、绩效查看 | 绑定仓库；全仓数据；含成本字段需额外授权 `VIEW_COST`（默认不给） |

PDA 一个用户可同时拥有多个作业角色（如中小仓一个人既收货又上架），此时首页显示所有被授权角色的卡片并集。

### 4.3 TMS 配送角色

| 角色编码 | 角色名 | 端 | 核心权限 | 数据范围 |
|---|---|---|---|---|
| `TMS_DISPATCHER` | 调度员 | 后台 Web | 配送任务池、调度单管理、派车、改派、在途监控、交账单审核 | 全部 |
| `TMS_DRIVER` | 司机 | 司机 APP | 接单、装车、发车、签收、结算、交账、现场退货 | 只看 `driver_id=自己` 的调度单/收款 |

| `TMS_LEADER` | 配送主管 | 后台 Web + APP | 调度看板、司机绩效、异常处理、交账复核；APP 可看本组 | 全部司机 |

> 司机也可同时拥有后台角色（如车队长），允许同一账号用手机验证码登 APP、用工号密码登后台。

### 5.3 数据权限维度与过滤规则

数据权限控制"能看到哪些行"，分**组织范围**（仓库/客户/供应商/业务员/货主）与**商品范围**（分类/品牌）两大类，全部在 Service 层强制拼入 SQL，前端隐藏只做体验。

#### 5.3.1 维度定义

| scope_type | 名称 | 取值形式 | 作用表/过滤列 | 典型角色 |
|---|---|---|---|---|
| `WAREHOUSE` | 仓库范围 | `ALL` / 指定仓库 ID 列表 | 单据头 `warehouse_id`；库存 `warehouse_id`；WMS 任务 `warehouse_id` | 仓管、收货/拣货员、采购 |
| `CUSTOMER` | 客户范围 | `ALL` / 指定客户 ID / 按片区 `REGION:<id>` | 销售单据 `customer_id`；客户主档 `customer_id` | 销售员、销售主管 |
| `SUPPLIER` | 供应商范围 | `ALL` / 指定供应商 ID | 采购单据 `supplier_id`；供应商主档 | 采购员、采购主管 |
| `SALESMAN` | 业务员范围 | `ALL` / `SELF` / `SUB_TREE` / 指定业务员 ID 列表 | 销售单据 `salesman_id`；应收 `salesman_id` | 销售主管、老板 |
| `OWNER` | 货主范围 | `ALL` / 指定货主 ID | 单据 `owner_id`（当前单货主默认 ALL） | 后期多货主 |
| `GOODS_CATEGORY` | 商品分类范围 | `ALL` / 指定分类 ID 列表（**含所有子分类**） | 商品 `category_id`；单据明细 `goods_id` 关联商品分类 | 品类主管、分区采购 |
| `BRAND` | 品牌范围 | `ALL` / 指定品牌 ID 列表 | 商品 `brand_id`；单据明细 `goods_id` 关联品牌 | 品牌主管 |

> 商品范围（分类/品牌）不仅过滤商品档案，**也过滤业务单据明细**：当用户只有部分商品可见时，销售/采购订单明细中不属于授权范围的商品行被过滤，主单金额按可见行汇总（主单本身若所有明细均不可见则整单不可见）。

#### 5.3.2 业务员层级（SALESMAN）规则

利用 `base_employee` 已有字段 `is_salesman` / `is_salesman_admin` / `parent_salesman` 构成上下级树：

| 取值 | 含义 | 翻译为 SQL |
|---|---|---|
| `ALL` | 全部业务员数据 | 不加条件 |
| `SELF` | 仅自己 | `salesman_id = :currentEmployeeId` |
| `SUB_TREE` | 自己 + 所有下级（递归） | `salesman_id IN (<递归查 parent_salesman 链>`) |
| 指定 ID 列表 | 指定业务员（含自己或跨组） | `salesman_id IN (...)` |

- `currentEmployeeId` 从 `sys_user_runtime.employee_id` 取（未绑定员工的后台账号该维度强制 `ALL` 或不可配）。
- 上级关系通过 `parent_salesman`（存上级 employee_name，与现有字段一致）递归查询，深度建议 ≤ 5 层。
- 销售员默认 `SELF`；销售主管默认 `SUB_TREE`；老板/财务默认 `ALL`。

#### 5.3.3 组合与优先级

1. **多角色并集**：同一用户多个角色，同维度范围取并集（`IN` 合并）。
2. **用户收窄**：`sys_user_data_scope` 某维度有配置时，与角色层结果取**交集**（只能更窄不能更宽）。
3. **维度叠加**：不同维度之间取**交集**（AND）。如"仓库A + 客户C1"表示只能看 A 仓的 C1 客户单据。
4. **ALL 短路**：某维度值为 `ALL` 时该维度不拼条件。
5. **默认拒绝**：角色完全未配置任何数据范围维度时，默认加 `create_by = :currentUserId`（仅自己创建的单据），避免新角色裸奔看到全公司数据。
6. **SYS_ADMIN 短路**：内置超管所有维度跳过过滤，直接返回全部。
7. **PDA 强制仓库**：WMS_PDA 登录时已绑定 `warehouseId`，该端所有查询强制追加 `warehouse_id = :tokenWarehouseId`，即使用户有多个仓授权也以登录时选择的仓库为准（切换仓库需重新登录）。

#### 5.3.4 典型角色数据范围示例

| 角色 | WAREHOUSE | CUSTOMER | SUPPLIER | SALESMAN | GOODS_CATEGORY | BRAND |
|---|---|---|---|---|---|---|
| 老板 BIZ_OWNER | ALL | ALL | ALL | ALL | ALL | ALL |
| 采购主管 | ALL | — | ALL | — | ALL | ALL |
| 采购员（按品类） | 指定仓 | — | 指定供应商 | — | 指定分类 | 指定品牌 |
| 销售主管 | ALL | ALL | — | SUB_TREE | ALL | ALL |
| 销售员 | — | 自己客户 | — | SELF | ALL | ALL |

> "—" 表示该维度不配置，走默认（仅自己创建）；对采购/销售员这类角色，通常业务上他们的单据都是自己创建的，所以"仅自己创建"已经能满足；若需看同组他人单则显式配范围。

### 5.4 司机账号自动开通

司机（`base_employee.is_deliveryman=TRUE`）首次用手机号+验证码登录时：

1. 查 `sys_user_runtime` 是否已存在该手机号/工号账号；
2. 若不存在，自动创建：
   - `username = employee_code`（工号），`mobile = 手机号`，`display_name = employee_name`，`employee_id = employee_id`；
   - 密码随机 16 位（司机不用密码登录，密码用于 PDA/后台备选）；
   - `status = 'NORMAL'`，`is_system = FALSE`，`must_change_pwd = TRUE`（首次用工号密码登录时强制改密）；
   - 自动绑定角色 `TMS_DRIVER`（该角色需种子存在）；
3. 已存在则直接签发 token。

这样司机不需要管理员预先建账号，人员档案里勾了"配送员"就能登 APP。

### 6.2 功能权限：全局功能 vs 模块功能

功能权限（按钮/操作）分两类，在 `sys_func_meta.func_scope` 区分：

- **全局功能（GLOBAL）**：跨模块通用操作，授一次对所有业务模块生效。典型如导出、导入、打印、审核/反审核等。角色配置页单独有一个"全局功能"分区，勾选后不用每个模块重复勾。
- **模块功能（MODULE）**：只作用于所属菜单（页面）的操作，编码为 `<menu_code>.<action>`。典型如某单据的"选单生单""低价授权""加急补货"。

| `global.low_price_approval` | 低价销售授权 | 低于最低售价时的授权放行（弹窗输入授权账号密码） |
| `global.over_credit_approval` | 超信用授权 | 超出客户信用额度时的授权放行 |
| `global.negative_stock_approval` | 负库存授权 | 可用量不足仍审核出库的授权放行。**口径（卡片6 校正）**：商品在余额表无任何记录（从未入库）时授权也不放行，提示先做入库；仅有余额而可用量不足时才可授权 |
| `global.change_created_by` | 修改制单人/业务员 | 改单头上的业务员/制单人（影响业绩归属，敏感） |
| `global.change_price` | 修改单价 | 单据明细单价是否可改（区别于"新增"），用于开单员只录数量不能改价 |
| `global.change_discount` | 修改折扣 | 整单折扣/明细折扣 |
| `global.settle` | 结算/核销 | 应收应付核销、交账确认等资金动作 |
| `global.data_export_sensitive` | 敏感数据导出 | 含成本/毛利/金额字段的导出；拥有 `global.export` 但无此项时，导出文件敏感列脱敏 |

> 设计要点：全局功能与模块功能**取并集**，但模块功能可以"反向收窄"——例如角色有全局 `audit`，但在销售订单菜单下做过模块级配置后，必须显式授予 `sales.order.audit` 才能审核销售订单。**回落粒度为菜单（卡片6 实现定稿）**：某角色一旦在目标菜单下配置过任意 MODULE 功能点（哪怕只有 view），即视为该菜单由模块级接管，全局功能对该菜单不再回落；该菜单下零个 MODULE 配置时，持有的全局功能才自动覆盖。
> `允许 = 显式模块功能点命中 ∨ (该角色在目标菜单零 MODULE 配置 ∧ 持有对应 global.*)`。
> 可回落动作白名单仅 8 个标准动作：audit/unaudit/close/delete/import/export/print/log（对应 global.audit/unaudit/close/delete/import/export/print/log_view）；view/add/edit 与 biz_* 非标准动作**永不回落**，必须逐模块显式授权。前端下发的"有效功能集"按同一规则展开（PermissionService.effectiveCodes）。

**审批型全局功能的交互协议（卡片6 落地）**：`low_price_approval`/`over_credit_approval`/`negative_stock_approval` 三个授权点走"现场二次授权"：

1. 当前登录人本人持有对应 `global.*_approval` → 直接放行（SELF，不弹窗）；
2. 否则请求未带授权凭证时，接口返回 **HTTP 400 + body `{code:'NEED_APPROVAL', data:{approvalType, bizNo}, message}`**；前端拦截该 code 弹出原生授权框（显示授权类型与单号、原因取 message），操作员请持权人当场输入账号密码，前端把 `approverAccount`/`approverPassword` 合并进**原请求体**重放一次（失败可换人重试，取消则放弃操作）；
3. 服务端校验链：账号存在 → 未停用 → 未锁定 → 密码正确 → 该账号确实持有此授权功能 → **不能给本人授权**；全部通过后放行（APPROVER）；
4. 留痕：授权成功写操作日志（类型 `LOW_PRICE_APPROVAL`/`OVER_CREDIT_APPROVAL`/`NEGATIVE_STOCK_APPROVAL`，结构化 detail + 含操作员/授权人/单号/原因的人话内容）；授权失败同样写日志（result=FAIL，失败原因写 fail_reason，用于暴力试密码审计）；日志写入失败不影响业务；
5. 三个触发点：销售订单保存（低价，在库存校验后、落库前）、销售订单审核（超客户信用额度）、销售出库审核（负库存；无库存记录的商品此步硬拒绝，见上表口径）。

**字段权限实现规则：**

1. **黑名单式隐藏**：未授权时后端在 JSON 序列化阶段把字段置 `null`（`FieldMaskingSerializer` + `@SensitiveField(VIEW_COST)`），前端拿到 null 不展示；
2. **导出同步脱敏**：导出 Excel 时未授权字段整列不导出或填 `***`；
3. **列表+详情+报表全覆盖**：不能只藏列表，详情和报表接口同样标注；
4. **汇总值也受控**：如库存余额汇总行的"库存金额合计"在无 `VIEW_COST_AMOUNT` 时显示 `***`；经营概览的毛利卡片无 `VIEW_PROFIT` 时不渲染；
5. **打印受控**：打印模板若包含敏感字段，无权限用户预览/打印时该字段留空或显示 `***`；
6. **管理员旁路**：`SYS_ADMIN` 拥有全部字段权限，不可取消。

### 6.4 权限元数据的自动注册机制

> 核心约定：**权限元数据（菜单/功能/字段）由代码定义，启动时自动同步入库，不允许在管理页面手工"新建"系统权限**。管理员只能调整名称/排序/可见性和给角色授权，不能凭空造一个功能点——这样新模块上线、老模块加按钮，权限记录自动出现，不会漏。

权限元数据有三个来源，全部在应用启动时（或 `/system/perm/refresh` 手动触发）由 `PermissionRegistry` 统一同步到 `sys_menu_meta`/`sys_func_meta`/`sys_field_meta`：

#### 6.4.1 来源一：菜单与页面——`MenuRegistry` 编程式注册

菜单树结构在一个集中配置类 `com.erp.system.perm.MenuConfig` 中声明（替代散落在 `SystemController.userMenuTree()` 和前端 `fallback-menus.js` 的硬编码）。新增模块只需加一个 Bean 方法：

```java
@Configuration
public class MenuConfig {

    @Bean
    public MenuNode salesMenus() {
        return dir("sales", "销售管理", "ShoppingCart")
            .page("sales.quick",     "销售快速开单", "/sales/quick",     "sales/QuickOrder.vue")
            .page("sales.order",     "销售订单",     "/sales/order",     "sales/OrderList.vue")
            .page("sales.outbound",  "销售出库",     "/sales/outbound",  "sales/OutboundList.vue")
            .page("sales.receipt",   "销售发货单",   "/sales/receipt",   "sales/ReceiptList.vue")
            // ...
            ;
    }

    @Bean
    public MenuNode wmsPdaMenus() {
        return pdaDir("wms_pda", "仓库PDA")
            .page("wms_pda.receive", "收货作业", "/receive")
            .page("wms_pda.pick",    "拣货作业", "/pick")
            // ...
            ;
    }

    // 三级结构：一级目录 > 二级分组目录 > 三级页面
    @Bean
    public MenuNode financeMenus() {
        return dir("finance", "财务管理", "Money")
            .page("finance.ar",        "应收管理", "/finance/ar",       "finance/ArList.vue")
            .page("finance.ap",        "应付管理", "/finance/ap",       "finance/ApList.vue")
            .dir("finance.gl", "总账")                                   // 二级目录
                .page("finance.gl.voucher", "凭证管理", "/finance/gl/voucher", "finance/gl/VoucherList.vue")
                .page("finance.gl.book",    "会计账簿", "/finance/gl/book",    "finance/gl/BookList.vue")
            ;
    }
}
```

- `dir(...)` / `page(...)` 是 `MenuNode` 的链式构造器，自动带 `appType`、`sortOrder`；
- **层级上限三级**：`dir` 可嵌套一层子 `dir`，`page` 只能挂在第 2/3 层（即 L1=目录，L2=目录或页面，L3=只能页面）。`MenuConfig` 解析时做深度校验，超过三级直接启动报错；
- 页面（`menuType=PAGE`）会自动挂上 11 个标准功能点（见 6.4.3），无需手写；
- 支持 `pdaDir(...)`/`driverDir(...)` 分别指定 `appType=WMS_PDA/DRIVER`；
- 超管专属菜单用 `.adminOnly()` 声明（如 `system.menu` 模块菜单管理），同步时写 `admin_only=TRUE`，对角色授权树不可见；
- 代码里只声明**默认**的名称/上级/排序；这三项允许管理员在【模块菜单管理】页面调整，调整后同步不再覆盖（见 6.4.5）。

#### 6.4.2 来源二：功能点——`@RequirePerm` 注解扫描

`@RequirePerm` 既是鉴权注解，也是**功能点声明**。`PermissionRegistry` 启动时扫描所有 `@RestController` 方法上的 `@RequirePerm`，自动 upsert 到 `sys_func_meta`：

```java
@RestController
public class OrderController {

    @PostMapping("/sales/order/audit")
    @RequirePerm(value = "sales.order.audit", name = "审核", global = false)
    public ApiResponse<?> audit(...) { ... }

    @PostMapping("/sales/order/low-price-approve")
    @RequirePerm(value = "global.low_price_approval", name = "低价销售授权",
                 global = true, type = FuncType.ACTION)
    public ApiResponse<?> lowPriceApprove(...) { ... }
}
```

扫描逻辑：
1. 遍历所有 `@RestController` Bean 的方法；
2. 取 `@RequirePerm.value()` 作为 `func_code`；
3. `func_code` 第一段是 `global` → `func_scope=GLOBAL`，挂到 `M_GLOBAL_FUNC`；否则为 MODULE，按 `func_code` 去掉最后一段动作名后匹配 `menu_code`（如 `sales.order.audit` → 菜单 `sales.order`）；
4. 取 `@RequestMapping`/`@PostMapping` 路径填 `api_path`，HTTP 方法填 `api_method`；
5. **upsert**：库里没有就 INSERT（`is_system=TRUE`），已有就更新 `func_name/api_path`；代码里删了的功能点不物理删，标记 `status='STOPPED'`（防止历史角色引用失效）。

> 这样新增一个接口 = 加一个 `@RequirePerm`，重启后功能点自动出现在角色配置页，**不需要任何手工 SQL**。

#### 6.4.3 标准功能点自动派生

每个 `menuType=PAGE` 的菜单，由 `PermissionRegistry` 按命名规范自动生成标准功能点（库里缺哪个补哪个），并根据页面是否有状态机决定生成哪些：

| 动作 | 自动生成条件 |
|---|---|
| `view/add/edit/delete` | 所有页面 |
| `audit/unaudit/close` | 检测到该模块 Controller 含 `audit`/`reverse-audit`/`close` 路径，或菜单显式声明 `withStateMachine=true` |
| `import/export/print/log` | 所有页面（前端没有对应按钮时也保留，授权后才显示） |

非标准业务动作用 `biz_` 前缀，必须在方法上写 `@RequirePerm("sales.order.biz_xxx")` 显式声明，不自动生成。

#### 6.4.4 来源三：受控字段——`@SensitiveField` + 字段注册表

本项目 Controller 多返回 `Map<String,Object>`（JdbcTemplate），没有统一 VO 类，字段脱敏不能靠实体反射。采用**集中字段注册表**声明哪些 key 属于哪个字段权限：

```java
@Component
public class SensitiveFieldRegistry {

    @Override
    protected void register() {
        // field_code, 该字段在响应 Map 中可能出现的 key（下划线/驼峰都列）
        field("VIEW_COST")
            .keys("costPrice", "cost_price", "costAmount", "cost_amount",
                  "unitCost", "avgCost");
        field("VIEW_PROFIT")
            .keys("grossProfit", "gross_profit", "grossProfitRate",
                  "gross_profit_rate");
        field("VIEW_PURCHASE_PRICE")
            .keys("latestPurchasePrice", "latest_purchase_price",
                  "referencePurchasePrice", "purchasePrice");
        field("VIEW_AR_BALANCE")
            .keys("arBalance", "ar_balance", "receivableBalance");
        // ... 26 个字段全部注册
    }
}
```

- 启动时校验：注册表中的 `field_code` 必须在 `sys_field_meta` 中存在（来自 V102 种子），缺失则启动报错（fail-fast，防止字段名写错导致脱敏失效）；
- 后续新模块引入新敏感字段，**加一行 `.keys(...)` 即可**，由 `FieldMaskingSerializer` 统一脱敏；
- 对少数有 VO 类的接口，可在 VO 字段上标注 `@SensitiveField("VIEW_COST")` 作为补充，注册表与注解都生效。

#### 6.4.5 同步算法（upsert，不删数据）

`PermissionRegistry.sync()` 启动时执行（`ApplicationReadyEvent`），逻辑：

```
1. 收集代码声明的菜单集合 C_menus（MenuConfig Beans）
2. 收集代码声明的功能集合 C_funcs（@RequirePerm 扫描 + 标准功能点派生）
3. 收集代码声明的字段集合 C_fields（SensitiveFieldRegistry）
4. 对库中每条记录：
   - 代码中存在 → 按"字段归属"分别更新（见下），仅 is_system=TRUE 记录可被同步
   - 代码中不存在且 is_system=TRUE → status='STOPPED'（停用，不删除）
   - 代码中不存在且 is_system=FALSE（管理员自建，远期菜单管理才会有）→ 保留
5. 对代码中存在、库中没有的 → INSERT，is_system=TRUE，三个 *_customized 标志=FALSE
6. 写一条操作日志：'PERM_SYNC'，记录新增/更新/停用各多少条
```

**菜单字段归属（关键）**：代码与页面各有领地，互不覆盖——

| 字段 | 归属 | 同步规则 |
|---|---|---|
| `menu_code`/`route_path`/`component_path`/`app_type`/`menu_type`/`icon` | 代码 | 每次同步强制覆盖（改错会导致路由/功能点错位） |
| `menu_name` | 代码默认，页面可改 | 仅 `name_customized=FALSE` 时覆盖；管理员改名后置 TRUE，同步保留 |
| `parent_id` | 代码默认，页面可改 | 仅 `parent_customized=FALSE` 时覆盖 |
| `sort_order` | 代码默认，页面可改 | 仅 `sort_customized=FALSE` 时覆盖 |
| `visible`/`remark` | 页面 | 同步不动 |
| `admin_only` | 代码 | 同步强制覆盖 |

管理员在【模块菜单管理】点"恢复默认"时，清掉对应 `*_customized` 标志，下次同步（或立即触发 `/system/perm/refresh`）重新取代码默认值。功能点/字段没有自定义项，同步规则不变。

幂等：重复启动结果不变。`SYS_ADMIN` 角色在同步后自动被授予所有 `status=NORMAL` 的菜单（含 `admin_only=TRUE`）/功能/字段权限（保证超管始终是全权限）；其他角色永远拿不到 `admin_only=TRUE` 的菜单。

#### 6.4.6 新增模块的标准动作（给开发的约定）

> 做成项目 checklist，Code Review 必查。

1. **加菜单**：在对应 `MenuConfig` Bean 里加一行 `.page("xxx.yyy", "名称", "/path", "component.vue")`；
2. **加接口**：Controller 方法上写 `@RequirePerm("xxx.yyy.action")`，查询接口用 `view`，写接口用标准动作或 `biz_xxx`；
3. **加敏感字段**：在 `SensitiveFieldRegistry` 把新字段 key 加到对应 `field_code`；
4. **数据权限**：新列表查询调用 `DataScopeHelper.forBill("表名")`；
5. **前端**：按钮加 `v-permission="'xxx.yyy.action'"`，敏感列加 `v-if="canViewField('VIEW_COST')"`；
6. **重启**：启动日志打印 `权限同步完成：新增 N 个功能点`，角色配置页自动出现新项；
7. **Flyway**：**不需要**为权限元数据写迁移 SQL（由代码注册）；只有当菜单/功能需要**授权给某个内置角色**时才写数据迁移（在 `sys_role_menu_rel`/`sys_role_func_rel` 插行）。

### 6.5 权限编码与模块归属规则（强约束）

为了让 `@RequirePerm` 的 `func_code` 能自动匹配菜单、避免各模块命名漂移，约定：

1. `func_code` 必须是 `<menu_code>.<action>`，`menu_code` 必须已在 `MenuConfig` 声明，否则启动报错；
2. 全局功能 `func_code` 以 `global.` 开头；
3. 一个 Controller 可包含多个菜单的功能，但 `func_code` 前缀必须与业务路径第一段一致（`/sales/order/audit` → `sales.order.audit`）；
4. CI 增加校验脚本/单测：扫描所有 `@RequirePerm`，校验其 `func_code` 前缀能在 `MenuConfig` 找到对应菜单（全局功能除外），不通过则构建失败。

## 九、后端鉴权落地

### 9.1 方法级注解 `@RequirePerm`

新增 `com.erp.common.security.RequirePerm`：

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface RequirePerm {
    String[] value();              // 功能编码，如 "sales.order.audit"
    Logical logical() default Logical.ANY;  // ANY=任一即可，ALL=全部需要
}
```

新增 `PermissionAspect`（AOP）拦截 `@RequirePerm`：

1. 从 `CurrentUser.roles()` 取用户全部角色；
2. 查 `sys_role_func_rel` join `sys_func_meta`，命中任一 `func_code` 即放行；
3. SYS_ADMIN 直接放行；
4. 未命中抛 `ForbiddenException`，由全局异常处理器返回 `403`。

**所有写操作 Controller 方法必须加 `@RequirePerm`**，例如：

```java
@PostMapping("/sales/order/audit")
@RequirePerm("sales.order.audit")
public ApiResponse<?> audit(@RequestBody AuditRequest req) { ... }
```

现有接口补注解的清单由实施时 grep `@PostMapping/@PutMapping/@DeleteMapping` 逐个补，作为 P0 任务。

### 9.2 数据权限注入

提供 `DataScopeHelper`，在 Service 层拼 SQL 时调用：

```java
// 销售订单查询
String where = DataScopeHelper.forBill("sales_order")  // 自动按当前用户角色拼 warehouse_id/customer_id/salesman_id/creator
    .build();
jdbcTemplate.queryForList("SELECT * FROM sales_order WHERE " + where + " AND ...", args);
```

`DataScopeHelper` 内部：

1. 从当前请求缓存（请求级 `ThreadLocal`，Caffeine 5 分钟）读取用户的角色数据范围；
2. 根据主表的可用列（`warehouse_id`/`customer_id`/`supplier_id`/`salesman_id`/`owner_id`/`create_by`）智能拼接；
3. 表无对应列的维度跳过；
4. 返回的 SQL 片段使用命名参数，值通过 `Map` 传入，防注入。

> **不引入 MyBatis 拦截器**：当前项目 JdbcTemplate 与 MyBatis-Plus 混用，拦截器方案改造成本高。采用显式 Helper 调用更可控，Code Review 也容易发现漏网的查询。

### 9.3 字段脱敏

新增 `FieldMaskingSerializer`（Jackson `JsonSerializer`），配合自定义注解 `@SensitiveField(VIEW_COST)`：

```java
public class SalesOrderVO {
    private BigDecimal amount;
    @SensitiveField("VIEW_COST") private BigDecimal costAmount;
    @SensitiveField("VIEW_PROFIT") private BigDecimal grossProfit;
}
```

序列化时检查当前用户角色是否拥有该字段权限，无则写 `null`。导出 Excel 同样走字段权限检查（在导出 Service 里 `if (!FieldPerms.canView("VIEW_COST")) continue;`）。

### 9.4 菜单/功能查询接口

| 接口 | 说明 |
|---|---|
| `GET /system/menu/tree?appType=ERP` | 全部菜单树（管理用）；**角色授权配置用树走独立接口，过滤 `admin_only=TRUE`** |
| `GET /system/menu/grant-tree?appType=ERP` | 角色权限设置中的可选菜单树：排除 `admin_only=TRUE` 与 `status=STOPPED` |
| `GET /system/menu/user-tree` | 当前登录用户在该端的菜单树（登录后调用；非超管不返回 `admin_only` 节点） |
| `GET /system/func/list?menuId=` | 菜单下功能点 |
| `GET /system/field/list` | 字段权限字典 |
| `GET /system/perm/mine` | 当前用户功能点编码集合 + 字段权限集合（前端 `v-permission` 用） |
| `PUT /system/menu-manage/{menuId}/name` | 修改菜单名称（仅 SYS_ADMIN，置 `name_customized=TRUE`，写审计日志） |
| `PUT /system/menu-manage/{menuId}/parent` | 更换上级（仅 SYS_ADMIN，校验层级≤3/防环，置 `parent_customized=TRUE`） |
| `PUT /system/menu-manage/sort` | 批量调整同级顺序（仅 SYS_ADMIN，置 `sort_customized=TRUE`） |
| `POST /system/menu-manage/{menuId}/reset` | 恢复默认（清 `*_customized` 标志，重新取 MenuConfig 值） |

`/system/menu-manage/**` 一组接口**不走 `@RequirePerm` 授权体系**，在 AOP/拦截器中硬编码要求 `SYS_ADMIN` 角色（即使其他角色被错误写入关联表也拒绝，双重保险）。

登录后前端一次性调 `/system/perm/mine` 拿到 `{funcs: Set<string>, fields: Set<string>}`，缓存到 Pinia/store，供按钮/列显隐判断。

**访问控制（三条硬规则）**

1. 仅 `SYS_ADMIN` 角色可访问页面与 `/system/menu-manage/**` 接口，后端按角色硬校验，不经过功能点授权；
2. 该菜单本身 `admin_only=TRUE`：在【角色/权限组管理】的菜单授权树中**不展示、不可勾选、不可通过任何角色间接授权**（授权树走 `/system/menu/grant-tree`，过滤 `admin_only`）；
3. 非超管账号即使手工输入 `/system/menu` 路由或直接调接口，也返回 403/路由重定向首页。

**页面结构**：顶部端切换页签（ERP / WMS_PDA / 司机APP），左侧可拖拽菜单树，右侧编辑面板。

**功能项**：

| 功能 | 说明 |
|---|---|
| 查看菜单树 | 按 `app_type` 展示全部菜单（含 STOPPED 灰色置底），三级缩进；节点显示菜单名称、`menu_code`、类型（目录/页面）、来源标记 |
| 调整顺序 | 同级节点拖拽排序（或上移/下移按钮），批量保存；后端对被拖动节点置 `sort_customized=TRUE` |
| 更换上级 | 树节点拖拽跨级移动，或编辑面板选"上级菜单"下拉；保存时做层级/防环校验 |
| 修改名称 | 编辑"菜单名称"输入框保存（`menu_code`、路由、组件路径只读展示，不可改） |
| 三级结构 | 支持把页面挂到二级目录下形成三级：一级目录 → 二级目录 → 页面；也支持一级目录 → 页面（两级，现状） |
| 恢复默认 | 单个节点或整棵树"恢复代码默认"：清 `name/parent/sort_customized` 标志并重取 `MenuConfig` 默认值，二次确认 |
| 操作留痕 | 改名/移动/排序/恢复均写操作日志，记录字段新旧值（如 parent：`finance → finance.gl`） |

**保存校验规则**：

1. 层级 ≤ 3：目标层级 = 新上级层级 + 自身子树最大深度，超过 3 拒绝；
2. 目录（DIR）只能放在 1、2 层；页面（PAGE）只能放在 2、3 层；PAGE 不能有下级；
3. 不能把节点拖到自己或自己的后代下（防环）；
4. 不能把目录下唯一的页面移走后使一/二级目录成为空目录（允许保存但弹确认提示"空目录将对所有用户隐藏"）；
5. 同一上级下菜单名称不允许重复；
6. `admin_only=TRUE` 的节点（即本菜单自己）允许改名，但不允许移动/停用，避免超管把入口弄丢；
7. `status=STOPPED`（代码已删除）的节点不允许移动，只展示。

**与自动注册的边界**：菜单的有无、路由、组件由代码决定（重启同步）；名称/上级/排序由管理员决定（同步保留），字段归属见 §6.4.5。前端动态路由按调整后的树生成，刷新即生效，无需重新登录（保存后推送/重拉 `/system/menu/user-tree`）。

## 十六、风险与权衡

| 风险 | 影响 | 应对 |
|---|---|---|
| 现有 Controller 数量多，补 `@RequirePerm` 工作量大 | P0 周期拉长 | 按模块分批补，先补采购/销售/库存/财务写操作；查询接口 P0 先只靠数据权限，P1 补 `view` 注解 |

## 十八、存量模块权限初始化方案

当前仓库有 46 个 Controller，全部没有 `@RequirePerm`，`SystemController` 里菜单是硬编码，前端 `fallback-menus.js` 也是硬编码。权限元数据"冷启动"分四步走：**盘点 → 建表 → 首次同步 → 角色授权**。

### 18.1 存量接口盘点（一次性，产出物：`docs/perm-inventory.md`）

新增一个开发期工具类 `PermInventoryDumper`（加 `@Profile("dev")`，不打包生产），启动时用反射扫所有 `@RestController` 的 `@*Mapping` 方法，输出一份 Markdown 清单到 `docs/perm-inventory.md`，列：

| 模块 | HTTP 方法 | 路径 | 当前 Controller#method | 建议 func_code | 建议菜单 | 动作类型 |
|---|---|---|---|---|---|---|
| 销售订单 | POST | /sales/order/create | OrderController#create | sales.order.add | sales.order | add |
| 销售订单 | POST | /sales/order/page | OrderController#page | sales.order.view | sales.order | view |
| 销售订单 | POST | /sales/order/audit | OrderController#audit | sales.order.audit | sales.order | audit |
| ... | ... | ... | ... | ... | ... | ... |

路径→动作的自动派生规则（与 6.4.3 一致）：

| URL 片段 | 动作 |
|---|---|
| `/page`, `/list`, `/detail`, `/get` | view |
| `/create`, `/save`（POST） | add |
| `/update`, `/edit` | edit |
| `/delete`, `/remove` | delete |
| `/audit`, `/approve` | audit |
| `/reverse-audit`, `/unaudit`, `/cancel-audit` | unaudit |
| `/close` | close |
| `/import`, `/upload` | import |
| `/export`, `/download` | export |
| `/print` | print |
| 其他 | `biz_<片段>`（需人工确认名称） |

开发 review 这份清单，把 `biz_*` 项命名补好，确认菜单归属。盘点结果在 PR 中一起提交。

### 18.2 菜单树初始化

`MenuConfig` 按盘点结果一次性建好 6 大目录 + 三端全部页面（PC 约 70 个页面、PDA 约 15 个、司机端约 12 个），结构与本文档第七章种子表完全对应。

- 这是**代码**，不是 Flyway 数据；
- 第一次启动应用时，`PermissionRegistry` 把这些菜单 upsert 进 `sys_menu_meta`；
- 同时把现有 `SystemController.userMenuTree()` 硬编码的菜单和 `fallback-menus.js` 标记为"待删除"，切换完成后清理。

### 18.3 功能点首次同步

在 18.1 盘点的基础上，按模块给 Controller 方法批量补 `@RequirePerm`。建议顺序（按风险/收益）：

| 批次 | 模块 | 范围 | 说明 |
|---|---|---|---|
| 1 | system | 用户、角色、菜单、参数、日志 | 权限系统自身，先稳住 |
| 2 | sales | 订单/快速开单/出库/发货/退货 | 写操作多、价格敏感，先补 audit/add/edit/delete 和价格字段 |
| 3 | purchase | 订单/入库/退货/费用/发票 | 同上，采购价字段脱敏 |
| 4 | inventory | 库存查询/盘点/调拨/其他出入库 | 数据权限按仓库强制过滤 |
| 5 | finance | 应收应付/收付款/核销 | 金额字段脱敏 + 数据权限 |
| 6 | base | 商品/客户/供应商/员工/仓库/库区 | 基础档案，数据范围按分类/品牌 |
| 7 | wms | PDA 收货/上架/拣货/复核/盘点 | 配合 WMS_PDA 登录 |
| 8 | tms | 司机端签收/退货/结算/装车 | 配合 DRIVER 登录 |

每批一个分支（见第十九章），补完后启动，`PermissionRegistry` 自动把功能点写入 `sys_func_meta`。**不需要手写功能点 INSERT SQL。**

> 对暂时来不及补 `@RequirePerm` 的查询接口，P0 阶段可在 `SecurityConfig` 放通但 `DataScopeHelper` 仍然生效（数据权限不依赖方法注解），P1 再补 view 注解收口。

### 18.4 存量角色与用户数据迁移

V102 迁移脚本负责"搬数据"，不负责"建权限点"（后者由代码同步）：

1. **角色**：现有 `sys_role_runtime` 中每个角色，在 V102 里：
   - 保留旧行不动；
   - 按 `role_code` 匹配第八章内置角色矩阵；能匹配上的，把其默认菜单/功能/字段/数据范围写入新建的关联表；
   - 匹配不上的（客户自建角色），默认只授权"我的桌面"和 `view` 权限，由管理员重新配置；
2. **用户**：现有 `sys_user_runtime` 用户：
   - 按 `role_name` 字符串在 `sys_role_runtime` 找到 `role_id`，写入 `sys_user_role_rel`；
   - `sys_user_warehouse` 从旧 `data_scope` 字段解析（若是 `WAREHOUSE:xxx,yyy` 格式）；解析不出的留空，登录后让管理员补选；
   - 默认密码策略保持，旧 BCrypt 哈希继续有效；
3. **admin 账号**：V102 确保 `admin / SYS_ADMIN` 存在，并自动绑定所有仓库、所有数据范围（`ALL`）；
4. **司机**：不在 V102 里预建用户，由司机首次登录时从 `base_employee(is_deliveryman=TRUE)` 自动建档（见第十一章）。

### 18.5 切换与回滚

- V102 脚本与代码同批上线，**先备份 H2**（生产环境为 MySQL，先用快照/`mysqldump`）；
- 上线后跑一次内置自检端点 `GET /system/perm/health`，返回：
  - 菜单/功能/字段元数据数量；
  - 每个角色授权数量；
  - "孤儿功能点"（`@RequirePerm` 声明但未匹配到菜单的 func_code，应为 0）；
  - "未鉴权写接口"（`@PostMapping` 但无 `@RequirePerm` 的方法清单，P0 允许存在但要列出）；
- 回滚：V102 是新增表 + 新增列，不删旧数据。代码回滚后旧 `role_name/menu_scope` 仍在，旧版本可继续运行（新表成为孤岛，不影响旧逻辑）。

## 20. 落地补遗（持续追加）

### 20.1 付款单核销端点补齐（2026-09-10，PRD-28 卡片7）

原设计中 `fin.payment_verify`（付款核销）只有从应付侧发起的快捷核销端点 `/finance/reconcile/pay`；付款单列表已审核行「核销」按钮的弹窗前端却与收款单共用，硬编码调用收款单侧 `/finance/receipt/unsettled-bills`、`/finance/receipt/reconcile`，付款单 ID 查 `fin_receipt_bill` 必返回「收款单不存在」——即付款单勾单核销从未真正可用（git 史确认 payment 侧对称端点从未存在）。卡片7 按对称实现补齐，不改变现有权限模型：

- `POST /finance/payment/unsettled-bills` → `fin.payment_verify.view`：核销弹窗数据源，往来单位数据范围 `assertCpVisible` 收窄，待核销金额取 `fin_payment_bill.total_amount - verified_amount`；
- `POST /finance/payment/reconcile` → `fin.payment_verify.writeoff`：勾单核销 AR/AP、回写 `fin_payment_bill.verified_amount`，核销记录写入 `fin_reconcile_record`，新增 `business_type` 取值 `SALES_PAYMENT`（付款核应收）/ `PURCHASE_PAYMENT`（付款核应付），与既有 SALES_RECEIPT/PURCHASE_RECEIPT 同列展示；
- 前端核销弹窗按 moduleCode 分支（receiptPayment 走 receipt 侧、paymentModule 走 payment 侧），核销内快速建费后的刷新同步分支；弹窗标题回退显示 paymentNo；
- 零权契约：零授权两 403；仅 view 可拉未结单、执行核销仍 403；view+writeoff 可执行；持 payment_verify 不触及 receipt 侧两端点（交叉 403）。

### 20.2 卡片7 范围与遗留（2026-09-10）

- 509 个 @RequirePerm 端点经零权账号实扫全部 403；卡片7 范围（base/inventory/finance 含 GL/report/transfer/system PC 端）未鉴权写端点清零，`/system/perm/health` 余 155 个全部归属 WMS（117）/TMS（38），按卡片9（PDA）、卡片10（司机）处理。
- 自助接口 `/system/perm/mine`、`/system/menu/user-tree` 刻意不挂功能点（任何登录用户取自身权限集与自身菜单树，数据本身已按人收窄），扫描时不计越权。
- GL 前端按钮不经 useRbac 文案解析，全部按后端权威注解显式 v-permission 挂码；纯查询页（账簿查询、对账）只靠菜单可见性 + 后端 view 兜底。
