## 1. 背景与目标

旧系统有「客户账户」：每客户一条记录，展示应收金额、储值余额，点余额可看往来流水（增加金额/减少金额/账户金额/结算标志/摘要/要货单号/出库或退货单号）。

现系统财务链路（V1.0 阶段六 + PRD-32 总账 + PRD-33 日结）已有零件但**缺一个客户维度的账户视图和预收能力**：

| 已有资产 | 现状 | 位置 |
|---|---|---|
| `fin_ar` 应收单 | 签收/退货/费用挂账/期初逐单立账，含税口径，`received/unreceived/status` | [SalesReceiptController.java:267-286](../backend/src/main/java/com/erp/sales/SalesReceiptController.java)、[SalesReturnController.java:873-878](../backend/src/main/java/com/erp/sales/SalesReturnController.java) |
| `fin_receipt_bill`/`fin_receipt_detail` 收款单 | 审核 FIFO 自动核销 AR + 资金流水 + 往来流水；**不区分预收与结算** | [FinanceController.java:1351-1428](../backend/src/main/java/com/erp/finance/FinanceController.java) |
| `fin_reconcile_record` 核销记录 | 每笔核销一行（ar_no/source_bill/reconcile_amount） | FinanceController `writeReconcileRecordV2` :2637 |
| `fin_counterparty_ledger` 往来流水 | IN/OUT + `balance_after`，客户供应商共用，**只记资金往来，不记应收形成**；多收的钱在此沉淀 | FinanceController :2787 |
| `fin_fund_ledger` 资金流水 + `base_fund_account.balance` | 资金账户侧流水，余额链可重排（`rebuildFundChain`） | FinanceController :2686-2726 |
| 总账 1122 应收账款 / **2203 预收账款**（均按客户辅助核算） | 科目已预置（V93）；事件池 + 模板生成凭证；收款审核已有 `onReceiptAudited` 钩子 | `finance/gl/GlHookService.java` :338 |
| 日结定版 | 应收定版把负余额重分类为预收（`advance_amount`），是**没有预收账户时的绕路** | `finance/dayclose/BizCloseSnapshotService.java` |
| TMS 门店结算 | 多收钱仅日志提示「请财务确认是否转预收」，**无实际动作** | TmsStoreSettleController.java:562 |

**目标**：新增【客户账户】模块——每个客户一条账户记录，管 **应收余额** 与 **预收余额**；点余额看往来流水；收款单支持预收；提供预收核销（预收冲应收）；应收结算可使用预收；全部动作留流水、可逆向、自动出凭证、可重算修复。

## 2. 范围

### 2.1 本期做

1. **客户账户主表**：每客户一条，应收余额、预收余额。
2. **客户账户流水**：分「应收」「预收」两个账户，增加/减少/账户余额滚存 + 结算标志 + 来源单据链接。
3. **收款单改造**：新增收款类型——应收结算（现状默认）/ 预收收款 / 预收退款。
4. **预收核销单（预收冲应收）**：选未结算应收行核销；审核生成「预收扣减 + 应收结算」双边流水、核销记录、凭证。
5. **应收结算可使用预收**：客户应收明细、对账单收款结算弹窗增加「本次使用预收」。
6. **期初预收**：PRD-34 期初初始化增加客户预收录入入口。
7. **数据修复**：按应收单/流水重算余额、重排余额链。
8. 历史数据迁移（V124 回填账户与流水）。
9. 总账事件/模板、日结定版、操作日志、菜单权限、对账单/TMS 联动、冒烟与覆盖测试。

### 2.2 本期不做

- 供应商侧「预付账户」对称改造（表结构预留思路，另立 PRD）。
- 储值/充值消费、积分等营销能力（旧系统「储值余额」名字不沿用，避免语义混淆）。
- 应收账龄重构（继续以 `fin_ar` 为准，本模块只展示）。
- 客户合并、客户变更后的账户迁移。
- 销售退货负向应收的退款自动化（沿用现有负向 AR 净额核销机制；退款先走预收退款由财务确认）。

## 3. 总体模型

```
                            客户账户 fin_customer_account（每客户一条）
                            ┌─────────────────────────────┐
                            │ ar_balance 应收余额          │◄──── 明细真值 = Σ fin_ar.unreceived_amount
                            │ advance_balance 预收余额     │◄──── 明细真值 = Σ 预收流水
                            └──────────────┬──────────────┘
                                           │ 1:N
                    ┌──────────────────────┴───────────────────────┐
                    ▼                                               ▼
        应收账户流水 account_type=AR                     预收账户流水 account_type=ADVANCE
  增加：签收生应收/退货红冲(负)/费用挂账/期初         增加：预收收款/期初预收
  减少：收款结算/预收冲应收/抹零/反审核冲回            减少：预收核销/预收退款/反审核冲回

  发货签收 ──► fin_ar（应收单，明细真值）─┬─► fin_reconcile_record（核销记录）
  销售退货 ──► 负向 fin_ar ─────────────┤      ▲              ▲
  费用挂账 ──► fin_ar ──────────────────┤      │              │
  期初应收 ──► fin_ar ──────────────────┘      │              │
                                              │              │
              收款单 fin_receipt_bill ─审核───┘              │
              · SETTLE 应收结算：资金流水 IN + FIFO 核销 ─────┤
              · ADVANCE 预收收款：资金流水 IN，不核销         │
              · ADVANCE_REFUND 预收退款：资金流水 OUT         │
                                                            │
              预收核销单 fin_advance_writeoff ─审核──────────┘
              预收↓ + 指定应收行核销（不碰资金）
```

**真值与缓存的分工（关键不变量）**：

- 应收明细真值永远是 `fin_ar`；账户表 `ar_balance` 是缓存，恒等于该客户全部 `fin_ar.unreceived_amount` 之和（含负向退货行）。
- 核销真值永远是 `fin_reconcile_record`；应收流水的「结算标志/已结金额」是缓存，按 `ar_no` 汇总。
- 预收没有单据级明细载体，**预收流水即真值**；`advance_balance = Σ 预收流水带符号金额`。
- 所有缓存可由「数据修复」从真值完整重建，重建结果与原缓存不一致时出差异报告。

### 4.4 `fin_receipt_bill` 改造

```sql
ALTER TABLE fin_receipt_bill ADD COLUMN IF NOT EXISTS receipt_type VARCHAR(20) DEFAULT 'SETTLE';
-- SETTLE 应收结算（默认，全部历史数据与现状行为）
-- ADVANCE 预收收款
-- ADVANCE_REFUND 预收退款
```

### 4.5 迁移与回填（V124 同脚本完成）

1. 建上述表、约束、索引。
2. 为每个 `base_customer` 建账户行。
3. 从 `fin_ar` 回填**应收形成流水**（一行 fin_ar 一行流水，`biz_key='AR:'+ar_no`）；金额口径：`increase_amount = ar_amount`（负向退货行带负号，`is_red=1`）；`settled_amount=received_amount`，结算状态按 0/部分/全额推导。
4. 从 `fin_reconcile_record` 回填**应收结算流水**（一条核销一行，`biz_key='ARR:'+id`，带出 ar_no/receipt_no/source_bill）。
5. 两类行按 `occurred_at, flow_id` 交错排序重排 `balance_after`（参照 `rebuildFundChain` 算法），账户 `ar_balance = 末笔余额`，并与 `Σ fin_ar.unreceived_amount` 校验，不一致写迁移日志（不阻断启动）。
6. 预收流水起步为空，所有客户 `advance_balance = 0`。历史遗留的「多收款」（`fin_counterparty_ledger` 中未形成核销的 IN 净额）**不自动转预收**，由财务核对后通过期初预收录入（§8）。
7. `fin_receipt_bill.receipt_type` 历史行全部 `SETTLE`。

## 6. 上下游流程（逐个场景说清）

### 6.1 发货签收 → 形成应收

- 现状不变：[SalesReceiptController.sign()](../backend/src/main/java/com/erp/sales/SalesReceiptController.java) 按**含税签收金额** `sign_amount` 自动审核并 `approveAndGenerateAr`（:267-286），拒收天然不进应收；到期日 +30 天；发总账 `onSalesSignAudited` 事件。
- **本需求新增**：同事务内追加一行 `AR_SIGN` 流水（increase=签收金额，未结算，回填 ar_no/客户/要货单号/发货单号），更新账户 `ar_balance += amount`，重排该客户 AR 余额链。
- 幂等：`biz_key='AR:'+ar_no`；流水写入失败整笔签收事务回滚（遵循"外层异常被吞仍标 rollback-only"的教训，不 catch 吞异常）。

### 6.2 销售退货 → 红字应收

- 现状不变：[SalesReturnController.writeReturnAr()](../backend/src/main/java/com/erp/sales/SalesReturnController.java) :873 插入**负向 fin_ar**，发红字凭证事件。
- 新增：同行写 `AR_RETURN` 流水（`increase_amount = -退货金额, is_red=1`），账户应收余额减小；前端红字展示在「减少金额」列。
- 负向行被后续结算/净额核销时，与正向行同样回写结算标志。

### 6.3 费用挂账、期初应收

- 费用单无资金账户审核生应收（现状）：写 `AR_EXPENSE`。
- PRD-34 期初应收过账逐行立 fin_ar（现状）：写 `AR_OPENING`。
- 规则与 6.1 相同。

### 6.4 新建收款单（预收收款）→ 预收增加

入口：收款单新增「收款类型」单选，默认应收结算（界面同现状）；选**预收收款**后：

1. 不加载未结算单据、不产生核销明细；表头只留客户/经手人/记账日期/资金账户多行/摘要/金额。
2. 审核（扩展 [FinanceController `/receipt/audit`](../backend/src/main/java/com/erp/finance/FinanceController.java) :1351）：
   - 收款单 → APPROVED；
   - 资金流水 `fin_fund_ledger` IN、`base_fund_account.balance` 增加（**现状逻辑照用**）；
   - 往来流水 `fin_counterparty_ledger` 照写 IN（保持现有往来资金视图不断档）；
   - **新增**：`ADV_RECEIPT` 流水（increase=金额），账户 `advance_balance += 金额`；
   - 发总账事件 `onReceiptAudited`（payload 带 `receiptType=ADVANCE`），模板生成：**借 1001/1002 资金科目，贷 2203 预收账款（客户辅助核算）**。
3. 反审核（扩展 cancel-audit :1435）：资金/往来追加 OUT 对冲行（现状）；预收侧追加 `ADV_REVERSE` 冲回行、原行置 REVERSED、余额回减；红字凭证事件。**校验：该预收若已被预收核销单使用，必须先反审核核销单**（按 ADV 流水去向校验）。

### 6.5 预收退款 → 预收减少

- 收款类型选「预收退款」：金额为正录入、资金实际付出（资金流水 OUT、账户余额减少，界面明确红色"退款"语义）。
- 审核校验：**退款金额 ≤ 该客户当前预收余额**，否则 `IllegalArgumentException`「预收余额不足」；写 `ADV_REFUND` 流水；凭证：借 2203，贷 1001/1002。
- 反审核对称冲回。

### 6.6 预收核销（预收冲应收）

入口：客户账户列表/流水页「预收核销」按钮 → 预收核销单新建页（XH 单）。

1. 选客户后显示该客户未结算应收行（fin_ar 未结金额 ≠ 0 的行，含退货负向行参与抵减的展示），顶部显示可用预收余额；勾选行并录本次核销金额（默认未结金额，可改小）；明细合计 ≤ 预收余额、≤ 各行未结金额。
2. 审核（一个 @Transactional）：
   1. 核销单 → APPROVED；
   2. **逐行写 `fin_reconcile_record`**（business_type 新增值 `ADVANCE_WRITE_OFF`，receipt_no 存 XH 单号，ar_no/source_bill/金额齐全）——核销记录仍是唯一核销真值；
   3. 逐行更新 `fin_ar.received_amount/unreceived_amount/status`（全额→ VERIFIED，部分→保持 UNVERIFIED 但流水标志为"部分结算"，与现状两档状态兼容）；
   4. 回写发货单 `receive_status`（未收款/部分收款/已收款，复用 TMS 现有回写口径）；
   5. **预收侧**：写 `ADV_WRITE_OFF` 流水（decrease=合计），`advance_balance` 减少；
   6. **应收侧**：每个应收行写一行 `AR_SETTLE_ADVANCE` 流水（decrease=该行核销额，reconcile_id 回写、ar_no 回写），并把对应 `AR_SIGN/AR_RETURN/...` 形成行的 `settled_amount`、`settle_status` **回写**；`ar_balance` 同步下降；
   7. **不写资金流水**（纯往来转账）；
   8. 新增总账事件 `onAdvanceWriteoffAudited`：**借 2203 预收账款，贷 1122 应收账款**（客户辅助核算）；
   9. 操作日志（OperationLogService，模块 `finance.advanceWriteoff`，动作 AUDIT）。
3. 反审核（仅 APPROVED 且后续无封账/月结）：删除核销记录（沿用收款反审核做法）、回退 fin_ar 三个金额与状态、冲回发货单收款状态；预收追加 `ADV_REVERSE`、应收追加 `AR_REVERSE` 并回置形成行结算标志；原 XH 单 → PENDING（可改/删）或作废（删单仅限 PENDING）；发红字事件。
4. XH 单本身不做"过账"概念，审核即生效；已被日结定版覆盖 `post_date` 的，按 PRD-33 封账规则禁止反审核。

### 6.7 应收结算时使用预收（客户应收明细 / 对账单两条入口）

- `/finance/ar/settle`（:212）与 `/finance/customer-statement/settle`（:2132）收款弹窗新增「**本次使用预收**」金额栏（≤ min(待结金额合计, 客户预收余额)，默认 0）。
- 确认结算时一个事务内：
  1. 现金/银行部分：照常生成收款单（SETTLE）并自动审核 → `AR_SETTLE_CASH` 流水（现状链路）；
  2. 预收部分：**自动生成一张 XH 预收核销单并审核**（business_source=AR_SETTLE / STATEMENT_SETTLE，source_bill_no 带对账单号）→ 6.6 全套流水与核销记录；
  3. 两部分按现有规则分配到具体应收行：预收部分优先冲最早到期行、现金部分接续（或按弹窗中手工录入的本次结算额逐行匹配；保持与现状 FIFO/手工两种模式一致）；
  4. 抹零仍生费用单并自动核销（`AR_WRITEOFF`），不受预收影响；
  5. 对账单 `已收款金额` 含预收核销额（视同收款），收款状态按总额判定。
- 反审核：对账单/结算撤销时，先反 XH 自动单再反收款单（级联反审核，留日志）。

### 6.8 TMS 门店结算联动

- 现状：`tms_store_settlement` 按 ar_no 定向核销，溢收部分只打日志"转预收"提示（:562）。
- 本期（V127，2026-09-16 验收）：溢收（实缴 > 本次核销应收合计）部分**自动生成 ADVANCE 收款单并审核**（真实 SK 序号，`business_source='DRIVER_OVERPAY_ADV'`、`related_bill_no=门店结算号`，可溯源/查重幂等）。资金已在门店结算中入账，**自动单不重复写资金流水**，只补预收流水（`ADV_RECEIPT`）+ 往来台账 + GL 事件（借资金科目/贷 2203，资金科目取该门店结算第一条正额资金账户明细，要求资金账户已配 GL 科目映射）；资金流水仍只按门店结算实缴记一次。
- 该行为做成参数 P0189（`tms.settle.overpay-to-advance`，默认开；关闭则保留现状仅写 `RECONCILE_REMAIN` 日志）。自动单是普通预收单：在收款单列表按**标准收款单反审核链**手工反审核（红字 `ADV_REVERSE` 同样不写资金流水），不做门店结算侧隐式级联。

### 6.9 撤销签收 / 反审核退货

- 现状守卫不变：`received_amount ≠ 0` 拒绝撤销签收/反审核退货（SalesReceiptController :564、SalesReturnController :932）。
- 新增守卫表述：凡已被现金结算或预收核销的应收，必须先反审核对应收款单/XH 单。
- 通过守卫后现状是 **DELETE fin_ar**；流水侧同事务 **DELETE 对应形成流水行**（该行从未被结算、无下游凭证过账，与 fin_ar 同生命周期；总账草稿事件按现状撤销事件处理）。这是"流水只增不删"的唯一例外，仅限尚未发生任何结算的形成行。

### 6.10 日结封账与总账

- 所有流水 `post_date` 取单据记账日期（签收=签收日期，收退款=收款单日期，XH=核销日期，均不回填，遵守 PRD-33 事实日/入账日规则）。
- `post_date` 落在已封账日期的审核/反审核一律硬拒（复用 PRD-33 封账校验入口）。
- 日结应收定版：`ar_balance` 直接取客户账户；预收定版取 `advance_balance`，V127 起快照到 `biz_close_ar_daily.advance_account_balance` 新列（向导展示账户预收合计勾稽提示，定版台账与 RJ 打印单新增「预收余额」列）；原「负应收重分类为预收」逻辑生成的 `advance_amount` 列保留作兜底校验，正常数据下两列应相等（验收勾稽：账户预收余额 = 定版 advance_account_balance，重分类额应为 0）。
- 新增凭证模板三组：预收收款、预收退款、预收冲应收（2203 ↔ 1122/资金），经会计事件工作台生成草稿，与现有凭证流程完全一致；反审核走 reverse_flag。

## 7. 余额一致性、并发与数据修复

### 7.1 不变量（修复/日结都要校验）

1. `fin_customer_account.ar_balance` = Σ `fin_ar.unreceived_amount`（按客户）。
2. `fin_customer_account.advance_balance` = Σ ADV 流水带符号发生额 = 该客户 ADV 账户末笔 `balance_after`。
3. 任一 AR 形成流水 `settled_amount` = Σ `fin_reconcile_record` 同 ar_no 金额。
4. AR 账户末笔余额 = 应收余额；两个账户余额链逐笔连续。
5. 预收余额 ≥ 0（任何时刻；历史多收款在迁移后期初处理，不允许把账户做成负数）。

### 7.2 并发

- 审核类事务内先 `SELECT ... FROM fin_customer_account WHERE customer_code=? FOR UPDATE`（H2/MySQL 均支持），再写流水重排余额链；同一客户的签收/结算/核销串行化，不同客户互不阻塞。
- 流水写入走统一服务 `CustomerAccountService`（新建，Controller 不直接拼 SQL），入参带 biz_key，唯一约束兜底幂等。
- 余额链重排参照 `rebuildFundChain`（FinanceController :2707）：按 `(occurred_at, flow_id)` 顺序重算本账户 `balance_after`，同事务完成。

### 7.3 数据修复（旧截图「数据修复」按钮对应能力）

入口：客户账户列表「数据修复」（独立功能点权限 + 操作日志 + 二次确认）。

- 范围：选定客户或全部客户。
- 动作：① upsert 账户行与档案快照；② 按 §7.1 重算两个余额；③ 按核销记录回填 AR 流水结算标志/已结额；④ 重排两账户余额链。
- **不删除、不新增业务流水**；发现缺流水（有 fin_ar 无流水等）才按 §4.5 口径补行并列入差异报告；修复前后差异、修复人、时间写 `sys_operation_log_runtime` 并返回页面提示。

## 8. 期初预收（PRD-34 扩展）

- 落地形态（V127，2026-09-16 验收）：**独立菜单「财务管理 → 客户期初预收」**（`/finance/init-adv`，权限点 `fin.init_adv.view/edit/delete/import/post/reverse`）+ 独立暂存表 `fin_adv_init`（镜像 `fin_ar_init`），复用期初向导外壳（OpeningShell/OpeningInitPanel）。模板列：客户编码/名称、原单据号/日期（仅留存）、预收金额（>0）、备注；导入部分成功（VALID/ERROR 全行落库 + 失败文件）。不与应收期初混表，避免两套过账状态互相阻塞。
- 过账：写 `ADV_OPENING` 流水（post_date = 建账日，来源号 `QCYK-<批号>-<seq>`，bizKey `ADVO:<批号>:<seq>`，批号 `QCyyyyMMdd+4位`），`advance_balance` 一次性建立并重排余额链；**不造收款单、不动资金流水**；ADV_OPENING 本身不发 GL 事件，2203 期初余额随总账现有「一键引入业务期初」借/贷平衡。
- 反建账守卫扩展：预收存在后续**仍生效**的核销/退款流水时拒绝反建账（必须排除 `reverse_status='REVERSED'` 的已冲回行，否则「先反审下游再反建账」路径永久卡死——M4 实证缺陷）；已有业务日结 / 总账已启用同样拒绝。
- 历史多收款（§4.5-6）由财务核对客户后，用本入口录入；不做"自动把往来流水沉淀余额转预收"。

| AC-16 | 并发：同客户两笔结算同时审核 | 无余额链断裂、无超核销 |
