## 一、三模块定位与关系

### 1.1 职责划分

| 模块 | 定位 | 可写? | 数据来源 |
| --- | --- | --- | --- |
| **客户价格调整单** | 制单入口，走「制单 → 审核」流程 | 可写 | 人工录入 |
| **客户价格查询** | 查**当前生效价**，一客户一商品一单位一条 | 只能停用 | 调整单审核后生成 |
| **客户商品变价查询** | 查**历史变价流水**，含变价前/后 | 完全只读 | 调整单审核后生成 |

一句话概括：**调整单是唯一的写入口，两个查询模块都是它审核后的产物。**

### 1.2 数据流向

```text
        ┌─────────────────────────┐
        │   客户价格调整单（制单）    │  status = PENDING
        │  base_customer_price_    │  ← 可编辑 / 可作废
        │  adjust + _detail        │
        └───────────┬─────────────┘
                    │  审核（audit）★ 唯一的价格生效动作
                    ▼
     ┌──────────────┴───────────────┬────────────────────┐
     ▼                              ▼                    ▼
┌──────────────┐        ┌──────────────────────┐  ┌──────────────┐
│base_customer │        │base_customer_price_  │  │base_customer_│
│_price_item   │        │change_log            │  │price（老表）  │
│（当前价）      │        │（变价流水）            │  │（兼容保留）    │
│ 按单位拆行     │        │ 每次变动一条           │  │ 一商品一行    │
│ upsert 覆盖   │        │ 只追加不修改           │  │ 不再被查询    │
└──────┬───────┘        └──────────┬───────────┘  └──────────────┘
       │                           │
       ▼                           ▼
  客户价格查询                客户商品变价查询
  （可停用）                    （只读）
```

### 1.3 三张价格表为什么并存

| 表 | 结构 | 现状 |
| --- | --- | --- |
| `base_customer_price` | 一商品一行，三单位挤在同一行的列里 | **老表，仅兼容保留**。审核时仍写入，但两个查询模块都不再读它 |
| `base_customer_price_item` | 按 `unit_level` 拆行，唯一键约束 | **当前价的唯一权威来源** |
| `base_customer_price_change_log` | 按 `unit_level` 拆行，只追加 | **变价历史的唯一来源** |

> **为什么不直接改老表？** `CLAUDE.md` 禁止修改已存在字段名。且两个新模块都需要「按单位类型」的行粒度（变价查询要「单位/单位类型」两列，价格查询要按单位类型筛选并单独停用某个单位），三列并排的结构做不到。新表命名与 `base_price_group_item` / `base_price_change_log`（价格组模块）刻意保持一致，便于维护。

## 二、数据库设计

### 2.1 迁移版本沿革

| 版本 | 做了什么 | 为什么 |
| --- | --- | --- |
| `V1` | 建 `base_customer_price_adjust`、`_detail`、`base_customer_price` | 初始版本，单一基本单位定价 |
| `V21` | 两张表各加 14 列（三级单位/启用状态/标价/现价 + 品牌/分类/存储属性） | 原来只支持「单一基本单位 + 原价/现价」，与商品档案的 `unit_config` 多单位体系不匹配 |
| `V22` | `_adjust` 加 5 列：`creator_name`/`create_time`/`auditor_name`/`audit_time`/`audit_date` | 原来只有 `creator_info`/`audit_info` 两个拼接字符串，列表无法分列展示与排序 |
| `V25` | 新建 `base_customer_price_item` + `base_customer_price_change_log` | 两个查询模块需要按单位拆行的粒度 |
| `V26` | 回填 V25 之前已审核单据的价格与变价记录 | 新表建于 V25，之前已审核的单据没进新表 |

> ⚠️ **V23、V24 是他人的采购退货相关迁移**，与本模块无关。本模块开发过程中两次撞号，均将自己的版本号顺延（V23→V24→V25）。新建迁移前务必 `ls` 查重，重复版本会让后端**直接启动失败**。

### 2.6 `base_goods.unit_config`（三级单位的源头）

`VARCHAR(4000)`，存 JSON 数组，**索引 0=小、1=中、2=大**：

```json
[
  {"unitType":"小单位","unitName":"瓶","convertQty":1,"standardPrice":1.5,"enabled":true},
  {"unitType":"中单位","unitName":"",  "convertQty":12,"standardPrice":0,  "enabled":false},
  {"unitType":"大单位","unitName":"箱","convertQty":24,"standardPrice":36, "enabled":true}
]
```

解析规则（后端 `parseUnitProfile` / 前端同名函数）：

- `enabled` 缺省视为 **启用**（`u.enabled !== false`）
- **索引 0 强制置为启用**（小单位恒启用）
- 小单位标价兜底取 `base_goods.standard_price`
- **未启用单位的标价一律落 NULL**，不落 0

## 三、核心业务规则

以下规则贯穿三个模块，是理解代码的前提。

### 规则 1：审核是唯一的价格生效动作

制单只写 `_adjust` 与 `_detail` 两张表，**不产生任何生效价格**。只有 `audit` 会写 `_item`（当前价）和 `_change_log`（流水）。因此：

- 待审核单据的价格在两个查询模块中**都查不到**
- 这也是两个查询都 `EXISTS (... status='APPROVED')` 的原因（双保险，防脏数据）

### 规则 2：小单位恒启用，中/大单位按快照判定

| 单位 | 启用判定 |
| --- | --- |
| 小单位（level 1） | **永远启用**，无需判断 |
| 中单位（level 2） | 看 `medium_unit_enabled` |
| 大单位（level 3） | 看 `large_unit_enabled` |

未启用的单位：前端输入框**置灰不可编辑**，后端**强制不落价格**（即使前端被绕过）。

### 规则 3：未启用单位的价格存 NULL，不存 0

商品档案里停用单位的 `standardPrice` 常是占位 `0`。若原样落库，下游会把 `0.00` 误读为「该单位真实售价 0 元」。因此：

- 后端 `parseUnitProfile` 对未启用单位的标价返回 `null`
- 前端展示统一显示 `—`（`fmtStandardPrice(v, enabled)`）

### 规则 4：商品信息一律从档案快照，不信任前端传值

`insertDetails()` 只采用前端传来的**现价**，其余（商品名、规格、条码、品牌、分类、存储属性、三级单位名、三级标价、启用状态）全部由后端 `loadGoods()` + `parseUnitProfile()` 从 `base_goods` 重新取值。防止前端篡改或数据不一致。

### 规则 5：价格未变不记变价日志

`applyUnitPrices()` 中若 `oldPrice.compareTo(newPrice) == 0` 则跳过日志写入，避免变价查询出现「变价前 = 变价后」的噪音记录。
注意：**`_item` 表的 UPDATE 仍会执行**（刷新 `adjust_no`、`updated_at` 等），只跳过日志。

### 规则 6：停用不可撤销，恢复价格必须走新调价单

**系统刻意不提供「恢复启用」按钮**。停用后若要重新给该客户该商品该单位定价，唯一路径是**新建调价单 → 审核**。

理由：价格变动必须有单据依据。若允许在查询页直接点「启用」恢复，这次价格恢复就没有对应的调价单与审核记录，变价查询里也追不到，审计链会断。

实现上如何支撑（`applyUnitPrices()` 的 UPDATE 分支）：

```sql
UPDATE base_customer_price_item
SET ..., is_active = TRUE, updated_at = CURRENT_TIMESTAMP
WHERE id = ?
```

**关键点：更新已有行时无条件把 `is_active` 置回 TRUE**。因此不论该行此前是被手工停用还是被作废单据连带停用，新调价单审核后都会重新生效。

两种情形都已实测通过：

| 新调价单填的价格 | 是否恢复生效 | 是否产生变价记录 |
| --- | --- | --- |
| 与原价**不同**（如 30.00 → 28.00） | ✅ 恢复 | ✅ 记一条（变价前 30.00 → 变价后 28.00） |
| 与原价**相同**（如 28.00 → 28.00） | ✅ 恢复 | ❌ 不记录（规则 5「价格未变不记日志」） |

> ⚠️ **注意第二种情形**：用「原价重填」的方式恢复一条被误停用的价格，价格能恢复生效，但**变价查询里不会留下任何痕迹** —— 因为价格数值确实没变。此时该次恢复只能通过调价单本身（以及 `_item.adjust_no` 已指向新单号）追溯。若希望恢复动作也留痕，可把新价格设成与原价不同的值。

### 规则 7：状态机与允许的操作

```text
        ┌──────────┐
  新建 →│ PENDING  │ 待审核
        └────┬─────┘
             ├── 编辑（update）    ✅ 仅 PENDING
             ├── 审核（audit）     ✅ 仅 PENDING → APPROVED
             └── 作废（cancel）    ✅ → CANCELLED
        ┌──────────┐
        │ APPROVED │ 已审核 —— 价格已生效
        └────┬─────┘
             ├── 编辑  ❌ 400「仅待审核单据可编辑」
             ├── 审核  ❌ 400「该单据已审核」
             └── 作废  ✅ → CANCELLED **且连带停用它生成的价格**
        ┌──────────┐
        │CANCELLED │ 已作废
        └────┬─────┘
             └── 作废  ❌ 400「该单据已作废」
```

> **作废已审核单据必须连带停用价格。** 否则「客户价格查询」仍会显示一张已作废单据带来的价格，销售按错价出单。实现上把 `_item.is_active` 置 FALSE、老表 `effective_status` 置 STOPPED，**变价日志不删**。

## 四、模块一：客户价格调整单

### 4.2 列表页（CustomerPriceAdjust.vue）

**12 列**：调整单号、客户、单据日期、生效方式、价格有效期、商品数、制单人、制单时间、审核人、审核时间、状态、操作

**行操作按钮（按状态互斥）**：

| 状态 | 显示按钮 |
| --- | --- |
| 待审核 | `编辑` `审核` `作废` |
| 已审核 / 已作废 | `查看` |

**双击任意行** → 弹出只读详情窗口（`CustomerPriceViewDialog`）。
实现细节：`ProTable` 双击时统一 emit `row-action('查看', row)`，列表页拦下来走 `openView()`。

**单据日期的显示口径**：后端 `billDateText = audit_date ?? bill_date` —— 审核后显示审核当日，未审核显示建单日。

**审核 / 作废前均有 `confirm()` 二次确认**，审核提示语会说明「价格立即生效，历史有效价将自动停用」。

### 4.3 商品选择窗口（CustomerPriceGoodsDialog.vue）

**不复用**销售订单的 `GoodsAddDialog`，是独立组件。

| 特性 | 实现 |
| --- | --- |
| 展示 13 字段 | 商品编号、名称、规格、条码、分类、品牌、小单位、小单位标价、大单位、大单位标价、中单位、中单位标价、存储属性 |
| 6 个查询条件 | 商品编号、名称、条码、品牌、分类、存储属性（**前端过滤**，`matchesFilter`） |
| 分页 | 默认 100，可切 500/1000/2000（**前端分页**） |
| 只查正常商品 | `status === 'NORMAL' \|\| '正常'` |
| 勾选不退出 | 勾选只改 `selected` Set，不关闭窗口 |
| 「确定」才返回 | `confirm()` → emit `confirm(selectedRows)` 并关闭 |
| 「关闭」不返回 | `close()` → 清空 `selected`，emit `close` |
| 同一商品不可重复添加 | 父组件传 `existing-codes`，已添加的复选框 `disabled` 且行置灰 |

数据源：`POST /base/goods/page`（一次拉 2000 条缓存，仅首次打开时加载）

> ⚠️ **列顺序是 小 → 大 → 中**（按需求指定的字段顺序），而 `_profile` 对象的字段声明顺序是 small/medium/large。模板绑定时必须**先绑 large 再绑 medium**，否则大/中两列数据会错位。

### 4.4 编辑页（CustomerPriceEdit.vue）

**表头字段**：客户（必填）、生效方式、生效时间（仅 SCHEDULED 显示）、价格有效范围、有效自/至（仅 RANGE 显示）、备注

**明细表 17 列**：`#`、商品编号、商品名称、规格、小单位、小单位标价、小单位现价\*、大单位、大单位标价、大单位现价、中单位、中单位标价、中单位现价、品牌、商品分类、存储属性、操作

**明细行对象（18 个字段）**：

```javascript
{
  goodsCode, goodsName, spec, barcode, brandName, categoryName, storageProperty,
  smallUnit,  smallStandardPrice,  smallCurrentPrice,
  mediumUnit, mediumEnabled, mediumStandardPrice, mediumCurrentPrice,
  largeUnit,  largeEnabled,  largeStandardPrice,  largeCurrentPrice,
}
```

**添加商品时的价格自动回填**：

```text
小单位现价 ← 小单位标价          （恒执行，小单位always启用）
中单位现价 ← 中单位标价          （仅 mediumEnabled 为真；否则 null）
大单位现价 ← 大单位标价          （仅 largeEnabled 为真；否则 null）
```

未启用单位的标价与现价**都留空**，避免展示档案里的占位 0。现价均可编辑。

**保存校验**：

1. 未选客户 → `请选择客户`
2. 无明细 → `请至少选择一条商品明细`
3. 某行所有启用单位的现价都为空 → `商品【XXX】请至少填写一个单位的现价`

**payload 字段映射（注意与前端字段名不同）**：

```javascript
{
  customerId: header.customerCode,      // ← 注意改名
  effectiveMode, effectiveTime, validType, validFrom, validTo, remark,
  details: [{
    goodsId: d.goodsCode,               // ← 注意改名
    unitId:  d.smallUnit,
    currentPrice: Number(d.smallCurrentPrice) || 0,   // 兼容老接口 @NotNull 校验
    smallCurrentPrice, mediumCurrentPrice, largeCurrentPrice,   // 未启用单位传 null
  }]
}
```

- **新建** → `POST /customer-price-adjust/create`
- **编辑** → `POST /customer-price-adjust/update`，额外带 `adjustId`

**编辑模式加载**：`GET /customer-price-adjust/detail?adjustId=X`，回填表头与明细。启用状态取**单据快照**的 `mediumUnitEnabled`/`largeUnitEnabled`，不重读商品档案。后端会把 `valid_range` 反解为 `validType` + `validFrom`/`validTo` 供表单还原。

### 4.5 后端流程

#### 创建（create）

```text
1. 生成 adjust_id = "CPA" + UUID前12位
2. 生成 adjust_no = billNoGen.nextNo("CPA", "base_customer_price_adjust", "adjust_no")

   → CPA + yyyyMMdd + 4位当日流水（COUNT(*) + 1），保证同日连续

3. operator = currentUserDisplayName()

   → SecurityContext 取登录账号 → 查 sys_user_runtime.display_name → 兜底账号名 → 兜底"系统"

4. 查 base_customer 补 customer_name（查不到不阻断）
5. INSERT _adjust：status='PENDING', bill_date=CURRENT_DATE, creator_name, create_time
6. insertDetails()：逐行 loadGoods() + parseUnitProfile()，商品信息全部重新快照

   detail_id = adjustId + "D" + 1-based序号
```

#### 编辑（update）

```text
1. 查 status；不存在 → 404；非 PENDING → 400「仅待审核单据可编辑」
2. UPDATE _adjust 表头字段
3. DELETE 全部明细 → insertDetails() 重新插入   ← 整体替换策略，避免逐行 diff
```

#### 审核（audit）★ 核心

```text
1. bizId 兜底：为空或以 "demo" 结尾时，取最新一张单（供冒烟测试用）
2. 先算 auditedAt / auditor（写日志要用）
3. 查单据；不存在 → 404；非 PENDING → 400（已审核/已作废各自提示）
4. 逐条明细：

   a. 老表：UPDATE base_customer_price SET effective_status='STOPPED'
            WHERE customer_code=? AND goods_code=? AND effective_status='EFFECTIVE'
   b. 老表：INSERT base_customer_price（27 列，effective_status='EFFECTIVE'）
   c. applyUnitPrices(head, detail, auditor)  ← 见下

5. UPDATE _adjust：status='APPROVED', auditor_name, audit_time, audit_date=CURRENT_DATE
```

**`applyUnitPrices()` 逐单位处理逻辑**：

```text
构造 3 个 UnitSlot(level, unitName, standardPrice, price, enabled)
  slot1: level=1, enabled=true（恒真）
  slot2: level=2, enabled=isTrue(medium_unit_enabled)
  slot3: level=3, enabled=isTrue(large_unit_enabled)

对每个 slot：
  ① 跳过条件：!enabled || price == null        ← 未启用 或 未填价都跳过
  ② SELECT id, price FROM _item WHERE 客户+商品+unit_level
  ③ 不存在 → INSERT（is_active=TRUE），oldPrice = null
     存在   → UPDATE（is_active 重置为 TRUE），oldPrice = 原 price
  ④ 若 oldPrice != null 且 与新价相等 → continue（不记日志）
  ⑤ INSERT _change_log（old_price=oldPrice，可能为 null 表示首次设价）
```

#### 作废（cancel）

```text
1. 查 adjust_no, status；不存在 → 404；已 CANCELLED → 400
2. 若 status='APPROVED'：

   - UPDATE _item SET is_active=FALSE WHERE adjust_no=? AND is_active=TRUE
   - UPDATE base_customer_price SET effective_status='STOPPED' WHERE adjust_no=? AND ...
   （变价日志不动）

3. UPDATE _adjust SET status='CANCELLED'
```

## 五、模块二：客户价格查询

### 5.1 定位

展示客户指定商品的**当前专属价格**，一客户一商品一单位一条。可停用生效中的价格、可导出。

前端：`views/CustomerPriceQuery.vue` ｜ 路由 `/customer-price-query` ｜ 接口 `POST /base/customer-price/query`

### 5.2 列表 14 列

客户编号、客户名称、商品编号、商品名称、规格、条码、单位、单位类型、商品分类、品牌、标价、现价、状态、操作

> **刻意不展示**调价单号、生效方式、价格有效期 —— 这三个是「来源单据」属性，本页语义是「当前生效价」。需要追溯请用变价查询。这三列在**后端 SQL 层就未查询**，不只是前端隐藏。

### 5.3 查询条件

| 界面标签 | 后端 filter key | 类型 | 可接受值 |
| --- | --- | --- | --- |
| 客户 | `customer` | 文本 | 模糊匹配编号或名称 |
| 商品 | `goods` | 文本 | 模糊匹配编号或名称 |
| 状态 | `status` | 下拉 | `生效中` / `已停用`（也接受 `正常`/`true`/`1`/`false`/`0`） |
| 单位类型 | `unitType` | 下拉 | `小单位`/`中单位`/`大单位`（也接受 `1`/`2`/`3`） |

前端 `FILTER_KEY_MAP` 负责把中文标签转成后端 key（`QueryBar` 以中文标签为 key 返回）。后端每个 key 都有备用名（`customerCode`/`goodsCode`/`isActive`/`unitLevel`），便于其它调用方。

### 5.4 SQL 要点

```sql
FROM base_customer_price_item i
LEFT JOIN base_goods gd ON gd.goods_code = i.goods_code   -- 取规格/条码/分类/品牌
WHERE EXISTS (SELECT 1 FROM base_customer_price_adjust h
              WHERE h.adjust_no = i.adjust_no AND h.status = 'APPROVED')
ORDER BY i.customer_code, i.goods_code, i.unit_level
```

规格/条码/分类/品牌**实时取商品档案**（非快照），因为这些是商品属性而非价格属性。

### 5.5 停用

- **单条停用**：操作列「停用」按钮，仅 `is_active=true` 的行显示；已停用行显示 `—`
- **批量停用**：勾选多行 → 顶部「批量停用(N)」；已停用行的复选框 `disabled`
- 均有 `confirm()` 确认，提示「停用后该客户该单位的专属价失效，销售将回退到价格组价格」
- 接口 `POST /base/customer-price/stop`，body `{ priceIds: [...], reason }`
- 后端先更 `_item`；若影响 0 行，兜底更老表 `base_customer_price.price_id`（保证历史入口不报错）

### 5.6 导出

`exportRows()` 用 `xlsx` 导出**当前页**，排除「操作」列。文件名 `客户价格查询_YYYYMMDD.xlsx`。

## 六、模块三：客户商品变价查询

### 6.1 定位

展示客户商品的**历史调价记录**，含变价前/变价后。**完全只读**，无任何操作按钮（停用请去客户价格查询）。

前端：`views/CustomerPriceChangeQuery.vue` ｜ 路由 `/customer-price-change` ｜ 接口 `POST /base/customer-price-change-log/page`

### 6.2 列表 15 列

调价单号、日期、客户编号、客户名称、商品编号、商品名称、单位、单位类型、商品分类、品牌、变价前、变价后、生效方式、价格有效期、备注

**「变价前」的显示**：`old_price` 为 NULL 时后端返回 `oldPriceText = "首次设价"`，前端以灰色展示；否则显示两位小数。

### 6.3 查询条件

界面 4 个：客户(`customer`)、商品(`goods`)、调价单号(`adjustNo`)、单位类型(`unitType`)

后端**额外支持**（前端暂未开放，可由其它调用方使用）：
`brandName`/`brand`、`categoryName`/`category`、`dateFrom`、`dateTo`（自动补 `00:00:00` / `23:59:59`）

### 6.4 SQL 要点

```sql
FROM base_customer_price_change_log l
WHERE EXISTS (SELECT 1 FROM base_customer_price_adjust h
              WHERE h.adjust_no = l.adjust_no AND h.status = 'APPROVED')
ORDER BY l.created_at DESC, l.goods_code, l.unit_level
```

本表所有展示字段都是**写入时快照**，不 JOIN 商品档案 —— 历史记录应保持当时的分类/品牌，不随档案变动。

### 6.5 导出

同前，导出当前页全部 15 列，文件名 `客户商品变价查询_YYYYMMDD.xlsx`。

### 前端 module-api 键名

```javascript
customerPrice:           { page, save, audit, cancel, import }
customerPriceQuery:      { page, stop }
customerPriceChangeLog:  { page }     // ← 注意键名
```

> ⚠️ 变价模块在 `module-config.js` / 路由 / 菜单里叫 **`customerPriceChange`**，但在 `module-api.js` 里叫 **`customerPriceChangeLog`**。视图直接 `moduleApis.customerPriceChangeLog` 引用，功能正常，但命名不统一，后续重构可统一。

### H2 数据库两个必知陷阱

1. **列别名会被大写**：连接串开了 `CASE_INSENSITIVE_IDENTIFIERS=TRUE`，`SELECT adjust_id adjustNo` 取回的 key 是 `ADJUSTNO`，前端读 `adjustNo` 全是 `undefined`。

   → **查询一律不写驼峰别名**，取原始列名后用 `toCamel()` 转换。
   （例外：`loadGoods()` 用了别名，但它只在后端内部消费，不返回前端。）

2. **没有 MySQL 专有函数**：即使 `MODE=MySQL`，`DATE_FORMAT()` 也不存在。时间格式化一律在 Java 层用 `DateTimeFormatter`。

## 八、已知限制与待办

| # | 限制 | 影响 | 位置 |
| --- | --- | --- | --- |
| 1 | 调整单列表的查询条件**不是按字段精确过滤**，而是 `PageResult.of()` 的**整行文本模糊匹配** | 条件能生效，但语义不精确：在「客户」框输入的值只要出现在该行任意字段（如单号、备注）就算命中；且多条件之间是「全部包含」而非按字段 AND | `adjustPage()` 未读 `filters()`，由 `PageResult.filter()` 兜底 |
| 2 | `effective_time` 创建时固定写 NULL | 选「定时生效」并填了时间，该时间不落库 | `createAdjust()` INSERT 硬编码 NULL |
| 3 | 「定时生效」无调度器（全局 `@Scheduled` 数量为 0） | 审核即刻生效，`SCHEDULED` 目前只是标记 | 无定时任务 |
| 4 | `valid_range` 到期后无自动失效 | 过期价格仍显示「生效中」，需手工停用 | 无定时任务 |
| 5 | 导入价格接口是假实现 | 点「导入价格」返回固定假数据 | `importAdjust()` |
| 6 | 三个列表的导出均为**当前页**导出 | 跨页需先调大每页条数 | 各 `exportRows()` |
| 7 | 商品选择窗口一次拉 2000 条前端过滤 | 商品超 2000 会被截断 | `CustomerPriceGoodsDialog.loadGoods()` |
| 8 | V26 回填的变价记录「变价前」全为「首次设价」 | 历史记录看不到真实涨跌幅 | 老表无变更链，无法还原 |
| 9 | 分页在应用层完成：`PageResult.of()` 先拿到全量 `List` 再 `subList` 切分 | 数据量大时全表进内存，有性能隐患 | `PageResult.of()` |
| 10 | `loadGoods()` 把 `min_sale_price` 别名为 `costPrice` | 语义易混淆（最低售价 ≠ 成本价） | `loadGoods()` |
| 11 | 两个查询模块的过滤在 **SQL 层**做（`WHERE ... LIKE`），调整单列表在 **应用层**做 | 同一套「查询栏」在不同模块行为不一致 | 见 #1 |

### 排查问题的建议顺序

1. **列表字段全空** → 检查 SQL 是否误用驼峰别名（H2 大写陷阱）
2. **价格查询查不到数据** → 确认来源单据 `status='APPROVED'`；未审核不显示是预期行为
3. **中/大单位灰着无法录价** → 查 `base_goods.unit_config` 对应索引的 `enabled`
4. **审核报 400** → 单据已审核或已作废，状态机不允许重复操作
5. **后端启动失败** → 先查 `db/migration/` 是否有重复版本号
