# 分支管理与开发流程规范

> 适用仓库：`csflyinfo/csERP`（ERP + WMS + TMS 全链路系统）
> 生效日期：2026-08-18
> 适用范围：后端 `backend/`、前端 `frontend/`、司机 APP `tms_driver_app/`、文档 `docs/`

---

## 一、分支模型：主干开发 + 短生命周期功能分支

`main` 是**唯一长期分支**，永远保持可部署状态。任何改动都走一个短命分支，做完合回 `main` 并立即删除。

```
main ──●──●──────●──────────●──────●─────▶  (唯一主干，永远可部署)
        \        /          /      /
         ●──●──●          /      /         feat/tms-exception-report
                \        /      /
                 ●──●──●       /           feat/finance-v2-costing
                              /
                        ●──●─              fix/sales-return-tax
```

**明确不采用 Git Flow。** 本项目为单人开发，`develop` + `release/*` 的双向回合只会增加合并负担，不带来收益。

### 1.1 分支类型与命名

| 类型 | 命名 | 来源 | 合入 | 存活上限 |
|---|---|---|---|---|
| 主干 | `main` | — | — | 永久 |
| 新功能 | `feat/<模块>-<简述>` | `main` | `main` | ≤ 5 天 |
| 缺陷修复 | `fix/<模块>-<简述>` | `main` | `main` | ≤ 2 天 |
| 生产急修 | `hotfix/<简述>` | 生产 tag | `main` | ≤ 1 天 |
| 重构/依赖/工程化 | `chore/<简述>` | `main` | `main` | ≤ 3 天 |

`<模块>` 必须使用与 PRD 一致的划分：`purchase`、`sales`、`inventory`、`finance`、`tms`、`wms`、`base`。

示例：`feat/tms-exception-report`、`fix/sales-return-tax`、`feat/finance-v2-costing`

### 1.2 硬性约束

1. **禁止工具自动命名的分支长期存活。** `appmod/*`、`copilot/*` 一律视为临时分支，合完即删，不得充当主干。
2. **5 天红线。** 分支活过 5 天必须 `git merge main` 回灌一次。长期不同步是分叉与大规模冲突的唯一根因。
3. **一个分支只做一件事。** 不要在 `feat/tms-*` 里顺手改财务模块；巨型合并一旦出问题无法二分定位。
4. **绝不提交冲突标记。** 由 CI 强制（见第六节）。
5. **绝不对已推送的提交 `git commit --amend` 或 rebase。** 已发布历史只能追加新提交来修正。

## 二、需求的完整生命周期

以"TMS 异常报告与到店签到"为例。

### 步骤 1｜先登记需求，拿到编号（此时不开分支）

在 `docs/PRD-版本化产品需求/00-总览与规范/00-PRD文档索引与版本路线图.md` 的需求登记表中新增一行，**先占号，再建文件**：

| 编号 | 需求 | 版本 | 分支 | Flyway 区段 | 状态 |
|---|---|---|---|---|---|
| PRD-23 | TMS 异常报告与到店签到 | V2.0 | `feat/tms-exception-report` | V65~V70 | 开发中 |

> 编号由索引表统一发放，不允许建文件时随手起号。历史上已因此撞号：
> `19-V1.0-单据明细仓库规则补充PRD.md` 与 `19-V1.0-系统方管理后台PRD.md` 同为 19。

### 步骤 2｜从最新 main 开分支

```bash
git checkout main && git pull          # 必须先拉，禁止从旧 main 开分支
git checkout -b feat/tms-exception-report
```

### 步骤 3｜锁定 Flyway 迁移号区段

```bash
ls backend/src/main/resources/db/migration/ | sort -V | tail -1   # 查当前最大号
```

在索引表登记本需求占用的区段（如 V65~V70）。下一个分支从区段之后取号。详见第四节。

### 步骤 4｜四类产出全部在同一分支内完成

| 类型 | 位置 |
|---|---|
| 需求/方案文档 | `docs/PRD-版本化产品需求/V2.0-.../23-V2.0-TMS异常报告PRD.md` |
| 后端 / 前端 / APP 代码 | `backend/`、`frontend/`、`tms_driver_app/` |
| 数据库迁移 | `backend/src/main/resources/db/migration/V65__*.sql`（不得超出登记区段） |
| 验收用例 | 追加至 `12-V1.0-测试验收用例全集.md` 或同级用例文档 |

> **硬规则：需求文档必须与实现它的代码同分支、同批合入 `main`。**
> 文档不再单独攒批次——曾因此导致 40 份文档在本地滞留两个月未推送。

### 步骤 5｜合并前自检（DoD）

```bash
git checkout main && git pull
git checkout feat/tms-exception-report
git merge main                      # 回灌，把冲突消化在自己分支里

# 自检
git grep -nE '^(<<<<<<< |>>>>>>> )' -- 'backend/src/**' 'frontend/src/**' 'tms_driver_app/lib/**'
cd backend && ./mvnw -q compile     # 必须在 backend/ 下执行，见第五节
```

### 步骤 6｜squash 合入并删除分支

```bash
git checkout main
git merge --squash feat/tms-exception-report
git commit -m "feat(tms): 异常报告与到店签到（PRD-23, V65~V70）"
git push
git branch -D feat/tms-exception-report      # 立即删除，不留僵尸分支
```

> 此处必须用 `-D` 而非 `-d`：`--squash` 合并不会在分支上记录合并关系，
> git 不认为它已被合入，`-d` 会拒绝删除。内容确已进入 `main`，`-D` 是安全的。

提交信息**必须带 PRD 编号与迁移区段**，这样 `git log --grep=PRD-23` 即可反查一个需求的全部落地代码。这是最廉价可靠的追溯手段。

## 三、提交信息规范

采用 Conventional Commits（本仓库前 32 个提交本就是该格式，恢复即可）：

```
<type>(<scope>): <简述>（<PRD编号>, <Flyway区段>）

type : feat | fix | docs | refactor | test | chore | perf
scope: purchase | sales | inventory | finance | tms | wms | base
```

```
✅ feat(tms): 异常报告与到店签到（PRD-23, V65~V70）
✅ fix(sales): 拒收入库单税额取含税金额（PRD-18）
✅ docs(finance): 补充 V2.0 财务核算 PRD

❌ Step 6: Run build & tests - Compile: SUCCESS      ← 这是日志不是提交信息
❌ fix BatchEditDrawer 动态数据                       ← 缺 type/scope
❌ Merge branch 'appmod/...' of https://github.com... ← 见下
```

消灭无意义 merge commit（一次性配置）：

```bash
git config --global pull.rebase true
```

### 合并方式

| 场景 | 方式 | 理由 |
|---|---|---|
| 功能分支 → `main` | `--squash` | 一个功能 = 一个提交，回滚即 revert 单个提交 |
| `main` → 功能分支（回灌） | `merge` | 保留双方历史，不改写已推送提交 |
| 拉取远端同名分支 | `rebase` | 不产生噪音 merge |

## 四、全局串行资源（本项目最大的分支管理风险）

以下两项是**全局唯一序号**，并行分支各自取号必然冲突：

1. **Flyway 迁移号** `backend/src/main/resources/db/migration/V<n>__*.sql`
2. **PRD 文档编号** `docs/PRD-版本化产品需求/**/<n>-*.md`

### 4.1 推荐做法：串行

**同时只开一个包含数据库迁移的分支。** 这不是保守，而是因为 Flyway 版本冲突的修复成本远高于等待成本。

### 4.2 必须并行时

| 情况 | 处理 |
|---|---|
| 两分支都不含迁移 | 自由并行，无风险 |
| 只有一个含迁移 | 自由并行 |
| 两个都含迁移 | **后合并者必须重编号** |

重编号步骤：

1. 重命名 SQL 文件为区段内的下一个可用号
2. **先停止后端**（H2 文件锁会阻挡连接）
3. 用 `h2-2.2.224.jar` 的 Shell 直连 `data/erp-v1`，删除 `flyway_schema_history` 中的对应记录
4. 重建库并验证迁移可完整执行

CI 会自动拦截重号（见第六节护栏 2）。

## 五、环境约束（易踩的坑）

1. **后端必须在 `backend/` 目录下启动或编译。** `pom.xml` 只存在于该目录，且 H2 数据源使用相对路径——在仓库根目录执行会连接到一个空库，测试结果不可信。
2. **启动必须使用 JDK 21**（`pom.xml` 中 `<java.version>21</java.version>`）。
3. **smoke test 不得进入 CI。** 它按单号前缀删除全部采购/销售单据，只能在本地备份 H2 之后手动执行。
4. **GitHub HTTPS 在国内网络下会间歇性超时。** `push`/`pull` 失败属常见现象，重试数次通常可成功；`fetch` 已成功时可用 `git merge origin/main` 离线完成合并。

## 六、自动化护栏

`.github/workflows/ci.yml` 在 push 到 `main` 及针对 `main` 的 PR 上运行三项检查：

| 护栏 | 拦截内容 |
|---|---|
| 1. 冲突标记检查 | `backend/src`、`frontend/src`、`tms_driver_app/lib` 中残留的 `<<<<<<< ` / `>>>>>>> ` |
| 2. Flyway 重号检查 | 同一迁移号出现多次 |
| 3. 后端编译 | `backend/` 下 `./mvnw compile` 失败 |

建议在 GitHub 仓库设置中对 `main` 开启 **Require status checks to pass**，使护栏成为强制门禁。

- `backend-run.log`、`*.log`、`*.class`、`backend/target/`

**待决事项：** `data/erp-v1.mv.db`、`data/erp-v1.trace.db` 及 `data/backup-*/` 下的 H2 数据库文件目前仍被 git 跟踪。二进制库文件无法有效 diff/合并，且包含业务数据。建议评估后改为不跟踪（改用 `V1__schema.sql` + 种子数据脚本重建），或明确其为受控的种子库。

## 九、一页速查

```
需求来了
  ├─ 1. 索引表登记 → 拿 PRD 编号 + 占 Flyway 区段
  ├─ 2. git pull && git checkout -b feat/<模块>-<简述>
  ├─ 3. 文档 + 代码 + 迁移 + 用例   全部在这一个分支内
  ├─ 4. 活过 5 天 → 必须 git merge main 回灌
  ├─ 5. 合并前：无冲突标记 + backend/ 下能编译
  └─ 6. git merge --squash → 提交信息带 PRD 编号 → git branch -D 删分支
```
