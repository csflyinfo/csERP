# 拒收入库单 实施方案

## 背景与关键前提

需求原文：「新建【拒收入库单】，它由签收拒收的商品自动生成，模块结构参照采购入库。它不能新建，可编辑。根据原出库单自动带出出库批次号和生产日期（如果对应有多个出库日期，取最新的生产日期）。审核后按入库流水走，拒收入库商品成本单价取原出库成本单价，重算成本。主单要有销售订单号、发货单号、出库单号、司机等信息。」

**探查结论（决定了本方案的范围）：**

1. **「签收」功能当前完全不存在。** `sales_receipt`（销售发货单）只有 `receive_status`（未收款/部分收款/已收款，收款状态），明细表 `sales_receipt_detail` 没有签收数量/拒收数量列。`sales_order.sign_status` 列存在但**全后端从未写入**（死列，仅 `ExcelController` 导出时读）。前端 `module-config.js:209-210` 的「确认签收」「签收数量」是 PRD 占位文案，点击只弹通用 confirm，不调任何接口。
   → 所以「由签收拒收的商品自动生成」**没有数据源，必须先把签收拒收做出来**。
2. **「司机」当前只有 `base_route_line.driver`**（线路的默认司机）。`sales_outbound` 有 `route_line` 但没有司机列，`sales_receipt` 也没有。
3. 全代码库 grep `拒收 / reject_qty / rejectQty` **零命中**，没有任何既有实现可复用。
4. 「取原出库成本单价」目前**没有先例**——销售退货入库（最接近的模块）用的是 `getCurrentCostPrice()` 当前移动加权均价，不是原出库成本（`SalesReturnController.java:776-781` 注释「退货入库成本 = 当前库存成本单价」）。本单是第一个真正回溯原出库成本的单据。
   ⚠️ **计价口径澄清（用户 2026-08-13 指正，勿再理解错）**：系统按「**商品 + 仓库**」维度做移动加权平均，**不按批次**。`InventoryCostService.salesOutbound` 写流水取的是 `inv_stock_balance.cost_price`，**不是 `inv_batch_stock.cost_price`**。因此：
   - 同一张出库单、同一商品拆几个批次，**成本单价都是同一个值**；
   - 同一张采购入库单、同一商品不同批次，**入库成本单价也都是同一个值**；
   - `inv_batch_stock.cost_price` 虽然存在，但出入库计价**不走它**；
   - 所以本单与退货入库/其他入库的差别是「**时点**」（出库时点快照 vs 审核时点均价），**不是**「批次成本 vs 汇总成本」。「取最新生产日期那批」只决定批次号与生产日期，**不影响成本**。
5. 数据是齐的：`sales_outbound_detail` 有 `batch_no` / `production_date` / `cost_price` / `qty` / `warehouse`；`sales_outbound.source_order`（销售订单号）；`sales_receipt.source_outbound_no`（1:1 关联出库单，唯一索引）。发货单明细本身**不含批次**（V17:50 注释「按 goods_code 从出库聚合而来，不含批次号」），所以必须经 `sales_receipt.source_outbound_no → sales_outbound → sales_outbound_detail` 回溯批次与成本。

**已确认的三个决策：**

| 决策项 | 结论 |
| --- | --- |
| 拒收来源 | 在**发货单上加签收拒收**（明细加签收/拒收数量+拒收原因，主单加签收状态），签收时有拒收量就**自动生成**拒收入库单。真正做到「自动生成、不能新建」 |
| 明细拆行 | **每个商品一行**。原出库即使拆了多批次，拒收入库只生成一行，批次号/生产日期取**生产日期最新**的那批。成本单价取原出库单**该商品**的出库成本单价 —— 系统按「商品 + 仓库」移动加权平均计价，**与批次无关**，同一张单据同一商品拆几个批次成本单价都是同一个值，所以「取最新生产日期那批」只决定批次号与生产日期，不影响成本 |
| 司机 | **`sales_outbound` 和 `sales_receipt` 都加 `driver` 列**，出库新建/编辑时可指定实际司机（默认带线路司机），发货单从出库快照，拒收入库单再从发货单快照 |

### 2. 新建 `backend/src/main/java/com/erp/sales/RejectInboundController.java`

放在 `com.erp.sales` 下、路径 `/sales/reject-inbound/*`，与既有的 `/sales/return-inbound/*`（销售退货入库）保持一致。

**实现风格采用 `OtherInboundController`（V49）的纯 `JdbcTemplate` + `Map<String,Object>` 写法**，而非 `PurchaseController` 的 MyBatis-Plus 实体写法。理由：V49/V48 是仓内单据最新且最完整的模板（自带 update/delete/cancel/reverse-audit/import），需求里「模块结构参照采购入库」指的是**模块形态**（列表→详情→编辑→审核→走入库流水重算成本），不是 ORM 选型。若你要求严格用 MyBatis-Plus 实体，需额外加 4 个样板文件（entity/mapper/service/impl ×2 张表），可以改。

**生成入口**：`public String generateFromReceipt(String receiptId)`，供 `SalesReceiptController` 签收时调用（同 `PurchaseController.auditInbound` 调 `receiptController.generateFromInbound` 的既有模式），不暴露为 REST 端点。

#### `generateFromReceipt` 逻辑

1. 幂等守卫：`reject_generated = TRUE` 或 `uk_reject_inbound_receipt` 已存在 → 直接返回既有单号，不重复生成。
2. 读 `sales_receipt` 主单 → 拿 `source_outbound_no` / `source_order_no` / `customer_*` / `warehouse` / `driver` / `salesman` / `route_line`。
3. 读 `sales_receipt_detail` 中 `reject_qty > 0` 的行。
4. **回溯原出库批次与成本**——按 `source_outbound_no` 查出库明细，每个商品取生产日期最新的一批：

```sql
SELECT detail_id, goods_code, goods_name, spec, unit_name, warehouse,
       batch_no, production_date, price, cost_price
FROM sales_outbound_detail d
JOIN sales_outbound o ON o.outbound_id = d.outbound_id
WHERE o.outbound_no = ?
ORDER BY d.goods_code, d.production_date DESC NULLS LAST, d.detail_id DESC
```

在 Java 层按 `goods_code` 取**首行**（即生产日期最新那批），得到该商品的 `batch_no` / `production_date`。**成本单价是按商品聚合取的**（SQL 里用相关子查询 `MAX(cost_price) WHERE outbound_id=… AND goods_code=…`），不是「首行那个批次的成本」：系统按「商品 + 仓库」做移动加权平均，`InventoryCostService.salesOutbound` 写流水取的是 `inv_stock_balance.cost_price`，**不走 `inv_batch_stock.cost_price`**，所以同一张单据同一商品各批次行的 `cost_price` 本来就相等，`MAX` 只是为了取一个确定值（并跳过 0 成本行避免拉低）。
   - 空批次兼容：`production_date` 可为 NULL（V33 起批次号可空），`NULLS LAST` 保证有日期的优先。
   - 兜底顺序：`sales_outbound_detail.cost_price`（该商品）→ `inv_stock_ledger`（`source_bill = 出库单号 AND direction='OUT' AND goods_code=?` 取最近一条）→ `inventoryCostService.getCurrentCostPrice()`（**兜底而非常态**，取到的是审核时点均价，已偏离需求口径）。三级兜底都取不到则该行成本记 0 并写操作日志告警。
5. 写主单（`status='PENDING'`, `stock_updated=FALSE`, `bill_date = 当天`）+ 明细（`qty` 默认 = `reject_qty`）。
6. 回写 `sales_receipt.reject_generated = TRUE`。
7. 操作日志：`log("sales.rejectInbound", "GENERATE", inboundNo, "签收拒收自动生成拒收入库单")`。

#### `audit` 逻辑（「审核后按入库流水走 + 重算成本」）

对齐 `OtherInboundController.audit`（`:283-336`）：

1. 校验 `status='PENDING'`，`qty > 0` 的行至少一条。
2. 逐行调**既有的入库原语**：

```java
inventoryCostService.purchaseInbound(
        goodsCode, goodsName, warehouse, batchNo,
        qty,
        costPrice,        // ← 原出库成本单价，明细上已快照，不再取当前均价
        inboundNo,        // → inv_stock_ledger.source_bill
        productionDate);
```

`InventoryCostService.purchaseInbound`（`InventoryCostService.java:44-102`，`@Transactional`）一次性完成三件事，正是「按入库流水走 + 重算成本」：
   - `upsertBatchStock()` → 累加 `inv_batch_stock`，批次成本按加权平均（scale 4），`production_date` 用 `COALESCE` 回填；
   - 重算 `inv_stock_balance` **移动加权平均成本**：`newCost = (oldStockAmount + qty×costPrice) / (oldQty + qty)`（scale 4 HALF_UP），更新 `physical_qty / available_qty / cost_price / stock_amount / last_inout_time`；
   - `writeLedger("IN", ...)` → 写 `inv_stock_ledger` 一条 `direction='IN'` 流水。

   ⚠️ **与本单的关键差异（是「时点」，不是「批次」）**：`OtherInbound`/`SalesReturnInbound` 传的是 `getCurrentCostPrice()`（**审核时点**的当前库存均价），**本单传明细上快照的「出库时点」成本单价**——这是需求的核心点，也是全项目首例。出库后若又有新价采购拉动了均价，两者才会不同；没有新采购时两者数值相同，但口径不同。
   注意 `inv_stock_ledger.cost_price` 这一列：`purchaseInbound` 往里写的是 `newCost`（**入库后**的库存均价），`amount` 写的才是 `inboundQty × 传入成本`。全系统所有采购入库都是这个语义，不是本单特例 —— 所以验证「用了出库时点成本」要看流水的 `amount`，不是 `cost_price`。
3. 回写明细 `cost_amount = qty × cost_price`，主单 `cost_amount = Σ`、`status='APPROVED'`、`stock_updated=TRUE`、`audit_user`、`audit_time`。
4. 操作日志 `log("sales.rejectInbound", "AUDIT", inboundNo, "拒收入库审核")`。

#### `reverse-audit` 逻辑

对称 `OtherInboundController.reverseAudit`（`:346-372`）：APPROVED→PENDING，逐行**先校验批次可用量**再调 `inventoryCostService.salesOutbound(..., inboundNo + "(反审核)")`。

> ⚠️ 必须自己先校验批次可用量：`salesOutbound`（`InventoryCostService.java:183-216`）只校验 `goods+warehouse` 聚合层，**不校验批次可用量**（既有已知坑，`OtherInboundController.java:613` / `TransferController.java:448` 都自己前置校验了）。

### 3. `SalesReceiptController.java` 改动

新增 `POST /sales/receipt/sign`（确认签收）：

- 入参：`{ bizId, driver?, details: [{ detailId, rejectQty, rejectReason }] }`
- 校验：仅 `sign_status='待签收'` 可签收；`0 ≤ rejectQty ≤ qty`；`rejectQty > 0` 时 `rejectReason` 必填。
- 逐行写 `reject_qty` / `reject_reason`，`signed_qty = qty - reject_qty`。
- **逐行汇总签收口径金额**（V52 起）：`sign_amount = signed_qty × price`（含税）、`reject_amount = reject_qty × price`、`tax_amount = sign_amount × 税率 ÷ (1+税率)`（**价内税倒算，与采购一致**）。明细 `amount` 是**发货金额**，出库审核时定死，签收**不改它**。
- 主单：`sign_status` = 全部拒收 / 部分拒收 / 已签收（按 Σ reject_qty 与 Σ qty 判定），`sign_time`、`sign_user`、`reject_qty = Σ`，并汇总写 `sign_amount` / `reject_amount` / `tax_amount` / `untaxed_amount`（`untaxed_amount = sign_amount − tax_amount`）。`deliver_amount`（发货金额）**不动**，`expense_amount` 是占位字段，不参与任何公式。
- **Σ reject_qty > 0 → 调 `rejectInboundController.generateFromReceipt(receiptId)`**，返回生成的拒收入库单号给前端提示。
- **签收金额 > 0 → 立即自动审核并生成应收**（`approveAndGenerateAr`）：写 `fin_ar`（`ar_amount = sign_amount`，**含税**，与采购应付取含税 `goods_amount` 对称）、发货单置 `status='APPROVED'` / `ar_status='已生成'`，返回 `arNo`。
- 幂等保护：`ar_status='已生成'` 时拒绝重复签收，提示「请先反审核再登记签收」。
- 操作日志 `log("sales.receipt", "SIGN", receiptNo, ...)`。
- `@Transactional` 加在 controller 方法上（本项目既有约定：业务逻辑与事务都在 controller，`PurchaseController.auditInbound:372` 同）。

> **为什么把审核并进签收**：应收必须按客户实际签收的数量开票，拒收的货客户没收到、不能收他钱。如果审核是独立的手工动作，就存在「先审核按发货量生成应收 → 再签收拒收」的错序窗口，应收就多算了。把两步绑成一个事务后，「应收在拒收之后生成」才是代码事实，从而**根本不需要冲减应收**。
>
> 配套地 `POST /sales/receipt/audit` 加了两道前置校验：
> - `sign_status` 为空或「待签收」→ 报错「请先确认签收再审核：应收金额按客户实际签收数量生成」
> - `sign_status = '全部拒收'` → 报错「该发货单全部拒收，签收金额为 0，无应收可生成」（此时签收后单据停在 PENDING，也不生成应收）

另新增 `POST /sales/receipt/unsign`（撤销签收）：**全量回滚**——
- 先校验：`fin_ar.received_amount > 0`（已收过款）则拒绝撤销；拒收入库单必须仍为 `PENDING`。

## 五、应收口径（本轮已一并处理）

需求原文只说「拒收不影响应收，因为应收是在拒收之后生成的」。但**这句话原先在代码里并不成立**：`sign` 不重算金额、`audit` 也不要求先签收，所以发货 100 箱、签收 90 箱时，应收仍是按 100 箱算的 3955。我先用一个探针脚本实测复现，确认是真缺陷，而不是读代码读出来的猜测。

按你的选择（**签收时重算发货单金额** + **签收后自动审核**）已修正为：

| 场景 | 结果（金额为 V52 口径，单价 35 含税、税率 13%）|
| --- | --- |
| 发货 100，签收 90 拒收 10 | `sign_amount = 3150`、`reject_amount = 350`、`tax = 362.39`、`untaxed = 2787.61`，自动审核，`fin_ar.ar_amount = 3150`（拒收的 10 箱不开票）|
| 全部签收 | `sign_amount = 3500`、`tax = 402.65`、`untaxed = 3097.35`，自动审核生成应收 3500 |
| 全部拒收 | 签收金额 0（`reject_amount = 3500`），**不生成应收**，单据停在 PENDING；此时手工点审核会被拒绝并提示「全部拒收」|
| 撤销签收 | 删拒收入库单 + 删应收 + 四个签收金额归 0（`deliver_amount` 不变）+ 退回 PENDING；`fin_ar` 已收过款则拒绝撤销 |

这样「应收天然只含签收部分」，**不需要任何冲减/红字机制**。回归断言见 `v1-reject-inbound-test.js` 第 6.0 / 13 / 14 步。

另外两点提示：

- `sales_order.sign_status` 是个从未被写入的死列。本方案在 `sales_receipt` 上做签收，**没有**去激活它。若你希望订单级也能看签收状态，需要额外回写。
- `inv_stock_ledger.cost_price` 是 `DECIMAL(18,2)`，`inv_stock_balance.cost_price` 也是 `DECIMAL(18,2)`。所以 6 位小数的原出库成本单价在**明细表上完整保留**，但写进流水/库存余额时会被 H2 截到 2 位。这是既有精度设计（V48/V49 同样如此），本方案不改；若要全链路 6 位小数，需单独一版迁移改这两列。

## 六、销售发货单金额口径重构（V52，2026-08-13）

在上面「应收口径」的基础上，按需求把发货单的四个金额字段重新定义成**两个时点**。核心是：一张发货单同时要回答「我发了多少货」和「客户实际签收了多少」，原来只有一组金额字段，两个问题混在一起。

### 6.1 字段与算法

| 字段（`sales_receipt`）| 算法 | 产生时点 |
| --- | --- | --- |
| `deliver_amount` 发货金额 | Σ 明细 `qty × price`（含税）| **销售出库单审核**生成发货单时定死，之后永不变 |
| `sign_amount` 签收金额 | Σ 明细 `signed_qty × price`（含税）| 签收时汇总，生单默认 **0** |
| `reject_amount` 拒收金额 | Σ 明细 `reject_qty × price` | 签收时汇总，生单默认 **0** |
| `tax_amount` 税额 | `sign_amount × 税率 ÷ (1+税率)`（**价内税倒算**）| 签收时，生单默认 **0** |
| `untaxed_amount` 不含税金额 | `sign_amount − tax_amount` | 签收时，生单默认 **0** |

- `fin_ar.ar_amount` 取 **`sign_amount`（含税）** —— 与采购应付取含税 `goods_amount` 对称。
- `expense_amount` 保留为 0 占位字段，**不参与任何公式**（原先它被加进 `final_amount`）。
- 主单 `reject_qty` 在库里**保留并继续写入**（历史数据里有值），但不再对外返回、列表不再展示 —— 需求要的是「拒收金额」而不是「拒收数量」。列表/详情都改成显式列清单，避免 `SELECT *` 又把它漏出去。

**这一版把销售侧从价外税改成了价内税**，和采购完全对称。同一张单（100 × 35 含税、13%）两边数字一致：`3500 / 402.65 / 3097.35`。

### 6.2 字段改名与迁移

`V52__sales_receipt_amount_scheme.sql`：`goods_amount → deliver_amount`、`final_amount → untaxed_amount`（H2 2.x 的 `ALTER TABLE … ALTER COLUMN … RENAME TO`），新增主单/明细的 `sign_amount`、`reject_amount`。

> ⚠️ 回填的判别条件用 **`ar_status = '已生成'`，不是 `sign_status`**。线上库里 `XSFH202607240001` 是「待签收」但已经是 APPROVED + 应收已生成（自动审核上线前的手工审核遗留）。按 `sign_status` 回填会把这行的金额清零，而它背后挂着一张真实的 72.32 应收。
>
> 已生成应收的历史行：`sign_amount` 取原 `final_amount`，`untaxed_amount` 重算为 `sign_amount − tax_amount`；历史 `tax_amount` **不重算**（当年按价外税算的，改了反而和已开票的凭证不符）。未生成应收的行四项全部归 0。

### 6.3 前端

- 列表列：发货金额 / 签收金额 / 拒收金额 / 税额 / 费用金额 / 不含税金额，去掉「拒收数量」。
- **`确认签收` / `撤销签收` 从工具栏移到行内操作列**，按 `signStatus` + `status` 状态化：待签收 → 确认签收；已签收/部分拒收 → 撤销签收（+ 补救用的审核/反审核）。
- 签收弹窗只能改**拒收数量 / 签收数量**（改任一个，另一个按发货数量自动补齐）＋ 拒收原因（拒收 > 0 时必填，按你的选择保留）。新增只读的行签收金额/拒收金额列，以及发货/签收/拒收/税额/不含税五项汇总条（前端现算预览，落库以后端为准，两边同一套价内税算法）。
- 勾选多行 → **批量签收**：一律按「全签」处理（拒收 0、签收 = 发货数量），不传 `details`，后端对没传的行就是这个口径。有拒收的单子必须走行内「确认签收」。

### 6.4 顺带修掉的 TMS 回归（我自己上一轮引入的）

「签收后自动审核」把 `status='APPROVED'` 变成了**送达之后**才有的状态，而 `TmsDispatchController.pool` 的筛选条件是 `status='APPROVED' AND dispatch_status='UNDISPATCHED'` —— 调度是**出车前**做的，于是待调度池永久为空。

已改为 `status <> 'CANCELLED' AND sign_status = '待签收' AND dispatch_status = 'UNDISPATCHED'`。同时 `pool` / `create` 里的 `r.final_amount` 改成 `r.deliver_amount AS final_amount`：调度看的是「这车货值多少」，就是发货金额；用 SQL 别名保持对外字段名不变，`DispatchPool.vue` 零改动。
