~~~markdown
# TMS 调度管理系统优化方案评审与完善建议

> 评审对象：TMS 调度管理系统优化方案 V1.0  
> 涉及范围：ERP 后台 TMS 调度域、司机 APP、库存与财务集成、数据模型、状态机、离线签收、地图与轨迹  
> 评审结论：**整体方向正确，可作为 V1.0 基础，但存在若干架构与一致性问题，建议修正后再进入正式开发。**

---

## 一、总体评价

方案具备以下优点：

1. **系统边界清晰**：TMS 作为 ERP 内部业务域，而非独立微服务，符合现有架构约束。
2. **最小侵入原则明确**：尽量复用销售订单、出库单、发货单、库存和应收链路。
3. **业务闭环较完整**：覆盖派车、配送点、车次、拣货、签收、差异处理、交账等核心流程。
4. **双签收通道合理**：后台签收用于补录和客户自提，司机 APP 签收用于现场作业。
5. **跨端技术选型可行**：Flutter 适合 iOS/Android 双端统一交付。
6. **存储抽象设计较好**：`FileStorageService` 支持本地、MinIO、OSS，便于后续切换。

但方案在以下方面仍需完善：

- 拣货、锁定库存与既有出库审核扣库存之间存在时序冲突；
- 发货单审核生成应收与按签收数量开票之间存在财务口径冲突；
- 并发控制、幂等约束和重复派车防护不足；
- MySQL 轨迹分区表设计不合法；
- 地图选型在中国境内使用时存在合规与坐标偏移风险；
- 司机 APP 离线签收缺少失败补偿和人工处理机制；
- 部分数据模型字段和关系设计不足以支撑长期业务演进。

---

## 二、P0：必须优先修正的问题

### 1. 拣货与库存扣减时序冲突

方案中既有流程为：

> 销售出库单审核 → 扣减库存 → 销售发货单审核 → 生成应收

但 TMS 又设计为：

> 发货单审核 → 派车 → 生成拣货单 → 校验库存 → 锁定库存 → 拣货完成转实际扣减

这会导致库存被重复锁定或重复扣减。

#### 建议方案

若坚持“最小侵入改造”，推荐采用以下规则：

1. **拣货单仅作为仓内集中拣货、复核、装车作业单**；
2. 不重复调用库存锁定和扣减接口；
3. 拣货数量来源于 `sales_receipt_detail.outbound_qty`；
4. 库存扣减仍以销售出库单审核为准；
5. 从方案中删除“拣货单锁定库存”“锁定转实际扣减”的描述。

若未来要支持真正的波次拣货和按车次拣货后出库，则需要重构销售出库流程，将出库审核后置，但该改动较大，不建议放入 V1.0。

---

### 2. 应收生成时点与按签收开票规则冲突

方案中既有逻辑为：

> 发货单审核时生成应收

同时又规定：

> 财务按 `sign_qty` 进行收入确认与开票

如果发货单审核时已按应发数量生成应收，而签收时发生少收、拒收，则必须有应收调整机制，否则会出现财务账实不符。

#### 建议补充

1. 区分两类应收：
   - `APPROVED` 后生成“暂估应收”或“待结算应收”；
   - `COMPLETED` 后按 `sign_qty` 生成“正式应收”或“开票应收”。
2. 部分签收或拒收时，自动生成：
   - 应收调整单；
   - 红字销售单；
   - 贷项通知单；
   - 拒收入库单或退货入库单。
3. 只有满足以下条件的发货单才能进入开票池：
   - 发货单状态为 `COMPLETED`；
   - 签收差异已处理；
   - 拒收或退货入库已完成；
   - COD 款项已核对，如适用。
4. COD 场景需补充：
   - 司机现场收款登记；
   - 回场交账；
   - 现金短款处理；
   - 应收核销与财务对账。

---

### 3. 缺少并发控制，可能导致重复派车和重复签收

方案中提到了 `client_req_id` 幂等键，但仍不足以覆盖所有并发场景。

#### 重复派车风险

两个调度员同时派车，或司机扫码与后台派车同时发生时，同一发货单可能被分配到多个车次。

#### 建议

- 如果 V1.0 不支持拆单：
  - 对 `tm_trip_stop.receipt_no` 增加唯一约束或增加“有效配送中”状态校验；
- 如果 V1.0 支持拆单：
  - 不能只对 `receipt_no` 加唯一约束；
  - 应在 `sales_receipt` 上增加 `current_trip_id`、`dispatch_status`、`version` 等字段；
  - 派车接口使用乐观锁或 `SELECT ... FOR UPDATE`。

#### 重复签收风险

后台签收与司机 APP 签收可能同时提交。

#### 建议

- 对 `tm_signoff_record.client_req_id` 建唯一索引；
- 签收接口校验发货单状态必须为 `IN_TRANSIT` 或允许补录的状态；
- 引入 `version` 或 `updated_at` 作为乐观锁条件；
- 重复签收时返回首次成功结果，不重复生成差异单据；
- 所有签收、撤销、改派、差异处理操作必须记录操作日志。

### 4. MySQL 轨迹表分区设计不合法

`tm_driver_location` 计划按月分区，但如果主键只有 `loc_id`，在 MySQL 中会报错。MySQL 分区表要求每个唯一键都必须包含分区字段。

#### 建议修正

```sql
CREATE TABLE tm_driver_location (
  loc_id        BIGINT NOT NULL,
  trip_id       VARCHAR(32),
  driver_id     VARCHAR(32) NOT NULL,
  lat           DECIMAL(10,7) NOT NULL,
  lng           DECIMAL(10,7) NOT NULL,
  accuracy      DECIMAL(10,2),
  speed         DECIMAL(10,2),
  recorded_at   DATETIME NOT NULL,
  created_at    DATETIME DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (loc_id, recorded_at),
  KEY idx_driver_time (driver_id, recorded_at),
  KEY idx_trip_time (trip_id, recorded_at)
)
PARTITION BY RANGE (TO_DAYS(recorded_at)) (
  -- 分区由 DBA 在生产环境维护
);
~~~



同时建议：



- 将 `dispatch_id` 统一命名为 `trip_id`；
- H2 开发环境不建分区；
- 生产环境分区由 DBA 脚本维护；
- 制定轨迹保留周期，例如保留 3～6 个月，历史数据归档；
- APP 端按运动状态采样，避免高频上传造成表膨胀。

### 5. 地图选型需考虑中国合规与坐标系问题



方案选择 `flutter_map + OpenStreetMap`，并称免费无商用授权。但如果系统在中国境内使用，需要关注：



- 公开地图服务通常需要使用有资质的地图服务商；
- OSM 瓦片在国内的访问稳定性和数据准确性不足；
- GPS 原始坐标多为 WGS-84，国内地图常使用 GCJ-02 或 BD-09；
- 坐标体系混用会导致车辆位置和配送点偏移。

#### 建议



1. 国内生产环境默认接入高德、百度或腾讯地图 SDK；
2. OSM 可作为海外部署或离线自托管瓦片方案；
3. 统一定义坐标类型：
   - `WGS84`
   - `GCJ02`
   - `BD09`
4. 在客户、仓库、配送点、签收位置中保存坐标类型；
5. 地图坐标转换必须在服务端或 SDK 层统一处理，避免各端自行转换。

------

### 6. 司机 APP 离线签收不能只依赖本地队列



方案设计为：



> APP 本地 SQLite 先落库，立即返回成功，后台队列异步补传。



该方向正确，但必须考虑离线期间业务数据变化。

#### 可能出现的问题



- 司机离线期间，车次被调度员撤销；
- 发货单被改派给其他司机；
- 单据已被后台补录签收；
- 配送点顺序或收货地址已变更；
- 图片上传失败或部分失败。

#### 建议补充



1. APP 本地签收队列增加状态：
   - `PENDING`
   - `UPLOADING`
   - `SUCCESS`
   - `FAILED`
   - `NEED_MANUAL_HANDLE`
2. 服务端返回明确错误码：
   - 单据已取消；
   - 车次已改派；
   - 单据已签收；
   - 司机无权限；
   - 图片上传失败。
3. 对无法自动重试的记录，在 APP 上提示司机联系调度员；
4. 图片应压缩、分批上传，并支持断点续传；
5. 服务端通过 `client_req_id` 保证幂等；
6. APP 恢复网络后应先同步最新车次状态，再上传离线数据。

------

### 7. 后台调度台不建议使用内存分页



方案中后台调度台继续使用 `PageResult` 内存分页。当日任务量较小时问题不明显，但随着历史车次和发货单增长，会出现性能问题。

#### 建议



- 后台调度台列表查询改为数据库物理分页；
- 司机 APP 当日任务一次性拉取可以保留，因为数据量通常较小；
- 常用查询建立联合索引：



sql





```sql
KEY idx_trip_date_status (trip_date, trip_status),
KEY idx_trip_driver_date (driver_id, trip_date),
KEY idx_trip_vehicle_date (vehicle_id, trip_date),
KEY idx_stop_receipt (receipt_no),
KEY idx_stop_trip_seq (trip_id, seq)
```



- 大偏移量场景可使用基于 `id` 或 `updated_at` 的游标分页；
- Count 查询与列表查询分离；
- 报表统计不要直接在业务列表接口中做重查询。

## 三、P1：重要优化建议

### 1. 配送点应保存客户和收货信息快照



`tm_trip_stop` 当前主要字段为：



- `customer_code`
- `receipt_no`
- `expected_arrive_time`
- `stop_status`



如果客户名称、地址、联系人后续变更，历史车次数据也会被改变，影响追溯。

#### 建议在 `tm_trip_stop` 中增加



| 字段                  | 说明           |
| --------------------- | -------------- |
| `customer_name`       | 客户名称快照   |
| `contact_name`        | 联系人快照     |
| `contact_phone`       | 联系电话快照   |
| `address_snapshot`    | 收货地址快照   |
| `longitude`           | 收货点经度     |
| `latitude`            | 收货点纬度     |
| `coord_type`          | 坐标类型       |
| `delivery_start_time` | 配送时间窗开始 |
| `delivery_end_time`   | 配送时间窗结束 |
| `goods_summary`       | 商品摘要       |
| `total_qty`           | 总数量         |
| `total_weight_kg`     | 总重量         |
| `total_volume_m3`     | 总体积         |

------

### 2. 固定线路模板不建议只用 JSON 字符串



`tm_route_template.stop_sequence` 使用 `VARCHAR(2000)` 保存 JSON，存在以下问题：



- 线路点较多时长度不足；
- 难以按客户查询所属线路；
- 难以维护每个站点的时间窗、经纬度和停靠时长；
- 更新单个站点时需要解析整段 JSON。

#### 建议



新增线路模板站点表：



sql





```sql
CREATE TABLE tm_route_template_stop (
  template_id        VARCHAR(32) NOT NULL,
  seq                INT NOT NULL,
  customer_code      VARCHAR(32) NOT NULL,
  address_snapshot   VARCHAR(500),
  expected_arrive    TIME,
  expected_leave     TIME,
  longitude          DECIMAL(10,7),
  latitude           DECIMAL(10,7),
  is_active          BOOLEAN DEFAULT TRUE,
  PRIMARY KEY (template_id, seq)
);
```



如果仍希望保留 JSON，建议在 MySQL 8 中使用 `JSON` 类型，而不是 `VARCHAR(2000)`。

------

### 3. 拣货明细按商品和批次聚合后与 `receipt_no` 冲突



方案中 `tm_pick_order_detail` 包含 `receipt_no`，但又说明按：



> `goods_code + warehouse + batch_no` 聚合生成拣货明细



如果同一商品、同一批次对应多张发货单，聚合后的一行无法只对应一个 `receipt_no`。

#### 建议



方案 A：不跨单聚合，按发货单明细生成拣货行：



- 主键维度为 `trip_id + receipt_no + goods_code + batch_no`；
- 实现简单，适合 V1.0。



方案 B：增加拣货分配表：



- `tm_pick_order_detail`：保存聚合后的拣货行；
- `tm_pick_order_allocation`：保存拣货行与发货单之间的数量分配关系。

#### 还需补充



- 拣货短缺；
- 批次不一致；
- 拣货破损；
- 复核差异；
- 拣货后车次取消；
- 拣货回库；
- 超拣或少拣规则。

------

### 4. 明确 V1.0 是否支持发货单拆单和合单



现状中提到发货单仅 1:1 绑定出库单，不支持拆合。当前 `tm_trip_stop` 基本是一张发货单一个配送点，只能实现多张发货单合到同一车次，不能实现一张发货单拆成多个配送批次。

#### 建议明确



如果 V1.0 不支持拆单：



- 在文档中写明约束；
- 对配送中的 `receipt_no` 增加唯一校验；
- 不提供拆单入口。



如果 V1.0 支持拆单：



- 增加 `parent_receipt_no`；
- 增加 `split_no`；
- 增加本次配送数量；
- 增加累计签收数量；
- 明确部分签收后剩余数量如何二次配送。

### 6. 派车时增加载重和体积校验



系统已有车辆最大载重和最大体积字段，但派单时应加入校验。

#### 建议



在发货单加入车次时计算：



text





```text
车次总重量 <= 车辆最大载重
车次总体积 <= 车辆最大体积
```



超限时应提示调度员，可配置为：



- 强校验：禁止加入；
- 弱校验：警告但允许保存。



后续可扩展冷链、危险品、尾板车、时区送达等约束。

------

### 7. 完善状态机约束

#### 发货单状态机



建议补充以下规则：



1. 已生成拣货单后，不允许直接撤销派车；
2. 已拣货后撤销派车，必须触发回库或库存释放；
3. `IN_TRANSIT` 后改派需走异常流程，不能直接回到 `WAIT_DISPATCH`；
4. `DELIVERY_FAILED` 必须记录失败原因、照片和是否二次配送；
5. 客户自提或电话确认收货时，应允许从 `APPROVED` 或 `WAIT_DISPATCH` 直接后台签收；
6. `PART_SIGNED` 和 `REJECTED` 必须有差异处置完成后才能进入 `COMPLETED`。

#### 配送点状态



建议增加独立的配送点状态：



| 状态          | 说明     |
| ------------- | -------- |
| `PENDING`     | 待配送   |
| `ARRIVED`     | 已到店   |
| `SIGNED`      | 已签收   |
| `PART_SIGNED` | 部分签收 |
| `REJECTED`    | 拒收     |
| `FAILED`      | 配送失败 |
| `SKIPPED`     | 跳过     |



车次状态应由配送点状态自动推导，而不是完全依赖人工设置。

#### 交账状态



`SETTLED` 前应校验：



- 所有配送点已完成、跳过或异常关闭；
- 签收照片和签名已上传；
- COD 现金已核对；
- 拒收商品已回库或登记；
- 异常单已处理；
- 里程信息已录入。

------

### 8. 后台签收需要更强权限和审计



后台签收是必要补录通道，但存在绕过现场证据的风险。

#### 建议



- 后台签收必须独立授权；
- 记录操作人、操作时间、操作 IP、备注；
- 后台签收也应要求填写差异原因；
- 后台签收记录使用 `signoff_type='ADMIN'`；
- 司机 APP 上线稳定后，可限制后台签收仅允许补录 N 天前的历史单据；
- 报表中区分后台签收与司机签收占比。

------

### 9. 文件存储安全需加强



`FileStorageService` 抽象设计合理，但需要注意敏感文件访问控制。

#### 建议



1. 签名、签收照片、身份证、驾驶证等文件不得放在公开静态目录；
2. 文件访问必须经过后端鉴权或使用签名 URL；
3. 数据库中建议保存文件对象标识，而不是永久绝对 URL：
   - `bucket`
   - `object_key`
   - `file_name`
   - `content_type`
   - `file_size`
4. 本地存储通过 Nginx 提供访问时，应使用内部跳转或签名校验；
5. 上传接口限制：
   - 文件类型；
   - 文件大小；
   - 图片分辨率；
   - 文件名路径穿越；
6. 后端避免一次性将大文件读入内存，建议使用流式上传或对象存储 presigned URL；
7. OSS/MinIO 使用临时签名 URL，不暴露永久公共链接。

### 10. 补充司机 APP 账号与权限设计



当前文档对 APP 登录鉴权描述较少。

#### 建议补充



- APP 使用独立登录接口；
- 司机账号与 `base_employee` 或 ERP 用户绑定；
- Token 有效期和刷新机制；
- 司机只能查看和操作本人名下的车次；
- 离职或禁用账号后 Token 立即失效；
- 设备绑定记录保存在 `tm_driver_device`；
- 接口限流，防止恶意重试；
- 敏感接口增加签名和防重放校验；
- 支持手机号一键登录或验证码登录，视项目要求确定。

## 八、最终结论



该 TMS 方案业务主线清晰，与 ERP 集成方向正确，具备较好的 V1.0 落地基础。但当前版本仍存在以下关键风险：



- 库存重复扣减；
- 应收和开票口径不一致；
- 并发重复派车和重复签收；
- MySQL 分区表设计错误；
- 地图合规与坐标体系问题；
- 离线签收缺少失败补偿；
- 部分数据模型不足以支撑拆合单和长期演进。



建议完成上述 P0 和 P1 项修正后，再进入正式开发。完成修订后，该方案可以形成较完整的 ERP-TMS 配送调度闭环，并为后续退货回收、运费结算、智能排线和经营分析打下基础。
