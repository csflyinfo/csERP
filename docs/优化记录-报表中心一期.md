## 1. 设计目标与容量承诺

用户明确的容量目标：**PC 后台 50+ 用户、日销售订单 2,000 条、商品行 10 万行**，多人同时查询不得拖慢业务录入（OLTP）。

一期按此目标落地并做了同规模实测（见第 9 节），核心手段：

1. **统一元数据驱动**：一张报表 = 一份 `ReportDefinition`（列定义/口径/数据范围/脱敏规则/SQL 计划），分页、合计、异步导出三者共用同一个 `Plan`，同口径、同数据范围、同字段脱敏，杜绝「页面一个数、导出一个数、合计第三个数」。
2. **读写物理隔离**：报表走独立 Hikari 连接池 `erp-report-pool`（readOnly、30s 语句超时、默认 10 连接），与业务池互不抢占；配置 `report.datasource.url` 即可切到只读从库，应用代码零改动。
3. **预聚合换并发**：高频汇总报表不扫明细表，查 DWS 日汇总表（夜间日结 + 当天分区每 30 分钟增量重算），明细报表走覆盖索引的 DWD 视图 + 短缓存。
4. **并发护栏**：全局 15 个 / 每人 3 个报表查询信号量，超限快速失败（给用户明确中文提示），不允许报表把库连接打满；结果缓存（明细 60s、DWS 5min）按「同数据范围+同字段权限」跨账号共享，叠加单飞合并，同条件并发洪峰只有 1 次真实落库查询。

## 2. 统一可复用元数据层（本期架构核心）

> 对应要求：「为系统设计底层的统一的可复用的元数据，提升报表查询效率，减少重复统计查询同样的数据」。

后端新增 `com.erp.report.meta` 包：

| 类 | 职责 |
| --- | --- |
| `ReportDefinition` | 单张报表的元数据契约：code/名称/查看权限、列定义、默认日期跨度、分页 SQL、合计 SQL、导出流式 SQL、数据范围拼接、字段脱敏配置 |
| `ReportColumnDef` | 列元数据：字段名、标题、宽度、对齐、数字精度、是否敏感列（有权限但被标记时前端橘色显示）、是否对该角色隐藏 |
| `Plan` | 一次请求编译出的查询计划（SQL + 参数 + 列 + 数据范围），分页/合计/流式导出共用，保证三处口径绝对一致；规模加固后新增三个可选钩子：`customPageSql`（头窗口分页，计数/取页 SQL 由定义自产，避开百万行外部排序）、`rowEnricher`（取页后按主键小批量补列）、`grandSql`（独立合计 SQL，不随分页重跑） |
| `ReportRegistry` | 全部报表定义注册表，按 code 取定义；新增报表只需注册一个 Bean |
| `ReportQueryEngine` | 统一执行入口：`page()` / `summary()` / `streamForExport()`；汇总行上限 10 万（超出引导收窄条件）、导出上限 10 万行、分批 2,000 行 fetch |

配套通用件（`com.erp.report.common`）：`ReportGuard`（信号量/缓存/审计/慢查询）、`ReportQueryRequest`（日期范围、分页上限 1000、offset 上限 10 万）、`ReportDateRange`（统一账期口径）、`SqlPager`（H2/MySQL 兼容分页）、`ReportCamel`、独立数据源 `ReportDataSourceConfig`。

**复用点（后续 24 张报表直接继承）**：

- 数据范围（仓库/往来单位/采购员等）只在元数据层拼一次；
- 字段级权限脱敏（成本/金额列）由统一 `FieldMasker` 在出口处理，页面与导出一致；
- 权限点约定 `report.<code>.view`，导出另需 `global.export`；
- 前端 `DrillGridReport.vue` 通用表格（合计栏、分组小计、橘色敏感列、联查跳转）+ `ReportFilterBar.vue` 筛选条 + `useCenterReport.js` 数据组合式函数，新报表页面通常只需几十行配置。

### 结果缓存按「可见性」共享，而不是按账号

初版缓存键为 `报表 + 入参 + 用户ID`，规模压测的 50 用户波次暴露出问题：同岗位、同角色、同数据范围的 50 个账号早晨打开同一张汇总表，会对同一批数据做 50 遍完全相同的全表聚合（实测 150 次查询 101 次被护栏挡下）。现改为：

- 缓存键 = `报表 code + 入参哈希 + 可见性签名`；可见性签名由两段组成——`DataScopeService.currentScopeSignature()`（七维数据范围规则规范化 MD5：维度标志/ID/区域/分类品牌收窄/PDA 强制仓）与 `PermissionService.currentFieldCodesSignature()`（当前账号敏感字段授权集合 MD5，脱敏在 loader 内已完成）。
- 规则含 `SELF`/`SUB_TREE`（只能看自己/下属）或一个数据范围维度都没配（DEFAULT DENY 落到本人建档）时，可见行与账号本人绑定，签名强制纳入用户身份，**绝不跨账号共享**；超管视角固定签名互相共享。
- 每用户并发信号量（3 个）仍按账号隔离，不受影响；导出后台线程不走交互缓存。
- 安全不变量有回归测试兜底：`ReportPurchaseAcceptanceTest.cacheSharedByVisibilitySignatureNotAccount`——无金额字段权的账号即使与有权账号同范围同入参，也必须重新执行 loader 拿到脱敏结果，不能命中对方缓存；同角色账号共享；超管共享。

**单飞合并（request coalescing）**：缓存未命中的同一瞬间若已有同键查询在途（50 人同一秒点开同一张报表），后来者不再各占一个全局数据库名额重复执行，而是等待并共享同一个在途 `CompletableFuture` 的结果（等待上限 65s，覆盖计数+取页两条语句各 30s 的最坏情况；超时给中文繁忙提示）。因此任意同条件洪峰中真正落库的重查询只有 1 个。领导者异常（护栏拦截/30s 超时/10 万行上限）同样传递给跟随者，但**异常不写缓存**，稍后重试会重新选主执行。该不变量由 `singleFlightCoalescesConcurrentIdenticalQueries` 锁定：同键并发 loader 只执行一次、跟随者拿到同一结果、成功后走缓存、失败后可重试。

## 3. 数据分层（DWD / DWS / 维度 / 快照）

`V110` 迁移新增：

- **DWD 视图**
  - `v_rpt_purchase_order_detail`：采购订单明细（审核通过），单价/金额口径统一为含税；
  - `v_rpt_purchase_detail`：采购入库（正数量正金额）UNION ALL 采购退货（**负数量负金额**，保证单价恒正，口径 K5），采购员/换算系数等用关联子查询带出；
  - 箱/基本单位换算（口径 K4）：有箱单位按 `基本单位数 ÷ 箱装量` 折算包装件数，无箱单位时包装件数 = 基本单位数量。
- **DWS 日汇总**：`rpt_dws_purchase_d`，主键 `(bill_date, supplier_code, buyer, goods_code, warehouse)`，按「日期 × 供应商 × 采购员 × 商品 × 仓库」预聚合入库/退货数量金额，#3/#4 汇总表直接查它。
- **维度快照**：`rpt_dim_goods`（商品主数据）、`rpt_dim_partner`（往来单位），凌晨/半小时全量刷新，报表 JOIN 快照而非业务主表。
- **库存日快照**：`inv_stock_daily_snapshot`，每日 02:10 重写前一日分区（Q6：测试环境同样日结）。
- **索引**：入库/退货单日期、来源单号、明细商品号、采购订单状态、往来台账等查询路径全部补索引（`idx_pur_inbound_rpt_date`、`pur_return_detail_rpt_goods` 等）；V111 再为 DWD 视图的换算率相关子查询补覆盖索引 `purchase_order_detail(goods_code, unit_name, convert_qty)`、`sales_order_detail(...)`（销售域下期直接受益）。

重算全部**幂等**：`DELETE 分区 + INSERT...SELECT GROUP BY`，可随时安全重跑。

### 规模压测驱动的六轮 SQL/分层加固（V111～V116）

10 万商品行/日 × 10 天的规模库（订单/入库明细各 100 万行、退货 50 万行、DWS 约百万分区行）上，V110 初版多条路径在 H2 文件库超过 30s 语句超时。按实测瓶颈逐轮修复，**每轮视图列名/口径不变、DWS 无需业务侧重算**：

| 迁移 | 瓶颈（实测） | 手段 |
| --- | --- | --- |
| V111 | DWD 换算率相关子查询反扫订单明细 | `purchase_order_detail(goods_code, unit_name, convert_qty)`、销售明细表同构覆盖索引（销售域下期直接受益） |
| V112 | 每行做相关子查询（换算率 `MIN(convert_qty)`、采购员），单日即超时 30s | 换算率改派生表一趟聚合后 JOIN（纯索引扫描）；采购员改订单表 LEFT JOIN（order_no 唯一索引） |
| V113 | 派生表收不到外层日期谓词，查一天也要对百万行 GROUP BY | 换算率是档案型数据：物化为 `rpt_dim_unit_factor`（P/S 两类），随商品维度快照 30 分钟/夜间重建，视图按主键 JOIN |
| V114 | 每页实时 JOIN `base_goods` 取条码/温区；视图内外两层各 JOIN 一次商品维度 | 条码/温区下沉 `rpt_dim_goods`（快照维护，压力移出业务库）；换算率兜底判定移到外层，每行省一次维度 JOIN |
| V115 | 视图每行对供应商/采购员做相关查找（scanCount≈明细行数 20 万） | **表头折叠**：供应商编码/采购员等表头级查找放进「只查单据表头」的派生表 `h`，按单据头做一次标量相关子查询而非每行；退货头无 buyer 列，采购员取供应商默认采购员。外层保留一层算术包装，使 H2 仍能把 `bill_date` 谓词下推到各分支表头日期索引 |
| V116 | #3/#4 聚合百万行时逐行探测 `rpt_dim_goods`/`base_supplier`，偶发超 30s | 温区 `storage_property`、供应商分类 `supplier_type` 是慢变档案属性，随日汇总快照进 `rpt_dws_purchase_d`（ETL 带出 + MERGE 回填历史分区）；#3/#4 聚合过程零档案表 JOIN |

**明细头窗口分页（#1/#2，框架钩子 `Plan.customPageSql`）**：不再对百万行排序取页。先在单据头表（约 2 万行、带日期索引）上用相关 COUNT 算每张单的命中行数，再以 `SUM(line_cnt) OVER (ORDER BY 日期 DESC, 单号 ASC ...)` 累计窗口定出「全局行号区间与哪几张单相交」，明细只 JOIN 这几张单；行在单内按商品排序后用 `cum_end - line_cnt + ROW_NUMBER() OVER (PARTITION BY doc_id ...)` 得到全局行号。#2 是入库/退货两类单据 UNION，两套头 CTE/明细 CTE 同构拼接，计数与取页共用同一份头窗口 SQL。深翻页成本只与表头数量有关，与明细总行数无关。

> **H2 2.2.224 缺陷及规避**：压测中发现「前序 CTE 使用 `?` 绑定参数 + 后序 CTE 计算窗口函数」时，窗口 CTE 在 H2 上静默返回零行（不报错；计数正常、取页为空）。经 8 组变体最小复现确认为 H2 缺陷后，头窗口 SQL 改为 `renderLiterals` 在拼 SQL 时把参数渲染为类型安全字面量（单引号字符串感知、内嵌引号双写、数值/日期/枚举分类处理），整条窗口 SQL 零绑定参数。MySQL 8 不存在该缺陷，且同样接受字面量 SQL，生产无需特殊处理。

**#3/#4 两层派生表**：内层只扫 DWS（分组键与九列度量全部 `d.*`），`GROUP BY ... LIMIT` 在派生表 `t` 内完成；条码/基本单位在外层按 `t.goods_code` 关联 `rpt_dim_goods` 补齐——JOIN 行数 = 分组结果（≤10 万）而非百万级明细。引擎的分页/合计包裹逻辑零改动（合计即对 `t` 的度量别名再 SUM）。

**合计懒加载**：明细分页响应不再内嵌合计（全区间重合计曾把每次翻页拖慢数秒），前端打开页面时与首页分页并行请求 `/summary`，翻页不重算合计。

## 6. 权限、字段脱敏与运维

- **RBAC**：每张报表一个程序化权限点 `report.<code>.view`；报表管理页 `report.admin.view` + 超管校验（前端路由 `meta.superAdmin`）。角色在「角色权限」里勾选报表菜单/功能码后才能看到对应页面与接口。
- **字段脱敏**：`VIEW_PURCHASE_PRICE` / `VIEW_PURCHASE_AMOUNT` 控制单价、金额列：无权限时后端直接置 null（列表与导出都不泄露原值），前端整列隐藏；有权限但被标记为敏感的列，数值以橘色（#e6a23c）显示，提示保密（Q4）。
- **报表管理页**（`/report/admin`）：选择日期区间手工重算采购 DWS 并返回对账结果（DWS 金额 vs DWD 实时金额，差额为 0 才显示 ✓平衡）、重建指定日库存快照、查看最近查询日志/慢查询（>3s 落 `rpt_query_log`）。
- 查询账期护栏：明细类报表单次最大跨度 366 天、汇总类 731 天（超出引导分段查询）；查询日志保留 90 天（定时任务每日清理）。

### ⚠️ 上线运维注意：新报表菜单需在「菜单管理」启用

V109 起代码注册的菜单进入 `sys_menu_meta` 时 `enabled=FALSE`，非超管用户的菜单树 SQL 要求 `enabled=TRUE`（超管不受此限，所以超管始终可见，容易漏掉这一步）。

新菜单授权给角色需要**两步**，缺一不可：

1. `POST /system/rbac/role/grants` 给角色勾上菜单（父目录 `M_report` + 各报表页）与功能码；
2. `PUT /system/menu-manage/{menuId}/enabled {"enabled":true}` 启用菜单，**父目录先启用再启用子页**。

仅授权不启用时，角色登录后菜单为空、访问报表路由会被守卫重定向回首页。

## 8. 顺带修复的既有缺陷

**采购入库列表 7 个筛选条件全部静默失效，且报表联查落地筛不到单据。**

`PurchaseController.inboundPage` 是采购域唯一一个不用 `PageResult.of(mapped, request)` 的列表：它走 MyBatis-Plus SQL 分页，却完全不读取 `request.filters()`——入库单号/采购单号/供应商/仓库/状态/入库日期/商品七个 QueryBar 筛选条件输入后无任何效果；报表 #2 联查跳转入库单列表时也无法定位目标单据。

修复与采购订单/采购退货列表保持一致：数据范围在 SQL 层收敛后 `list()` 全量装载，字段脱敏，再交 `PageResult` 统一内存过滤/排序/分页。已用「带筛选=1 条 / 不带=2 条」与真实浏览器分页栏「共 1 条 第 1/1 页」双向验证。

同时修正联查参数：入库/退货列表的日期字段是普通文本框，PageResult 过滤是「每个筛选值都必须是行文本子串」的全值包含语义，`入库日期_from/_to` 这类区间键反而会把结果筛空；单据号本身唯一，故联查只携带单据号单值键。

仪表盘采购相关旧图表接口已重新指向 `purchase_order`，首页采购金额/订单数/趋势正常。

## 9. 性能验收

### 方法

`backend/src/test/java/com/erp/report/ReportScalePerf.java`（无 `Test` 后缀，不被 surefire 自动执行，独立 main 运行）：

- 独立 H2 文件库跑真实 Flyway 全量迁移（V1～V116）；

- 阶段一：每轮请求携带只影响缓存键、不参与 SQL 的 `_nocache` 入参强制冷查询（缓存改为按可见性共享后，换超管账号已不能绕缓存），测单用户冷查询 p50/p95/max；
- 阶段二：50 个线程同时起跑（CountDownLatch），50 个同视角超管账号、每人 3 次、交替打 DWS 汇总与 DWD 明细，入参完全相同——这是「同岗位 50 人早晨打开同一张报表」的真实模型，预期首批在途查询受全局信号量约束、其后同视角请求命中共享缓存；同时统计成功/护栏快速失败与延迟；
- 阶段三：200 次单行 INSERT 提交，分别在无负载与 50 用户报表并发下测中位延迟，量化 OLTP 受影响幅度。

#### 最终结果（V116 + 头窗口分页 + 可见性共享缓存 + 单飞合并）

规模：H2 文件库，10 天 × 100,000 商品行/日（订单/入库明细各 100 万行）。

阶段一·单用户冷查询（每轮 `_nocache` 强制不落缓存，5 轮中位数/p95）：

| 场景 | p50 | p95 | 说明 |
| --- | --- | --- | --- |
| #1 采购订单明细·全区间首页（1,000 行） | 4.2s | 9.6s | 头窗口分页，只 JOIN 窗口内单据 |
| #1 全区间深翻页（第 100 页） | 4.0s | 5.2s | 成本只与表头数有关，与明细总量无关 |
| #2 采购明细·当日首页 | 2.2s | 2.5s | 入库/退货双头窗口 UNION |
| #2 采购明细·3 日区间首页（≈真实一个月行量） | 2.7s | 3.0s | 加固前同场景 44.3s |
| #2 当日合计 | 1.9s | 2.2s | 懒加载，不拖翻页 |
| #3 商品采购汇总·全区间（DWS 聚合） | 8.7s | 9.3s | 零档案表 JOIN；加固前偶发 30s 超时 |
| #4 供应商商品汇总·当日（50,000 分组行） | 4.5s | 4.9s | 分组后才关联条码/单位 |
| #4 全区间最细叶子（约 54 万行） | — | — | 10 万行上限友好拦截 ✓ |

阶段二·50 用户同视角并发波次（每人 3 次 = 150 次，同一秒起跑，交替打 #3 全区间 DWS 与 #2 当日明细，入参完全相同）：

| 版本 | 成功 | 护栏快速失败/超时 | 墙钟 | 成功延迟 |
| --- | --- | --- | --- | --- |
| 按用户 ID 缓存（初版） | 49 | 101 / 0 | 56.5s | p50 9.2s / p95 43.3s |
| 可见性共享缓存 | 63 | 87 / 2 | 50.6s | p50 0ms / p95 40.4s |
| **可见性缓存 + 单飞合并（最终）** | **150** | **0 / 0** | **10.9s** | **p50 3.1s / p95 10.8s** |

最终波次中真正落库的重查询只有 2 个（#3/#4 类 DWS 全区间一个、#2 当日明细一个），48 个同条件请求单飞跟随，每人第 2/3 次请求命中共享缓存（亚毫秒）。p50/p95 即跟随者等待两个「首次冷查询」的时长；H2 文件库单条冷查询偏慢是其文件存储机制所致（见下），MySQL 8 上同 SQL 预期秒级以内，需生产复验。

阶段三·OLTP 写入受报表并发影响：200 次单行提交，基线中位数 0.08ms → 50 用户报表洪峰下 0.05ms（测量噪声范围内，无锁互锁、无变慢）。报表连接池物理隔离 + readOnly + 30s 语句超时，业务录入不受报表洪峰影响。

> **数字口径说明**：以上绝对值来自 H2 2.2.224 文件库（单机文件存储、单写检查点、缓冲池远小于 InnoDB），用于验证架构行为（护栏、缓存共享、单飞、无锁互锁、深分页不随总量恶化），**不能外推 MySQL 8 生产延迟**。可移植的结论是护栏行为与相对量级；H2 上 8～10s 的 DWS 全表聚合在 MySQL 缓冲池 + 哈希聚合下预期显著更快。

#### MySQL 生产复验

同一驱动可通过 `-Dperf.days=...` 等参数调规模；生产环境更应关注的是真实 MySQL 8 上的表现（H2 文件库与 MySQL 的并发模型不同，H2 上 OLTP 数字仅用于发现锁互锁问题，不能外推绝对值）。复验步骤：用同一套 Flyway 迁移在 MySQL 建库后，以 JDBC 参数替换驱动内 URL 运行（或部署测试环境后通过页面/接口压测），重点确认：DWS 全区间查询 p95 < 1s、50 并发下无异常失败风暴、业务录入接口在报表高峰无明显抖动。

### 护栏行为说明

- 每人超过 3 个并发 → `IllegalArgumentException`：「报表查询排队中（每人最多 3 个并发），请稍后再试或缩小查询范围」；
- 全局名额 5 秒内拿不到 → 「报表查询繁忙，请稍后再试或缩小查询范围」；
- 两条提示都是快速失败而非排队拖死，避免占用 Web 线程；配合明细 60s / DWS 5min 的结果缓存，同一报表同条件（含同可见性跨账号）的重复查询直接命中缓存；
- 同键并发的缓存未命中走单飞合并：跟随者等待在途结果，不占信号量与数据库名额，因此 50 人同条件洪峰不会产生 50 条重查询。
