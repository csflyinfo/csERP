## 一、先想清楚：谁在用、什么时候用、要解决什么问题

报表不是"把单据数据列出来"，而是**特定岗位在特定节奏下的决策工具**。先立用户场景，字段和口径都为场景服务。

| 角色 | 使用节奏 | 核心诉求 | 对应报表 |
|---|---|---|---|
| 老板/总经理 | 每天手机/电脑看几眼，月初必看 | 赚不赚钱（销售、毛利）、货压了多少（库存金额/周转）、钱收没收回来（应收账龄）、采购花了多少 | 17、12、13、20、7、8 |
| 采购员 | 每天早上看缺货和在途，按箱下单 | 缺什么、缺多少、找谁买、上次买多少钱；下单后跟催入库 | 5、6、1、3、4 |
| 销售业务员 | 每天开单前后、月底冲业绩 | 自己客户欠多少钱、自己卖了多少、毛利多少（看不到成本时只看金额） | 12、13、15、16、23 |
| 库管员 | 每天作业、盘点后对账 | 每笔进出能不能对上、期末和库存余额对不对得上、拣货上架干了多少活 | 9、8、18 |
| 财务/会计 | 月结对账、日常记账 | 应收应付账龄、客户/供应商对账、现金银行流水逐笔可查、和总账能勾稽 | 20、21、22、23、24 |
| 司机主管/调度 | 每天发车后、月底算绩效 | 谁送了几单、签收率、拒收、代收货款交没交 | 19 |

由此确定四条总原则：

1. **默认条件开箱即用**：打开报表不用先填一堆条件——默认"最近一个月"（截止昨天，口径见 K2）、全部状态（只统计已审核），点查询就有数。
2. **能钻透**：汇总数点得动——汇总 → 明细 → 原始单据，一路点到底，财务对账尤其依赖这个。
3. **导出来就能直接发**：Excel 前几行自带报表名称、查询条件、生成时间、制单人，老板/供应商/客户拿到不用再问"这是什么数"。
4. **敏感字段有遮挡**：成本价、毛利、毛利率是老板敏感字段，必须单独权限点；业务员只能看自己的数据（数据范围权限复用现有 DataScopeService）。

## 二、竞品对标与取舍

参考用友 T+、金蝶精斗云/云星辰、管家婆、秦丝、思迅/商锐（批发流通行业主流），共性做法如下，本方案全部吸收：

| 竞品共性做法 | 本方案采纳方式 |
|---|---|
| 查询区在顶部，默认本月/近 30 天，条件可折叠 | 统一报表查询区组件，默认"最近一个月"（截止昨天），记住上次条件（按用户存 localStorage，换电脑走用户偏好表） |
| 数量双计量（散数 + 件数），批发按箱订货 | 所有商品类报表双列：小单位数量、件数；箱价同理 |
| 表格底部固定合计行，分组时有组小计 | 统一合计行（数量/金额/成本/毛利列），自定义分组时组小计 + 总计 |
| 汇总数字可穿透到明细 | 3/4/7/8/10~14/23 等汇总表全部支持钻取，统一跳到对应明细报表并带条件 |
| 进销存汇总与库存台账是库存核算两张主表 | #8 期间汇总（期初/收入/发出/结存）、#9 逐笔台账，两表互相钻取 |
| 应收应付必做账龄分档（30/60/90/180） | #20/#21 账龄分析，按截止日期的**时点报表**（不是期间报表） |
| 现金日记账按资金账户逐笔、日清月结 | #22 日小计 + 月合计 + 期初/期末，与总账现金科目勾稽 |
| 建议采购量 = 日均销量 × 备货天数 − 库存 − 在途 | #5 公式，另加"按主供应商/最近采购供应商分组一键生成订单" |
| 导出 Excel 带查询条件抬头 | 全报表统一导出模板（前 4 行抬头） |
| 大数据量走异步导出中心 | PRD 原有规划（P0）；同步前端 xlsx 先撑 5 万行，超限走后端异步任务 |

**竞品有但本期不做**（避免过度设计，后续可迭代）：自定义报表设计器（拖拽列/公式）、报表定时邮件/公众号推送、手机端报表 H5（建议二期在司机/管理层 APP 内嵌只读简版）。

## 三、通用设计约定（24 张表共用）

### 3.1 数据口径总则（最重要，先和业务确认）

| # | 口径 | 说明 |
|---|---|---|
| K1 | **只统计已审核单据**；已作废单据不参与；红字/冲销以**负数**参与合计（与总账"已过账+已冲销轧差"口径一致） |
| K2 | **期间类报表按单据业务日期**（采购=入库/退货审核日期，销售=**司机签收日期**，见 K8）；**时点类报表**（账龄、库存余额类快照）按"截止日期"取数，默认今天。**期间类报表默认"最近一个月"：截止日 = 昨天，起始日 = 截止日上一月同日的前一天**（例：今天 2026-09-11，则默认期间 2026-08-09 ~ 2026-09-10；月末无同日时取上月最后一天再退一天）。该规则与商贸行业月度对账周期一致，不使用"近 30 天"也不用自然月。**例外**：月结类报表 #8 进销存、#9 台账、#18/#19 绩效、#22 日记账、#23/#24 往来汇总默认自然月本月（盘点/结账/算工资习惯），日期控件均提供"最近一个月"快捷项可一键切换 |
| K3 | **金额为含税口径**（价内税，采购 V52 起、销售均如此），应收/应付取含税金额。毛利相关列同时给出：销售额（含税签收额）、成本（不含税移动平均成本）、毛利额、毛利率。**毛利率固定按含税口径**（Q9 已确认）：毛利率 = 毛利额 ÷ 含税签收金额 × 100%，不做口径切换；列名统一标注"含税毛利率"，与总账利润表（不含税）的差异在 #17 文案中说明 |
| K4 | **数量双单位口径**：小单位数量 = 单据明细基本单位数量（base_qty / small_unit_qty）；件数 = 小单位数量 ÷ 大单位换算率（取 base_goods.unit_config 中大单位 convertQty；无大单位时件数=小单位数量、基本单位即大单位）。**单据类报表换算率取单据快照**（明细 convert_qty），档案类/预测类报表取当前档案 |
| K5 | **小单位单价 = 行金额 ÷ 小单位数量**（反推，避免录入单位层级歧义）；箱价（大单位单价）= 小单位单价 × 大单位换算率，无大单位时箱价=小单位单价。禁止直接用录入价除算产生尾差 |
| K6 | **退货一律负数显示**：数量、件数、金额均为负；汇总表"采购/销售净额 = 入库/销售 − 退货"，退货列另以正数展示发生额、净额列体现轧差 |
| K7 | **成本口径**：移动加权平均，按**商品+仓库**核算（不按批次）。同单同商品跨批次成本必然相等；台账单价取 inv_stock_ledger.cost_price；报表成本金额取单据/流水上的 cost_amount，不重算 |
| K8 | **销售统计一律按司机签收口径**（需求方明确）：以发货/签收单 `sales_receipt(_detail)` 为准——日期取**签收时间 sign_time 的日期**，数量取**签收数量 signed_qty**，金额取**签收金额 sign_amount**（签收时按实收重算的含税金额）；销售退货按退货审核日期负计。**拒收数量/金额（reject_qty/reject_amount）不计入销售**（货物随车退回、经 inv_reject_inbound 回库），仅在司机配送绩效 #19 和订单执行表 #15 中体现。**销售成本与收入同口径配比**：签收单对应销售成本 = 出库单 cost_amount − 拒收回库 inv_reject_inbound.cost_amount，按签收日落期间；退货成本负计。**注意：库存实物账（#8 进销存/#9 台账）仍按实际出入库流水日期**（出库审核即减库存），与销售损益口径是两本账，跨期表现为"已出库未签收"的在途。签收审核即生成应收 fin_ar，因此销售额与本期新增应收口径天然一致 |
| K9 | **采购统计按入库审核日期**（pur_inbound，写库存的单子）；应付按收货口径（pur_receipt，立 fin_ap）。入库与收货通常同日，跨月时以各自口径为准，#21/#24 按应付口径 |
| K10 | 空值金额按 0 展示，比率分母为 0 时显示 "—"，不显示 NaN/∞；负数红色、负号前置不显示括号（国内批发习惯） |
| K11 | 数量精度 4 位、单价 6 位、金额 2 位，遵循现有"显示精度设置"，只可加大 |
| K12 | 所有报表只读（#5 生成采购订单、#6 手工重算快照除外），不提供新增/编辑/删除按钮 |

```

├──────────────────────────────────────────────────────────┤

├──────────────────────────────────────────────────────────┤

└──────────────────────────────────────────────────────────┘
```

通用交互细则：

1. **查询**：回车即查；条件控件复用档案选择器（编号/名称模糊搜索下拉），日期段预设快捷项：**最近一个月（默认，截止昨天，规则见 K2）**/今天/近 7 天/近 30 天/本月/上月/本季/自定义。时点类报表（账龄）用单个"截止日期"，默认今天。
2. **记住条件**：同一报表上次使用的条件（日期除外，日期每次回默认）本地记忆。
3. **合计行**：固定在表格底部（不分页时为全量合计，分页时也要全量合计——合计走独立聚合 SQL，不随分页变化）。
4. **列设置**：显示/隐藏、拖拽排序、首列冻结，按用户+报表持久化；成本/毛利类列即使被调出，无权限也不显示数据（显示 ****）。
5. **钻取**：可钻数字蓝色下划线，点击新页签打开目标报表并自动带入条件（期间、商品、供应商/客户、单据类型），目标报表顶部显示"由 XX 报表钻取：条件回显 + 返回"。
6. **单据跳转**：点单据号以抽屉/新页签打开原单据（只读）。
7. **空数据**：显示"当前条件下无数据，可放宽日期或清空条件"，不是空白表格。
8. **超大数据保护**：结果行数 > 5 万时提示"数据量较大，建议缩小期间或使用异步导出"，表格仍可查询（服务端分页），同步导出禁用。

### 3.3 导出统一规范

- 文件名：`报表名称_yyyyMMddHHmm.xlsx`。
- Sheet 抬头（前 4 行，与竞品对账单格式一致）：
  - 第 1 行：报表名称（大字加粗，合并单元格）
  - 第 2 行：查询条件回显（如"日期：2026-08-12~2026-09-11；供应商：全部；审核状态：已审核"）
  - 第 3 行：生成时间、制单人
  - 第 4 行空行，第 5 行表头
- 导出列与当前列设置一致（隐藏列不导出）；合计行/分组小计导出；钻取列导出为纯值。
- 实现路径：
  - **明细/小数据量（≤5 万行）**：沿用前端 xlsx（GenericBusinessList 现有能力）扩展抬头行；
  - **大数据量/异步**：实现 PRD 规划的"导出中心"——后端 EasyExcel 落文件、sys_export_task_runtime 任务记录、完成后通知下载（**现有 /report/export 是空壳、ExcelController 部分 moduleCode 导出"示例数据"，本期必须补真实实现**）；
  - 导出受 `global.export` 权限 + 数据范围 + 字段脱敏约束（FieldMasker 现有机制）。

### 3.5 技术落地约定

**现状问题（必须先解决，否则报表是假的）**：

1. `ReportController` 的四张报表无任何筛选参数、在内存里 filters 匹配、毛利是 `amount*0.12` 占位假值、`/report/export` 是假导出；
2. 销售/采购趋势图还在查**已废弃的 pur_order 旧表**，应统一用 purchase_order；
3. `PageResult.of` 是 SQL 查全量 → Java 内存过滤/分页（pageSize 上限 200），报表场景必须改为 **SQL 端 WHERE + GROUP BY + 聚合分页**，合计走独立 `SELECT SUM`；
4. H2 限制：无 DATE_FORMAT（日期截断在 Java 层或用 `CAST(... AS DATE)`）、别名必须蛇形（`bill_date bill_date`，否则被碾平）、JOIN 同名列加表别名限定、字符串只用单引号；SQL 同时要兼容 MySQL（docker profile）。

## 四、报表技术架构方案（独立库/独立服务？先选型再落地）

### 4.1 决策前提（本系统的真实约束）

1. **生产环境是 MySQL 8 单机**（docker-compose：MySQL + Redis + 后端 + Nginx），开发/冒烟是 **H2 文件库**——所有报表 DDL/SQL 必须双兼容（H2 无 DATE_FORMAT、别名蛇形、单引号字面量等既有约束继续生效）；
2. **H2 文件库是单进程嵌入式独占**，无法挂第二个服务/进程共库——"独立报表服务共库"在本地/冒烟形态根本不成立，只有生产 MySQL 形态可行；
3. 现有后端是单体 Spring Boot + JdbcTemplate，**没有** BI、数仓、消息队列、Canal 等基础设施；团队小，单组织私有化部署，数据量级为中小商贸企业（预计明细行数百万级以内）；
4. 系统已有"同库日汇总"成功先例：`wms_dashboard_daily`、`wms_performance_daily`（定时任务写日表，报表只做聚合）；
5. 报表必须复用现有的鉴权/数据范围/字段脱敏链路（`@RequirePerm` + DataScopeService + FieldMasker），独立服务会把这条链路全部重做一遍。

### 4.2 四个候选方案对比

| 维度 | A. 单体同库直查 | **B. 单体同库 + 预聚合/快照（推荐起步）** | C. 独立报表服务 + MySQL 只读从库 | D. 专用分析库（ClickChain/Doris）+ CDC + 独立报表服务 |
|---|---|---|---|---|
| 实时性 | 实时 | 明细实时 + 汇总 T+1 与当天实时合并 | 受从库延迟影响（秒~分钟） | T+0 分钟级或 T+1 |
| 对业务库影响 | **大**：大 GROUP BY 与业务事务争抢锁/CPU | 小：重活夜间跑完，白天查小日表 | 业务库零影响（走从库） | 业务库零影响 |
| 适配数据量 | < 几百万行 | 千万行级 | 亿行级 | 数十亿行+ |
| 开发成本 | 最低（现状） | 低：1 批日表 + 1 个定时任务 + 视图 | 中：拆服务、安全链路重做/内部化 | 高：新组件 + ETL/CDC 运维 |
| 运维成本 | 无新增 | 无新增进程（同 JVM 调度） | +1 服务 +1 从库 | +3~5 个组件，需专职运维 |
| H2 冒烟兼容 | ✔ | ✔（日表/视图 H2 均支持） | ✘（H2 无法共库，冒烟要换 MySQL） | ✘ |
| 安全/数据范围复用 | ✔ | ✔（同进程直接复用） | 需下沉公共包或内部接口 | 同 C，且要同步权限数据 |
| 回滚成本 | — | 低：删 rpt_ 表即回到直查 | 高 | 很高 |
| 致命问题 | 报表慢查询可拖垮开单 | 无（汇总表可随时重建） | 当前量级过度设计 | 严重过度设计 |

### 4.3 选型结论

> **本期采用方案 B：不新建专用数据库、不部署独立报表服务。** 报表作为现有单体中的高内聚模块 `com.erp.report`，数据分三层获取——明细/台账/账龄走业务表**实时直查**（强制索引+期间护栏），汇总/分析走**日预聚合表**（夜间任务），库存/缺货走**每日快照表**；异步导出在同进程内以线程池起步。
>
> 架构沿 **B → 只读从库 → 独立报表服务 → 专用 OLAP 库** 四级平滑演进，每一级都有量化触发阈值（4.9），达不到阈值坚决不升级——不为臆想中的规模付出真实的运维成本。

为什么不是 A：现有 ReportController 的"SQL 查全量 + Java 内存过滤分页 + 假毛利"模式在数据量增长后会直接拖垮开单/出库等核心交易，必须在本期就改成 SQL 端聚合，但**不需要为此引入新基础设施**——日汇总表 + 索引 + 查询护栏在 MySQL 上支撑千万级明细行绰绰有余（商贸批发单组织典型量级）。

为什么能平滑拆出去：本期约束 `com.erp.report` 包**只读业务表、只写自有 rpt_ 表、所有能力 REST 化**，将来抽独立服务时整体平移，业务代码零依赖。

### 4.5 数据分层与新增对象（全部可重建，不做备份）

**(1) 视图层 DWD——口径只写一处（H2/MySQL 均支持视图，只做 UNION ALL 不加参数）**

| 视图 | 构成 | 服务报表 |
|---|---|---|
| `v_rpt_purchase_detail` | pur_inbound/detail（正）UNION ALL pur_return/detail（负，按 K6） | 2、3、4 及日汇总任务 |
| `v_rpt_sales_detail` | sales_receipt/detail 的**签收行**（signed_qty / sign_amount，按 sign_time，正）UNION ALL sales_return/detail（负）；拒收行（reject_qty）不入视图，成本侧关联出库单成本−拒收成本 | 10~14、16、17 及日汇总任务 |
| `v_rpt_stock_move` | inv_stock_ledger 关联单据类型字典（来源类型 → 采购入库/销售出库/采购退货/销售退货/调拨/其他） | 8、9 |

视图内固化含税金额、小单位数量、退货负数、已审核过滤等通用口径；后续改口径只改视图，24 张报表同时生效。

**(2) 日汇总层 DWS（rpt_ 前缀，夜间任务写入，MERGE 幂等）**

| 表 | 粒度 | 主要度量 |
|---|---|---|
| `rpt_dws_goods_wh_d` | 日期+商品+仓库 | 采购入/退数量、件数、金额；**销售签收/退货**数量、件数、含税金额、配比成本（出库成本−拒收成本） |
| `rpt_dws_partner_d` | 日期+往来类型(客户/供应商)+往来单位+业务员/采购员 | 销售/采购净额、退货额、成本、订单数、交易客户数 |
| `rpt_dws_finance_d` | 日期+客户/供应商 | 新增应收/应付、回款/付款、核销折让（来源 fin_ar/ap、收付款单、核销记录） |
| `inv_stock_daily_snapshot` | 日期+商品+仓库（3.5 已定） | 库存量、成本金额、在途、7/30 天销量、日均 |

- 汇总表冗余名称快照（品牌/分类/名称），但页面展示**编码 JOIN 实时档案取最新名**，防止档案改名后报表对不上单据；
- **新鲜度策略：T+1 历史 + 当天实时**——查询区间落在今天的部分实时聚合后 `UNION ALL`（或 FULL OUTER 合并，H2 不支持 FULL JOIN，用 LEFT JOIN + UNION 模式），保证白天查当月报表数是准的；
- **滚动重算**：每晚重算近 3 天分区（反审核/补录会改近期历史）；另提供"按区间手工重算"和"全量重建"接口（权限控制 + 操作日志）；
- 每次任务结束做行数/金额对账（汇总表合计 vs 业务表同期合计），差异写日志告警。

**(3) 查询审计**：`rpt_query_log(report_code, param_hash, user_id, data_scope, cost_ms, row_count, slow, created_at)`，索引 (report_code, cost_ms)。保留 90 天。

> 以上对象与 3.5 的快照表、防重表放在同一批 Flyway 迁移（建表前按老规矩查目录+并行分支+flyway_schema_history 撞号）。

### 4.6 查询防护与资源隔离（一期就要有的护栏）

1. **独立只读连接池**：报表查询使用单独 HikariDataSource（最大连接 10、只读事务 `@Transactional(readOnly=true)`），与业务连接池物理隔离——报表再慢也不挤占开单/审核的连接；数据源经 `AbstractRoutingDataSource` 走 `report` 路由键，**一期指向主库，未来切从库只改 yml**；
2. **语句超时 30 秒**：JdbcTemplate 设 queryTimeout（MySQL 等价 max_execution_time，H2 会话级 SET QUERY_TIMEOUT），超时即报错提示缩小期间；
3. **强制期间护栏**：默认"最近一个月"（K2）；明细类单次跨度 ≤ 366 天，汇总类 ≤ 2 年，**#9 台账 ≤ 92 天且必须选商品或仓库（条件不足不执行查询）**；超出提示走异步导出；所有 SQL 必须以日期列为 leading WHERE 走索引（销售类 leading 列为 sign_time）；
4. **禁止内存分页**：报表 SQL 端 WHERE/GROUP BY/分页，合计独立 `SUM` 聚合（覆盖索引）；深分页用 keyset pagination 或引导导出（pageNo×pageSize > 10 万禁止翻页）；
5. **并发、防重与短缓存**：全局报表查询信号量 15、单用户并发 ≤ 3（前端 loading + 后端信号量，超出快速失败提示"查询排队中"）；相同 报表+条件+数据范围 hash 的结果，明细类缓存 30~60s、DWS 类 5 分钟（容量评估见 4.9）；
6. 汇总任务：夜间全量/近 3 天滚动重算低峰（02:10）执行 + 当日分区每 30 分钟增量刷新，按日小批 MERGE，避免大事务长锁；
7. 慢查询（>3s）落 rpt_query_log，作为加索引/改写 SQL/提前触发演进的依据。

### 4.7 异步导出（同进程起步，对齐未来独立 worker）

现有 `sys_export_task_runtime` 任务表 + 假 `/report/export` 改造为真实链路：

- 状态机 PENDING→RUNNING→DONE/FAILED；同进程线程池**并发 2**，EasyExcel **流式写 xlsx** + keyset 分批游标取数；**预计 ≤1 万行同步导出、>1 万行自动转异步任务**（10 万行/日规模下近 30 天明细约 300 万行是常态需求），单次硬上限 100 万行，超限拒绝并提示拆条件；
- 文件落服务器挂载目录（与备份策略一致），保留 7 天自动清理；完成写 sys_notification，前端"导出中心"轮询进度、断点可重新下载；
- 导出复用查询的同一套过滤/数据范围/脱敏逻辑（先查 ID/权限范围再分批流式取数，不取进内存）；
- **演进位**：未来独立导出 worker 只需消费同一张任务表（认领 PENDING），应用代码无感。

### 4.8 演进路线（量化触发，不到阈值不升级）

| 级别 | 形态 | 触发阈值（任一满足，且持续观察 1~2 周） | 改动量 |
|---|---|---|---|
| **R0（本期）** | 方案 B：单体内聚报表模块 + 视图 + DWS 日表 + 快照 + 异步导出，预留从库路由键 | — | 本期工作 |
| **R1 只读从库** | MySQL 主从复制，报表数据源切从库 | 明细主表 > 2000 万行；或报表 P95 > 5s；或业务库高峰期 CPU > 70%；或报表并发 > 20 | 仅配置+部署，代码零改 |
| **R2 独立报表服务** | com.erp.report 平移为独立 Spring Boot 应用（安全/DataScope 下沉公共 jar，或经内部 API 鉴权），读从库 | 报表发版频繁需与业务解耦、报表需独立扩容、团队拆分 | 中（包已隔离，平移为主） |
| **R3 专用 OLAP** | ClickHouse/Doris + Canal/Debezium CDC（或 DataX 批同步）+ 报表服务 | 明细 > 5 亿行 / 多组织多账套 / 要求多年即席分析与实时大屏 | 大，单独立项 |

明确否定的选项：现在就上 ClickHouse/Doris（运维成本与团队规模不匹配）、现在就拆微服务（安全链路要重做、H2 冒烟失效）、用 Redis/ES 做报表库（Redis 不适合多维聚合，ES 成本价比值低且引入双写一致性问题）。

### 4.9 目标规模容量与并发评估（50+ 用户 / 日 2000 单 / 日 10 万商品行）

**数据量推算**：

| 对象 | 日增 | 月增 | 年增 | 主查询保障 |
|---|---|---|---|---|
| 签收/出库/退货明细行 | ~10 万 | ~300 万 | ~3650 万 | sign_time/bill_date 范围索引 + LIMIT 分页；合计走覆盖索引 |
| 库存流水 inv_stock_ledger | ~15~25 万 | ~500 万 | ~5500万~9000 万（最大表） | **强制商品+仓库+期间**，单商品近 30 天仅数百行；#8 汇总绝不直查本表 |
| DWS 商品×仓日表（仅当天有发生组合） | 1~3 万 | 30~90 万 | 400~1100 万 | 汇总报表主数据源，近 30 天聚合 < 0.5s |
| 库存日快照（稀疏：有结存/有在途） | ~9 万（3万SKU×3仓量级） | ~270 万 | ~3300 万 | 主键等值/范围，按年归档 |
| 往来单据 fin_ar/ap（未结清在池） | 2000 | — | 账期 30 天 ≈ 6 万在池 | 客户+状态索引，账龄查询秒级 |

**并发推算**：50 用户 × 在线率 80% × 同时点查询概率 5~10% ≈ 峰值 5~10 个并发报表查询；早会/月底高峰按 15 预留。业务交易仅约 3 单/分钟，与报表基本不争抢锁，争抢点只在 CPU/IO。

**响应时间目标（MySQL 8，建议 8C16G、Buffer Pool 8~10G、SSD，索引齐备）**：

| 查询类型 | 目标 P95 |
|---|---|
| 明细分页（#1/#2/#15/#16/#9 带日期+条件） | ≤ 0.5s |
| 明细合计行（近 30 天 ~300 万行覆盖索引聚合） | ≤ 2s |
| 汇总/分组报表（#3/#4/#10~#14，走 DWS） | ≤ 1s |
| #5 采购预测（销量取 DWS、库存/在途实时） | ≤ 2s |
| #8 进销存 / #20~#24 财务 | ≤ 2s |
| 全量/跨期导出 | 异步，不占在线请求 |

**为达到上述目标，在 4.6 护栏之上追加 6 条硬措施（本规模刚需）**：

1. **汇总类报表一期全部强制走 DWS 日表**，禁止运行时对明细大表做全期间 GROUP BY；当日增量每 **30 分钟增量刷新当日分区**（夜间仍做近 3 天滚动重算兜底），把"实时 UNION 当天"的扫描量从 10 万行压到 ~2000 行；
2. **#9 台账强制必选"商品 或 仓库"+ 期间 ≤ 92 天**（不满足条件不执行查询，前端置灰查询按钮并提示）——ledger 是年近亿级的最大表，任何无边界查询都是事故；
3. **大表按年逻辑归档**（H2/MySQL 双兼容做法，不用 MySQL 分区语法，避免 H2 冒烟不兼容）：每年初将 2 年前的 `*_detail`、`inv_stock_ledger`、快照/DWS 数据迁入同名 `_hist` 归档表，建 UNION ALL 视图（热表近 24 个月 + 归档表）；默认期间只查热表，跨历史查询自动走视图并强制异步导出。热表保留 24 个月时 ledger 约 1.1 亿~1.8 亿行——因台账查询强制商品+仓库+期间索引、不存在全表扫描，行数本身不构成问题；归档后 DBA 可对 hist 表做压缩（OPTIMIZE/透明压缩）；
4. **报表结果短缓存**：相同 报表+条件+数据范围 hash 的结果，明细类缓存 30~60s、DWS 类 5 分钟（写操作/换条件不命中）；早会多人同查"本月销售"时直接命中，削峰最明显；
5. **异步导出阈值下调**：预计行数 > 1 万行即转异步导出中心（近 30 天明细约 300 万行是常态需求，同步导出必拖慢全站）；EasyExcel 流式 + 分批游标（keyset pagination，不用 LIMIT OFFSET 深翻）；
6. **硬件与部署**：MySQL 独立磁盘（SSD/NVMe，数据盘起步 200G，按年 ~40~80G 规划），Buffer Pool 按物理内存 60~70%；后端与 MySQL 同机房低延迟；**rpt_query_log 上线即开**，P95/慢查询每周复盘。

**结论**：50 用户、日 2000 单、10 万行/日（年明细 3650 万行）在方案 B + 上述措施下，多人查询不会引起业务系统卡顿；最差情况（月底十几人同时跑大范围报表）表现为查询排队 1~3 秒，而不是系统卡死。只读从库（R1）按此增速约 8~10 个月触达"2000 万行"数字阈值，但是否真拆**以 rpt_query_log 的 P95 实测和业务库 CPU 为准**——DWS 分流 + 归档后热表扫描量很小，实测达标可继续不拆；建议上线满 12 个月做一次正式容量评审。

### 4.10 前端架构补充

统一报表协议，避免 24 张表 24 种写法：

- `POST /report/{code}/page`（条件+分组+分页+排序）、`POST /report/{code}/summary`（合计）、`POST /report/{code}/export`（异步任务）、`GET /report/export/tasks`；
- 公共件见 3.2/3.5（ReportFilterBar / DrillGridReport / PurchaseForecast / 合计行 / 列设置）；统一请求防重、查询中态、错误空态、钻取路由协议；
- 报表结果不做浏览器缓存（条件一变即重查）；导出进度统一轮询导出中心，不自实现。

# 六、逐表设计

## 报表 1｜采购订单明细查询

**典型场景**：采购员每天跟催"我下的单到了多少、还差多少"；主管查订单执行。

**取数口径**：purchase_order + purchase_order_detail（只取已审核，作废单列状态可查但默认不查）。**行级已入库数量系统无字段**，按 `pur_inbound.source_order = order_no` 且入库单已审核、stock_updated=1 的明细，按订单行/商品聚合 received_qty（小单位）。采购退货不冲减订单执行量（退货走独立业务）。

**显示字段**：

| 字段 | 取数/算法 |
|---|---|
| 订单号 | purchase_order.order_no（可点开单据） |
| 订单日期 | bill_date |
| 审核状态 | 待审核/已审核/已作废（反审核回到待审核） |
| 入库状态 | 取行级执行结果重算：未入库/部分入库/已入库（头 inbound_status 仅作筛选用，展示以行聚合为准，避免头行不一致） |
| 供应商编号/名称 | supplier_code / supplier_name |
| 采购员 | buyer |
| 商品编号/名称/条码 | detail.goods_code/goods_name + base_goods.barcode |
| 基本单位 | base_goods.base_unit |
| 数量（小单位数量） | detail.base_qty |
| 单价（小单位单价） | detail.amount / detail.base_qty（K5） |
| 件数（大单位数量） | base_qty ÷ 大单位 convertQty；无大单位=base_qty |
| 箱价（大单位价格） | 小单位单价 × convertQty；无大单位=小单位单价 |
| 订单金额 | detail.amount（含税） |
| 已入库数量/件数 | 聚合 received_qty（小单位）/ 换算件数 |
| 未入库数量/件数 | 订单数量−已入库；最小为 0；若已入>订单（超收）显示 0，超收部分在备注图标提示 |
| 品牌/商品类别/存储属性 | base_goods.brand_name/category_name/storage_property |
| 预计到货日期 | purchase_order.expected_arrival_date（列设置默认隐藏） |

**查询条件**：订单号（模糊）、订单日期段（默认最近一个月，K2）、审核状态（默认已审核）、入库状态（全部/未入库/部分/已入库，默认全部）、供应商编号/名称（选择器模糊）、商品编号/名称、商品分类、品牌、存储属性、采购员。

**合计行**：数量、件数、订单金额、已入库数量/件数、未入库数量/件数。

**导出**：统一抬头模板；合计行导出。

**边界**：① 入库单未关联源订单（无订单零星入库）不进本表，进 #2；② 订单被终止：终止行未入库量按 0 展示并在入库状态显示"已终止"；③ 同一商品多行订单按行分别展示（不合并）。

## 报表 2｜采购明细查询（入库 / 采购退货）

**典型场景**：财务月结对采购发生额、采购查某商品所有进出、#3/#4 的钻取落点。

**显示字段**：

| 字段 | 取数/算法 |
|---|---|
| 单据号 | 入库单号 / 退货单号（可点开单据） |
| 单据日期 | 入库日期 / 退货日期 |
| 单据类型 | 采购入库 / 采购退货（筛选项，默认全部） |
| 源单号 | 采购订单号 / 采购退货申请单号 |
| 供应商编号/名称、采购员 | 单据头；采购员缺失时回溯源订单 buyer |
| 商品编号/名称/条码/基本单位 | 明细 + 档案 |
| 数量（小单位） | 入库 received_qty；退货 −退货数量 |
| 单价（小单位） | 行金额 ÷ 小单位数量（退货取绝对值计算、数字带负号） |
| 件数/箱价 | 按 K4/K5 |
| 采购金额 | 含税行金额，退货为负 |
| 仓库 | 单据头 warehouse（列设置默认显示，#3/#4 汇总时不体现） |
| 品牌/类别/存储属性 | 档案 |

**查询条件**：单号、单据日期段（默认最近一个月，按单据业务日期，K2）、单据类型（默认空=全部）、供应商编号/名称、商品编号/名称、商品分类、品牌、存储属性、采购员、仓库。

## 报表 3｜商品采购汇总表

**典型场景**：老板/采购主管看一段时间每个商品采了多少、退了多少；按分类/品牌/采购员出汇总给供应商谈判用。

**钻取**：入库数量/件数/金额 → #2（带入期间+商品+类型=采购入库）；退货列 → #2（类型=采购退货）。

**合计行**：6 个数值列（入/退/净 × 数量金额，含件数）。

## 报表 5｜商品采购预测分析（一期重点，交互最复杂）

**典型场景**：采购员早上打开：系统按最近一个月**签收净销量**算出 20 天后会断货的商品、给出建议量和主供应商，勾选后一键生成一堆待审核采购订单，自己只改数量和供应商。

### 5.1 计算公式（表头固定展示，参数拼进文案）

```
期间销量   = 查询期间内【司机签收净销量】（已审核 sales_receipt 的 signed_qty 按签收日 sign_time 统计
             − 已审核 sales_return 退货数量）；选了仓库只统计该仓签收单 warehouse；拒收 reject_qty 不计销量
日均销量   = 期间销量 ÷ 期间日历天数
预计需求   = 日均销量 × 预销天数（默认 20，1~90 的正整数）
采购在途   = 已审核、未终止采购订单的"未入库数量"（小单位，
             由采购订单行 − pur_inbound 已收量实时聚合；不用余额字段以免滞后）
建议数量   = MAX(ROUND(预计需求 − 可用库存 − 采购在途(勾选时), 0), 0)
可销天数   = 日均销量 > 0 ? 可用库存 ÷ 日均销量 : 显示 "—"
```

表头文案随参数实时变化，例如：

> 建议采购量 = 日均销量 × 预销天数 − 可用库存 − 采购在途。当前：销量取 2026-08-09~2026-09-10（默认期间，截止昨天）司机签收净销量（签收数量−销售退货，仅已审核，拒收不计），预销 20 天，在途参与计算，按数量生成，供应商按主供应商取值。

### 5.2 字段

| 字段 | 说明 |
|---|---|
| 主供应商编号/名称 | base_goods.default_supplier；档案缺主供应商时红字提示"未设置主供应商"，供应商格可手工选 |
| 采购员 | 商品 goods_manager → 供应商 default_buyer 兜底 |
| 商品编号/名称/条码/基本单位 | 档案 |
| 7 天销量 / 月销售（近 30 天） | 固定窗口净销量，与"查询期间销量"并列三列，便于和期间值对比感知趋势 |
| 查询期间销量、日均销量 | 按当前条件实算 |
| 可用库存/可用件数 | inv_stock_balance.available_qty 按查询仓库汇总（空仓库=全部仓求和）；件数=÷大单位换算率 |
| 可销天数 | 公式如上 |
| 采购在途 | 实时聚合（公式注释） |
| 建议数量/建议件数 | 系统算，不可编辑 |
| **采购数量/采购件数** | 默认=建议值，**可编辑**；按件数模式时，改件数自动带数量=件数×换算率，并做整箱校验提示 |
| 采购供应商 | 默认按计算参数（主供应商/最近采购供应商），**行内下拉可改** |
| 最近采购供应商 | 期间内最近一张入库单的供应商（无则显示 —） |
| 最近采购价（小单位/箱价） | 取最近入库单小单位含税价（base_goods.latest_purchase_price 兜底），作为生成订单的单价依据 |
| 品牌/类别/存储属性 | 档案 |

### 5.3 查询条件与计算参数（点"查询"才计算，不自动算）

- 查询条件：供应商（主供应商维度过滤）、商品分类、品牌、采购员、仓库（默认空=全部仓合计销量与库存）；
- 计算参数：
  - 销售期间：默认最近一个月（截止昨天，K2，可改快捷项/自定义）；
  - 预销天数：数字输入，默认 20，校验 1~90 正整数；
  - 是否计算在途：勾选，默认勾选；
  - 生成方式：单选 按数量 / 按件数（决定生成订单行的录入单位层级）；
  - 采购供应商取值：单选 按主供应商（默认）/ 按最近采购供应商；
  - 显示未销售商品：默认不勾；勾选后返回期间 0 销量商品（此类建议量通常为 0；若商品设了库存下限且可用+在途低于下限，建议量补到下限，表头文案同步说明）；
  - 默认只列出**建议数量 > 0** 的商品；另提供勾选"显示建议量为 0 的商品"。

### 5.4 生成采购订单

- 表格复选框（可全选当前页/全部结果），底部"生成采购订单（N 种商品）"；
- 按**采购供应商分组**：每个供应商生成 1 张待审核 purchase_order，同供应商多行商品；采购员取行上采购员（一张单只一个采购员，同供应商跨采购员时拆单）；
- 价格取最近采购小单位含税价换算到生成单位；仓库取查询仓库，未选仓取商品 default_warehouse；
- 生成后弹窗展示"已生成 N 张订单：单号链接列表"，订单为待审核，走现有采购订单审核流程；
- **防重**：写 report_purchase_suggest_log，同一商品存在"预测生成且仍待审核"的订单时，行上黄色警告图标"X 号待审核订单已含此商品"，默认不勾选（仍允许强制生成）；
- 生成动作记操作日志；本页所有数据可导出（抬头含全部计算参数）。

## 报表 6｜缺货商品分析（含每日缺货快照）

## 报表 7｜商品周转率分析

**典型场景**：老板看资金压在哪些货上、哪些是呆滞品；财务算存货周转天数。

**取数口径**：

- 周转率（次）= 期间销售成本（**签收配比成本**：对应发货单出库 cost_amount − 拒收回库成本 − 销售退货成本，按签收日落期间，见 K8）÷ 平均库存成本；
- 平均库存成本 =（期初库存金额 + 期末库存金额）÷ 2；周转天数 = 期间日历天数 ÷ 周转率；
- 期初/期末金额取 inv_stock_daily_snapshot（按日结快照取数；测试/预发同样跑日结任务积累，上线日起持续攒数——不提供流水倒推近似开关，Q6 已确认；系统启用期初通过初始化录入保证连续）。

**字段**：商品编号/名称/品牌/分类、仓库（可按商品汇总或商品+仓库）、期初数量/成本金额、本期入库金额、本期销售成本、期末数量/成本金额、平均库存金额、周转率(次)、周转天数、期间销售额、毛利率（列权限）、呆滞标记（周转天数 > N 天，N 系统参数默认 60）。

**条件**：期间默认最近一个月（K2）、仓库、分类、品牌、商品、排序（默认周转率升序=最慢在前）、仅看呆滞品。

**交互**：合计行（金额列，周转率为加权值=总销售成本÷总平均库存）；商品→#8、→#9；导出。

## 报表 8｜商品进销存汇总表

**典型场景**：月底盘库必出表；财务存货核算主表。行业标准表：期初 + 本期收入 − 本期发出 = 期末，按商品+仓库。

## 报表 9｜商品库存台账

**典型场景**：库管/会计逐笔对账：某商品某仓这个月每一笔进出、每一笔后的结存。

**取数口径**：inv_stock_ledger（ledger_no、occurred_at、source_bill、direction IN/OUT、qty、cost_price、amount、balance_qty、operator_name、批次）。**期初置顶一行虚拟行**；每行：收入数量/发出数量分列、单价、金额、结存数量；结存金额按"期初金额 + 累计发生"逐行滚算（流水表无 balance_amount 字段，建议 V110 补列，回填后优先取落库值）。

**显示字段**：日期、单据号（可打开源单据）、单据类型（采购入库/销售出库/采购退货/销售退货/调拨/其他出入库/红冲…）、方向、摘要、批次、收入数量、发出数量、单位、单价（成本单价）、金额、结存数量、结存金额、经办人。

**条件**：期间（默认本月，**强制 ≤ 92 天**）、**商品或仓库至少必选一项**（ledger 为年近亿级大表，不满足条件时查询按钮置灰并提示"请先选择商品或仓库"）、批次、单据类型（多选）、方向、单据号。

**交互**：
1. 期初行（灰底，不可钻）→ 可继续往前翻期间；
2. 期末合计行：收入合计、发出合计、期末结存（数量+金额）；
3. 连续打印/导出：导出按台账账簿格式（抬头 + 期初 + 逐笔 + 期末，A4 可纵向打印）；
4. 单据号钻取源单据；红冲行负数红字显示。

**勾稽**：页面显示"期末结存 = 库存余额表 available+locked+frozen"校验结果（数量口径一致，若有差提示重算）。

## 报表 20｜应收账款分析（账龄）

**典型场景**：财务每周/每月例会：谁逾期了、欠多久、还能不能发货（信用额度占用）。

**报表性质**：**时点报表**，条件是"截止日期"（默认今天），不是期间。

**布局**：上部账龄分布柱图（未到期/逾期 1~30/31~60/61~90/91~180/180+）+ 应收趋势；下部表格两个视图切换：

- **按客户汇总**：客户编号/名称、业务员、区域、信用额度、额度占用率、应收总额、已收、未收、未到期金额、逾期 1~30/31~60/61~90/91~180/180+、最长逾期天数、最后收款日期；
- **按单据明细**：应收单号、源单（签收单号）、客户、单据日期、到期日（due_date）、应收金额、已收、未收、逾期天数（fin_ar.overdue_days）、账龄档、开票状态（invoice_status）。

**取数**：fin_ar（status 有效，红字负向轧差；fin_ar.received_amount/unreceived_amount）；账龄按 due_date 与截止日差；未到期单独一档。

**条件**：截止日期、客户、业务员、区域、账龄档（默认全部，可筛"仅逾期"）、开票状态、最小欠款金额。
**交互**：客户→客户对账单（fin_customer_statement）；单据→应收详情；信用额度占用 ≥80% 红字预警；合计行（各账龄档合计）；导出（图+表两个 sheet）。

## 报表 22｜现金日记账

**典型场景**：出纳每天登记/核对现金银行流水；会计月末与总账"库存现金/银行存款"科目勾稽（PRD-31 M6 对账已有基础）。

**取数**：fin_fund_ledger（fund_account、direction IN/OUT、amount、source_bill、balance_after、occurred_at）+ 关联 fin_receipt_bill/fin_payment_bill/fin_expense_bill 取摘要、对方单位、收支项目。

**格式**（按账户，标准日记账三栏式）：

| 日期 | 单据/凭证号 | 摘要 | 对方单位 | 收支项目 | 收入金额 | 支出金额 | 余额 | 经办人 |
|---|---|---|---|---|---|---|---|---|

- 顶部账户选择（可多选分 sheet/分组），期初行（上期最后余额，取期间首日 0 点前 balance_after 最近值）；
- **每日日小计**（日清）、每月**本月合计/本年累计**（月结，跨月期间按月分段）；
- 余额逐笔滚算并与 balance_after 校验，不一致行红标；
- **条件**：资金账户（默认第一个现金账户）、期间（默认本月）、收支项目、对方单位、单据号；
- 导出：账簿格式（抬头+期初+逐笔+日小计+月合计），可直接打印；与总账科目对账入口复用 GlReportController.reconcile。

**口径说明**：这里"现金"泛指全部资金账户（现金、银行、微信/支付宝等 base_fund_account），选择具体账户即为该账户日记账。

## 报表 23｜客户应收汇总表

**典型场景**：月结对账和回款管理的主表——区别于 #20：#20 是**时点账龄**，本表是**期间发生额**（期初+本期增−本期收=期末）。

**取数**：fin_ar/fin_receipt_bill/核销记录 + fin_customer_statement。

**字段**：客户编号/名称、业务员、区域、**期初应收**（期间前未收余额）、**本期新增应收**（签收立账口径，含税）、本期回款（现金/票据等全部收款核销金额）、折让/核销减免、**期末应收**（=期初+新增−回款−减免）、其中逾期、信用额度、占用率。

**条件**：期间（默认本月）、客户、业务员、区域、仅显示期末有余额。
**交互**：客户行钻取客户对账单（fin_customer_statement，已有模块）；期末应收→#20（客户+截止日期）；合计行；导出抬头带期间。
**勾稽**：期末应收合计与 #20 截止日应收总额一致；本期新增应收与 #16 同期签收金额合计一致（签收审核即立应收，K8）。已出库未签收的发货单既不算销售也不立应收，表现为库存"已出库未签收"在途，如出现两边差异即数据异常，需排查。
