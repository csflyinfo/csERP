## 一、项目概览

**ERP-WMS-TMS** 是一个面向商贸经销商行业的全链路数字化管理系统，覆盖 **进销存（ERP）+ 仓储作业（WMS）+ 配送运输（TMS）** 三大领域。

| 维度 | 内容 |
|------|------|
| **项目定位** | 商贸经销商数字化转型一站式平台 |
| **目标用户** | 经销商管理层（PC后台）、仓库作业员（PDA）、配送司机（手机APP） |
| **成本算法** | 移动加权平均法（按仓库成本分组独立核算） |
| **开发周期** | 6阶段约35周（8-12人团队） |
| **当前阶段** | Sprint 1 后期 — 系统底座+核心闭环已完成 |

## 二、技术架构分析

### 2.1 实际落地架构 vs 远景架构

项目存在"双轨"技术设计：

```
远景架构（docs/architecture）              实际落地（backend/ + frontend/）
─────────────────────────────────      ─────────────────────────────
Spring Cloud Alibaba 微服务             Spring Boot 3.3.6 模块化单体
Nacos + Dubbo + Gateway + Sentinel      无注册中心/无网关/无RPC
PostgreSQL + MySQL + Redis + ES         H2 文件数据库（开发阶段）
RocketMQ + XXL-JOB                      无消息队列/无定时任务
K8s + Prometheus + SkyWalking           Docker Compose 部署
```

**评价**：这是务实的架构决策。V1.0阶段采用模块化单体降低复杂度，按业务域划分包结构（base/purchase/sales/inventory/finance/report/system），为后续微服务拆分预留了清晰的边界。这份克制值得肯定。

### 2.2 后端技术栈

| 组件 | 选型 | 评价 |
|------|------|------|
| **框架** | Spring Boot 3.3.6 + Java 21 | 版本较新，合理 |
| **ORM** | MyBatis-Plus 3.5.7 | 基础CRUD效率高 |
| **数据库** | 开发：H2；生产：MySQL 8.0 | 开发便捷，切换有风险 |
| **认证** | JWT（jjwt 0.12.6）+ BCrypt | 实现简洁 |
| **安全** | Spring Security（仅密码编码，授权全放行） | ⚠️ 无接口级权限控制 |
| **工具** | EasyExcel 3.3.4 + Fastjson2 2.0.52 | 导入导出能力强 |
| **缓存** | Redis（已配置但未实际使用） | 仅占位 |

### 2.3 前端技术栈

| 组件 | 选型 | 评价 |
|------|------|------|
| **框架** | Vue 3 + Vite | 主流，开发体验好 |
| **状态管理** | Pinia（setup语法） | 现代化 |
| **UI库** | Element Plus（已安装但几乎未使用） | ⚠️ 实际使用自研组件 |
| **HTTP** | Axios + Fetch 双客户端并存 | ⚠️ 存在冗余 |
| **类型系统** | 无 TypeScript | ⚠️ 风险较高 |
| **图表** | ECharts（CDN引入） | 与npm管理方式不一致 |

## 三、代码结构分析

### 3.1 后端模块划分（7个业务模块）

```
com.erp
├── auth/         认证模块（登录/登出/JWT）
├── base/         基础资料（商品/客户/供应商/仓库/价格/主档）
├── purchase/     采购管理（订单/入库/收货/退货/费用/发票）
├── sales/        销售管理（订单/出库/收货/退货/快速开单）
├── inventory/    库存管理（余额/流水/调拨/报损/成本核算）
├── finance/      财务管理（应收/应付/收付款/核销/费用）
├── report/       报表中心（仪表盘/图表/数据导出）
├── system/       系统管理（用户/角色/菜单/参数/日志/通知/待办）
└── flow/         业务流程演示（内存模拟闭环）
```

### 3.2 核心业务闭环

后端已实现两个完整的业务闭环：

```
采购闭环：
  采购订单(审核) → 采购入库(成本重算) → 采购收货(生成应付) → 付款核销

销售闭环：
  销售订单(审核/锁库存) → 销售出库(扣库存/记成本/生成应收) → 销售收货(签收) → 收款核销
```

### 3.3 前端组件架构

前端采用 **"配置驱动 + 泛型组件"** 的架构模式：

- `GenericBusinessList.vue`（~980行）承载了40+个业务模块的列表页，通过 `route.meta.module` 动态适配
- `module-config.js` 和 `module-api.js` 两个超大配置文件定义了所有模块的UI和API行为
- 6个通用组件：ProTable、QueryBar、BaseInfoDrawer、BillDrawer、FundBillDrawer、GoodsDrawer
- 5个Composables：useAuth、useNavigation、usePermission、useDashboard、useToast

**优点**：添加新模块只需改配置，不需新建视图，开发效率极高。
**缺点**：配置文件体量巨大，未来定位和维护困难；所有模块共享同一组件，特殊需求难以满足。

### 3.4 数据库设计

**30+张业务表**，命名规范按模块前缀：

| 前缀 | 模块 | 核心表 |
|------|------|--------|
| `base_` | 基础资料 | category, unit, brand, warehouse, goods, customer, supplier等19张 |
| `pur_` | 采购 | order, order_detail, inbound, inbound_detail |
| `sales_` | 销售 | order, order_detail, outbound, outbound_detail |
| `inv_` | 库存 | stock_balance, stock_ledger |
| `fin_` | 财务 | ar, ap, fund_ledger, receipt_bill, payment_bill, expense_bill |
| `biz_` | 通用 | simple_bill（通过bill_type区分退库/调拨/报损/费用等） |
| `sys_` | 系统 | user, role, param, bill_no_rule, operation_log, export_task, import_task, notification, todo |

表结构通过 `schema.sql` 定义（`CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ADD COLUMN IF NOT EXISTS`），种子数据用 `data.sql`（H2的`MERGE INTO`语法）。

## 六、关键问题与风险

### 🔴 高风险

| # | 问题 | 影响 | 建议 |
|---|------|------|------|
| 1 | **后端接口无授权控制** — Spring Security所有请求`permitAll()`，仅靠JWT验证登录态 | 任何登录用户可访问任意接口 | 增加基于角色的接口级授权 |
| 2 | **前端Token存储键不一致** — `erp-token` vs `erp-demo-token` | 登录后路由守卫可能无法识别已登录状态 | 统一为一个键 |
| 3 | **依赖版本全用"latest"** — package.json所有核心依赖未锁定版本 | `npm install`可能获取不兼容版本 | 锁定具体版本号 |
| 4 | **密码明文风险** — 支持明文密码回退，虽会自动升级但首次暴露 | 密码安全性不足 | 强制BCrypt，禁止明文回退 |

### 🟡 中风险

| # | 问题 | 影响 | 建议 |
|---|------|------|------|
| 5 | **H2→MySQL迁移** — 开发用H2，生产用MySQL，语法差异（如MERGE INTO） | 切换时可能出问题 | 尽早切换到MySQL开发 |
| 6 | **前端双HTTP客户端** — Axios和Fetch并存，401处理逻辑不同 | 维护成本高，行为不一致 | 统一为一个HTTP层 |
| 7 | **无TypeScript** — 前端全部JavaScript | 大型项目缺乏类型安全 | 至少核心模块迁TS |
| 8 | **配置文件巨大** — module-config.js + module-api.js 超千行 | 维护困难 | 按模块拆分配置文件 |

### 🟢 低风险

| # | 问题 | 影响 | 建议 |
|---|------|------|------|
| 9 | Element Plus已安装但未使用 | 包体积浪费 | 移除或正式使用 |
| 10 | ECharts通过CDN引入 | 离线环境不可用，版本不可控 | 改为npm安装 |
| 11 | Vite/插件放在dependencies而非devDependencies | 生产包体积增大 | 移入devDependencies |
| 12 | 远景架构文档与实际代码不一致 | 新成员困惑 | 在架构文档中标注"当前实际采用模块化单体" |
